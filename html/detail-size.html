LLVM 17 不透明指针强制（Opaque Pointers）

LLVM 17 起，不透明指针（Opaque Pointers）成为 IR 中唯一支持的指针表示形式。 在旧版 IR 中，指针带有元素类型（Typed Pointers），编译器需要频繁插入 bitcast 和复杂的 getelementptr 链来匹配类型。 这些冗余指令不仅增加 IR 的体积，也使得后端代码生成更难做全局优化。

示例 — IR 层面：Typed Pointers → Opaque Pointers
; === LLVM 16 及之前：Typed Pointer 需要 bitcast + 多层 GEP ===
%1 = bitcast i8* %base to %struct.Foo*
%2 = getelementptr %struct.Foo, %struct.Foo* %1, i32 0, i32 3
%val = load i32, %struct.Foo* %2

; === LLVM 17+：Opaque Pointer 直接按偏移计算 ===
%gep = getelementptr i8, ptr %base, i64 12
%val = load i32, ptr %gep

; 效果：指令数从 3 条缩减为 2 条；消除了类型转换的 IR 开销

对代码体积的影响链路：IR 指令减少 → 后端 SelectionDAG 节点减少 → 指令选择阶段需要处理的模式更少 → 最终生成的机器码更紧凑。 在 -Oz 场景下，消除冗余指针操作带来的体积缩减通常在 1-4%， 对于指针密集型代码（如容器遍历、虚函数调用分发）效果尤为明显。

示例 — C++ 虚函数调用的 IR 简化
// C++ 源码
struct Base { virtual int f(); };
int call(Base* b) { return b->f(); }

; LLVM 16（Typed）：vtable 访问需要 bitcast + 多层 GEP
%0 = bitcast %struct.Base* %b to i8**
      ;  ^── 额外的类型转换指令
%vtable = load i8**, i8*** %0

; LLVM 17+（Opaque）：无需 bitcast，直接访问
%vtable = load ptr, ptr %b
      ;  ^── 简单直接，无冗余指令
注意： 不透明指针是 LLVM 17 的强制默认行为，不再支持 Typed Pointer 模式。 如果项目中有自定义的 LLVM IR Pass 或后端，需要确认其已适配不透明指针模型； 对于纯 C/C++ 编译用户，此变更完全透明。

LLVM 20 Size-aware Machine Block Placement

LLVM 20 的 Machine Block Placement Pass 引入了大小感知（size-aware）的代码布局策略。 在 -Oz 和 -Os 模式下， 基本块的排列不仅考虑执行频率（fall-through 优化），也以减少跳转指令编码的字节数 作为优化目标。相关实现见 PR #109711。

核心原理：x86-64 跳转指令的编码长度取决于目标距离：

  • 短跳转（JMP rel8）：2 字节 — 目标在 ±127 字节范围内
  • 近跳转（JMP rel32）：5 字节 — 目标在 ±2GB 范围内

传统布局（追求执行频率最优）可能导致大量 5 字节跳转指令。 大小感知布局在热块执行效率可接受的范围内，优先将跳转目标放置在短跳转可达范围， 从而每个跳转节省 3 字节。

示例 — 大小感知布局 vs 性能优先布局
; === 传统布局（性能优先，追求 fall-through）===
.Lhot_entry:
    mov    eax, [rdi]
    test   eax, eax
    je     .Lcold_error     ; 5 字节：E9 xx xx xx xx
    ; ... 热路径代码（约 40 字节）...
    ret
.Lcold_error:               ; ← 距离 > 127，无法用短跳转
    call   log_error

; === 大小感知布局（-Oz，缩短跳转距离）===
.Lhot_entry:
    mov    eax, [rdi]
    test   eax, eax
    je     .Lcold_error     ; 2 字节：EB xx（冷块移到附近）
    ; ... 热路径代码 ...
    jmp    .Lreturn
.Lcold_error:               ; ← 紧邻热块，短跳转可达
    call   log_error
.Lreturn:
    ret

对于包含大量条件分支的函数（如解析器、状态机、协议处理）， 累积的跳转指令字节节省可达函数体积的 2-5%。在固件/嵌入式等 严格限制 .text 段大小的场景，此优化直接贡献于整体目标。

适用场景： 此优化仅在 -Oz（极致体积）和 -Os（优化体积）模式下启用。 在 -O2/-O3 模式下，编译器仍使用传统的性能优先布局。

LLVM 19 冷热路径分离优化

LLVM 19 增强了冷热路径的识别和分离能力。编译器能够更准确地判断代码路径的冷热属性， 并据此调整内联策略和代码布局：

  • 热路径：频繁执行的核心逻辑 → 可能被内联以减少函数调用开销
  • 冷路径：错误处理、初始化、边界情况 → 保持在函数外部，避免内联膨胀
示例 — 冷热路径分离与内联决策
void process(int x) {
    do_work(x);                    // 热路径 → 可能内联，减少调用开销

    if (__builtin_expect(err, 0)) {  // __builtin_expect 标记冷路径
        handle_error(err);        // 冷路径 → 不内联，保持体积
    }
}

// LLVM 19 的处理方式：
// 1. do_work() 被识别为热路径 → 内联进 process()
// 2. handle_error() 被识别为冷路径 → 保持独立函数
// 3. 冷路径块被放置在函数末尾或独立代码段

// 效果：热路径紧凑高效；冷路径不膨胀核心代码体积

冷热分离优化的关键改进点：

  • profile 信息整合：如果提供了 PGO 数据（-fprofile-use）， 编译器会基于实际运行时频率精确判断冷热路径。没有 profile 时，则基于 __builtin_expect、异常处理路径、noreturn 等启发式规则。
  • 冷函数分段：在支持 -function-sections 的场景下， 冷路径函数可被放入独立的 .text.unlikely 段， 配合链接器进一步优化内存布局。
  • 减少 I-cache 污染：冷路径代码不占据热路径的指令缓存行， 间接提升整体性能（虽然本页面仅关注体积，但这个副作用值得了解）。
示例 — 带 profile 的冷热分离（PGO + -Oz）
// 编译命令
// Step 1: 插桩运行
clang -fprofile-generate -Oz -o app app.c && ./app
// Step 2: 使用 profile 构建
clang -fprofile-use -Oz -o app app.c

// 源码：解析器主循环
int parse_packet(const uint8_t* buf, size_t len) {
    switch (buf[0]) {
    case 0x01: parse_data(buf, len);     break;  // 90% 的流量 → 热路径
    case 0xFF: parse_reset(buf, len);    break;  // <1% 流量 → 冷路径
    default: handle_unknown(buf, len);  break;  // <0.1% → 冷路径
    }
    return 0;
}
// LLVM 19 + PGO：仅内联 parse_data，parse_reset/handle_unknown 保持外部函数

LLVM 16–21 Machine Outliner 改进

Machine Outliner 是 LLVM 后端的一个重要优化 Pass，它能够识别多个函数中重复出现的 机器码序列，并将其提取为一个独立的共享函数（outline function）， 原始位置替换为对该函数的调用。这是一个代码去重技术，直接减小 .text 段的大小。

在 LLVM 15 到 21 的版本迭代中，Machine Outliner 经历了多次重大重构和改进， 其识别能力和优化覆盖范围显著提升：

Machine Outliner 跨版本演进

  • LLVM 16：支持 AArch64 上的全局 outlining（跨编译单元）， 不再局限于单个函数的局部序列。
  • LLVM 17：改善 outlining 候选序列的收益评估，避免 "outline 后反而增大体积"的情况（考虑调用/返回指令的开销）。
  • LLVM 18：重构候选搜索算法（PR #90074）， 使用更高效的后缀树匹配，扩大搜索范围且不显著增加编译时间。
  • LLVM 19-20：扩展至更多目标架构（RISC-V、MIPS）， 优化调用约定的 outline 函数参数传递。
  • LLVM 21：增强全局 outlining 与 LTO 的协同（PR #105398）， 在 LTO 模式下跨整个链接单元搜索重复序列。
示例 — 全局 Outlining 效果
; === Outlining 前：三个函数中有重复的 3 条指令序列 ===

func_a:
    mov    rdi, [rsi+8]
    add    rdi, 16
    call   alloc
    ; ... 函数 A 的其他代码 ...

func_b:
    mov    rdi, [rsi+8]    ; ← 重复序列（共 3 条指令 × 3 次 = 9 条）
    add    rdi, 16        ;    每次重复占约 10+ 字节
    call   alloc
    ; ... 函数 B 的其他代码 ...

func_c:
    mov    rdi, [rsi+8]
    add    rdi, 16
    call   alloc
    ; ... 函数 C 的其他代码 ...

; === Outlining 后：提取为共享函数 ===

OUTLINED_FUNCTION_0:         ; 提取出的共享函数（~10 字节）
    mov    rdi, [rsi+8]
    add    rdi, 16
    call   alloc
    ret

func_a:
    call   OUTLINED_FUNCTION_0   ; 5 字节 call
    ; ...

func_b:
    call   OUTLINED_FUNCTION_0   ; 5 字节 call
    ; ...

func_c:
    call   OUTLINED_FUNCTION_0   ; 5 字节 call
    ; ...

; 体积变化：outline 前 3 × 10 = 30 字节 → outline 后 10 + 3 × 5 = 25 字节（节省 ~17%）

在大型固件/嵌入式项目中，Machine Outliner 通常能节省 3-8% 的 .text 段大小。 结合 -Oz（outliner 在 -Oz 下更激进地搜索候选序列）， 实际节省可能更高。启用方式： 

# Machine Outliner 在 -Oz 下默认启用，也可显式控制：
-mllvm -enable-machine-outliner        # 启用
-mllvm -enable-machine-outliner=always # 始终启用（即使是 -O0）
全局 Outlining 与 LTO： 在 LTO（Link-Time Optimization）模式下，PR #105398 的增强使 Machine Outliner 能够在整个链接单元的所有编译单元之间搜索重复序列， 远超单文件范围。对于大型项目（数百个 .o 文件），额外的去重效果显著。

LLVM 18 LLD 代码段排序 — cdsort 算法

LLD（LLVM Linker）在 LLVM 18 中引入了 cdsort （Call-Density Sort）算法，用于改善二进制文件中函数的物理排列顺序。

核心思想：基于调用图亲和性（call graph affinity）， 将频繁相互调用的函数在内存中相邻排列。这直接改善指令缓存（I-cache）的空间局部性， 减少 I-cache miss。同时，相邻的函数可以共享同一个 cache line， 提高代码段的空间利用率。

示例 — cdsort 排序对比
# 使用 cdsort 算法进行代码段排序
clang -fuse-ld=lld -Wl,--call-graph-profile-sort=cdsort ...

; === 未排序（编译顺序）===  内存地址   === cdsort 排序后 ===
;                             0x1000     
func_main:    ; 热函数      0x1000    func_main:
func_cold:    ; 冷函数      0x1200    func_helper:  ; 与 main 频繁互调
func_helper:  ; 热辅助函数  0x1400    func_sub:      ; 被 helper 频繁调用
func_init:    ; 初始化函数  0x1600    func_cold:     ; 冷函数移到末尾
func_sub:     ; 热辅助函数  0x1800    func_init:     ; 仅启动时执行

; 效果：热函数聚集在连续的地址范围 → 更少的 cache line 占用 → 更好的 I-cache 命中率

虽然 cdsort 主要优化的是 I-cache 效率（属于性能领域）， 但其对代码段组织的优化间接影响代码体积的感知质量：

  • 减少因 cache line 碎片导致的对齐填充：将紧密相关的函数连续排列， 减少 .p2align 带来的内部碎片。
  • 辅助 Cold Function Splitting：冷函数集中放置， 可以配合链接器脚本将其放入不同的内存区域（如低速 flash）， 为热代码腾出更多宝贵的片上 SRAM。
示例 — LLD 链接选项
# 启用 cdsort（LLVM 18+，配合 PGO 使用效果最佳）
-fprofile-use                              # 使用 PGO profile
-fuse-ld=lld                               # 使用 LLD 链接器
-Wl,--call-graph-profile-sort=cdsort       # 开启 cdsort 排序
-Wl,-z,keep-text-section-prefix            # 保留 section 前缀，辅助排序

# 可选的排序策略
# --call-graph-profile-sort=none     : 禁用排序
# --call-graph-profile-sort=hfsort   : 传统算法（LLVM 17 及之前默认）
# --call-graph-profile-sort=cdsort   : 新算法（LLVM 18+ 推荐）

LLVM 16–21 内联成本模型改进对 -Oz 的影响

内联优化对代码体积有直接影响：内联消除了一次 call/ret 的开销，但如果被内联的函数体积较大，反而会增加总体代码量。 编译器需要在"消除调用开销"和"避免代码膨胀"之间做权衡， 这个权衡由内联成本模型（Inliner Cost Model）决定。

在 -Oz 模式下，内联成本模型的阈值更加保守， 只内联那些"内联后反而减小总体体积"的情况（如极小的 getter/setter、 单行转发函数等）。以下跨越多个 LLVM 版本的关键修正，直接影响 -Oz 的代码体积：

LLVM 18 switch 默认分支成本修正

此前版本中，当函数包含 switch 语句时， default 分支的成本可能被高估， 导致编译器错误地将整个函数视为"昂贵的"且不应内联。 LLVM 18 修正了这一偏差，使内联决策更加准确。

示例 — switch default 成本修正（LLVM 18）
// 此前：default 分支被高估为"全量成本"，阻止内联
static int dispatch(int op) {
    switch (op) {
    case 0: return do_a();
    case 1: return do_b();
    default: return -1;   // 实际只有 1 条 return，成本很低
    }
}
// LLVM 18：正确评估 default 成本，允许 -Oz 下内联此轻量级函数

LLVM 20 __memcpy_chk 等不再增加内联罚分

__memcpy_chk、__memset_chk 等 带边界检查的内存操作函数（Fortify Source），在此前版本中会显著增加调用函数的 内联成本评估，导致不必要的内联抑制。LLVM 20 识别出这些函数在编译时常数折叠后 与普通 memcpy 等价，不再计入内联成本罚分。

示例 — __memcpy_chk 内联罚分消除（LLVM 20）
// 此前：__memcpy_chk 被当作"昂贵"操作，阻止函数内联
static void copy_header(char* dst, const char* src) {
    __builtin___memcpy_chk(dst, src, 16, __builtin_object_size(dst, 0));
    // LLVM 20：识别为常量大小的 memcpy，不增加内联成本罚分
    // → copy_header() 在 -Oz 下可以内联到调用者
}

void caller(char* buf) {
    copy_header(buf, "HEAD");  // LLVM 20：成功内联，消除 call/ret 开销
}

LLVM 21 内联汇编计入成本

此前的内联成本模型不计算内联汇编（Inline Assembly）指令的体积。 当函数包含大量内联汇编时，编译器可能错误地内联它，导致代码体积膨胀。 LLVM 21 将内联汇编的体积纳入成本计算，避免不恰当的内联膨胀。

示例 — 内联汇编成本计数（LLVM 21）
// 此前：内联汇编被忽略，函数可能被不当内联
static void cpuid(int code, int* a, int* b, int* c, int* d) {
    asm volatile("cpuid"
         : "=a"(*a), "=b"(*b), "=c"(*c), "=d"(*d)
         : "a"(code));
    // LLVM 21：此函数包含大段内联汇编 → 成本高，-Oz 下不会内联
    // → 避免在每个调用点重复展开 cpuid 指令
}
总结 — 内联成本模型与 -Oz： 这三个修正共同作用，使 -Oz 模式的内联决策更加合理： 轻量级函数得以正确内联（消除调用开销而体积基本持平）， 大体积函数避免内联（防止代码膨胀）。 对于包含 Fortify Source 和内联汇编的代码库，LLVM 20-21 的体积表现预计优于之前版本。

-Oz 验证建议

编译器升级后，建议按照以下流程系统性地验证代码体积变化：

1. 二进制体积对比

工具用途典型命令
size(1) 查看 ELF 段大小（.text / .data / .bss） size -A ./output_binary
bloaty 按编译单元/符号/库分析体积构成 bloaty -d compileunits ./binary
nm --print-size 列出每个符号的大小，检查关键函数体积变化 nm --print-size --size-sort -t d ./binary
readelf -S 查看段表详细信息 readelf -S ./binary | grep -E '\.text|\.rodata'
bloaty --domain=vm 按虚拟内存区域分析 bloaty -d symbols,vmsize ./binary
示例 — 体积对比自动化脚本
#!/bin/bash
# size_compare.sh — 对比升级前后 .text 段体积变化
set -e

OLD_CC="/path/to/clang-16/bin/clang"
NEW_CC="/path/to/clang-21/bin/clang"
CFLAGS="-Oz -fuse-ld=lld -fno-lto"
SRC_DIR="src/"

# 使用旧编译器构建
CC="$OLD_CC" make clean && CC="$OLD_CC" CFLAGS="$CFLAGS" make
cp build/myapp build/myapp_old

# 使用新编译器构建
CC="$NEW_CC" make clean && CC="$NEW_CC" CFLAGS="$CFLAGS" make
cp build/myapp build/myapp_new

# 对比体积
echo "====== ELF 段大小对比 ======"
echo "--- 旧版本 (LLVM 16) ---"
size -A build/myapp_old
echo "--- 新版本 (LLVM 21) ---"
size -A build/myapp_new

# 按编译单元分析体积差异（需要 bloaty）
echo "====== 编译单元体积差异（前 20）======"
bloaty -d compileunits build/myapp_new -- build/myapp_old 2>/dev/null | head -20

2. 关键函数体积检查

使用 nm --print-size 对比关键函数的体积变化。 重点关注：

  • 体积异常增长：某个函数的体积在新版本中显著增大（如增长超过 20%）， 可能指向不当的内联决策或代码生成回退。
  • 体积显著缩减：可能是 Machine Outliner 或更好的指令选择带来的优化效果。
  • 新增函数：Outliner 生成的 OUTLINED_FUNCTION_* 函数是正常现象。
示例 — 关键函数体积变化分析
# 列出所有函数，按体积降序排列，保存到文件对比
nm --print-size --size-sort -t d build/myapp_old | sort -k2 -nr > funcs_old.txt
nm --print-size --size-sort -t d build/myapp_new | sort -k2 -nr > funcs_new.txt

# 找出体积增长最大的 10 个函数
diff <(awk '{print $NF, $2}' funcs_old.txt) \
     <(awk '{print $NF, $2}' funcs_new.txt) \
  | grep '^>' | sort -k2 -nr | head -10

3. 内联决策验证

检查是否有意外的函数内联（导致体积膨胀）或未内联（导致体积增加-调用开销）， 使用 LLVM 的内联诊断报告功能：

示例 — 内联诊断报告
# 编译时生成内联诊断信息
-Rpass=inline -Rpass-missed=inline -Rpass-analysis=inline

# 保存优化记录（YAML 格式，供 tooling 分析）
-fsave-optimization-record -foptimization-record-file=inline.yaml

# 示例输出片段
// 成功内联（-Oz 下只有体积收益为正时才内联）

4. 验证要点总结

验证流程建议

  1. 快速体积对比：使用 size -A 对比 .text 段总大小。如果增长超过 3-5%，需要深入分析。
  2. 按编译单元分析：使用 bloaty -d compileunits 定位体积增长的具体来源（哪个 .o 文件变大）。
  3. 异常函数定位：使用 nm --print-size --size-sort 找出体积异常变化的函数，结合反汇编（objdump -d）分析原因。
  4. 内联审查：使用 -Rpass-missed=inline 确认关键的轻量级函数未被错误地抑制内联；同时确认大函数未被错误地内联。
  5. 链接后效果验证：LTO 和 Machine Outliner 的效果只有在最终链接后才能完全体现，不要仅对比中间 .o 文件的大小。
注意： 代码体积分析要特别关注 LTO 模式下的表现。 许多代码体积优化（Machine Outliner 全局模式、cdsort 排序、冷热分离的跨模块效果） 仅在 LTO 链接时才会完全发挥。建议在验证时同时测试 -fno-lto 和 -flto=thin 两种模式的体积差异。
