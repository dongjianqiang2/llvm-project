关键变更

1. Lifetime DSE（死对象存储消除）

Dead Store Elimination (DSE) 是一项编译器优化，用于消除对不再被读取的内存位置的写入（"死存储"）。 Clang / LLVM 21 中，基于对象生命周期（lifetime）的 DSE 变得更加激进——编译器现在更积极地推断对象何时"死亡"， 并消除该对象死亡后发生的任何存储操作。

这项优化在正常代码中通常是有益的（减少不必要的写入，提升性能），但对于依赖"对象销毁前清零敏感数据"的安全代码， 以及依赖"在调试器中观察变量最后值"的调试场景，可能产生意外行为。

场景一：敏感数据清零被优化掉

源代码（期望清零）
void processSecret() {
  MyObject obj;
  obj.setSecret(key);   // 写入敏感数据
  obj.encryptAndSend(); // 使用敏感数据
  // obj 在此之后死亡 — 不再被读取
  memset(&obj, 0, sizeof(obj)); // 期望清零
} // LLVM 21 可能消除上面的 memset！
LLVM 21 的实际行为
// memset 被认为是对"死对象"的存储，
// 编译器判断 obj 之后不再被读取，
// 因此消除 memset 调用。
// 敏感数据可能残留在栈上！

场景二：调试标记值被优化掉

调试代码
void debugWork() {
  int x = 42;
  doWork(&x);  // x 被使用
  x = -1;       // 标记"已使用过"
  // x 在此死亡 — 不再被读取
  // 期望在调试器中看到 x == -1
}
LLVM 21 的实际行为
// 赋值 x = -1 被识别为对即将
// 死亡对象的存储，被优化消除。
// 调试器中 x 可能仍为 42 或
// 未定义值。
应对措施：使用编译选项 -fno-lifetime-dse 禁用此优化。
迁移建议：迁移期先使用 -fno-lifetime-dse 禁用此优化， 确保现有代码行为不变。随后审计代码中依赖"对象死亡前最后写入"的场景， 使用 std::fill 配合 volatile 或编译器屏障（如 asm volatile("" : : "r"(ptr) : "memory")） 来确保清零不被优化。审计完成后再根据安全需求决定是否重新启用。
语言严格化

2. break / continue 在循环条件/增量语句中严格化

在 C 标准中，break 和 continue 语句只能出现在循环体（loop body）或 switch 语句中。 然而，历史上某些编译器（包括旧版 Clang）允许在 GNU 扩展下，将 break/continue 放置在 for 循环的条件表达式（condition）或增量表达式（increment）中。

Clang 21 收紧了这一行为，与 GCC 最新版本对齐：在循环的条件、增量、以及 init-statement 中使用 break 或 continue 不再被允许，即使使用了 GNU 扩展模式也会报错（ill-formed）。

Before（旧版 Clang 允许，但在 Clang 21 中 ill-formed）
// 在 while 条件中使用 break — 现在不允许
while (({ break; })) {}    // error: 'break' statement not in loop or switch

// 在 for 增量语句中使用 break — 现在不允许
for (;; ({ break; })) {}   // error: 'break' statement not in loop or switch

// 在 for 条件中使用 continue — 现在不允许
for (int i = 0; ({ continue; i < 10; }); ) {}  // error
After（Clang 21 — 与 GCC 行为对齐）
// 以上写法全部报错。break / continue 只能出现在循环体中：
while (condition) {
  if (shouldStop)
    break;           // 正确：在循环体内
  if (shouldSkip)
    continue;        // 正确：在循环体内
}
说明：此项变更是与 GCC 行为对齐的一部分。使用 GNU statement expression ({ ... }) 在循环条件/增量中内嵌 break/continue 是一种罕见的 编码模式，大多数代码不受影响。如果代码中存在此类写法，需要将控制流逻辑移到循环体内。
语言严格化

3. 行号/数字指令解析为未求值字符串

Clang 21 现在将行号指令（#line）、数字指令（# digit）中的 文件名、模块名和原始文件名解析为未求值字符串（unevaluated string）。 这意味着这些字符串中的转义序列（如 \x12、\012）不再被解析， 使用转义序列的代码现在会报错（ill-formed）。

Before（旧版 Clang 允许，Clang 21 中 ill-formed）
// 文件名含转义序列 — 现在报错
# 1 "original\x12source.c"     // error: 未求值字符串中不允许转义序列

// 模块导入名含转义序列 — 现在报错
#pragma clang module import "\x41"  // error

// 行号控制文件名含转义序列 — 现在报错
# 50 "a\012.c"                 // error
After（Clang 21 — 正确写法）
// 文件名直接使用字面字符，不使用转义序列
# 1 "original_source.c"        // 正确：直接写文件名

#pragma clang module import "MyModule"  // 正确

# 50 "a.c"                     // 正确
影响范围：此变更主要影响包含特殊字符文件名的预处理器指令。 绝大多数代码不依赖此类转义序列，实际影响很小。如果确实需要在行号指令中表达特殊字符， 应直接使用字面字符而非转义序列。
语义变更

4. __has_feature(modules) 语义变更

__has_feature(modules) 是 Clang 的内置宏，用于检测编译器是否启用了 Clang Modules 功能。 在 Clang 20 及之前版本中，当使用 -std=c++20 时，该宏会返回 true， 即使并未显式启用 -fmodules。原因是 C++20 标准引入了 modules 特性， 旧版 Clang 将 __has_feature(modules) 与 "C++20 modules 可用" 做了过度关联。

Clang 21 修正了这一语义：__has_feature(modules) 现在仅在显式指定 -fmodules（Clang Modules）时才返回 true。仅使用 -std=c++20 不再使该宏为真。

Before（Clang 20）
// 编译: clang -std=c++20
#if __has_feature(modules)
  // true! — 仅因为有 -std=c++20
  import std;  // 但这可能不工作
#endif
After（Clang 21）
// 编译: clang -std=c++20
#if __has_feature(modules)
  // false — 因为没指定 -fmodules
#endif

// 正确检测 C++20 modules：
#if __cpp_modules >= 201907L
  // C++20 modules 可用
#endif
修正方法：
  • 如需 Clang Modules：显式添加 -fmodules 编译选项
  • 如需检测 C++20 modules 可用性：改用 __cpp_modules >= 201907L（标准 feature-test macro）
  • 检查代码中所有 __has_feature(modules) 的使用，确认其意图后再选择正确的检测方式
C++ Modules

5. export 声明在模块实现分区中被拒绝

C++20 Modules 规范规定，export 声明只能在模块接口单元（interface unit）中使用， 不能在模块实现分区（implementation partition）中使用。旧版 Clang 在某些情况下未能正确拒绝 模块实现分区中的 export 声明。

Clang 21 修正了此行为：在模块实现分区中使用 export 声明现在会触发编译错误。 （#GH107602）

Before（Clang 20 — 静默接受）
// math.cppm (模块实现分区)
module math:detail;

// 旧版 Clang 可能未报错
export int helper() { return 0; }
// 不合规：实现分区不应 export
After（Clang 21 — 正确报错）
// math.cppm (模块实现分区)
module math:detail;

int helper() { return 0; }
// 正确：实现分区中无 export，
// 如需导出请使用接口分区

// 如需导出，应使用接口分区：
// export module math:detail;
迁移建议：如果模块实现分区中使用了 export 声明导致编译失败， 根据需求选择以下任一方案：(1) 移除 export 关键字（如是内部实现）， 或 (2) 将分区改为接口分区 export module name:partition;。
C++ 语言

6. 嵌套局部类跨块作用域被拒绝

C++ 标准要求嵌套局部类必须定义在与父类相同的块作用域（block scope）内。 旧版 Clang 在某些情况下未能正确拒绝在不同于父类的块作用域中定义的嵌套局部类。

Clang 21 修正了此行为：嵌套局部类如果定义在与父类不同的块作用域中，现在会触发编译错误。 （#GH193472）

Before（Clang 20 — 可能静默接受）
void f() {
  struct Outer {
    void g() {
      // Inner 定义在 g() 内，
      // 而 Outer 定义在 f() 内
      // — 不同块作用域：不合规
      struct Inner { int x; };
      // 旧版 Clang 可能不报错
    }
  };
}
After（Clang 21 — 正确报错）
// 嵌套局部类必须在同一块作用域
void f() {
  struct Outer {
    struct Inner { int x; };  // 正确
    void g() { Inner obj; }
  };
}

// 或定义为非局部类型
// 如有名称冲突请调整结构
迁移建议：将嵌套局部类移动到与父类相同的块作用域中定义， 或将嵌套类作为父类的普通成员类型定义。此模式在实践中较为罕见，影响范围有限。
模板推导

7. _BitInt 模板参数推导变更

_BitInt(N) 是 C23 标准引入的位精确整数类型，允许指定任意位宽的整数（如 _BitInt(3) 表示 3 位有符号整数， _BitInt(32) 表示精确 32 位整数）。Clang 也支持在 C++ 中使用此扩展。

在 Clang 20 及之前版本中，当 _BitInt(N) 作为非类型模板参数（NTTP）时，N 被推导为 int 类型。 Clang 21 修正了此行为：N 现在被正确推导为 size_t（无符号类型）， 与位宽参数的自然语义一致。（#GH195033）

Before（Clang 20）
template<auto N>
void f() {
  // N 被推导为 int
  // 对于 _BitInt(32)，N 是 int{32}
}

f<_BitInt(32)>();  // N = int{32}

// 问题：对于大位宽 _BitInt(1024)，
// 1024 可能超出 int 范围
After（Clang 21）
template<auto N>
void f() {
  // N 被推导为 size_t
  // 对于 _BitInt(32)，N 是 size_t{32}
}

f<_BitInt(32)>();  // N = size_t{32}

// 更合理：位宽天然是非负值，
// size_t 是更合适的类型
影响分析：如果你的代码对 decltype(N) 做了显式类型判断（如 std::is_same_v<decltype(N), int>）， 需要更新为 size_t。大多数场景下，由于 auto 推导会自动适配，不需要修改代码。
ABI 变更

8. Coroutine ABI 稳定化（C Calling Convention）

C++20 协程的底层实现依赖两个关键函数：resume（恢复协程执行）和 destroy（销毁协程帧）。 在 LLVM 20 及之前版本中，这些函数使用 fastcc（fast calling convention）调用约定。

LLVM 21 将 resume/destroy 函数的调用约定从 fastcc 切换为平台的 C calling convention。 这项变更是为了稳定协程 ABI——使得协程的底层调用约定跨 LLVM 版本保持一致， 并且理论上允许不同编译器（如 Clang 和 GCC）编译的协程代码在二进制层面互操作。

Before（LLVM 20 — fastcc）
; LLVM IR: resume/destroy 使用 fastcc
define fastcc void @my_coro.resume(
    %coro.frame* %frame) {
  ...
}

define fastcc void @my_coro.destroy(
    %coro.frame* %frame) {
  ...
}
After（LLVM 21 — C calling conv）
; LLVM IR: resume/destroy 使用 C CC
define void @my_coro.resume(
    %coro.frame* %frame) {
  ...
}

define void @my_coro.destroy(
    %coro.frame* %frame) {
  ...
}
影响范围：
  • 大多数平台无影响：在 x86-64、AArch64、ARM32、RISC-V 等主流平台上，fastcc 与 C calling convention 在 ABI 层面行为一致。
  • 受影响平台（fastcc 与 C CC 行为不同）：
    • i686（32 位 x86）
    • MIPS O32
    • PowerPC64 ELFv1
    • Lanai
  • 价值：使协程 ABI 跨 LLVM 版本稳定，未来可与其他编译器（GCC、MSVC）的协程实现互操作。
ABI 变更

9. ABI 变更汇总

除上述 Coroutine ABI 变更外，LLVM 21 还包含以下多项 ABI 级别的修改。 以下变更在特定目标平台/场景下可能影响二进制兼容性。

9a. _BitInt 位域宽度超过 255 位 MSVC ABI 修复

问题：当 _BitInt 位域宽度超过 255 位时，在 MSVC 目标上的结构布局不正确。 内部位域跟踪字段使用了 unsigned char 类型，无法容纳超过 255 位的位宽。

修复：内部跟踪字段类型从 unsigned char 改为 uint64_t，解决了溢出问题。 此修复可能导致此类结构体与早期 Clang 版本编译的代码之间存在 ABI 不兼容。

9b. __regcall 结构体传参修复（非 Windows x86-64）

问题：__regcall 调用约定在非 Windows x86-64 目标上存在多项问题， 包括处理空结构体参数时的崩溃，以及包含数组、浮点类型或 _Complex float 类型的结构体传参不正确。

修复：修正了这些类型的传参行为。这可能与早期 Clang 版本编译的使用 __regcall 的代码不兼容。（#GH62999, #GH98635）

9c. Itanium Lambda 名称修饰修复（NSDMI）

问题：在实例化的非静态数据成员初始化器（NSDMI）中，lambda 表达式的 Itanium 名称修饰 （mangling）未能保留字段名闭包前缀（field-name closure-prefix）。

修复：修正了名称修饰算法，为受影响 lambda 表达式生成正确的符号名。 此修复改变了受影响 lambda 的符号名称。（#GH190555）

9d. AArch64 SVE MSVC Compatible Manglings

问题：当面向 Microsoft ABI 时，AArch64 SVE 内置类型使用了非 MSVC 兼容的名称修饰。

修复：Clang 21 现在对支持的 AArch64 SVE 内置类型使用 MSVC 兼容的名称修饰。 此变更会影响受影响声明的符号名。（#GH196170）

9e. Coroutine Resume/Destroy: C Calling Convention

详见第 8 节 Coroutine ABI 稳定化。 在 i686、MIPS O32、PowerPC64 ELFv1 和 Lanai 平台上为 ABI 断裂性变更。

9f. x86-64 大向量结构体返回修复

问题：在 x86-64 目标上，当函数返回包含单个大型向量（256 位或 512 位）的结构体时， 结构体返回方式不正确。该缺陷自 Clang 21 早期引入（#GH120670）。

修复：修正了此类结构体的返回 ABI。（#GH203760）

ABI 变更整体建议：升级编译器版本后进行全面的 ABI 兼容性测试。 涉及跨模块边界的代码（动态库、插件系统等）需要使用同一编译器版本重新编译，避免 ABI 不匹配导致的运行时错误。
Frontend

10. Clang Frontend 变更

Clang 21 在前端驱动层面引入了多项重要变更，主要涉及 offload 驱动、协程支持声明以及 HIPSPV 工具链的弃用。

10a. 新 Offload 驱动默认启用

新的 offload 驱动（--offload-new-driver）现在为所有 offloading 编译的默认选项。 这改变了可重定位设备代码（relocatable device code）的 ABI。

影响：现有的 offload 库需要使用新驱动重新编译，或临时使用 --no-offload-new-driver 回退到旧行为。--no-offload-new-driver 选项将在下一个版本中移除。

迁移路径：尽快使用新 offload 驱动重新编译所有 offload 库和依赖项。 如需立即恢复旧行为，使用 --no-offload-new-driver 作为临时缓解措施。

10b. __cpp_impl_coroutine 在 32 位 x86 MS ABI 下不再定义

Clang 不再在 32 位 x86 Microsoft ABI 目标下定义 __cpp_impl_coroutine 特性测试宏， 因为该目标上的协程支持不完整。在该目标上使用协程时会发出警告 -Wcoroutines-unsupported-target，可用 -Wno-coroutines-unsupported-target 禁用。（参见 #GH59382）

10c. HIPSPV 工具链弃用

HIPSPV 工具链中，--offload-targets=spirv{32,64} 选项已被弃用， 将在新 offload 驱动成为默认时移除。

替代方案：使用新 offload 驱动时， 应改用 --offload-targets=spirv{32,64}-unknown-chipstar。

建议：检查构建系统中是否使用了 HIPSPV 相关 offload 选项， 尽早迁移到新的目标三元组格式。
新语法

11. 浮点字面量表示法变更（f0x 前缀）

C++ 和 C 标准传统上使用 0x 前缀表示十六进制浮点字面量（如 0x1.0p0 表示 1.0）。 然而，随着 C++23/C23 引入更多浮点类型（如 std::float16_t、std::bfloat16_t 等）， 需要更精确地指定浮点字面量的类型和编码。

Clang 21 引入了新的 f0x 前缀，用于更明确地表示十六进制浮点字面量。 这是对现有 0x 十六进制浮点表示法的扩展和规范。

Before（传统十六进制浮点）
// 使用 0x 前缀表示十六进制浮点数
double  a = 0x1.0p0;     // 1.0
double  b = 0x1.8p1;     // 3.0  (1.5 × 2¹)
double  c = 0x1.ffffp0;  // 约 1.99997
float   d = 0x1.0p-3f;   // 0.125 (1.0 × 2⁻³)，float 类型
After（Clang 21 — f0x 前缀）
// 使用 f0x 前缀明确十六进制浮点类型
float f   = f0x1.0p0;    // 明确为十六进制浮点 float
double d  = f0x1.0p0;    // 明确为十六进制浮点 double
// 同样支持指数表示
auto  val = f0x1.8p1;    // 3.0，类型推导为 double
说明：0x 前缀的旧语法仍然有效（向后兼容）。f0x 是新的可选语法， 提供更清晰的语义区分。现有代码无需修改，新代码推荐使用 f0x 以获得更好的可读性和类型安全性。
优化变更

12. 空指针算术优化

C/C++ 标准规定，对空指针进行算术运算是未定义行为（UB）。LLVM 21 更加积极地利用这一事实进行优化： 编译器现在会假设参与指针算术的指针不为空，从而消除空指针检查或进行更激进的代码简化。

这会影响一些历史上常用的编程惯用法，最典型的是基于指针算术的 offsetof 模拟，以及 某些依赖"看似无用的空指针算术"的技巧。

受影响的惯用法：offsetof 模拟
// 旧的 offsetof 模拟（在 stddef.h 出现之前常用）
#define MY_OFFSETOF(type, member) \
  ((size_t)(&((type*)0)->member))

// 这里 (type*)0 产生空指针，
// 对空指针使用 -> 是未定义行为。
// LLVM 21 可能更激进地优化包含此模式的代码。

// 现代 C/C++ 应使用标准 offsetof：
#include <cstddef>
size_t off = offsetof(MyStruct, field);  // 安全
受影响场景：空指针上的算术
// 对空指针进行算术运算 — UB
int* p = nullptr;
int* q = p + 10;  // UB: 空指针算术

// LLVM 21 更积极优化：
int* p = getPtr();
int* q = p + offset;
if (p == nullptr)  // 如果之前做了算术运算，
  return;          // 编译器可能推断 p 非空，消除此检查
应对措施：
  • 使用 -fno-delete-null-pointer-checks 禁用空指针检查删除优化
  • 使用 -fwrapv-pointer 使指针算术像有符号整数一样回绕（减少 UB 依赖）
  • 在代码中避免依赖空指针算术：使用标准 offsetof、确保指针在算术前非空
迁移建议：优先审计代码中是否存在自定义的 offsetof 宏或空指针算术惯用法。 将其替换为标准 offsetof 或 reinterpret_cast<uintptr_t> 的安全写法。 短期可使用 -fno-delete-null-pointer-checks 保持兼容。
内联决策

13. 内联汇编指令影响内联成本计算

函数内联（inlining）是编译器最重要的优化之一。LLVM 使用内联成本模型（inline cost model） 来评估将某个函数内联到调用处是否有利——它会权衡代码膨胀和执行效率。

在 LLVM 20 及之前版本中，内联汇编指令（inline assembly）不参与内联成本计算。 这意味着包含大量内联汇编的函数可能被过度内联，导致代码膨胀和指令缓存压力。

LLVM 21 中，内联汇编指令现在计入内联成本计算。编译器会考量内联汇编的体积和复杂度， 使得含有内联汇编的函数的内联决策更加准确。

Before（LLVM 20）
// 此函数含大量内联汇编，但
// 内联成本模型中不计入 asm 开销
static inline int cpuid_ecx(int leaf) {
  int val;
  asm volatile(
    "cpuid"
    : "=c"(val)
    : "a"(leaf)
    : "ebx", "edx"
  );
  return val;
}

// 可能被过度内联到每个调用处
// 即使调用 100 次也会内联
After（LLVM 21）
// 内联汇编体积计入成本模型
// 编译器评估：此函数含 asm，
// 内联成本较高

static inline int cpuid_ecx(int leaf) {
  int val;
  asm volatile(
    "cpuid"
    : "=c"(val)
    : "a"(leaf)
    : "ebx", "edx"
  );
  return val;
}

// 内联决策更加保守和准确
// 避免过度内联导致的代码膨胀
影响分析：
  • 正面影响：减少代码膨胀，提高指令缓存利用率，内联决策更合理。
  • 可能影响：部分之前被内联的小型内联汇编包装函数可能不再被内联。 如果性能敏感，可以考虑使用 __attribute__((always_inline)) 强制内联。
  • 性能影响：大多数情况下，此项变更有助于整体性能（减少膨胀，提高 I-cache 命中率）。
LLVM IR

14. LLVM IR 变更

LLVM 21 在 IR 层面引入了多项重要变更。这些变更主要影响编译器开发者、IR 解析/生成工具、 以及直接操作 LLVM IR 的项目。普通 C/C++ 用户通常不直接受此影响，但了解这些变更有助于 理解编译器行为的变化。

14a. llvm.convert.to.fp16 / from.fp16 移除

llvm.convert.to.fp16 和 llvm.convert.from.fp16 内建函数已被移除。 这些内建函数等价于 fptrunc 和 fpext 配合 half 类型和 bitcast 使用。 现有 IR 和 bitcode 将被自动更新。

14b. denormal-fp-math 迁移为 denormal_fpenv 属性

"denormal-fp-math" 和 "denormal-fp-math-f32" 字符串属性已迁移至 一等属性（first-class attribute）denormal_fpenv。这是 IR 属性系统的现代化改进。

14c. nooutline 属性语法变更

"nooutline" 属性现在的标准写法是 nooutline（不带引号）。 现有 IR 和 bitcode 将被自动更新。此变更与属性系统规范化保持一致。

14d. ConstantPointerNull 向量 Splat

ConstantPointerNull 现在可以表示固定长度和可缩放向量（scalable vector）的空指针 splat。 此类常量可能打印为 splat (ptr null) 而非 zeroinitializer。

14e. 浮点字面量新格式（f0x）

详见第 11 节 浮点字面量表示法变更。旧的十六进制按位表示法已被弃用， 将在下个版本中移除。标准文本输出已改为使用新的浮点字面量格式。

14f. Coroutine Resume/Destroy CallingConv::C

详见第 8 节 Coroutine ABI 稳定化。LLVM IR 中协程的 resume/destroy 函数现在使用 CallingConv::C 而非 CallingConv::Fast。

14g. Assume Bundles 属性限制

Assume bundles 现在只接受实际被处理的属性。具体包括：align、cold、 dereferenceable、dereferenceable_or_null、nonnull、 noundef 和 separate_storage。 使用不支持的属性将导致错误。

14h. Fast Math Flags on uitofp / sitofp

Fast math flags（如 nnan、ninf 等）现在允许用于 uitofp 和 sitofp 指令。

14i. noipa 属性

新增 noipa 属性，用于禁用所有检查函数定义的跨过程分析（interprocedural analysis）。 此属性不控制内联或外联（outlining）。如需同时禁用内联和外联， 请额外添加 noinline 和 nooutline 属性。

14j. AArch64 Backend 变更

  • sysp / mrrs / msrr 指令：sysp、mrrs 和 msrr 指令现在不再需要 +d128 特性开关即可接受。 此变更扩展了这些系统寄存器和内存屏障指令的可用范围。
  • TLS 调试信息：新增内部选项 -aarch64-emit-debug-tls-location，允许为线程局部变量（TLS）生成 DW_AT_location 调试信息。当前默认禁用以保持与旧版 Binutils 和 LLVM 工具链的兼容性。
  • x29 / x30 内联汇编 Clobber 修复：修复了一个 bug，该 bug 导致 LLVM IR 内联汇编 中使用 xN 名称（如 x29、x30）而非 ABI 名称（如 FP、LR）的 clobber 声明被忽略。 Clang 始终使用 ABI 名称，但其他前端可能不使用。（#167783）

14k. ARM Backend 变更

  • r14 寄存器别名：r14 寄存器现在可以在内联汇编中作为链接寄存器 lr 的别名使用。Clang 始终将名称规范化为 lr，但其他前端可能不这样做。
  • subs pc, lr, #imm 谓词化：subs pc, lr, #imm 指令现在可以在 Thumb2 模式下被谓词化（predicated）。
Sanitizers

15. Sanitizers 变更

LLVM 21 中的 Sanitizer 工具体系引入了多项重要更新，增强了自定义抑制规则的控制能力和跨平台路径匹配的一致性。

15a. UBSan __ubsan_default_suppressions

UndefinedBehaviorSanitizer (UBSan) 现在支持 __ubsan_default_suppressions 机制。 用户可以在代码中定义此变量来指定默认的抑制规则，类似于 ASan 的 __asan_default_suppressions。这允许库和应用程序以编程方式配置 UBSan 的抑制行为， 而无需依赖外部抑制文件。

使用示例：定义默认抑制规则
// 在任意源文件中定义
extern "C" const char *__ubsan_default_suppressions() {
  return "vla_bound\n"
         "function:sometimes_buggy_func\n";
}
// UBSan 会在初始化时自动加载这些抑制规则

15b. Sanitizer Special Case List v4 / v5

Sanitizer Special Case Lists（-fsanitize-ignorelist）现在支持版本 4 和版本 5 的格式。

版本 4：引入路径规范化过渡期。版本 4 同时匹配规范化路径和非规范化路径（不含前导 ./），但会对弃用的匹配发出警告。由文件头 #!special-case-list-v4 标识。

版本 5：移除向后兼容性，要求规则必须匹配规范化路径（不含前导 ./）。

迁移建议：检查 ignorelist 文件中的路径规则是否包含前导 ./。 如有，移除 ./ 前缀或将文件头更新为 v4 以进入过渡期。

15c. Sanitizer 路径匹配在 Windows 上的改进

在 Windows 平台上，Sanitizer Special Case Lists（-fsanitize-ignorelist）和 警告抑制映射（--warning-suppression-mappings）的路径匹配现在是斜杠无关的 （slash-agnostic）：正向斜杠（/）和反斜杠（\）在模式和路径中 均匹配任一路径分隔符。此变更需要版本 4 及以上格式（#!special-case-list-v4）。
