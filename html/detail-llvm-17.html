LLVM 17.0.0 · 2023-09-05

LLVM 17 是 LLVM 项目的第 17 个大版本，于 2023 年 9 月 5 日发布。 本页面聚焦 LLVM 16 → 17 的核心变更，按对数通产品线影响从高到低排列。 每个变更均配有 Before/After 代码示例，方便直接对照迁移。

不透明指针（Opaque Pointers）完全强制

Breaking Change

变更说明

LLVM 15 开始默认启用 opaque pointers，LLVM 16 中 typed pointers 已标记为废弃但仍可通过 -opaque-pointers=0 使用。到了 LLVM 17， -opaque-pointers 选项彻底移除，typed pointers 不再被支持。 这是 LLVM IR 最重要的一次语法简化。

影响范围 主要影响手写 LLVM IR、使用 LLVM C++ API 的工具/Pass、基于 IR 文本的处理脚本。 普通 C/C++ 代码通过 Clang 编译不受影响（Clang 从 LLVM 15 起已默认生成 opaque pointer IR）。

代码示例：LLVM IR 中指针类型的变化

示例 1：基本指针类型 LLVM 16 (typed pointers) LLVM 17 (opaque pointers)
Before: Typed Pointer
; 指针携带完整的元素类型信息
define i32 @add(i32* %p) {
  %v = load i32, i32* %p
  ret i32 %v
}

; 结构体指针: 类型信息在指针中
define i32 @get_x({ i32, i32 }* %s) {
  %p = getelementptr { i32, i32 }, { i32, i32 }* %s, i32 0, i32 0
  %v = load i32, i32* %p
  ret i32 %v
}
After: Opaque Pointer
; 指针类型统一为 ptr
define i32 @add(ptr %p) {
  %v = load i32, ptr %p
  ret i32 %v
}

; 结构体指针: 也是 ptr，类型取指 load/store 指定
define i32 @get_x(ptr %s) {
  %p = getelementptr { i32, i32 }, ptr %s, i32 0, i32 0
  %v = load i32, ptr %p
  ret i32 %v
}
示例 2：bitcast 消除
Before: 需要 bitcast 转换指针类型
define i32 @example(float %f) {
  %a = alloca i32
  store i32 42, i32* %a
  ; 需要 bitcast 把 i32* 转成 float*
  %bc = bitcast i32* %a to float*
  store float %f, float* %bc
  %v = load i32, i32* %a
  ret i32 %v
}
After: bitcast 不再需要
define i32 @example(float %f) {
  %a = alloca i32
  store i32 42, ptr %a
  ; 所有指针都是 ptr，不需要 bitcast
  store float %f, ptr %a
  %v = load i32, ptr %a
  ret i32 %v
}

C++ API 代码迁移

示例 3：LLVM C++ API 中创建指针类型的变更 LLVM 16 API LLVM 17 API
Before: getPointerTo() / getInt8PtrTy()
// 创建指向 i32 的指针类型
Type *Int32Ptr = Type::getInt32Ty(Ctx)
                   ->getPointerTo();

// 获取地址空间 0 的 i8*
Type *I8Ptr = Type::getInt8PtrTy(Ctx);

// 获取地址空间 1 的 i32*
Type *I32PtrAS1 = PointerType::get(
    Type::getInt32Ty(Ctx), 1);

// 检查是否是指针
if (Ty->isPointerTy()) { ... }
After: PointerType::get() 统一入口
// 创建 opaque pointer（默认地址空间 0）
Type *PtrTy = PointerType::get(Ctx, 0);

// 获取地址空间 0 的 ptr
Type *PtrTy = PointerType::get(Ctx, 0);

// 获取地址空间 1 的 ptr
Type *PtrAS1 = PointerType::get(Ctx, 1);

// 检查是否是指针（同上）
if (Ty->isPointerTy()) { ... }
迁移要点
  • LLVM IR 文本处理脚本：移除所有指针元素的类型标注
  • C++ Pass/工具：将 getPointerTo()、getInt8PtrTy() 替换为 PointerType::get(Context, AddrSpace)
  • GEP 类型参数：第一个参数从元素类型指针改为元素类型本身（getelementptr { i32, i32 }, ptr %s, ... 而非 getelementptr { i32, i32 }, { i32, i32 }* %s, ...）
  • 对 JIT 工具影响较大，需全面适配 LLVM 17 的 llvm::Type API

asm goto 间接边拆分

行为变更

变更说明

在 GCC/Clang 扩展 asm goto 中，同一个 label 如果有多个输出（即多个输入引用同一个 label）， 在 LLVM 16 及之前的版本中这些引用被合并为一条间接边。这种合并行为是不正确的——它可能导致编译优化基于错误的假设进行。 LLVM 17 修复了这个问题：指向同一 label 的多个输入不再保证相等，每个输入产生一条独立的间接边。

影响场景 嵌入式设备驱动、固件和内核代码中广泛使用的内联汇编跳转（如 kernel 的 _ASM_EXTABLE 模式、错误处理跳转表）， 如果使用同一 label 引用多次，编译产物的控制流图会发生变化。

代码示例

示例：asm goto 中同一 label 被两个输入引用
Before: LLVM 16 — 两个输入合并为一条间接边
int example(int x) {
  int result = 0;
  asm goto(
    "cmp %1, #0\n\t"
    "beq %l[zero]\n\t"
    "bne %l[zero]"
    /* 两个条件分支指向同一个 label */
    : /* 无输出 */
    : "r"(x), "i"(&&zero)
    : : zero
  );
  result = 1;
zero:
  return result;
}

// LLVM 16 行为:
// 两个跳转合并为一条间接边
// 优化器可能错误地认为
// 只有一个零条件到达 zero label
After: LLVM 17 — 每个输入生成独立间接边
int example(int x) {
  int result = 0;
  asm goto(
    "cmp %1, #0\n\t"
    "beq %l[zero]\n\t"
    "bne %l[zero]"
    /* 两个条件分支指向同一个 label */
    : /* 无输出 */
    : "r"(x), "i"(&&zero)
    : : zero
  );
  result = 1;
zero:
  return result;
}

// LLVM 17 行为:
// 两个跳转生成两条独立的间接边
// 控制流图更准确地反映
// assembler 的真实行为
示例：更简洁的差异展示
Before: LLVM 16
; asm goto "# %0 %1"
;   :: "i"(&&foo), "i"(&&foo)
;   :: foo;
;
; 两个 %label 输入被合并，
; 编译认为它们取值相同。
; 如果优化器基于"它们相同"
; 做常数折叠，可能出错。
After: LLVM 17
; asm goto "# %0 %1"
;   :: "i"(&&foo), "i"(&&foo)
;   :: foo;
;
; 两个 %label 输入独立处理，
; 每个生成一条间接边。
; 优化器不再假设它们等价，
; 控制流分析更精确。
对数通产品线的影响
  • 设备驱动和固件中的内联汇编跳转模式需要检查
  • 如果代码依赖旧行为（假设同一 label 的多个输入等价），需调整逻辑
  • 产生的二进制大小可能有微小变化（额外的间接边）
  • 内核风格的异常表 / 跳转表宏通常不受影响，因为它们使用不同的 label

void* 解引用 (C++) 从 warning-as-error → 硬 Error

C++ · Breaking Change

变更说明

在 LLVM 16 中，C++ 代码中对 void* 进行解引用已被设为 warning-as-error（默认 -Werror 下报错），但可以通过 -Wno-error=void-ptr-dereference 降级为 warning。 到了 LLVM 17，这项检查被收紧为硬错误（hard error），即使用 -Wno-error= 也无法降级。

破坏性 如果代码中存在 void* 解引用的模式，在 LLVM 17 下直接编译失败。 虽然这种写法本身是语言扩展（非标准 C++），但在老旧的嵌入式 C 代码中被混入 C++ 编译时可能出现。

代码示例

示例：void* 解引用
Before: LLVM 16 — warning-as-error（可降级）
// C++ 代码
void func(void *p) {
    *p;  // LLVM 16: warning-as-error
         // -Wno-error=void-ptr-dereference 可降级
}

void *buf = malloc(128);
// 某些代码直接对 void* 做算术
void *next = buf + 16;  // 也涉及 void* 算术
After: LLVM 17 — 硬 Error（不可降级）
// C++ 代码 — 必须修复
void func(void *p) {
    *p;  // ERROR: 硬错误，编译失败
}

// 修复方案 1：转为 char* 再解引用
void func(void *p) {
    *(char *)p;  // OK
}

// 修复方案 2：void* 算术改为 char* 算术
char *buf = (char *)malloc(128);
char *next = buf + 16;  // OK
常见 void* 解引用模式与修复
旧代码模式LLVM 17 状态修复方案
void *p = ...; *p; 硬 Error *(char *)p; 或 *(int *)p;
void *p = ...; p + offset; 硬 Error (char *)p + offset;
void *p = ...; p++; 硬 Error p = (char *)p + 1;
sizeof(*p) where p is void* 硬 Error 直接写目标大小，如 sizeof(int)
应对策略
  • LLVM 17 下无法通过编译选项降级，必须修复源代码
  • 在升级前，先在 LLVM 16 上开启 -Wvoid-ptr-dereference 找出所有违规点
  • 典型修复：将 void* 显式转换为 char*（编译器对 char* 别名有例外，优化不会出问题）
  • 如果代码量大，可使用 clang-tidy 的 modernize-replace-disallow-copy 等进行批量修复
  • 此变更仅限于 C++ 模式；C 语言下 void* 解引用行为不变

std::experimental::coroutine_traits 不再搜索

C++ 协程 · 迁移提醒

变更说明

在 C++20 协程正式标准化之前，Clang 支持 std::experimental::coroutine_traits 作为 TS（技术规范）的实现。随着 C++20 协程（std::coroutine_traits）的标准化和广泛采用， LLVM 17 移除了对 std::experimental 命名空间中协程 traits 的搜索。 编译器只会在 std 命名空间中查找 coroutine_traits。

影响范围 使用 std::experimental 命名空间编写协程的代码（常见于早期 C++20 协程实验项目）。 已经迁移到标准 std::coroutine_traits 的代码不受影响。

代码示例

示例：协程 traits 命名空间迁移
Before: experimental 命名空间 (LLVM 16 可用)
// 实验性协程 TS 风格
#include <experimental/coroutine>

template<class T, class... Args>
struct std::experimental::coroutine_traits<T, Args...> {
  using promise_type = typename T::promise_type;
};

struct my_task {
  struct promise_type { /* ... */ };
};

// LLVM 16 同时搜索 experimental 和 std
my_task foo() {
  co_return;
}
After: 标准命名空间 (LLVM 17 要求)
// 标准 C++20 协程风格
#include <coroutine>  // 注意头文件变化

template<class T, class... Args>
struct std::coroutine_traits<T, Args...> {  // 去掉 experimental
  using promise_type = typename T::promise_type;
};

struct my_task {
  struct promise_type { /* ... */ };
};

// LLVM 17 只搜索 std 命名空间
my_task foo() {
  co_return;
}
常见需要修改的地方
项目旧 (experimental TS)新 (C++20 标准)
头文件 #include <experimental/coroutine> #include <coroutine>
traits std::experimental::coroutine_traits std::coroutine_traits
handle std::experimental::coroutine_handle std::coroutine_handle
trivial_awaitables std::experimental::suspend_never std::suspend_never
迁移建议
  • 全局搜索 experimental/coroutine 和 experimental::coroutine_traits
  • 替换为 <coroutine> 和 std::coroutine_traits
  • 同时确认 -fcoroutines-ts 编译选项已被移除（LLVM 17 不再支持该选项）
  • 如果同时需要支持旧版 LLVM，可使用条件编译：#if __has_include(<coroutine>)

CWG2518: static_assert(false) 在模板中合法

C++ 标准缺陷修复

变更说明

在 C++ 标准缺陷报告 CWG2518 之前，在模板声明中写 static_assert(false) 会立即触发断言失败， 即使模板从未被实例化。这迫使模板库作者使用一些"脏"技巧（如 static_assert(sizeof(T) == 0) 或依赖某个总是为 false 的表达式） 来延迟断言求值，直到模板实例化时。

LLVM 17 实现了 CWG2518 的修复：未实例化的模板中的 static_assert(false) 不再立即报错， 而是等到模板被实例化时才求值。这使得模板库的编写更加直观和安全。

正面影响 对于模板库编写者（尤其是 C++ 模板元编程），这消除了一个常见的痛点。 在数通产品线中，如果存在自定义的 C++ 泛型容器或协议处理模板，可以利用此特性简化代码。

代码示例

示例 1：经典模板约束场景
Before: LLVM 16 — static_assert(false) 立即报错
// ERROR: 即使模板从未实例化也报错
template<class T>
void process(const T& val) {
    static_assert(false,
        "未特化的 process 不可用");
    // ^ LLVM 16: 立即报错，编译失败
}

// 旧式 workaround：依赖模板参数
template<class T>
void process_workaround(const T& val) {
    static_assert(sizeof(T) == 0,
        "未特化的 process 不可用");
    // sizeof(T) 依赖 T，等到实例化时才求值
}
After: LLVM 17 — 等到实例化时才报错
// CWG2518 后：合法！
template<class T>
void process(const T& val) {
    static_assert(false,
        "未特化的 process 不可用");
    // LLVM 17: 不报错，等实例化时才求值
}

// 特化正常工作
template<>
void process<int>(const int& val) {
    printf("processing int\n");
}

// 只有这行才会触发 static_assert
// process("hello"); // 实例化时报错
示例 2：实用场景 — 编译时接口契约检查
Before: 需要 ugly workaround
template<class T>
struct serializer {
    // 旧方法：用 always_false<T> 依赖 T
    template<class>
    struct always_false : std::false_type {};

    static void serialize(const T&) {
        static_assert(
            always_false<T>::value,
            "需要特化 serializer");
    }
};
After: 简洁直观的写法
template<class T>
struct serializer {
    // CWG2518: 直接写 false，干净利落
    static void serialize(const T&) {
        static_assert(false,
            "需要特化 serializer");
    }
};

// 特化
template<>
struct serializer<packet_header> {
    static void serialize(
        const packet_header& h) {
        /* 实际的序列化逻辑 */
    }
};
使用注意事项
  • static_assert(false, ...) 仅在模板声明内部被延迟求值
  • 非模板上下文中写 static_assert(false) 仍然立即报错
  • 需要 LLVM 17+ 且以 C++20 或更高标准编译（CWG2518 被追溯应用到所有标准版本）
  • 如果模板确实被实例化且没有合适的特化，static_assert 仍会触发编译错误，行为符合预期
  • 建议将旧的 sizeof(T)==0 / always_false<T> workaround 替换为直接使用 false

AArch64 FEAT_GCS 汇编支持

安全特性

变更说明

LLVM 17 新增了对 AArch64 FEAT_GCS（Guarded Control Stack） 硬件安全特性的汇编器和反汇编器支持。 GCS 是 ARMv9.4-A 引入的控制流完整性（CFI）保护机制，通过硬件维护一个独立的"影子栈"来保护函数返回地址不被篡改。 这是对 ROP（Return-Oriented Programming）攻击的重要硬件级防御。

LLVM 17 支持以下 GCS 相关指令和系统寄存器的汇编/反汇编，为后续编译器自动生成 GCS 保护代码奠定基础。 注意：LLVM 17 中仅在汇编层面支持这些指令；编译器自动插入 GCS 保护（如 prologue/epilogue 中的 GCS 操作）在后续版本（LLVM 19+）中才完整实现。

对数通产品线的价值 基于 ARM 架构的数通设备（如使用 ARM Neoverse 处理器的路由器/交换机）如果目标硬件支持 GCS， 可以利用此特性防御控制流劫持攻击，提升设备安全性。

示例 2：GCS 系统寄存器与函数调用模式 
; ════════════════════════════════════════
; GCS 系统寄存器 (LLVM 17 新增支持)
; ════════════════════════════════════════

; 读取 GCS 控制寄存器
mrs     x0, GCSCR_EL1         ; GCS Control Register
mrs     x0, GCSPR_EL1         ; GCS Pointer Register
mrs     x0, GCSCRE0_EL1       ; GCS Current Record El0

; 写 GCS 控制寄存器

msr     GCSPR_EL1, x0

; ════════════════════════════════════════
; GCS 保护下的函数序言示意
; ════════════════════════════════════════
my_function:
    ; 序言：将返回地址压入 GCS
    str     x30, [sp, #-16]!   ; 常规栈帧保存 LR
    gcspushx                   ; GCS 记录返回地址
    stp     x29, x30, [sp, #-16]!
    mov     x29, sp

    ; ... 函数体 ...

    ; 结语：从 GCS 验证返回地址
    ldp     x29, x30, [sp], #16
    gcspopx                    ; 验证返回地址未被篡改
    ldr     x30, [sp], #16
    ret
示例 3: C/C++ 中使用内联汇编调用 GCS 指令
// 在 C/C++ 中通过内联汇编读取 GCS 指针
#include <stdint.h>

// 读取 GCS 指针寄存器 (GCSPR_EL1)
static inline uint64_t read_gcs_pointer(void) {
    uint64_t gcspr;
    asm volatile(
        "mrs %0, GCSPR_EL1\n"
        : "=r"(gcspr)
    );
    return gcspr;
}

// 读取 GCS 控制寄存器
static inline uint64_t read_gcs_control(void) {
    uint64_t gcscr;
    asm volatile(
        "mrs %0, GCSCR_EL1\n"
        : "=r"(gcscr)
    );
    return gcscr;
}

// 在初始化代码中验证 GCS 特性存在
void check_gcs_support(void) {
    uint64_t gcscr = read_gcs_control();
    // bit 0 表示 GCS 启用
    if (gcscr & 1) {
        printf("GCS enabled, ptr=0x%lx\n",
               read_gcs_pointer());
    }
}
使用说明
  • 汇编时需要指定支持 GCS 的目标架构，如 -march=armv9.4-a+gcs
  • 反汇编时使用 -mattr=+gcs 以正确解码 GCS 指令
  • 此特性仅在 AArch64 (ARM64) 架构上可用
  • LLVM 17 仅提供汇编/反汇编支持，编译器自动插入 GCS 保护在 LLVM 19+ 中通过 -mbranch-protection= 实现
  • 需要 ARMv9.4-A 或更高版本的硬件（或具备 FEAT_GCS 特性的 ARMv8.x 实现）
7

LLD 线程数上限 16 核

链接器 · 默认行为变更

变更说明

LLD（LLVM 链接器）的 --threads=N 选项用于控制链接时的并行线程数。 在 LLVM 17 之前，--threads= 的上限为 256 核，实际上等于没有限制。 但在实践中发现，当线程数超过 16 时，glibc 的 malloc 实现会出现严重的锁竞争， 导致性能反而下降——线程数越多，链接越慢。

LLVM 17 将 --threads= 的默认值从 CPU 核心数改为 min(CPU 核心数, 16)， 并且在自动检测时也限制不超过 16。显式指定超过 16 的值也会被 cap 到 16。 此变更旨在防止过度并行带来的性能反噬。

实际场景 在高端服务器（如 64 核 / 128 核机器）上构建大型项目时，旧版本 LLD 可能默认启动 64+ 线程， 导致大量的 malloc/free 竞争。LLVM 17 的 cap 机制使链接性能更加可预测。

代码示例

示例：编译脚本中 LLD 线程参数的行为差异
Before: LLVM 16 — 无上限限制
# 128 核服务器上
# LLD 16 默认使用全部 128 线程
clang -fuse-ld=lld foo.o bar.o \
    -o output

# 等效于
clang -fuse-ld=lld foo.o bar.o \
    -Wl,--threads=128 -o output

# 显式指定超多线程
clang -fuse-ld=lld foo.o bar.o \
    -Wl,--threads=64 -o output
# LLVM 16: 实际使用 64 线程 ✓
# 但可能比 16 线程还慢！
After: LLVM 17 — cap 到 16
# 128 核服务器上
# LLD 17 默认最大 16 线程
clang -fuse-ld=lld foo.o bar.o \
    -o output

# 等效于
clang -fuse-ld=lld foo.o bar.o \
    -Wl,--threads=16 -o output

# 显式指定超多线程会被 cap
clang -fuse-ld=lld foo.o bar.o \
    -Wl,--threads=64 -o output
# LLVM 17: 实际只用 16 线程
# 并输出一条 warning

场景LLVM 16 行为LLVM 17 行为说明
不指定 --threads 使用全部 CPU 核心数 min(CPU核心数, 16) 自动限制
--threads=8 8 线程 8 线程 小于 16 无影响
--threads=16 16 线程 16 线程 等于上限，行为不变
--threads=32 32 线程 16 线程 + warning 被 cap
--threads=64 64 线程 16 线程 + warning 被 cap
--threads=1 单线程（等同于 --no-threads） 单线程 确定性构建

对数通产品线的影响
  • 绝大多数场景下，此变更是正面优化（避免过度并行导致性能下降）
  • 如果构建脚本中硬编码了 --threads=32 或更高值，会看到 warning 输出
  • 在构建日志中检查是否存在 --threads 超过 16 的情况，建议直接移除显式设置
  • 对于 CI 构建服务器，移除硬编码线程数后可能反而获得更稳定的链接时间
  • 如果坚持使用超过 16 线程，需自行编译 LLD 并修改源码中的上限常量
