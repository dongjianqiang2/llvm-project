不透明指针（Opaque Pointers）完全强制

Breaking Change

变更说明

LLVM 15 开始默认启用 opaque pointers，LLVM 16 中 typed pointers 已标记为废弃但仍可通过 -opaque-pointers=0 使用。到了 LLVM 17，-opaque-pointers 选项彻底移除，typed pointers 不再被支持。

影响范围主要影响手写 LLVM IR、使用 LLVM C++ API 的工具/Pass、基于 IR 文本的处理脚本。普通 C/C++ 代码通过 Clang 编译不受影响（Clang 从 LLVM 15 起已默认生成 opaque pointer IR）。

LLVM IR 文本对照

基本指针类型LLVM 16 (typed)LLVM 17 (opaque)
Before: Typed Pointer
; 指针携带完整元素类型
define i32 @add(i32* %p) {
  %v = load i32, i32* %p
  ret i32 %v
}
; GEP 第一个参数为元素类型指针
define i32 @get_x({ i32, i32 }* %s) {
  %p = getelementptr { i32, i32 }, { i32, i32 }* %s, i32 0, i32 0
  %v = load i32, i32* %p
  ret i32 %v
}
After: Opaque Pointer
; 指针类型统一为 ptr
define i32 @add(ptr %p) {
  %v = load i32, ptr %p
  ret i32 %v
}
; GEP 第一个参数为元素类型本身
define i32 @get_x(ptr %s) {
  %p = getelementptr { i32, i32 }, ptr %s, i32 0, i32 0
  %v = load i32, ptr %p
  ret i32 %v
}
bitcast 消除
Before: 需要 bitcast
define i32 @example(float %f) {
  %a = alloca i32
  store i32 42, i32* %a
  %bc = bitcast i32* %a to float*
  store float %f, float* %bc
  %v = load i32, i32* %a
  ret i32 %v
}
After: bitcast 不需要
define i32 @example(float %f) {
  %a = alloca i32
  store i32 42, ptr %a
  store float %f, ptr %a
  %v = load i32, ptr %a
  ret i32 %v
}
C++ API 迁移LLVM 16LLVM 17
Before: getPointerTo()

                 ->getPointerTo();
Type *I8Ptr = Type::getInt8PtrTy(Ctx);
Type *I32PtrAS1 = PointerType::get(
    Type::getInt32Ty(Ctx), 1);

Type *PtrTy = PointerType::get(Ctx, 0);

迁移要点
  • IR 处理脚本：移除指针元素类型标注
  • C++ Pass：将 getPointerTo() 替换为 PointerType::get(Context, AddrSpace)
  • GEP：第一个参数从元素类型指针改为元素类型本身
  • 对 JIT 工具影响较大，需全面适配

asm goto 间接边拆分

行为变更

变更说明

在 GCC/Clang 扩展 asm goto 中，同一个 label 如果有多个输出（即多个输入引用同一个 label），在 LLVM 16 及之前这些引用被合并为一条间接边，这种合并行为是不正确的。LLVM 17 修复了这个问题：指向同一 label 的多个输入不再保证相等，每个输入产生一条独立的间接边。同时，LLVM 17 还支持了 asm goto 沿间接边的输出操作数。

影响场景嵌入式设备驱动、固件和内核代码中广泛使用的内联汇编跳转（如 kernel 的 _ASM_EXTABLE 模式、错误处理跳转表）。
asm goto 同一 label 被两个输入引用
Before: LLVM 16 — 合并为一条边
// 两个条件分支指向同一个 label
int example(int x) {
  int result = 0;
  asm goto(
    "cmp %1, #0\n\t"
    "beq %l[zero]\n\t"
    "bne %l[zero]"
    : : "r"(x), "i"(&&zero)
    : : zero
  );
  result = 1;
zero:
  return result;
}
// LLVM 16: 两个跳转合并为一条间接边
// 优化器可能错误地认为只有一个
// 零条件到达 zero label
After: LLVM 17 — 独立间接边
// 两个条件分支指向同一个 label
int example(int x) {
  int result = 0;
  asm goto(
    "cmp %1, #0\n\t"
    "beq %l[zero]\n\t"
    "bne %l[zero]"
    : : "r"(x), "i"(&&zero)
    : : zero
  );
  result = 1;
zero:
  return result;
}
// LLVM 17: 每个输入生成独立间接边
// 控制流图更准确反映 assembler 的真实行为
// 同时支持间接边上的输出操作数
对数通产品线的影响
  • 设备驱动和固件中的内联汇编跳转模式需要检查
  • 如果代码依赖旧行为（假设同一 label 的多个输入等价），需调整逻辑
  • LLVM 17 新增支持 asm goto 间接边上的输出操作数（Issue #53562）

void* 解引用 (C++) 从 warning-as-error 变为硬 Error

C++ · Breaking Change

变更说明

LLVM 16 中 C++ 代码的 void* 解引用被设为 warning-as-error（可通过 -Wno-error=void-ptr-dereference 降级）。LLVM 17 中这被收紧为硬错误，无法降级。

破坏性如果代码中有 void* 解引用模式，LLVM 17 下直接编译失败。
void* 解引用修复
Before: LLVM 16
void func(void *p) {
    *p;  // warning-as-error
}
void *buf = malloc(128);
void *next = buf + 16;  // void* 算术
After: LLVM 17
void func(void *p) {
    *(char *)p;  // OK: 显式转换
}
char *buf = (char *)malloc(128);
char *next = buf + 16;  // OK
旧代码模式LLVM 17 状态修复方案
void *p = ...; *p;硬 Error*(char *)p;
void *p = ...; p + offset;硬 Error(char *)p + offset;
void *p = ...; p++;硬 Errorp = (char *)p + 1;
sizeof(*p) where p is void*硬 Error直接写目标大小
应对策略
  • LLVM 17 下无法通过编译选项降级，必须修复源代码
  • 在升级前使用 -Wvoid-ptr-dereference 找出所有违规点
  • 将 void* 显式转换为 char*（编译器对 char* 别名有例外）
  • 此变更仅限于 C++ 模式；C 语言下 void* 解引用行为不变

std::experimental::coroutine_traits 不再搜索

C++ 协程 · 迁移提醒

变更说明

LLVM 17 移除了对 std::experimental 命名空间中协程 traits 的搜索。编译器只会在 std 命名空间中查找 coroutine_traits。

影响范围使用 std::experimental 命名空间的协程代码。已迁移到标准 std::coroutine_traits 的代码不受影响。
协程 traits 命名空间迁移
Before: experimental (LLVM 16)
#include <experimental/coroutine>
template<class T, class... Args>
struct std::experimental::coroutine_traits<T, Args...> {
  using promise_type = typename T::promise_type;
};
After: 标准 (LLVM 17)
#include <coroutine>
template<class T, class... Args>
struct std::coroutine_traits<T, Args...> {
  using promise_type = typename T::promise_type;
};
项目旧 (experimental TS)新 (C++20 标准)
头文件#include <experimental/coroutine>#include <coroutine>
traitsstd::experimental::coroutine_traitsstd::coroutine_traits
handlestd::experimental::coroutine_handlestd::coroutine_handle
迁移建议
  • 全局搜索 experimental/coroutine
  • 替换为 <coroutine> 和 std::coroutine_traits
  • -fcoroutines-ts 选项也在此版本移除

CWG2518: static_assert(false) 在模板中合法

C++ 缺陷修复

变更说明

LLVM 17 实现 CWG2518 修复：未实例化的模板中的 static_assert(false) 不再立即报错，而是等到模板被实例化时才求值。此前模板库作者需使用 sizeof(T)==0 等 workaround 来延迟断言。

正面影响对于模板库编写者（尤其是 C++ 模板元编程），消除了一个常见的痛点。
经典模板约束场景
Before: LLVM 16 立即报错
// 即时错误！即使模板未实例化
template<class T>
void process(const T& val) {
    static_assert(false, "不可用");
}
// Workaround: 依赖 T 延迟求值
template<class T>
void process(const T& val) {
    static_assert(sizeof(T) == 0, "不可用");
}
After: LLVM 17 延迟求值
// CWG2518: 合法！延迟到实例化时
template<class T>
void process(const T& val) {
    static_assert(false, "不可用");
}
// 特化正常
template<>
void process<int>(const int& val) {
    printf("processing int\n");
}
// process("hello"); // 实例化时才触发
使用注意事项
  • 仅模板声明内部延迟求值；非模板上下文中仍立即报错
  • 需 C++20 或更高标准编译

enum 常量超出范围诊断增强

诊断改进

变更说明

LLVM 17 改进了当非固定底层类型的枚举在常量表达式中被设置为超出范围的值时的诊断信息：现在会输出枚举类型的名称，大幅提升错误定位效率。

该诊断由 -Wenum-constexpr-conversion 控制（该标志在 LLVM 16 中首次引入，LLVM 17 中增强了诊断内容）。在 LLVM 16 中此诊断可降级为 warning；LLVM 17 保留相同行为。后续 LLVM 18 中将在系统头文件中也启用此诊断，再后续版本将转为硬错误。

enum 常量超出范围诊断对比
Before: LLVM 16 — 无类型名
enum Color { Red = 0, Green = 1, Blue = 2 };
static constexpr Color c =
    static_cast<Color>(7);
// LLVM 16 诊断:
// error: integer value 7 is outside
// the valid range of values [0, 3]
// for this enumeration type
//          ^ 没有显示类型名
After: LLVM 17 — 显示类型名
enum Color { Red = 0, Green = 1, Blue = 2 };
static constexpr Color c =
    static_cast<Color>(7);
// LLVM 17 诊断:
// error: integer value 7 is outside
// the valid range of values [0, 3]
// for this enumeration type 'Color'
//                           ^^^^^^
// 现在显示了枚举类型名!
实用场景：大项目中定位问题
// v8/src/base/bit-field.h 中常见模式
enum MyBitField { kValue0, kValue1, kValue2 };
static constexpr int kMax =
    static_cast<int>(kValue2 - 1);
// LLVM 17 诊断明确指出 'MyBitField'
// 在大型项目中快速定位到具体枚举定义
升级影响
  • 此变更不改变编译成功/失败的判断，仅改善诊断质量
  • 如果代码中已有此类超出范围的枚举转换，LLVM 17 的诊断更易定位修复
  • -Wno-enum-constexpr-conversion 可抑制此诊断（但不推荐）

__builtin_object_size 与柔性数组成员指定初始化器

行为变更 · 与 GCC 对齐

变更说明

__builtin_object_size 和 __builtin_dynamic_object_size 现在在计算包含柔性数组成员（flexible array member, FAM）的结构体大小时，会计入指定初始化器中指定元素的 sizeof。这是为了与 GCC 的行为保持一致。

潜在影响此变更可能影响依赖 __builtin_object_size 进行缓冲区溢出检测的代码（如 _FORTIFY_SOURCE）。如果代码期望旧的（较小的）对象大小，可能在 LLVM 17 下出现误报或行为变化。
FAM 指定初始化器大小计算
Before: LLVM 16
struct S {
  int a;
  int fam[];  // 柔性数组成员
};
// 指定初始化器给 FAM 分配空间
struct S s = { .a = 1, .fam = {2, 3, 4} };
// LLVM 16: sizeof(S) = 4 (不含 FAM)
// __builtin_object_size(&s, 0) 可能返回 4
After: LLVM 17
struct S {
  int a;
  int fam[];  // 柔性数组成员
};
// 指定初始化器给 FAM 分配空间
struct S s = { .a = 1, .fam = {2, 3, 4} };
// LLVM 17: 计入 FAM 元素的 sizeof
// __builtin_object_size(&s, 0) = 4 + 3*4 = 16
// 与 GCC 行为一致
_FORTIFY_SOURCE 场景可能受影响
// 如果代码依赖 __builtin_object_size 检测溢出
struct header { int len; char data[]; };
struct header h = { .len = 3, .data = {1, 2, 3} };

void copy_data(char *buf, size_t sz) {
  // LLVM 17: __builtin_object_size(&h, 0) 返回 sizeof(header)+3
  // 而非 sizeof(header)。_FORTIFY_SOURCE 的 __memcpy_chk
  // 将基于新的大小做检查，可能改变运行时行为。
  memcpy(buf, &h, sz);
}
检查建议
  • 如果代码中使用 __builtin_object_size 或启用了 _FORTIFY_SOURCE，需验证 FAM 指定初始化器场景
  • 此变更是向 GCC 行为的靠拢，长期看是正确方向
  • 如果期望旧行为，可考虑显式使用 sizeof 而非 __builtin_object_size

namespace std 禁止声明为 inline namespace

C++ · Breaking Change

变更说明

C++ 标准 [namespace.std]p7 明确禁止将 std 声明为 inline namespace。LLVM 17 实现了此规则：将 namespace std 声明为 inline 现在会产生编译错误。

破坏性少数代码在自定义实现标准库组件时会使用 inline namespace std 模式，这些代码在 LLVM 17 下将编译失败。
inline namespace std 禁止
Before: LLVM 16 — 允许
// LLVM 16 允许: 自定义 std 组件
inline namespace std {
  template<class T>
  struct hash;
  // 可以为自定义类型特化 std::hash
}
// 无编译错误
After: LLVM 17 — 禁止
// LLVM 17: 编译错误!
inline namespace std {   // ERROR
  template<class T>
  struct hash;
}
// error: cannot declare namespace 'std'
//        to be inline
// 正确做法: 移除 inline 关键字
namespace std {  // OK
  template<class T>
  struct hash;
}
修复方案
  • 将 inline namespace std { ... } 改为 namespace std { ... }
  • 标准库 component 的特化仍可在非 inline 的 namespace std 中进行
  • 此规则适用于所有版本 C++ 标准

final 类型 dynamic_cast 优化：直接 vtable 比较

C++ · 性能优化

变更说明

LLVM 17 优化了到 final 类型的 dynamic_cast。在 ABI 要求 vtable 地址唯一的平台上（如 Itanium ABI），Clang 现在直接比较 vtable 指针，而不是调用 RTTI 运行时函数。这避免了 __dynamic_cast 的运行时开销。

此优化可通过 -fno-assume-unique-vtables 禁用，目前尚未在 MS C++ ABI 上实现。

性能意义对大量使用 dynamic_cast 的代码（如序列化框架、消息分发系统），此优化可减少虚函数调用开销。
final 类型 dynamic_cast 优化
Before: LLVM 16 — 运行时函数调用
struct Base { virtual ~Base(); };
struct Derived final : Base { };

void check(Base* b) {
  auto* d = dynamic_cast<Derived*>(b);
  // LLVM 16 生成: 调用 __dynamic_cast
  // 运行时通过 RTTI 字符串比较类型
}

; LLVM 16 生成的 IR 伪代码:
;   call @__dynamic_cast(Base* b, ...)
After: LLVM 17 — vtable 指针比较
struct Base { virtual ~Base(); };
struct Derived final : Base { };

void check(Base* b) {
  auto* d = dynamic_cast<Derived*>(b);
  // LLVM 17 生成: 直接比较 vtable 指针
  // 因为 Derived 是 final, vtable 唯一
}

; LLVM 17 生成的 IR 伪代码:
;   %vtable = load ptr, ptr %b
;   %cmp = icmp eq ptr %vtable, @vtable.Derived
;   %result = select i1 %cmp, ptr %b, ptr null
禁用此优化
# 如果 vtable 合并场景导致问题，可禁用:
clang -fno-assume-unique-vtables file.cpp
# 默认行为 (-f[no-]assume-unique-vtables 是新增选项)
影响
  • 仅当目标类型标记为 final 且使用 Itanium ABI 时触发
  • 可能改变 dynamic_cast 失败时的行为路径（但结果一致）
  • 新增 -f[no-]assume-unique-vtables 控制选项

AArch64 综合变更

后端 · 安全 · 调用约定 · 汇编

LLVM 17 为 AArch64 带来了多项重要增强：硬件安全扩展汇编支持、preserve_all 调用约定修复、.arch 指令修正、short range thunk、MEMTAG 动态标签、BTI+range extension 等。

10.1 FEAT_GCS / FEAT_CHK / FEAT_ATS1A 汇编支持

LLVM 17 新增了对 AArch64 2022 A-profile 扩展的汇编器/反汇编器支持：FEAT_GCS（Guarded Control Stack）、FEAT_CHK（Check Feature Status）、FEAT_ATS1A。GCS 是 ARMv9.4-A 通过硬件影子栈防御 ROP 攻击的机制。

GCS 汇编指令示例
; GCS 压栈/弹栈指令
gcspushx              ; 将返回地址压入 GCS (硬件影子栈)
gcspopx               ; 弹栈并验证返回地址
gcspushm  x29, x30    ; 批量压入多个寄存器

; GCS 系统寄存器
mrs     x0, GCSCR_EL1      ; GCS Control Register
mrs     x0, GCSPR_EL1      ; GCS Pointer Register
msr     GCSCR_EL1, x0
msr     GCSPR_EL1, x0

; FEAT_CHK: 特性状态检查
; FEAT_ATS1A: 地址翻译阶段 1 增强
GCS 保护下的函数序言/结语示意
; GCS 保护下的完整函数模式
my_function:
    str     x30, [sp, #-16]!  ; 常规栈帧
    gcspushx                  ; GCS 记录返回地址
    stp     x29, x30, [sp, #-16]!
    mov     x29, sp
    ; ... 函数体 ...
    ldp     x29, x30, [sp], #16
    gcspopx                   ; 验证返回地址未被篡改
    ldr     x30, [sp], #16
    ret

汇编时需指定 -march=armv9.4-a+gcs，反汇编时使用 -mattr=+gcs。

10.2 preserve_all 调用约定

LLVM 17 修复了在 AArch64 上使用 preserve_all 调用约定时的崩溃问题（Issue #58145），并为该调用约定添加了完整的支持。

preserve_all 调用约定
// preserve_all: 被调用者保存所有寄存器
__attribute__((preserve_all))
void my_interrupt_handler(void) {
  // 此函数不会修改任何调用者寄存器
  // 适用于中断处理、信号处理等场景
  // LLVM 16: AArch64 上可能崩溃
  // LLVM 17: 正常工作
}

10.3 .arch 指令修复

LLVM 17 修复了汇编指令 .arch <level> 在没有 +<ext> 后缀时的行为。此前该指令完全没有效果；现在 .arch <level> 可以正确地启用更高级别中包含的所有扩展，或用作降低级别以禁用不需要的扩展。同时新增了 .arch_extension 指令支持缺失的 arch 扩展。

.arch 指令修复
// 修复前 (LLVM 16): .arch armv8.5-a 无任何效果
// 修复后 (LLVM 17): 正确启用/禁用对应的扩展
.arch armv8.5-a        ; 现在正确启用 armv8.5-a 的扩展
.arch_extension crypto  ; 新增: 启用缺失的扩展

10.4 AArch64 short range thunk

LLD 17 实现了 AArch64 short range thunk，用于缓解长跳转 thunk 的性能损失。当代码距离在短跳转范围内时，使用更高效的短 thunk 而非完整的 long range thunk，减少指令开销。

10.5 DT_AARCH64_MEMTAG_* 动态标签

LLD 17 新增对 DT_AARCH64_MEMTAG_* 系列动态标签的支持，这是 AArch64 内存标签扩展 (MTE) 的 ELF 动态链接基础设施。

10.6 BTI landing pad 与 range extension thunk

LLD 17 为通过 range extension thunk 或 relative vtable 访问的 PLT 条目添加了 BTI landing pad，确保间接分支目标符合 BTI 要求，增强 AArch64 控制流完整性。

额外 AArch64 亮点

  • __arithmetic_fence 内建函数和 -fprotect-parens 选项现在支持 AArch64
  • 内联汇编现在支持 NZCV 标志输出操作数（如 "=@cceq"(*b)），与 GCC 行为一致
  • 新增对非法目标三元组 --target=aarch64-*-eabi 的警告诊断
AArch64 NZCV 标志输出操作数（新增）
// AArch64 内联汇编的条件标志输出
int a = foo();
int* b = bar();
asm("ands %w[a], %w[a], #3"
    : [a] "+r"(a), "=@cceq"(*b));
// 如果 a & 3 == 0, 则 *b 被设置
// LLVM 17 新增: =@cceq, =@ccne, =@cccs 等

LLVM IR 变更

核心基础设施

11.1 nofpclass 属性

LLVM 17 引入了 nofpclass 属性，用于指示浮点值不属于哪些特殊类别（如 NaN、无穷大、负零、正零、非正规数等）。这使编译器可以在浮点比较优化中做更激进的常数折叠。

nofpclass 属性用法
; nofpclass 属性: 告诉优化器该值不属于指定类别
; nofpclass(nan inf) = 该值不是 NaN, 也不是无穷大
define float @example(float nofpclass(nan inf) %x) {
  ; 优化器知道 %x 不是 NaN, 可以简化 fcmp
  %cmp = fcmp oeq float %x, %x
  ; 这将折叠为 true（不是 NaN 则总是与自己相等）
  ret float %x
}

; 可用的类别: nan, inf, norm, sub, zero, all, 以及
; 正负变体: ninf, pinf, nnorm, pnorm, nsub, psub, nzero, pzero
; nofpclass(nan pinf ninf nzero) 排除 NaN, +/-inf, -0

11.2 ldexp / frexp 内建函数

LLVM 17 引入了 llvm.ldexp（加载指数）和 llvm.frexp（分解浮点数）内建函数，以及其约束浮点变体 llvm.experimental.constrained.ldexp。

ldexp / frexp intrinsics
; ldexp: x * 2^exp
; 计算 x 乘以 2 的 exp 次方
%result = call float @llvm.ldexp.f32(float %x, i32 %exp)

; frexp: 分解 x 为 significand 和 exponent
; x = significand * 2^exponent, 0.5 <= |significand| < 1.0
%struct = call { float, i32 } @llvm.frexp.f32(float %x)
%sig = extractvalue { float, i32 } %struct, 0
%exp = extractvalue { float, i32 } %struct, 1

; 约束浮点变体 (保留舍入模式和异常行为)
%result = call float @llvm.experimental.constrained.ldexp.f32(
    float %x, i32 %exp, metadata !"round.tonearest",
    metadata !"fpexcept.strict")

11.3 select 常量表达式变体移除

LLVM 17 移除了 select 指令的常量表达式变体。此前可以在常量表达式中使用 select（如全局变量初始化器中），现在这些需要改用其他方式表达。

select 常量表达式移除
Before: LLVM 16
; 常量表达式中的 select (已移除)
@global = global i32 select (
    i1 icmp eq (i32 ptrtoint (...), i32 0),
    i32 42, i32 0)
; LLVM 16: 常量 select 仍然可用
After: LLVM 17
; select 常量表达式已移除
; 如果源码生成此类 IR, 需要改用
; 其他方式（如全局构造函数）
; 或确保前端不再生成此类模式

11.4 传统优化管线移除

LLVM 17 移除了传统优化管线（PassManagerBuilder.h）。所有 Pass 必须迁移到新 Pass Manager API。详见 NewPassManager 文档。

11.5 收敛控制内建函数（实验性）

引入一组实验性收敛控制内建函数，用于显式定义收敛操作的语义。

后端与汇编层改进

多架构

12.1 LoongArch 提升为官方目标

LLD 17 中 LoongArch 已作为正式支持的目标，不再是实验性质。LLVM 17 中 LoongArch 后端持续完善：

  • 汇编器/反汇编器：新增 LSX、LASX、LVZ 和 LBT ISA 扩展支持
  • ABI：lp64s ABI 现已支持（已通过 Rust bare-metal 目标测试）
  • 代码模型：新增 large 代码模型支持，等同于 GCC 的 extreme
  • unaligned access：引入 ual 目标特性，允许非对齐内存访问（generic 64-bit 处理器默认启用）
  • 函数入口补丁：-fpatchable-function-entry 在 LoongArch 上已支持
  • Sanitizer：MSan、DFsan、Profile、XRay、libFuzzer 已移植到 LoongArch
  • llvm-objcopy：现已支持处理 LoongArch 目标文件

12.2 Arm Cortex-M Security Extensions (CMSE)

LLD 17 实现了 Arm Cortex-M Security Extensions，支持 Armv8-M 架构的 TrustZone 安全扩展所需的链接器功能，包括 secure gateway (SG) 指令和 secure/non-secure 函数调用的特殊处理。

CMSE 安全/非安全调用
// Armv8-M CMSE: secure gateway
__attribute__((cmse_nonsecure_entry))
void secure_function(void) {
  // 从 non-secure 世界调用的安全函数
  // LLVM 17 的 LLD 正确生成 SG 桩代码
}
// LLD 17 正确处理 secure/non-secure 重定位
// 并生成正确的导入/导出表

12.3 x86-64 大数据段布局优化

LLD 17 将 x86-64 large data sections 放置到远离代码段的位置，缓解重定位溢出压力。在处理大型二进制文件时，32 位相对重定位可能溢出；将大数据段移到远离代码段的位置可以减少此类问题。

12.4 AArch32 BE-8 / BE-32 大端模式

LLD 17 的 AArch32 端口现在支持 BE-8（字节不变大端）和 BE-32（字不变大端）两种大端模式，支持 R_ARM_THM_ALU_ABS_G* 重定位。

12.5 RISC-V 全局指针（GP）松弛

LLD 17 实现了 RISC-V 全局指针松弛优化。通过 --relax-gp 选项启用链接器松弛，利用 gp 寄存器缩短全局数据的访问指令序列，减少代码大小和提升性能。同时新增 R_RISCV_PLT32 重定位支持 C++ relative vtables，以及 PT_RISCV_ATTRIBUTES 程序头部。

RISC-V GP 松弛
# 启用 RISC-V 全局指针松弛
ld.lld --relax-gp -o output input.o

# RISC-V GP 松弛说明:
# 正常: lui + lw (两条指令, 8 bytes)
# GP松弛后: lw gp, offset (一条指令, 4 bytes)
# 前提: 数据在 gp +/- 2KB 范围内

LLD 链接器新选项与功能

ELF · COFF · MinGW

LLD 17 带来了大量新选项和功能增强。

13.1 --remap-inputs 和 --remap-inputs-file

新增输入文件重映射功能。可以动态替换输入文件的路径，适合在构建系统需要根据平台/配置切换输入文件时使用，无需修改链接命令本身。

--remap-inputs 用法
# 将 old.o 替换为 new.o
ld.lld --remap-inputs=old.o=new.o ...
# 等效的批量文件模式:
ld.lld --remap-inputs-file=remap.txt ...
# remap.txt 内容格式:
#   old1.o new1.o
#   old2.o new2.o

13.2 --lto-CGO[0-3]

新增 --lto-CGO[0-3] 选项，允许独立于 LTO 优化级别来控制 CodeGenOpt::Level。此前 LTO 优化级别和代码生成优化级别绑定在一起；现在可以分别控制（如 LTO 用 O2 优化，但 CodeGen 用 O3）。

--lto-CGO 用法
# LTO 优化级别 O2, CodeGen 优化级别 O3
ld.lld --lto=thin --lto-O2 --lto-CGO3 ...
# LTO 优化级别 O1, CodeGen 优化级别 O0 (快速调试)
ld.lld --lto=thin --lto-O1 --lto-CGO0 ...

13.3 --check-dynamic-relocations

修复了 32 位目标上 --check-dynamic-relocations 选项在 addend 大于 0x80000000 时的正确性。此选项用于验证动态重定位中的 addend 值是否在合法范围内。

13.4 --print-memory-usage

实现了内存区域（memory regions）的 --print-memory-usage，可以按内存区域打印链接后的内存使用统计。

--print-memory-usage 输出示例
# LD 链接时启用内存使用报告
ld.lld --print-memory-usage -o output ...
# 输出示例:
# Memory region         Used Size  Region Size  %age Used
#             RAM:        12 KB       256 KB      4.69%
#           FLASH:        48 KB       512 KB      9.38%

13.5 REVERSE 与链接脚本增强

LLD 17 新增多项链接脚本功能：

REVERSE 与链接脚本增强
/* REVERSE: 反转输入段的顺序 */
SECTIONS {
  .text : { *(.text) }
  .rodata : { REVERSE(*(.rodata)) }
  /* .rodata 中的输入段按反转顺序排列 */
}

/* MEMORY 可不带 SECTIONS 使用 */
MEMORY { ROM (rx) : ORIGIN = 0, LENGTH = 256K }
/* LLVM 17: 无需 SECTIONS 命令即可定义内存区域 */

/* 输出段名现在支持引号 */
SECTIONS {
  "my section" : { *(.data) }
}

/* OVERLAY 中可使用程序头分配 (之前丢失的功能) */

13.6 LLD 线程数上限 16（默认行为变更）

当未指定 --threads= 时，并行线程数上限被 cap 到 16。超过 16 线程在使用 glibc malloc 时会产生严重的锁竞争导致性能反而下降。显式指定超过 16 的值也会被 cap 并输出 warning。

线程数 cap 行为
场景LLVM 16LLVM 17
不指定 --threads全部 CPU 核心min(CPU, 16)
--threads=88 线程8 线程
--threads=3232 线程16 线程 + warning
--threads=1单线程单线程（确定性构建）

13.7 其他 LLD 亮点

  • SHF_MERGE / ICF / build-id=fast 切换到 64-bit xxh3 哈希，性能提升
  • LoongArch：LLD 现已支持 LoongArch 作为正式目标
  • PowerPC64：--no-power10-stubs 现在生效；DT_PPC64_OPT 动态标签支持
  • AVR：新增多个重定位类型支持
  • COFF (lld-link)：支持相对路径库查找；新增 -print-search-paths；默认搜索 toolchain 目录
  • MinGW：对过窄的运行时伪重定位发出警告，避免加载位置过远导致运行时错误
