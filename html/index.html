核心结论

本报告针对数通产品线关注维度，系统梳理 LLVM 15.0.4 → 21.1.8 六大版本的所有关键差异，并提供分阶段迁移建议。

🔴 最高优先级 · 行为变化
TBAA 默认启用 + 指针溢出 UB
strict-aliasing 违例代码被静默错误优化；依赖指针包装语义的边界检查失效。两项皆为 LLVM 20 引入，升级后必须第一时间验证。 详情→
LLVM 20.1 · -fno-pointer-tbaa / -fwrapv-pointer
🔴 最高优先级 · ABI Break
C++ 函数模板名称重整
受约束模板、auto 返回类型、依赖参数的模板的 mangled name 改变，造成二进制不兼容。是 LLVM 18 最关键的 ABI 变更。 详情→
LLVM 18.1 · -fclang-abi-compat=17
🔴 最高优先级 · 优化语义
Lifetime DSE 死对象存储消除
对象死亡后的存储操作被更积极消除，依赖此行为的代码（如 RAII 资源释放标记）可能失效。 详情→
LLVM 21.1 · -fno-lifetime-dse
🔴 最高优先级 · 小型化
SVE/SVE2 ARMv9.0 变为可选
-march=armv9-a 不再隐含 +sve/+sve2。依赖 SVE 自动向量化的场景需显式指定，否则可能降级为 NEON。 详情→
LLVM 19.1
🟡 重要 · 编译配置
C++17 默认标准（原 C++14）
LLVM 16 起默认 gnu++17。C++17 的 if constexpr、折叠表达式、结构化绑定等新规则可能导致旧的 C++14 代码编译失败或语义变化。
LLVM 16.0 · -std=gnu++14 恢复
🟢 推荐 · 安全与质量
libc++ Hardening + 新 Sanitizers
LLVM 18+ 引入 _LIBCPP_HARDENING_MODE 生产级加固；LLVM 18+ 新增 Numerical Sanitizer；LLVM 19+ 新增 Realtime Sanitizer。 详情→
-D_LIBCPP_HARDENING_MODE=FAST
🟢 推荐 · AArch64 防护
Pointer Authentication (PAuth)
BTI + PAC-RET + PAuth-LR 组合保护，LLVM 19 起完全支持。对嵌入式网络设备的控制流完整性有重要价值。 详情→
-mbranch-protection=standard
🟡 重要 · 链接阶段
LLD 性能大幅提升 + 默认行为变更
LLVM 16 起重定位扫描并行化；LLVM 18 起 cdsort 算法排序。同时 --no-undefined-version 默认启用，--build-id 默认改为 SHA1。
需确认链接脚本与 version script

📈 代码体积优化进展

版本变更对代码体积的影响

⚡ 关键性能优化改进
  • LLVM 16–17：ML-inliner 稳定化 + 内联决策中冷热分离更精确
  • LLVM 17：nofpclass 浮点属性 → 更激进的浮点比较优化（可提升数值密集代码性能）
  • LLVM 18：cdsort 排序算法替代 hfsort（调用面剖面条目排序更优）；FatLTO 支持
  • LLVM 19：nusw/nuw GEP flags → 更精确的越界分析；MMRAs 内存模型松弛标注
  • LLVM 20：TBAA 默认启用 → 更激进的别名分析（性能收益 vs. 安全风险的权衡）
  • LLVM 20：Size-aware Machine Block Placement → 对 -Oz 场景代码体积优化
  • LLVM 21：Lifetime DSE → 更积极消除死存储（可能提升性能，但需验证语义）

未定义行为

UB & Sanitizers
🔴 核心变更：LLVM 20 起编译器更积极利用 UB 进行优化 这是 LLVM 15→21 最重大的语义变化。之前"恰好工作"但实际属于 UB 的代码，在新版本中可能被优化掉或行为改变。

UB 相关关键变更

版本变更UB 表现修复/兼容方案
20指针加法溢出 UB 更积极优化ptr + offset < ptr → 优化为 false-fwrapv-pointer / 改用整数运算
20TBAA 标签默认启用违反 strict-aliasing 的指针访问被错误优化-fno-pointer-tbaa / 修复 aliasing 违规
20-fwrapv 不再影响指针溢出需用 -fwrapv-pointer 单独控制同时设置 -fwrapv -fwrapv-pointer
21Lifetime DSE 更积极对象死亡后的存储被消除（memset/memcpy 等）-fno-lifetime-dse
16-fsanitize-memory-param-retval 默认启用MSan 下未初始化参数传递被检测-fno-sanitize-memory-param-retval
18enum constexpr 范围检查超出范围的 enum 值作为常量表达式被拒绝修复 enum 值（LLVM 20 起不可压制）
20libc++ 内部 UB 修复无条件启用list/tree/hash_table/forward_list 节点指针 UB 固定不可禁用（旧 flag 已无条件启用）
21null 指针算术优化旧式 offsetof 惯用法可能被优化破坏-fwrapv-pointer / -fno-delete-null-pointer-checks

Sanitizers 增强（UB 检测利器）

版本Sanitizer 变化对数通设备的推荐
16MSan param-retval 默认启用CI 中启用 -fsanitize=memory
17+ASan stack-use-after-return 改进CI 测试用 -fsanitize=address
18+Numerical Sanitizer 新增 (#94322)检测数值计算异常（除零/溢出）
19+Realtime Sanitizer 新增 (#92460)实时系统（RTOS/嵌入式）内存安全检查

🟡 数通产品线 UB 治理建议
  1. 立即行动：用新编译器（20/21）+ -fwrapv-pointer 构建，先用 -fsanitize=undefined,pointer-overflow 做一轮全量测试，发现潜在 UB
  2. 修复优先级：先修复 pointer-overflow 和 strict-aliasing 违规（这两项在 LLVM 20 会静默改变行为）
  3. 长期：在 CI 中持续启用 UBSan + ASan，防止新的 UB 引入
  4. 生产构建：评估是否启用 -fwrapv-pointer 使指针溢出有明确定义

内联差异

Inliner · Inline Cost
📌 数通产品线关注点 内联决策直接影响代码体积和执行速度。数通设备通常使用 -Oz 或 -Os 控制体积， 内联成本模型的变化可能导致关键函数被不同地内联。

Inliner 关键变更（15→21 共 20+ 次 Inliner.cpp 修改、66+ 次 InlineCost.cpp 修改）

版本变更对数通设备的影响
16ML-inliner 稳定（release 模式可用）默认使用 ML 模型做内联决策，对吞吐敏感的转发面代码可能更积极内联
17Always inliner 路径清理__attribute__((always_inline)) 路径更可靠
18InlineCost：Switch 语句默认分支成本修正（#85160）含大 switch 的协议分发函数内联决策更准确
19冷热 callsite 处理改进；BFI（块频率信息）更广泛应用冷路径（错误处理/初始化）更少被内联 → 代码体积改善
19getelementptr 添加 nusw/nuw flags指针分析更精确 → 内联后的优化更高效
20TBAA 默认启用内联后的别名分析更激进的，可能推动更多后续优化
20Size-aware Machine Block Placement对 -Oz 构建的内联后代码布局优化
20__memcpy_chk 等折叠内联不再增加罚分（#117876）涉及内存拷贝的安全函数不再被错误地惩罚 → 更合理的内联决策
20递归函数内联优化（#139982）特定模式的递归可被优化为迭代，减少栈压力
21__builtin_structured_binding_size 新内建函数结构化绑定场景的编译期计算
21内联汇编指令在内联成本中的计算（#146628）含有内联汇编的函数内联决策更合理（数通设备驱动/PLD 代码常见）
21store-to-load forwarding 解析调用参数（#190607）内联后存储转发分析 → 减少不必要的内存访问
🟡 内联差异验证建议
  • 对关键模块进行 -Oz / -Os 两种构建的 .text 段对比
  • 使用 -Rpass=inline / -Rpass-missed=inline 输出内联决策日志，与旧编译器对比
  • 关注内联汇编密集的驱动代码的内联决策变化（LLVM 21 起影响）
  • LTO 场景下内联策略变化更大，需单独验证
