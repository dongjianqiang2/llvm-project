LLVM 16 差异详解

毕昇编译器升级 — LLVM 15 → 16 变更全景

LLVM 16.0.0 (2023 年 3 月) 相比 LLVM 15，引入了多项影响广泛的变更： 4 项 Warning 升级为 Error（隐式函数声明、隐式 int、不兼容函数指针、void* 解引用）、 默认 C++ 标准切换为 gnu++17、 2 项 ABI 调整（packed struct 非 POD 成员对齐、POD 判定规则）、 资源目录路径变更（仅含主版本号）、 MSan 参数/返回值检测默认启用、 LLD 并行化与多项新功能、 AArch64/x86 新 CPU 及 ISA 支持、 libc++ 多项废弃与移除。 本页面逐项梳理关键差异，附代码示例与应对方案，辅助毕昇编译器用户平滑迁移。

📜 默认 C++ 标准升级为 gnu++17 中影响
变更 #1 · 编译器前端 · Clang (C++/ObjC++)

自 LLVM 16 起，Clang 的默认 C++/ObjC++ 标准从 gnu++14 (C++14 + GNU 扩展) 升级为 gnu++17 (C++17 + GNU 扩展)。未显式指定 -std= 标志的 C++ 代码将默认以 C++17 模式编译，可能暴露旧代码中与 C++17 新特性冲突的写法。

潜在影响场景

  • if constexpr — 旧代码可能用 if constexpr 作为变量名，升级后被解析为关键字。
  • register 关键字 — C++17 中 register 存储类说明符被移除，使用即报错。
  • noexcept — 成为类型系统的一部分，函数指针与虚函数签名匹配更严格。
  • 折叠表达式 — 与宏展开可能产生冲突。
  • 结构化绑定 — auto [a, b] = ... 语义在 C++14/C++17 下不同。
问题代码 (C++17 下编译失败)
// 旧代码中 if constexpr 作为变量名 void foo() { int if constexpr = 42; // C++17: "if"是关键字, "constexpr"紧随其后, 非法 return; }
修复后
void foo() { int if_constexpr = 42; // 重命名变量 return; }
register 关键字 (C++17 中非法)
void bar() { register int x = 1; // C++17: error: ISO C++17 does not allow 'register' }
修复后
void bar() { int x = 1; // 直接删除 register }
⚠ 应对措施 若项目尚未准备好迁移到 C++17，请显式添加编译选项： -std=gnu++14 或 -std=c++14。 建议尽早完成 C++17 适配以获得更好的语言特性与性能。
⛔ -Wimplicit-function-declaration 升级为 Error 高影响
变更 #2 · C 语言前端 · Clang

在 C99 及之后的标准中，隐式函数声明 (implicit function declaration) 早已被移除。LLVM 15 及以前调用 未声明函数仅为 Warning；从 LLVM 16 起，该诊断升级为 Error，直接导致编译失败。 对历史悠久的 C 代码库影响最大。在 C2x 模式下，隐式函数声明被彻底删除，该警告选项不再生效。

LLVM 15: 仅 Warning (编译通过)
/* legacy.c -- LLVM 15 仅警告, LLVM 16 报错 */ void foo() { bar(42); // bar() 未声明, 隐式假定返回 int } int main() { foo(); return 0; }
LLVM 16: Error -- 编译失败
$ clang -c legacy.c legacy.c:2:5: error: call to undeclared function 'bar'; ISO C99 and later do not support implicit function declarations [-Wimplicit-function-declaration] bar(42); ^
修复方式 A: 添加函数声明
/* legacy.c -- 修复后 */ void bar(int x); // 显式声明 void foo() { bar(42); }
修复方式 B: 引入正确的头文件
/* legacy.c -- 修复后 */ #include <other.h> // bar() 在此头文件中声明 void foo() { bar(42); }
🚨 应对措施 短期 (紧急绕过):
添加编译选项 -Wno-error=implicit-function-declaration 将 Error 降级回 Warning。

长期 (推荐):
逐步为所有隐式调用添加函数声明或包含正确的头文件。建议 configure 脚本在设置此选项前后验证结果一致性。
⛔ -Wimplicit-int 升级为 Error 高影响
变更 #3 · C 语言前端 · Clang

在 K&R C 及 C89 时代，允许省略类型说明符而默认为 int (如 static flag = 1; 等价于 static int flag = 1;)。C99 标准已移除此特性。LLVM 16 将 -Wimplicit-int 从 Warning 升级为 Error。在 C89 模式下指定 -Wimplicit-int 现在也会产生警告 (此前为 noop)。

LLVM 15: Warning (编译通过)
/* legacy.c */ static flag = 1; // 省略 int, C89 风格 const MAX_SIZE = 1024; // 省略 int int main() { return flag; }
LLVM 16: Error -- 编译失败
$ clang -c legacy.c legacy.c:1:8: error: type specifier missing, defaults to 'int'; ISO C99 and later do not support implicit int [-Wimplicit-int] static flag = 1; ^ legacy.c:2:7: error: type specifier missing, defaults to 'int' ... const MAX_SIZE = 1024; ^
修复后
static int flag = 1; // 显式补充 int 类型 const int MAX_SIZE = 1024; // 显式补充 int 类型 int main() { return flag; }
🚨 应对措施 短期绕过: -Wno-error=implicit-int

长期修复: 为所有省略类型的声明补充 int 类型说明符，大多数情况下是机械性修复。 建议 configure 脚本验证设置此选项前后的结果一致性。
⛔ -Wincompatible-function-pointer-types 升级为 Error 高影响
变更 #4 · C 语言前端 · Clang

当函数指针赋值或传递时，如果目标类型与源类型不兼容 (如参数类型不匹配、返回类型不一致)， LLVM 16 在所有 C 语言模式中从 Warning 升级为 Error。 在回调函数、插件系统、dlsym 动态加载等场景中尤为常见。

LLVM 15: Warning (编译通过)
/* 函数指针类型不兼容 -- LLVM 15 仅警告 */ typedef void (*callback_t)(int); void my_handler(long x) { /* ... */ } void register_cb() { callback_t cb = my_handler; // 参数类型不兼容: int vs long }
LLVM 16: Error -- 编译失败
$ clang -c callback.c callback.c:6:20: error: incompatible function pointer types assigning to 'callback_t' (aka 'void (*)(int)') from 'void (long)' [-Wincompatible-function-pointer-types] callback_t cb = my_handler; ^ ~~~~~~~~~
void* 与函数指针混用 (常见于 dlsym 场景)
typedef int (*fn_t)(int); void* ptr = dlsym(handle, "my_func"); fn_t fn = ptr; // LLVM 16: error: void* 赋值给函数指针
修复方式 A: 显式类型转换
typedef int (*fn_t)(int); void* ptr = dlsym(handle, "my_func"); fn_t fn = (fn_t)ptr; // 显式转换, 明确意图
修复方式 B: 修正函数签名
typedef void (*callback_t)(int); void my_handler(int x) { /* ... */ } // 修正为 int, 匹配回调签名 void register_cb() { callback_t cb = my_handler; // 类型完全匹配 }
🚨 应对措施 短期绕过: -Wno-error=incompatible-function-pointer-types

长期修复: 逐个审查不兼容的函数指针赋值：1) 修正函数签名以匹配目标指针类型； 2) 使用显式类型转换 (cast) 表明有意为之； 3) 重构 API 使用通用回调签名 (如 void (*)(void*))。
⛔ void* 间接访问 (C++) 升级为 Error 中影响
变更 #5 · C++ 前端 · Clang

在 C++ 中，对 void* 指针进行解引用 (dereference) 在语义上是非法的 -- 因为 void 类型没有大小。LLVM 16 将此诊断从 Warning/ExtWarn 升级为 硬 Error, 且是 SFINAE 错误 (与其他编译器行为一致)。

C++ 区域中 void* 解引用
// C++ 代码: 对 void* 解引用 void* ptr = get_buffer(); int value = *(ptr); // LLVM 16: error: 'void *' is not a pointer-to-object type int value2 = ptr[0]; // 同样错误: 下标操作等价于 *(ptr+0)
修复方式 A: 先转型再解引用
void* ptr = get_buffer(); int value = *static_cast<int*>(ptr); // 先转为 int* 再解引用 int value2 = static_cast<int*>(ptr)[0]; // 转为 int* 再下标
修复方式 B: 使用 memcpy 读取 (类型无关)
void* ptr = get_buffer(); int value; memcpy(&value, ptr, sizeof(value)); // 安全地从 void* 复制数据
⚠ 应对措施 此变更为硬 Error, 无法通过 -Wno-error= 降级。
推荐使用 static_cast 将 void* 转换为具体对象指针类型后再解引用。 如不确定目标类型, 使用 memcpy 按字节数安全读取。
📁 资源目录路径变更 (仅含主版本号) 低影响
变更 #6 · 构建/部署 · Clang

Clang 的资源目录 (resource directory) 路径此前包含完整的版本号 (如 16.0.0)。 从 LLVM 16 起，路径中仅包含主版本号 (major version)。 新路径格式为 $prefix/lib/clang/$CLANG_MAJOR_VERSION。

旧路径 vs 新路径对比
# LLVM 15 及之前: 完整版本号 /usr/lib/clang/15.0.7/include/stddef.h /usr/lib/clang/15.0.7/lib/linux/libclang_rt.builtins-x86_64.a # LLVM 16 起: 仅主版本号 /usr/lib/clang/16/include/stddef.h /usr/lib/clang/16/lib/linux/libclang_rt.builtins-x86_64.a
查询资源目录
$ clang -print-resource-dir /usr/lib/clang/16
ℹ 应对措施 如果你的构建脚本或工具链通过硬编码路径引用 Clang 资源目录 (如 lib/clang/15.0.7/), 需要更新为只含主版本号的路径 (如 lib/clang/16/)。 建议始终使用 clang -print-resource-dir 动态获取路径。
📜 __ppc64__ 移除 / -p 标志拒绝 低影响
变更 #7 · 平台兼容性 · Clang

LLVM 16 为了与 GCC 保持一致，进行了以下两项平台相关的调整：

__ppc64__ 宏不再定义

在 PowerPC64 目标上，__ppc64__ 不再被预定义。请改用 __powerpc64__。 这是为了与 GCC 行为对齐。

受影响的代码
/* 编译目标: powerpc64-linux */ #ifdef __ppc64__ #error "__ppc64__ is no longer defined in LLVM 16" // 不会触发! #endif #ifdef __powerpc64__ // LLVM 16 中仍然定义, 请使用此宏 #endif

-p 标志仅限 AIX/OpenBSD

-p 标志 (生成 prof 性能分析代码) 现在仅在 AIX 或 OpenBSD 目标上被接受。 在其他目标上使用将被拒绝 (此前仅产生 unused argument 警告)。

Linux 上使用 -p 标志
$ clang -p hello.c -o hello clang: error: unsupported option '-p' for target 'x86_64-linux-gnu'
修复方式
# Linux/x86_64 上使用 -pg 替代 -p $ clang -pg hello.c -o hello # 或在 AIX/OpenBSD 上 -p 仍然可用 $ clang -p hello.c -o hello
ℹ 应对措施 在非 AIX/OpenBSD 目标的构建系统中，将 -p 替换为 -pg。 将 PowerPC64 平台上的 __ppc64__ 宏检查替换为 __powerpc64__。
📦 Packed Struct ABI 变化 (非 POD 成员对齐) 中影响
变更 #8 · ABI · Clang

LLVM 16 修改了带 __attribute__((packed)) 属性的结构体中非 POD 成员 的对齐和布局行为。GCC 不会打包 packed struct 中的非 POD 成员 (除非成员本身也标记 packed)。 Clang 现在与 GCC 行为对齐 (Darwin、PS4、AIX 除外)。这可能导致 ABI 不兼容。

受影响的 packed struct 示例
// 非 POD 类型 (有用户定义构造函数) struct NonPOD { int x; NonPOD() : x(0) {} }; struct __attribute__((packed)) Packed { char c; short s; NonPOD np; // 非 POD 成员 -- LLVM 15/16 行为可能不同 int i; };
跨编译单元二进制兼容问题
// TU1 (libfoo.so): 用 LLVM 15 编译 struct __attribute__((packed)) Packed { char c; short s; NonPOD np; int i; }; void process(Packed* p) { /* 按 LLVM 15 布局访问 */ } // TU2 (main): 用 LLVM 16 编译 main() { Packed p; // 按 LLVM 16 布局创建 process(&p); // 传递给 LLVM 15 编译的代码 -> 布局不一致! }
⚠ 应对措施 兼容性开关: 添加 -fclang-abi-compat=15.0 以保持与 LLVM 15 一致的 ABI 行为。

最佳实践: 1) 避免在 packed struct 中放置非 POD 类型成员; 2) 如确实需要, 确保跨模块编译使用相同的 Clang 版本; 3) 在 ABI 边界优先使用 C 语言接口。
📦 POD 类型判定规则 ABI 变化 中影响
变更 #9 · ABI · Clang (Itanium ABI)

GCC 允许拥有 defaulted (显式默认) 特殊成员函数的类型被视为 POD (用于 Itanium ABI)。 Clang 此前将此类类型归类为非 POD。LLVM 16 与 GCC 行为对齐 (Darwin、PS4、AIX、z/OS 除外)。这会影响 Itanium ABI 下结构体的传参方式。

受 POD 判定影响的结构体
// LLVM 15: 视为 non-POD (使用栈传参) // LLVM 16: 视为 POD (可能通过寄存器传参) struct MyType { int a; double b; MyType() = default; // defaulted 构造函数 ~MyType() = default; // defaulted 析构函数 }; void func(MyType t); // LLVM 15 和 LLVM 16 可能使用不同传参方式
⚠ 应对措施 使用 -fclang-abi-compat=15.0 恢复 LLVM 15 的 POD 判定行为。若跨模块使用不同编译器版本，注意传参 ABI 差异。
⚠ enum constexpr 范围检查升级 中影响
变更 #10 · C++ 前端 · Clang

LLVM 16 现在会正确诊断常量表达式中将没有固定底层类型的 enum 设置为超出枚举值范围的情况。 此前这是一个长期存在的 bug (与主要 C++ 实现一致的错误行为)。 该错误可通过 -Wno-error=enum-constexpr-conversion 降级为警告。

LLVM 15: 编译通过 (行为不一致)
enum E { Zero, One, Two, Three, Four }; constexpr E Val1 = (E)3; // Ok constexpr E Val2 = (E)7; // Ok (最大值为 7, 即 4->8 范围的边界) constexpr E Val3 = (E)8; // LLVM 16: error: 超出范围 [0, 7] constexpr E Val4 = (E)-1; // LLVM 16: error: 超出范围 [0, 7]
修复: 使用具有固定底层类型的 enum
enum E : int { Zero, One, Two, Three, Four }; // 固定底层类型 constexpr E Val3 = (E)8; // OK: int 范围足够大 constexpr E Val4 = (E)-1; // OK
⚠ 应对措施 短期降级: -Wno-error=enum-constexpr-conversion。
长期修复: 为需要宽范围值的 enum 添加固定底层类型 (如 enum E : int)。
🧪 MSan 参数/返回值检测默认启用 中影响
变更 #11 · Sanitizer · Clang (MemorySanitizer)

-fsanitize-memory-param-retval 现在是默认开启的。 当使用 -fsanitize=memory (MemorySanitizer) 时, 传递未初始化变量给函数以及从函数返回未初始化变量将被更加积极地报告。 使用 -fno-sanitize-memory-param-retval 可恢复旧行为。

LLVM 15: 可能不报告
// 编译: clang -fsanitize=memory -g test.c #include <stdio.h> int helper(int x) { return x * 2; // LLVM 15: 可能不报告 x 未初始化 } int main() { int a; // 未初始化 return helper(a); // LLVM 16: 报 use-of-uninitialized-value }
MSan 编译器检查的新行为
# LLVM 16: -fsanitize-memory-param-retval 默认为 on $ clang -fsanitize=memory -g test.c -o test $ ./test == WARNING: MemorySanitizer: use-of-uninitialized-value #0 in helper test.c:4 #1 in main test.c:9 # 如需恢复 LLVM 15 行为: $ clang -fno-sanitize-memory-param-retval -fsanitize=memory -g test.c
⚠ 应对措施 这是一项安全加固，帮助发现更多未初始化内存使用。如果造成大量误报 (如旧库 ABI 边界处), 可使用 -fno-sanitize-memory-param-retval 暂时关闭。 建议修复代码中的未初始化变量问题。
📐 C2x 特性 / C 语言变更 / 已废弃标志 低影响
变更 #12 · C 语言前端 · Clang

C2x 新增特性

  • typeof / typeof_unqual 运算符 (N2927/N2930): C2x 模式下支持 typeof(expr) 获取表达式类型, typeof_unqual(expr) 移除所有限定符。
  • 标签任意位置 (N2508): 标签可放在复合语句中的任何位置。
  • [[maybe_unused]] 用于标签 (N2662): 可应用于标签以抑制 -Wunused-label 警告。
  • va_start 放宽要求 (N2975): C2x 模式下函数可声明为完全可变参数, va_start 不再需要第二参数。

C 语言格式化警告调整

-Wformat 警告根据 WG14 N2562 调整, 考虑默认参数提升。 int 参数使用 %hhd/%hd 不再产生不必要的警告。

已废弃的编译器标志

标志说明移除版本
-fcoroutines-ts 协程 TS 标志已废弃, 请使用 -std=c++20 或更高 Clang 17
-fmodules-ts 模块 TS 标志已废弃, 请使用 -std=c++20 或更高 Clang 17
-enable-trivial-auto-var-init-zero-knowing-it-will-be-removed-from-clang 请使用 -ftrivial-auto-var-init=zero (现已无条件可用) Clang 18
ℹ 应对措施 如果在构建脚本中使用上述已废弃标志, 请按表格中的替代方案更新。 C2x 特性仅在显式指定 -std=c2x 时启用, 不影响默认编译模式。
🗑 旧 Pass Manager 相关标志移除 低影响
变更 #13 · 优化框架 · Clang / LLVM

LLVM 的新 Pass Manager (New PM) 自 LLVM 12 起已是默认。LLVM 16 正式移除了已无效的标志: -fexperimental-new-pass-manager 和 -fno-legacy-pass-manager (自 Clang 15 起已被静默忽略)。

需要删除的标志 (LLVM 16 不再识别)
# Makefile / CMakeLists.txt 中移除以下标志 -fexperimental-new-pass-manager # 早已是默认选项 -fno-experimental-new-pass-manager # 不再支持退回旧 PM -fno-legacy-pass-manager # 不再需要 -mllvm -enable-new-pm=1 # LLVM 内部标志, 已移除
典型场景 -- CMakeLists.txt
# 旧 CMakeLists.txt (LLVM 15 可用) target_compile_options(myapp PRIVATE -fexperimental-new-pass-manager # <-- 删除此行 ) # LLVM 16 修复后 target_compile_options(myapp PRIVATE -O2 # New PM 已默认启用, 无需显式指定 )
ℹ 应对措施 在项目的 Makefile、CMakeLists.txt 及构建脚本中搜索并直接删除所有旧 Pass Manager 相关标志。 LLVM 16 的 New PM 已完全替代旧 PM, 这些标志不再有任何作用。
🔗 LLD 链接器: 并行化与新功能 正向变更
变更 #14 · 链接器 · LLD (ELF / MinGW / COFF)

ELF 链接器改进

链接速度大幅提升: 输入段初始化 (input section initialization) 和重定位扫描 (relocation scanning) 现已并行化, 大型项目链接时间显著缩短。

新功能:

  • --no-warnings / -w — 抑制链接器警告。
  • --compress-debug-sections=zstd — 使用 Zstandard 压缩调试段 (ELFCOMPRESS_ZSTD)。同时支持读取 ZSTD 压缩的输入段。
  • --no-undefined-version — 现已成为默认行为。version script 中指定但无匹配符号的符号将被报告。使用 --undefined-version 恢复旧行为。
  • DT_STATIC_TLS — AArch64/PPC32/PPC64 的 initial-exec TLS 模型在生成共享库时设置此标记。
  • -V 现在是 -v 的别名 (支持 gcc -fuse-ld=lld -v)。
  • ELFCOMPRESS_ZSTD 压缩输入段现已支持。
LLD 新选项使用示例
# 使用 zstd 压缩调试信息 $ clang -fuse-ld=lld -Wl,--compress-debug-sections=zstd -g -o myapp *.o # 抑制链接器警告 $ clang -fuse-ld=lld -Wl,-w -o myapp *.o # --no-undefined-version 已是默认, 无需显式指定 # 如需恢复旧行为 (允许未定义 version): $ clang -fuse-ld=lld -Wl,--undefined-version -o myapp *.o # LLD 链接速度自动提升, 无需额外标志 $ clang -fuse-ld=lld -o myapp *.o

MinGW 改进

  • --guard-cf / --no-guard-cf — Control Flow Guard (控制流保护) 开关。启用 --guard-cf 也会启用 --guard-longjmp (除非显式指定 --no-guard-longjmp)。默认关闭。
  • --guard-longjmp / --no-guard-longjmp — longjmp 强化保护。依赖 --guard-cf, 不可单独使用。
  • 使用 -l<name> 链接时正确识别 <name>.lib 文件 (即使指定了 -static), 与 GNU ld 行为一致。
  • 修复了 i386 MinGW 上 Rust 代码的 unwinding 问题。

COFF 改进

  • PDB 类型哈希从 SHA1 切换为 BLAKE3 (-gcodeview-ghash)。
  • DLL OrdinalBase 从 0 改为 1 (与 MS link.exe 和 GNU ld 一致)。
  • 改进 PCH.OBJ 文件处理, 与 MSVC link.exe 行为一致。
⚠ Breaking Change 提醒 --no-undefined-version 已成为默认。如果 version script 引用了不存在的符号, 链接将失败。使用 --undefined-version 恢复旧行为。
✅ 性能受益 LLD 的并行化改进是透明优化, 无需任何代码或构建系统改动即可自动受益。

📚 libc++ 废弃与移除 中影响
变更 #17 · 标准库 · libc++

已移除

  • unary_function / binary_function — C++17 及更新标准模式中不再提供。 可通过 _LIBCPP_ENABLE_CXX17_REMOVED_UNARY_BINARY_FUNCTION 宏重新启用。
  • std::function C++03 实现 — _LIBCPP_ENABLE_CXX03_FUNCTION 宏已被移除。 需要使用 std::function 的用户应切换到 C++11 及以上标准。
  • to_chars/from_chars 整数版本在 C++11/14 中的扩展 — 这些函数从 C++17 开始才正式提供。 libc++ 此前在 C++11/14 中提供的非标准扩展已被移除。
  • _LIBCPP_DEBUG 宏 — 不再生效, 使用即报错。请迁移至 _LIBCPP_ENABLE_DEBUG_MODE。
  • 大量 C++23 模式下的 incidental transitive includes (传递包含) 被移除 — 包括 <algorithm>, <array>, <atomic>, <chrono>, <functional>, <memory>, <string>, <vector> 等数十个头文件。 可通过 _LIBCPP_REMOVE_TRANSITIVE_INCLUDES 在所有语言版本中移除。

已废弃 (即将移除)

  • std::char_traits 基础模板 (base template) — 已标记为废弃, 将在 LLVM 18 中移除。 如果对 char, wchar_t, char8_t, char16_t, char32_t 或自定义字符类型之外的类型使用 std::char_traits, 代码将停止工作。 标准不要求提供基础模板, 且此类模板对某些类型可能导致未检测到的错误行为。
  • <experimental/memory_resource> — 已废弃, 请迁移至 <memory_resource>。 将在 LLVM 18 中移除。
  • _LIBCPP_AVAILABILITY_CUSTOM_VERBOSE_ABORT_PROVIDED — 将在 LLVM 18 中不再生效。
受影响代码 (C++17 模式下)
// LLVM 15: 编译通过 // LLVM 16: C++17 模式下编译失败 #include <functional> struct MyFunc : std::unary_function<int, bool> { // error: no member 'unary_function' bool operator()(int x) const { return x > 0; } };
修复方式 A: 自行定义类型别名
struct MyFunc { using argument_type = int; // 替代 unary_function<int, bool>::argument_type using result_type = bool; // 替代 unary_function<int, bool>::result_type bool operator()(int x) const { return x > 0; } };
修复方式 B: 使用宏重新启用 (C++17 模式)
// 在包含任何头文件之前定义 #define _LIBCPP_ENABLE_CXX17_REMOVED_UNARY_BINARY_FUNCTION #include <functional> // unary_function / binary_function 重新可用
⚠ 应对措施 unary_function/binary_function: 迁移到 C++17 风格的 using argument_type = ... 类型别名定义。
char_traits: 仅对标准字符类型使用 std::char_traits。
transitive includes: 如果代码依赖隐式包含 (如通过 <string> 间接获得 <algorithm>), 需要显式添加对应的 #include。
_LIBCPP_DEBUG: 将 _LIBCPP_DEBUG 替换为 _LIBCPP_ENABLE_DEBUG_MODE。
⚠ C++ 其他潜在破坏性变更 低影响
变更 #18 · C++ 前端 · Clang

枚举 constexpr 范围检查 (enum constexpr conversion)

见上方 变更 #10。

重载决议变更 (DR692/DR1395/DR1432)

作为实现 DR692/DR1395/DR1432 的副作用, 当一个候选函数模板具有 trailing parameter pack 时, Clang 现在可能拒绝某些之前接受的重载函数模板调用 (判定为二义性)。

LLVM 16 中判定为二义性的代码
template <typename T> void g(T, T = T()); template <typename T, typename... U> void g(T, U...); void h() { g(42); // LLVM 16: error: ambiguous (pack vs default argument) }

C++ 标准头单元定义限制

Clang 现在禁止 C++ 标准头单元 (header units) 中的非内联外部可见定义, 符合 [module.import/6]。在 Clang 15 中这些定义被允许 (但包含多次即构成 ODR 违规)。

数组元素大小与对齐检查

Clang 现在禁止将大小不是对齐倍数 (size not a multiple of alignment) 的类型用作数组元素类型。

受影响的代码
typedef char int8_a16 __attribute__((aligned(16))); int8_a16 array[4]; // LLVM 16: error: 元素大小不是数组对齐的倍数
ℹ 应对措施 这些变更影响面较窄, 大多数项目不会遇到。若受到重载决议变更影响, 可能需要显式消歧义或重构模板代码。
