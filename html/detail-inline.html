概述：为什么内联行为会变化？

内联（Inlining）是编译器最核心的优化之一。它决定了一个函数调用是保留为 call 指令 还是将函数体直接展开到调用点。正确的内联决策影响深远：过度内联导致代码膨胀、指令缓存压力增大； 内联不足则损失跨函数优化机会（常量传播、死代码消除、别名分析等）。

从 LLVM 15 到 LLVM 21，内联相关的提交超过 66 次， 涵盖成本模型修正、启发式算法调整、机器学习模型引入、以及新语言特性的适配。 这些变化意味着同一份源码在升级后可能得到不同的内联结果，进而影响性能和二进制大小。

下表按影响力从高到低列出关键变化。

变更 引入版本 影响范围 一句话说明
内联成本模型变化 LLVM 15 → 21 高 66+ 次 InlineCost 修改，阈值与计算方式持续演进
Switch 默认分支成本修正 LLVM 18 中 default 分支成本计算更准确，影响大 switch 的内联
ML-inliner 稳定化 LLVM 16 中 机器学习模型可在 release 模式下使用
内联汇编成本计入 LLVM 21 中 inline asm 的指令体积参与内联决策
__memcpy_chk 折叠罚分移除 LLVM 20 中 安全检查内置函数不再被错误惩罚
递归函数内联优化 LLVM 20 低 尾递归可转换为迭代后被内联
冷热路径分离 持续演进 中 冷路径更少被内联，缩小热代码体积
store-to-load forwarding LLVM 21 低 内联后通过存储转发消除内存访问

内联成本模型变化 LLVM 15 → 21

编译器的内联器（Inliner）对每个可内联的调用点计算一个"成本"和一个"收益"， 当收益大于成本时执行内联。InlineCost 是这一决策的核心模块。 LLVM 15 到 LLVM 21 之间，InlineCost.cpp 经历了 66 次以上的修改，涵盖：

  • 指令成本权重的重新校准（如 call、alloca、getelementptr 的代价）
  • 简化基本块（simplified BB）的成本估算改进
  • 对 select / phi 节点处理的修正
  • 函数属性（norecurse、nosync 等）对内联决策的影响
  • 新指令类型的成本纳入（如 llvm.experimental.* 内建函数）
示例 1：成本模型变化导致内联决策翻转
// ========== 被调用方: util.cpp ==========
int compute_offset(int base, int stride) {
    int tmp = base * stride;               // mul:  低成本指令
    int arr[4] = {tmp, tmp+1, tmp+2, tmp+3}; // alloca + 4 stores:  成本较高
    int result = arr[0];
    for (int i = 1; i < 4; i++)          // loop:  LLVM 15 可能简化后认为成本可接受
        result += arr[i];                  //         LLVM 21 的简化模型可能更精确
    return result;
}

// ========== 调用方: main.cpp ==========
void process() {
    // LLVM 15: compute_offset 在 -O2 下可能被内联
    // LLVM 21: 成本模型中 alloca + loop 的权重变化,
    //          结果可能从"内联"变为"不内联"
    int off = compute_offset(100, 4);
    do_something(off);
}
通俗解释：内联器就像一个会计，它给每条指令记账。 LLVM 15 的"价目表"和 LLVM 21 的"价目表"不同， 导致同一个函数在两个版本中可能获得不同的"报价"。 价格适中的就内联，太贵的就保留调用。
注意：__attribute__((always_inline)) 标记的函数 不受成本模型影响，无论成本多高都会强制内联。 因此对性能极其敏感的小函数，建议显式加入此标记以确保行为稳定。
示例 2：always_inline 不受影响
// always_inline:  无论 LLVM 版本如何, 始终被内联
__attribute__((always_inline))
inline int add(int a, int b) {
    return a + b;
}

// 普通 inline:  编译器自行决定, 受成本模型影响
inline int multiply(int a, int b) {
    return a * b;
}

int caller(int x, int y) {
    // add()     → 始终内联 (always_inline)
    // multiply() → 取决于 LLVM 版本的成本模型
    return add(x, y) + multiply(x, y);
}
升级建议：如果你发现升级后性能下降，很可能是关键热函数不再被内联。 请使用 -Rpass=inline 和 -Rpass-missed=inline 对比两个版本的内联决策日志， 定位具体是哪个函数的内联行为发生了变化。

Switch 语句默认分支成本修正 LLVM 18

在 LLVM 17 及更早版本中，switch 语句的 default 分支 在计算内联成本时被低估或忽略。这导致包含大量 case 的 switch 函数 ——例如协议分发器、状态机处理器——被不恰当地内联，造成代码膨胀。

LLVM 18 修复了这一问题：default 分支的成本现在被准确计入， 使得内联器对这些函数做出更合理的决策。

示例：协议分发函数中的大 switch
// 协议处理函数 — 含大量 case 的 switch
int handle_packet(PacketType type) {
    switch (type) {
        case TYPE_CONNECT:    return process_connect();
        case TYPE_DATA:       return process_data();
        case TYPE_ACK:        return process_ack();
        case TYPE_NACK:       return process_nack();
        case TYPE_KEEPALIVE:  return process_keepalive();
        case TYPE_HANDSHAKE:  return process_handshake();
        case TYPE_AUTH:       return process_auth();
        case TYPE_DISCONNECT: return process_disconnect();
        case TYPE_ERROR:      return process_error();
        case TYPE_TIMEOUT:    return process_timeout();
        // ... 可能还有几十个 case
        default:
            log_unknown(type);        // default 分支
            return -1;
    }
}

void dispatch(PacketType type, Packet* pkt) {
    // LLVM 17: default 分支代价被低估
    //          → handle_packet 可能被内联到 dispatch 中
    //          → 二进制膨胀明显（每个调用点一份完整 switch）
    //
    // LLVM 18: default 分支代价被正确计入
    //          → handle_packet 更倾向于保留为 call 指令
    //          → 缩小代码体积的同时, 减少指令缓存 miss
    int result = handle_packet(type);
    if (result != 0) cleanup(pkt);
}
通俗解释：一个大 switch 就像一个有很多房间的走廊。 LLVM 17 只计算了走廊的长度，忘了还有一个"其他门"（default）。 LLVM 18 补上了这个计算，发现走廊太长就不把整个房子搬进客厅了。

ML-inliner 稳定化 LLVM 16

ML-inliner 是 LLVM 中基于机器学习模型的内联决策模块。它使用 TensorFlow 或 ONNX 模型替代传统手工调参的启发式算法。LLVM 16 起，ML-inliner 在 release 构建模式下可作为稳定特性使用。

传统内联器使用固定的"成本-收益"公式；ML-inliner 则提取调用点和被调用函数的特征 （函数大小、调用深度、循环嵌套、参数常量性等），交给训练好的模型输出"内联/不内联"决策。

示例：吞吐敏感函数可能被更积极内联
// 场景：一个频繁调用的轻量包装函数
static int scale_value(int val, int factor) {
    return (val * factor) >> 10;
}

void process_stream(int* data, int count) {
    for (int i = 0; i < count; i++) {
        // 传统模型: 依据函数体大小和调用频率判断
        // ML 模型:  还会考虑以下特征:
        //   - 调用点在循环内 (用循环深度 +1 作为特征)
        //   - 被调用函数无副作用 (norecurse/nounwind)
        //   - 参数 'val' 来自内存加载, 内联后可能被 SROA 消除
        //
        // 结果: ML 模型倾向于内联此调用, 即使传统模型可能拒绝
        data[i] = scale_value(data[i], factor_lut[i]);
    }
}
通俗解释：传统方法像是用计算器算账，ML 模型则像一个经验丰富的老师傅， 能看一眼就知道"这个函数该不该内联"。ML 模型学到的模式可能比手工规则更精准， 尤其对吞吐敏感的热循环函数。
启用方式：ML-inliner 需要通过 -mllvm -enable-ml-inliner=release 在 Clang 中显式开启。默认情况下 LLVM 仍使用传统内联器。

内联汇编指令影响内联成本 LLVM 21

在 LLVM 20 及之前，内联汇编（__asm__ volatile）指令 在内联成本计算中不被计入。这导致包含大量内联汇编的函数可能被过度内联， 实际展开后的代码体积远超预期。

LLVM 21 修正了这一问题：内联汇编的指令条数现在参与成本计算， 使得内联决策更加合理。

示例：嵌入式驱动中的寄存器写入
// 嵌入式驱动中常见的内联汇编包装函数
static inline void write_reg(uint32_t addr, uint32_t val) {
    __asm__ volatile(
        "str %1, [%0]"
        :
        : "r"(addr), "r"(val)
        : "memory"
    );
}

static inline void init_peripheral() {
    write_reg(REG_CLOCK,   0x01);   // 每条 write_reg 调用有一行汇编
    write_reg(REG_POWER,   0x03);   // LLVM 20: 内联汇编成本 = 0
    write_reg(REG_MODE,    0x10);   //          → 可能被无条件内联
    write_reg(REG_ENABLE,  0x01);   //
}                                   // LLVM 21: 内联汇编成本 = 实际指令数
                                    //          → 内联决策更合理
通俗解释：过去编译器看到 __asm__ 就当看不见， 以为它不占地方。LLVM 21 终于开始"算账"了，内联汇编的行数被计入成本， 嵌入式驱动这类大量使用汇编包装函数的场景受益最大。
示例：带 clobber 的复杂内联汇编
// AArch64 上的原子操作包装
static inline uint64_t atomic_fetch_add(uint64_t* ptr, uint64_t val) {
    uint64_t old, temp;
    __asm__ volatile(
        "1: ldxr %0, [%3]\n"
        "   add  %1, %0, %4\n"
        "   stxr %w2, %1, [%3]\n"
        "   cbnz %w2, 1b"
        : "=&r"(old), "=&r"(temp), "=&r"(int){1}
        : "r"(ptr), "r"(val)
        : "memory", "cc"
    );
    return old;
}
// 这个函数有 4 条 ARM 汇编指令
// LLVM 20: 内联成本 = C++ 部分 (几乎为 0)
// LLVM 21: 内联成本 = C++ 部分 + 4 条 asm 指令的估算代价
//          → 在深层调用链中更不容易被内联 → 减少总体代码体积

__memcpy_chk 等折叠不再增加罚分 LLVM 20

__memcpy_chk、__memset_chk、__memmove_chk 等是编译器在启用 -D_FORTIFY_SOURCE 时插入的安全检查包装函数。 它们在优化阶段通常被折叠（fold）为普通的 llvm.memcpy 等内部指令。

LLVM 19 及之前，内联器在计算成本时无法识别这些将被折叠的调用， 从而错误地"惩罚"包含这些调用的函数，导致它们不被内联。 LLVM 20 修复了这个问题：内联器识别这些调用会在后续优化中被消除， 不再将其计入成本。

示例：FORTIFY_SOURCE 场景
// 编译选项: -O2 -D_FORTIFY_SOURCE=2
// 源码中的 memcpy 被编译器替换为 __memcpy_chk

void serialize_header(char* buf, const Header* hdr) {
    // 用户写的代码:
    memcpy(buf, hdr, sizeof(Header));

    // 编译器实际生成的 IR (简化示意):
    //   call __memcpy_chk(buf, hdr, sizeof(Header), __builtin_object_size(buf, 0))
    //
    // LLVM 19: __memcpy_chk 调用被计入内联成本
    //          → serialize_header 可能被视为"太贵"而不内联
    //
    // LLVM 20: 内联器识别到 __memcpy_chk 将在后续优化中被折叠为
    //          llvm.memcpy → 不计入成本 → 内联决策更合理

    buf[sizeof(Header)] = '\0';
}

void send_message(const Header* hdr) {
    char buffer[256];
    // serialize_header 在 LLVM 20 中更可能被内联
    serialize_header(buffer, hdr);
    send_to_socket(buffer);
}
通俗解释：编译器之前看到 __memcpy_chk 就以为这是个很重的函数调用， 不敢内联。实际上这些安全检查函数在优化阶段会被简化成普通的 memcpy。 LLVM 20 认识到了这一点，不再"错怪"它们。
示例：受影响的函数列表
// 以下内置函数在 LLVM 20 中不再增加内联罚分：

void example_all(void* dst, const void* src, size_t n) {
    __memcpy_chk(dst, src, n, __builtin_object_size(dst, 0));  // ✓ 不再罚分
    __memmove_chk(dst, src, n, __builtin_object_size(dst, 0)); // ✓
    __memset_chk(dst, 0, n, __builtin_object_size(dst, 0));    // ✓
    __strcpy_chk((char*)dst, (const char*)src,
                 __builtin_object_size(dst, 1));               // ✓
    __stpcpy_chk((char*)dst, (const char*)src,
                 __builtin_object_size(dst, 1));               // ✓
    // 等等 —— 所有 _chk 变体均受影响
}

递归函数内联优化 LLVM 20

传统上，递归函数不能被内联——因为那会导致无限展开。LLVM 20 增强了对 尾递归（tail recursion）模式的识别能力： 当检测到尾递归模式时，先将递归转换为等价的迭代循环， 然后对转换后的函数体执行常规内联分析。

示例 1：尾递归被转换为迭代后内联
// 尾递归形式的阶乘 (不是好的实践, 仅为演示)
static int factorial_tail(int n, int acc) {
    if (n <= 1) return acc;
    return factorial_tail(n - 1, acc * n);  // 尾递归调用
}

int factorial(int n) {
    // LLVM 19:  尾递归识别后转为迭代, 但内联分析保守
    // LLVM 20:  转换为迭代后, 若循环体足够小, 可被内联
    //
    // 等价的迭代形式 (LLVM 自动生成):
    //   int acc = 1;
    //   while (n > 1) { acc *= n; n--; }
    //   return acc;
    return factorial_tail(n, 1);
}

void compute() {
    // 在 LLVM 20 中, factorial(5) 的整个计算可能被
    // 内联 + 常量折叠为 return 120
    int result = factorial(5);
    use_result(result);
}
通俗解释：递归就像俄罗斯套娃，一层套一层。编译器以前看到套娃就放弃了。 现在它学会了把套娃拆开重新排列成一个环（循环），然后判断这个环是否小到可以塞进调用者体内。
示例 2：链表遍历中的尾递归
struct Node { int value; Node* next; };

// 尾递归形式的链表求和
static int sum_list_tail(Node* node, int acc) {
    if (!node) return acc;
    return sum_list_tail(node->next, acc + node->value);  // 尾递归
}

int total(Node* head) {
    // LLVM 20 先转换尾递归为循环, 然后根据循环复杂度决定是否内联
    return sum_list_tail(head, 0);
}

冷热路径分离

从 LLVM 16 开始，内联器逐步增强对冷热路径的辨别能力。 标记为 __attribute__((cold)) 的代码路径，以及由 Profile-Guided Optimization（PGO）识别为低频执行的路径， 在内联决策中会受到"压制"——即更倾向于保留为函数调用而非内联。

这么做的好处是显著减小热路径代码体积，提升指令缓存命中率。 错误处理、初始化失败路径、异常处理等冷代码不再膨胀热代码段。

示例：冷路径更少被内联
// 错误处理函数: 带 cold 属性
__attribute__((cold))
static void handle_error(int code) {
    log_error(code);
    cleanup_resources();
    if (code == FATAL) abort();
}

// 正常处理函数: 不带 cold 属性
static void do_work(WorkItem* item) {
    transform(item);
    validate(item);
}

void process(WorkItem* item) {
    // ===== 热路径 (hot) =====
    // do_work 不带 cold 属性
    // → 内联器倾向于内联（如果它足够小）
    do_work(item);

    // ===== 冷路径 (cold) =====
    // handle_error 带 cold 属性
    // → 内联器倾向于保留为 call 指令
    // → 热代码路径体积减小, 指令缓存更高效
    if (__builtin_expect(item->error != 0, 0)) {
        handle_error(item->error);
    }
}
通俗解释：编译器像一个厨师，把常用的食材（热路径）放在案板上（内联到调用点）， 不常用的食材（冷路径）留在冰箱里（保留为函数调用，需要时再取）。 案板整洁了，做菜（执行代码）就快了。
示例：PGO 驱动冷热分离
// 编译步骤:
//   1. clang -O2 -fprofile-generate -o prog prog.c
//   2. ./prog  (训练运行, 生成 .profraw)
//   3. llvm-profdata merge -o prog.profdata *.profraw
//   4. clang -O2 -fprofile-use=prog.profdata -o prog prog.c

void parse_config(const char* file) {
    int fd = open(file, O_RDONLY);
    if (fd < 0) {
        // 冷路径: 文件打开失败 (PGO 发现执行频率极低)
        // → 内联器降低此路径的内联倾向
        report_open_error(file);
        return;
    }
    // 热路径: 正常解析 (PGO 发现执行频率极高)
    // → 内联器保持正常判断
    parse_and_apply(fd);
    close(fd);
}

store-to-load forwarding 优化 LLVM 21

当一个函数被内联后，调用点传给函数参数的值（通常通过寄存器传递）可能在函数体内 被写入栈（store），随后又从栈读取（load）。LLVM 21 的内联器在计算"内联的收益"时， 更加精确地预估了内联后 store-to-load forwarding（存储到加载转发） 能消除的内存访问次数。

示例：内联后消除冗余内存访问
// 被调用函数: 参数以值传递
static int apply_factor(int value, int factor) {
    // 未内联时:  value 存储在栈上 (%stack_value)
    //            factor 存储在栈上 (%stack_factor)
    //            每次使用都要 load
    int scaled  = value * factor;       // load value, load factor → mul
    int offset  = value + factor;       // load value, load factor → add
    int shifted = (value << factor);    // load value, load factor → shl
    return scaled + offset + shifted;
}

int caller(int a) {
    // 内联后:  a 的值在寄存器 %r0 中
    //          LLVM 21 预估到:
    //            无需 spill+reload a 到栈
    //            直接使用寄存器值进行计算
    //          → 消除 6 次 load, 显著节省指令
    return apply_factor(a, 3);
}

// 更直观的对比 (LLVM IR 层面):
//
// 未内联的 apply_factor (简化):
//   store %value, %stack_value       ← spill
//   store %factor, %stack_factor     ← spill
//   %v1 = load %stack_value          ← reload
//   %f1 = load %stack_factor         ← reload
//   %mul = mul %v1, %f1
//   %v2 = load %stack_value          ← reload
//   %f2 = load %stack_factor         ← reload
//   %add = add %v2, %f2
//   ... (更多 reload)
//
// 内联到 caller 后:
//   %mul = mul %a, 3                 ← 直接使用寄存器
//   %add = add %a, 3                 ← 直接使用寄存器
//   %shl = shl %a, 3                 ← 直接使用寄存器
//   ... (零次 spill/reload)
通俗解释：没有内联时，参数传递像寄信——要封装（spill 到栈）再拆封（load 到寄存器）。 内联后参数直接在函数内部可见，LLVM 21 能更好地评估这种"免邮费"带来的收益， 从而对这类函数做出更积极的内联决策。
9

内联决策查看方法

要分析内联行为变化，最直接的方法是让编译器报告它的内联决策。 Clang 提供了 -Rpass 系列诊断选项。

基础用法
# 只查看成功内联的决策
clang -O2 -Rpass=inline file.cpp -c

# 只查看内联失败 (未内联) 的决策
clang -O2 -Rpass-missed=inline file.cpp -c

# 同时查看成功和失败的内联决策
clang -O2 -Rpass=inline -Rpass-missed=inline file.cpp -c
输出示例与解读
# 成功内联的典型输出:
# file.cpp:42:5: remark: 'compute_offset' inlined into 'process'
#   with (cost=15, threshold=35) [-Rpass=inline]
#
# 解读: compute_offset 的内联成本为 15,
#       低于阈值 35 → 被内联

# 内联失败的典型输出:
# file.cpp:58:10: remark: 'handle_packet' not inlined into 'dispatch'
#   because it should never be inlined
#   (cost=never): function too large [-Rpass-missed=inline]
#
# 解读: handle_packet 的函数体太大,
#       内联器判定成本不合算 → 不内联
对比 LLVM 15 和 LLVM 21 的内联决策差异
# 用两个编译器分别编译相同的优化后的源码，对比差异：

# 使用 LLVM 15 工具链
clang-15 -O2 -Rpass=inline -Rpass-missed=inline file.cpp -c 2>inline_llvm15.log

# 使用 LLVM 21 工具链
clang-21 -O2 -Rpass=inline -Rpass-missed=inline file.cpp -c 2>inline_llvm21.log

# 对比两者差异 (简化 shell 脚本示意)
# 提取函数名, 排序后对比
grep -oP "'[^']+' (inlined|not inlined)" inline_llvm15.log | sort > /tmp/15.txt
grep -oP "'[^']+' (inlined|not inlined)" inline_llvm21.log | sort > /tmp/21.txt
diff /tmp/15.txt /tmp/21.txt
提示：如果有大量文件需要对比，建议写一个自动化脚本， 对每个编译单元收集内联日志并汇总统计。重点关注热函数（通过 perf/flamegraph 识别） 的内联状态变化。
进阶技巧：
  • 使用 -Rpass-analysis=inline 获取更详细的内联分析（包括成本分解）
  • 使用 -mllvm -print-after=inline 查看内联 pass 执行后的 IR 变化
  • 使用 -fdiagnostics-show-hotness 让 PGO 热信息出现在 remark 中
  • 使用 llvm-remark-size-diff 工具对比两个编译的内联差别
∞

总结

LLVM 15 到 LLVM 21 之间，内联子系统经历了多维度、持续性的改进。 这些变化的总趋势是使内联决策更加精确——更少地过度内联（减少代码膨胀）， 同时不遗漏关键热函数的内联机会（保证运行时性能）。

在毕昇编译器升级过程中，建议：

  1. 对比内联日志 —— 使用 -Rpass=inline 逐文件对比两个版本
  2. 关注热函数 —— 优先排查 perf 报告中 top 函数的内联状态变化
  3. 评估二进制大小 —— 如果大小显著变化，通常是内联行为差异导致
  4. 善用 always_inline —— 对性能绝对关键的小函数显式标记
  5. 持续监控 —— 每次 LLVM 主版本升级都建议做内联决策对比
