代码体积优化（-Oz / -Os）

LLVM 17 Opaque Pointers → 减少 GEP/bitcast 链

LLVM 17 默认启用 Opaque Pointer 模式，IR 中的指针不再携带元素类型信息。 这一 IR 层的简化消除了大量冗余的 GEP（GetElementPtr）和 bitcast 指令链。

对代码体积的直接影响：更少的 IR 指令意味着后端指令选择阶段生成更紧凑的机器码。 在 -Oz 场景下，减少指针操作开销尤为明显—— 嵌入式设备报告的 .text 段缩减约 1-3%。

示例 — Opaque Pointer 简化 IR
; LLVM 16 (Typed Pointer)：需要 bitcast + GEP 链
%ptr = bitcast i8* %base to %struct.Foo*
%gep = getelementptr %struct.Foo, %struct.Foo* %ptr, i32 0, i32 2

; LLVM 17+ (Opaque Pointer)：直接计算偏移
%gep = getelementptr i8, ptr %base, i64 16   ; 单条指令

LLVM 20 Size-aware Machine Block Placement

LLVM 20 引入了针对 -Oz 场景的大小感知代码布局优化器。 Machine Block Placement pass 在布局基本块时，将 "减少跳转指令编码字节数" 作为优化目标之一，而不单纯追求执行频率。

示例 — 大小感知布局
; -Oz 下，布局算法优先使用短跳转（2 字节）而非长跳转（5 字节）
; 将热/冷块重新排列，使跳转目标在短跳转可达范围（±127 字节）内
jmp .Lcold_path      ; 短跳转：EB xx（2 字节） vs. 长跳转：E9 xx xx xx xx（5 字节）

LLVM 20 内联成本模型改进

内联成本模型得到显著改进，更好地识别调用点的冷热属性。 在 -Oz 下，编译器倾向将冷路径代码保留在函数外部 （避免内联膨胀），同时将频繁执行的热路径内联以减少调用开销。 冷热分离更精确，避免了过去"一刀切"式的内联决策。

示例 — 冷热分离
void process(int x) {
    if (__builtin_expect(x < 0, 0)) {  // 冷路径
        log_error(x);   // 不内联，保持体积
    }
    handle(x);          // 热路径：内联，减少调用开销
}

性能优化关键变更

LLVM 16 ML-inliner 稳定

基于机器学习的内联决策模型从实验性阶段毕业。 使用强化学习训练的模型预测每个调用点的内联收益， 替代了传统的手工启发式规则。

ML-inliner 带来的改进：更准确的内联收益预估（综合考虑调用频率、函数体积、 后续优化机会等），通常带来 2-5% 的性能提升（SPEC CPU 级别）。 启用方式： 

# 使用训练好的模型指导内联决策
-mllvm -enable-ml-inliner=release
效果 — 内联决策质量
// 传统启发式：仅看函数体积 → 可能错过小但关键的内联机会
// ML-inliner：综合考虑调用频率 + IR 简化潜力 → 更精准

LLVM 17 nofpclass 属性

nofpclass 属性标注了浮点值不可能属于的类别 （NaN、Inf、负零、正零、subnormal 等），使编译器能够进行更积极的 浮点比较优化和常量折叠。

示例 — 浮点比较优化
// nofpclass(nan inf) 标注后：编译器知道 x 不可能是 NaN 或 Inf
bool is_finite(double x) __attribute__((nofpclass(nan inf))) {
    return x == x;  // 编译器可直接优化为 return true
}

LLVM 18 cdsort 算法

cdsort（Clang Data Section Sort）是 PGO（Profile-Guided Optimization）场景下的代码段布局排序算法。 它将函数按调用图亲和性重新排列，使频繁共同执行的函数在内存中相邻， 从而提升指令缓存（I-cache）利用率。

与传统的 hfsort 相比，cdsort 在大型二进制文件 （数百 MB 的 .text 段）上排序质量更高，且算法复杂度更低。

示例 — 代码段布局优化
# 使用 PGO + cdsort 获得最优布局
-fprofile-generate  # 训练运行
-fprofile-use        # 构建时自动触发 cdsort 排序

LLVM 19 nusw/nuw GEP Flags

nusw（No Unsigned Signed Wrap）和 nuw（No Unsigned Wrap） 是 GEP（GetElementPtr）指令上的新标志位，表明指针偏移量不会发生回绕。

这些标志使别名分析和边界检查更加精确：

  • 越界分析：已知偏移不溢出 → 可以推断出指针操作的有效范围。
  • 别名分析：两个带 nusw/nuw 的指针如果基址不同，编译器可断定它们永不别名。
示例 — 推导无别名
; 两个带 nuw 的 GEP，基址不同 → 编译器可安全断定无别名
%p1 = getelementptr nuw i8, ptr %base1, i64 %offset1
%p2 = getelementptr nuw i8, ptr %base2, i64 %offset2
; → 对 *p1 和 *p2 的内存操作可自由重排 / 向量化

LLVM 20 TBAA 默认启用

Type-Based Alias Analysis（TBAA）在 LLVM 20 中默认启用。 TBAA 利用 C/C++ 的类型系统信息推断指针别名关系， 使编译器能够进行更激进的内存访问重排和向量化。

⚠ 潜在风险： 如果代码中存在 strict aliasing 违规（例如通过 float* 访问 int 对象），TBAA 默认启用可能导致错误的优化。 建议使用 -fno-strict-aliasing 作为临时规避手段， 同时修复违规代码。
示例 — TBAA 驱动的优化
void update(int* a, float* b) {
    *a = 42;
    *b = 3.14f;
    // TBAA 告知编译器：int* 和 float* 不别名 → 两条写可自由重排
}

LLVM 21 Store-to-Load Forwarding

LLVM 21 增强了内联后的 store-to-load forwarding 分析能力。 当内联将调用者的 store 和被调用者的 load 放入同一函数体时， 编译器能识别出直接的值传递关系，消除冗余的内存读写。

示例 — 消除内存中转
// 内联前：调用者 store → callee load（两次内存操作）
void caller() {
    int buf[4] = {1,2,3,4};
    callee(buf);   // callee 从 buf load 数据
}
// 内联后 + forwarding：直接传递值 → 零内存操作

可能回退的风险

SVE 自动向量化降级（LLVM 19）

LLVM 19 中 -march=armv9-a 不再默认启用 SVE（Scalable Vector Extension）自动向量化。 此前编译器会尝试生成 SVE 指令，但某些场景下 SVE 代码生成质量不稳定， 因此改为需要显式指定 -march=armv9-a+sve 或 +sve2。依赖 SVE 自动向量化的 AArch64 代码 可能观察到向量化程度降低。

向量化 Cost Model 变化

各版本 LLVM 持续调整向量化代价模型（LoopVectorizeCostModel）。 某些在旧版本中会被向量化的循环，在新版本中可能因为代价评估更保守 而放弃向量化（反之亦然）。这在 -Os / -Oz 下尤为明显——编译器在体积和性能之间的权衡策略 可能随版本变化。

TBAA 导致错误优化

TBAA 默认启用（LLVM 20+）后，存在 strict aliasing 违规的代码 可能被编译器错误优化，表现为非预期的值丢失、顺序颠倒等。 发现此类问题后：可临时使用 -fno-strict-aliasing， 但根本修复是消除代码中的类型双关（使用 memcpy 或 union 进行安全的类型转换）。

通用建议： 升级编译器后，始终对关键路径进行回归测试。 编译器优化策略的改变是"零和博弈"——某些场景提升、某些场景回退在统计上是正常的。 目标是确保整体方向（特别是你们的代表性工作负载）是正向的。

验证建议

二进制体积对比

工具用途典型命令
size(1) 查看 ELF 段大小（.text / .data / .bss） size -A ./output_binary
bloaty 按编译单元/符号分析体积构成 bloaty -d compileunits ./binary
nm --size-sort 按符号大小排序，识别异常大的符号 nm --size-sort -t d ./binary | tail -30
示例 — 体积对比脚本
#!/bin/bash
# 对比升级前后的二进制体积
echo "=== 旧版本 (LLVM 16) ==="
size -A build_old/bin/myapp > old_size.txt
echo "=== 新版本 (LLVM 20) ==="
size -A build_new/bin/myapp > new_size.txt
diff old_size.txt new_size.txt

性能基准

基准侧重说明
CoreMark CPU 核心流水线 / 基本运算 轻量级嵌入式基准，快速发现指令调度回退
Dhrystone 整数运算 / 分支预测 经典基准，对编译器优化策略变化敏感
协议栈吞吐 网络 I/O / 内存带宽 反映 TCP/UDP 协议栈处理的端到端性能
应用级基准 业务真实负载 最关键的指标——以自己的代表性工作负载为最终评判

内联决策日志分析

使用 LLVM 的内联诊断报告功能获取每个调用点的内联决策及其原因： 

# 生成内联诊断报告（成功 + 失败）
-Rpass=inline -Rpass-missed=inline -Rpass-analysis=inline

# 保存到文件供后续分析
-fsave-optimization-record -foptimization-record-file=inline.yaml
示例 — 内联决策输出
// 成功内联
remark: foo.cpp:42:15: 'callee' inlined into 'caller'
  with (cost=25, threshold=50)

// 放弃内联
remark: bar.cpp:10:3: 'heavy_func' not inlined into 'hot_loop'
  because it should never be inlined (cost=120, threshold=50)
验证流程建议：
1. 先做二进制体积对比（低开销，快速发现异常）
2. 运行 CoreMark / Dhrystone 基准（排查基本代码生成回退）
3. 运行业务代表性工作负载（最终评判标准）
4. 如有回退，使用 -Rpass 系列选项 + Git bisect 定位引入变更的提交
