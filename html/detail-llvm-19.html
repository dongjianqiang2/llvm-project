LLVM 19 变更概览

对 AArch64 影响最大 SVE/SVE2 ARMv9.0 变为可选特性
破坏性变更 在 LLVM 19 之前，-march=armv9-a（以及 -march=armv9.1-a、-march=armv9.2-a 等）会隐式启用 SVE 和 SVE2 扩展。LLVM 19 起，这些扩展从默认扩展列表中移除，变为可选特性。这与 ARM 架构手册的规范保持一致——SVE 和 SVE2 在 ARMv9.0 中确实是可选扩展。

变更动机

在 ARM 架构规范中，ARMv9.0-A 基线要求 SVE（Scalable Vector Extension），但 SVE2 仅为 ARMv9.0-A 的可选扩展。然而，在 ARMv8.9-A 和 ARMv9.3-A 之前，SVE2 不被认为是基线特性。之前 Clang 在所有 ARMv9.x 目标中默认启用 SVE/SVE2 的行为过于激进，与实际硬件能力不匹配——许多 ARMv9.0/9.1/9.2 实现并不支持 SVE。

核心影响 依赖 SVE 自动向量化的代码可能降级为 NEON，导致性能回退。如果 CPU 实际上支持 SVE，但编译时未显式指定 +sve/+sve2，编译器将不再生成 SVE 指令。

示例 1：-march=armv9-a 不再隐含 +sve/+sve2

LLVM 18 及之前（SVE 默认启用）
# armv9-a 自动包含 SVE/SVE2
# 编译器生成 SVE 向量化代码
clang -target aarch64-linux-gnu \
      -march=armv9-a \
      -O2 -c example.c

# 等价于自动添加了 +sve+sve2
LLVM 19+ （SVE 需显式指定）
# armv9-a 不再自动包含 SVE/SVE2
# 必须显式添加 +sve 和/或 +sve2
clang -target aarch64-linux-gnu \
      -march=armv9-a+sve+sve2 \
      -O2 -c example.c

# 或仅启用 SVE
clang -target aarch64-linux-gnu \
      -march=armv9-a+sve \
      -O2 -c example.c

示例 2：检查现有 -march/-mcpu 配置

检查脚本 — 扫描构建系统中的 -march 配置
#!/bin/bash
# 检查项目中所有使用 armv9-a 但不包含 +sve 的编译配置
grep -rn "armv9" Makefile CMakeLists.txt *.cmake *.mk \
  | grep -v "+sve"

# 输出示例（需要修复的条目）：
# Makefile:42: CFLAGS += -march=armv9-a
# CMakeLists.txt:15: set(CMAKE_C_FLAGS "-march=armv9-a")
#
# 修复方式：
# Makefile:42: CFLAGS += -march=armv9-a+sve+sve2
# CMakeLists.txt:15: set(CMAKE_C_FLAGS "-march=armv9-a+sve+sve2")
使用 -mcpu 时的注意事项
# -mcpu 指定的 CPU 实现如果实际支持 SVE，
# -mcpu 会自动启用对应的 SVE 扩展
# 例如 Neoverse V2 支持 SVE2，无需额外 +sve2
clang -target aarch64-linux-gnu \
      -mcpu=neoverse-v2 \
      -O2 -c example.c

# 但使用通用 -march 时不再自动获取 SVE
# 推荐做法：优先使用 -mcpu 指定具体目标 CPU
# 或在 -march= 中明确列出所有需要的扩展

迁移建议

  • 如果 CPU 支持 SVE：在 -march=armv9-a 中显式添加 +sve 和 +sve2
  • 如果 CPU 不支持 SVE：无需操作，行为与之前使用 NEON 一致
  • 推荐用法：使用 -mcpu=<具体CPU型号> 替代泛型 -march=armv9-a，编译器会根据 CPU 特性自动启用正确的扩展
  • 性能验证：升级后务必对比关键模块的向量化情况，确认是否意外降级为 NEON（可通过 -Rpass=vectorize 检查）
  • SVE 版本说明：
    • +sve：SVE（ARMv8.2-A 起可选，ARMv8.6-A 起部分实现）
    • +sve2：SVE2（ARMv9.0-A 可选，ARMv8.9-A / ARMv9.3-A 起基线要求）
    • +sve2-bitperm：SVE2 位排列扩展（ARMv8.9-A / ARMv9.3-A 起基线要求）
重要安全特性 Pointer Authentication (PAuth) 完全支持
重要安全增强 LLVM 19 完成了对 AArch64 Pointer Authentication 的 ELF 重定位类型支持，包括新增的 R_AARCH64_AUTH_ABS64 和 R_AARCH64_AUTH_RELATIVE 静态重定位类型。同时链接器支持 GNU_PROPERTY_AARCH64_FEATURE_PAUTH 属性 note，标志着 PAuth 在 ELF/Linux 平台进入了生产可用阶段。

Pointer Authentication 是什么

Pointer Authentication（PAC）是 ARMv8.3-A 引入的硬件安全特性。它利用 64 位指针中未使用的高位来存储基于密钥的"指针认证码"（Pointer Authentication Code, PAC）。在指针被使用前（如函数返回、间接跳转），硬件验证 PAC 的正确性。如果攻击者试图篡改指针，PAC 将不匹配，触发异常。

主要防护场景：

  • 返回导向编程（ROP）：通过 PAC-RET 保护函数返回地址
  • 跳转导向编程（JOP）：通过 PAC/BTI 组合保护间接跳转
  • 数据指针篡改：通过 PAC 保护关键数据指针

示例 1：静态 PAuth 重定位类型

新支持的 ELF 重定位类型
// PAuth 签名指针的重定位
// R_AARCH64_AUTH_ABS64: 用于静态初始化中已签名的绝对指针
// R_AARCH64_AUTH_RELATIVE: 用于静态初始化中已签名的相对指针

// C 源码示例：需要 PAuth 保护的关键函数指针表
__attribute__((used))
static void (*const critical_handlers[])(void) = {
    handle_packet_ingress,
    handle_packet_egress,
    handle_security_event,
    NULL
};
// 链接时这些函数指针可被 PAC 签名，
// R_AARCH64_AUTH_ABS64 用于重定位签名后的指针

示例 2：-mbranch-protection=standard 启用 PAuth-LR

编译选项 — ARMv9.3-A+ 使用 FEAT_PAuth_LR
# -mbranch-protection=standard 在兼容目标上自动启用 PAuth-LR
# PAuth-LR（FEAT_PAuth_LR）是 ARMv9.3-A 的简化版 PAC，
# 专为低开销场景设计，适合嵌入式网络设备

# 针对支持 FEAT_PAuth_LR 的目标（如 ARMv9.3-A+）
clang -target aarch64-linux-gnu \
      -march=armv9.3-a \
      -mbranch-protection=standard \
      -O2 -c example.c

# standard 等价于 bti+pac-ret+pc（含 PAuth-LR）
# 当 +pauth-lr 通过 -mcpu= 传入时，standard = bti+pac-ret+pc
# bti: Branch Target Identification（防护 JOP）
# pac-ret: PAC 保护返回地址（防护 ROP）
# pc: 同时保护叶子函数
精细控制 PAuth 选项
# 完整 PAuth 保护（ARMv8.3-A+）
clang -mbranch-protection=bti+pac-ret+leaf

# 仅 BTI（最低要求 ARMv8.5-A）
clang -mbranch-protection=bti

# 仅 PAC 返回地址保护
clang -mbranch-protection=pac-ret

# 标准模式（LLVM 19 推荐）
clang -mbranch-protection=standard

示例 3：GNU_PROPERTY_AARCH64_FEATURE_PAUTH

链接器 — GNU property note 支持
# 链接时，lld 和 ld.lld 支持 GNU_PROPERTY_AARCH64_FEATURE_PAUTH
# 该 note 标记 ELF 文件启用了 PAuth 特性
# 动态链接器（ld.so）可在加载时检查此标记

# 编译带 PAuth 的目标文件
clang -mbranch-protection=standard -c module.c

# 链接（自动处理 PAuth property）
ld.lld -o libmodule.so module.o

# 检查生成的 ELF 中的 PAuth 属性
readelf -n libmodule.so | grep PAUTH
# 输出示例：
#   Properties: AArch64 feature: PAUTH

对数通设备的价值

  • 控制流完整性（CFI）：BTI + PAC-RET + PAuth-LR 组合提供硬件级别的 ROP/JOP 防护，对网络数据面代码的保护尤为重要
  • 低开销：PAuth-LR（FEAT_PAuth_LR）在 ARMv9.3-A+ 上以极低性能开销（通常 <1%）提供返回地址保护
  • 固件安全：嵌入式网络设备固件中，PAuth 可防止缓冲区溢出利用篡改控制流
  • 与上游对齐：Linux 内核、Android、各大发行版已逐步启用 PAC/BTI 保护
迁移建议 对于运行在 ARMv8.3-A+ 或 ARMv9.x-A 平台的数通设备，强烈建议在编译器标志中添加 -mbranch-protection=standard，以获得硬件级别的控制流完整性保护。需要在所有编译单元和链接阶段一致使用此选项。
AArch64 ABI 变更 AArch64 FMV ifunc 全局别名移除
破坏性变更 移除了指向 AArch64 Function Multiversioning (FMV) ifunc 的全局别名。该别名的初衷是为了在 ".ifunc" 后缀从名称修饰（name mangling）中移除后保持向后兼容性。但该别名与 GlobalOpt 优化 pass 产生不良交互，可能导致错误行为（参阅 issue #96197）。

变更动机

Function Multiversioning 允许同一函数根据运行时 CPU 特性选择不同的实现版本。在 LLVM 中，FMV 通过 ifunc（indirect function）机制实现。早期实现中，ifunc 的符号名包含 ".ifunc" 后缀，后续版本将其从名称修饰中移除。为保持向后兼容，LLVM 引入了一个不带后缀的全局别名指向实际的 ifunc 符号。

然而，该全局别名被 GlobalOpt pass 识别为"可替换"的间接引用，GlobalOpt 可能将其替换为对特定函数版本的直接调用，这破坏了 FMV 的运行时分发语义。移除该别名后，GlobalOpt 不再错误优化 FMV 函数调用。

受影响场景
// AArch64 Function Multiversioning 示例
__attribute__((target_clones("default,sve")))
int compute(int *data, int len) {
    // ... 实现
    return result;
}

// LLVM 18: 生成 ifunc compute，以及全局别名 compute（指向 compute.ifunc）
// LLVM 19: 仅生成 ifunc compute，无全局别名
//
// 影响：如果代码通过 dlsym 查找 "compute" 符号并依赖别名间接调用，
// 需确认实际链接行为。正常的函数调用不受影响。
影响范围 此变更主要影响使用了 AArch64 Function Multiversioning 且依赖全局别名符号的极少数场景（如 JIT 运行时通过 dlsym 查找 ifunc）。正常的源代码函数调用完全不受影响。如果发现 FMV 函数在 LLVM 19 下行为异常（之前工作正常），可能是 GlobalOpt 错误优化的遗留问题已得到修复。

C 语言扩展 C 原始字符串字面量（Raw String Literals）
C99+ 新扩展 LLVM 19 在 -std=gnuXY 模式下（C99 及以后）支持原始字符串字面量（raw string literals）作为 GNU 扩展。此行为可通过 -f[no-]raw-string-literals 覆盖。修复了 #85703。

功能说明

原始字符串字面量使用 R"delimiter(...)delimiter" 语法，在字符串中无需转义字符。这在包含正则表达式、JSON、嵌入脚本等场景中非常有用。

C 语言中使用原始字符串字面量
// 使用 -std=gnu99 或更高版本的 GNU 模式编译
// clang -std=gnu99 -c example.c

// 传统方式：需要大量转义
const char *json_old = "{\"name\":\"value\",\"count\":42}";

// 原始字符串字面量：无需转义（LLVM 19 C 新增）
const char *json_new = R"({"name":"value","count":42})";

// 也可用于正则表达式
const char *pattern = R"(\d+\.\d+)";

// 多行字符串（保留换行和缩进）
const char *multiline = R"(
    Line 1
    Line 2
)";
控制选项
# 显式启用 C 原始字符串字面量
clang -fraw-string-literals -std=gnu99 example.c

# 禁用（恢复到 LLVM 18 行为）
clang -fno-raw-string-literals -std=gnu99 example.c
注意事项 此扩展仅在 GNU 模式（-std=gnu99、-std=gnu11、-std=gnu17、-std=gnu23）下可用。在严格标准模式（-std=c99 等）或 C89/C90 模式下不可用。C++ 中的原始字符串字面量支持不受影响（自 C++11 起标准支持）。如果代码中包含 R"(...)" 形式的宏定义或字符串，升级后行为可能与预期一致或出现新解析——请注意检查。
诊断变更 模板参数自阴影诊断
行为变更 在 LLVM 19 之前，函数模板或变量模板如果与自身的模板参数同名，编译器不会报错（或仅产生警告）。LLVM 19 起，这种情况被视为编译错误（error），因为模板名会遮蔽模板参数名，导致代码含义不明确。

问题说明

C++ 标准规定，模板声明中的模板参数名在其作用域内是有效的实体名。如果函数模板或变量模板的名字与其中某个模板参数同名，则模板名字会在其定义内部遮蔽（shadow）同名的模板参数，造成混淆和潜在的错误。

示例 — 现在报 error 的代码
// LLVM 19 起：这些都是编译错误

// 错误 1：函数模板与类型参数同名
template<class T>
void T() {}  // ERROR: 函数模板 'T' 与其模板参数同名

// 错误 2：变量模板与类型参数同名
template<class V>
int V = 42;  // ERROR: 变量模板 'V' 与其模板参数同名

// 错误 3：类模板外的函数定义与模板参数同名
template<typename U>
struct Wrapper {
    template<typename U>  // 合法：类作用域内的重声明
    void U() {}  // ERROR: 成员函数模板 'U' 与模板参数同名
};
正确写法 — 避免同名
// 修正：使用不同的名称
template<class T>
void func_t() {}  // OK: 函数名与模板参数不同

template<class V>
int value_v = 42;  // OK: 变量名与模板参数不同

// 或者使用描述性名称
template<class ValueType>
void processValue(ValueType val) {}  // OK
影响范围 此诊断主要影响使用了短模板参数名（如 T、V、U）的通用代码。如果代码库中有函数模板或变量模板恰好与模板参数同名（虽然罕见但可能存在于历史代码中），升级到 LLVM 19 后将导致编译失败。可通过 -Wno-strict-primary-template-shadow 临时禁用此诊断以保持与旧版本兼容。
默认行为变更 -frelaxed-template-template-args 默认启用
模板匹配规则放宽 LLVM 19 起，-frelaxed-template-template-args 编译器标志默认启用，该标志本身已废弃。该特性使模板模板参数（template template parameter）的匹配规则更加灵活，允许接受参数不精确匹配的模板作为模板参数，与 GCC 行为对齐。

问题背景

C++17 标准（P0522R0）放宽了模板模板参数的匹配规则：一个模板模板参数可以匹配一个实参模板，即使实参模板的参数列表与形参不完全匹配，只要实参模板可以接受形参所使用的参数即可。但在 C++17 标准化过程中，此变更被视为缺陷报告，理论上应追溯适用于 C++14 及更早标准。

此前，Clang 将此作为可选特性通过 -frelaxed-template-template-args 提供。LLVM 19 起，该行为默认启用。负拼写（-fno-relaxed-template-template-args）仍可用于兼容旧版本（伴随废弃警告，可通过 -Wno-deprecated-no-relaxed-template-template-args 禁用警告）。

示例 — 松弛匹配的具体表现
// 一个接受默认参数的模板
template<typename T, typename Alloc = std::allocator<T>>
class MyContainer { /* ... */ };

// 模板模板参数：期望一个接受单个参数的模板
template<template<typename> class Container>
struct Processor {
    Container<int> data;
};

// LLVM 18 及之前（-frelaxed-template-template-args 未启用）：
//   错误：MyContainer 接受 2 个模板参数，
//        但 Container 模板模板参数期望 1 个
//
// LLVM 19（默认启用松弛匹配）：
//   OK：MyContainer<int> 等价于 MyContainer<int, allocator<int>>
//       默认参数使其可以接受 1 个实参
Processor<MyContainer> proc;  // LLVM 19 起合法

兼容性与控制

恢复旧行为的选项（已废弃）
# -frelaxed-template-template-args 标志已废弃（始终默认启用）
# 负拼写可用于兼容旧版本（产生废弃警告）

# LLVM 19 中禁用松弛匹配（含废弃警告）
clang++ -fno-relaxed-template-template-args example.cpp

# 禁用负拼写的废弃警告
clang++ -fno-relaxed-template-template-args \
       -Wno-deprecated-no-relaxed-template-template-args example.cpp
潜在影响 此变更通常不会导致现有代码编译失败（只是让更多代码通过编译）。唯一需要注意的是：如果代码依赖"模板模板参数匹配失败"来触发 SFINAE 选择其他重载或特化，则行为可能改变——松弛匹配下，某个原本不匹配的候选现在可能匹配，改变了重载决议的结果。这种情况较为罕见，但仍建议在升级后进行全量编译验证。
C++ 行为变更 decltype(&(foo::bar)) 不再形成成员指针
语义修正 LLVM 19 不再尝试在已限定且有括号的未求值上下文（unevaluated context）中将表达式 decltype(&(foo::bar)) 解析为 pointer-to-member（成员指针）。这是一个编译正确性的修正，修复了 #40906。

问题说明

在 C++ 中，&(foo::bar) 在未求值上下文中的类型取决于 foo::bar 是静态成员还是非静态成员。之前的 Clang 版本在某些情况下错误地将此表达式解析为 pointer-to-member 类型（指向成员的指针），而正确的行为应该是将其解析为普通指针（如果 bar 是静态成员）或触发 SFINAE。

受影响的代码
// 受此变更影响的模式
struct Foo {
    static int bar;
    void baz();
};

// LLVM 18: 错误地将 &(Foo::bar) 解析为 pointer-to-member
// LLVM 19: 正确解析为普通函数指针 int (*)()
using T1 = decltype(&(Foo::bar));  // 静态成员，应为 int*

// 对于非静态成员函数
using T2 = decltype(&(Foo::baz));  // 成员函数指针（不变）

// 关键修正：已限定且有括号的表达式不再错误匹配
// 之前可能导致 SFINAE 条件错误触发或失效
影响范围 此变更主要影响使用了 decltype(&(qualified-id)) 模式的模板元编程代码。对于大多数用户，这是正确的修正，应使代码行为更符合 C++ 标准。如果代码依赖旧的错误行为（如将静态成员的地址误识别为成员指针触发 SFINAE），需要调整相关模板条件。
标准库兼容性 libstdc++ 14.1.0 兼容性问题（需 14.1.1+）
编译失败 LLVM 19 现在对已知为非类非枚举类型的依赖类型操作数进行一元运算符（如 ++、--）的语义分析，而不再推迟到模板实例化阶段。此变更暴露了 libstdc++ 14.1.0 中的一个 bug，可能导致使用该版本的系统编译失败。

错误表现

典型错误信息
// 编译时的错误输出：
error: expression is not assignable
    4 |     ++this;
      |     ^ ~~~~

// 此错误来自 libstdc++ 14.1.0 头文件内部的模板代码
// 当 libstdc++ 模板中对 this 指针使用 ++ 运算符时，
// 新的语义分析在实例化前就检测到 this 不可赋值

解决方案

将 libstdc++ 更新到 14.1.1 或更高版本即可解决问题。这个 bug 已在 GCC/libstdc++ 端修复。此变更本身是正确的标准符合性改进，只是在过渡期间暴露了现有库代码中的潜在问题。

对数通设备的影响 如果数通产品线使用较新的 Linux 发行版（如 Ubuntu 24.04 以上的滚动版本），需确认系统 libstdc++ 版本不低于 14.1.1。对于使用自定义工具链的场景（常见于嵌入式开发），应确保交叉编译工具链中的 libstdc++ 版本不是 14.1.0。
行为变更 -fdelayed-template-parsing 不再强制需要
MSVC 兼容性改进 在 LLVM 19 中，对于使用了 MSVC 兼容模式的代码，-fdelayed-template-parsing 不再像早期版本那样是必需选项。Clang 对模板解析的处理得到改进，许多之前在非延迟模式下无法正确解析的 MSVC 风格模板代码现在可以直接编译。

背景

-fdelayed-template-parsing 是 Clang 为兼容 MSVC 而引入的选项。它模仿 MSVC 的模板解析策略：将模板体作为词法令牌流存储，推迟到模板实例化时才进行完整的语法和语义分析。虽然这提高了与 MSVC 代码的兼容性，但也意味着模板体中的语法错误要到实例化时才会被发现。

LLVM 19 的模板解析改进减小了延迟解析与立即解析之间的差距。对于多数现代 MSVC 代码，-fdelayed-template-parsing 不再是必需的。

使用建议
# 旧方式（LLVM 18 之前可能需要）
clang-cl /Zc:twoPhase- example.cpp

# LLVM 19 推荐：尝试不加延迟解析，验证代码是否可以编译
clang-cl example.cpp
# 如果需要兼容旧 MSVC 头文件，仍可使用
clang-cl -fdelayed-template-parsing example.cpp
迁移建议 建议逐步减少对 -fdelayed-template-parsing 的依赖。在升级到 LLVM 19 后，先尝试不加该选项编译项目。如果遇到模板相关的编译错误，再决定是否需要重新启用或修复源代码。
ABI 变更 MSVC 名称修饰与调用约定修复
多项 ABI 修复 LLVM 19 包含多项影响 MSVC ABI 兼容性的修复：名称修饰（name mangling）改进和调用约定修正。这些修复使 Clang 与 MSVC 编译的代码更好地互操作，但可能引入与较早版本 Clang 编译的代码的 ABI 不兼容。

MSVC 名称修饰修复

以下四项修复修正了 Clang 在 MSVC 名称修饰中的偏差：

1. 线程安全静态本地变量初始化（#GH83616） 修正了用于线程安全静态本地初始化（thread-safe static local init）的隐式定义变量的名称修饰。此变更解决了与 MSVC 编译代码的不兼容问题，但如果带有 __declspec(dllimport) 的内联成员函数中包含带动态初始化器的静态本地变量，则可能与旧版 Clang 编译的代码不兼容。
2. 生命周期延长临时对象（#GH85423） 修正了生命周期延长临时对象（lifetime extended temporaries）的名称修饰。此变更修正了缺失的反向引用注册（back reference registration），该 bug 可能导致错误的反向引用索引和令人困惑的 demangled 名称结果。由于 MSVC 对这些对象使用不同的名称修饰方式，兼容性不受影响。
3. auto NTTP 指针类型（MSVC 1920+） 修正了指针类型的 auto 非类型模板参数（auto non-type template parameter）的名称修饰，以匹配 MSVC 1920+ 的行为。此变更解决了与 MSVC 1920+ 编译代码的不兼容问题，但如果未使用 -fms-compatibility-version=19.14 选项来模拟 MSVC 1914 的名称修饰行为，则会引入与旧版 Clang 编译代码的不兼容。
4. auto NTTP 成员指针类型（MSVC 1920+）（#GH70899） 修正了成员指针类型的 auto 非类型模板参数的名称修饰，以匹配 MSVC 1920+ 的行为。与上述指针类型修复类似，需要使用 -fms-compatibility-version=19.14 来保持与旧版 Clang 编译代码的向后兼容。

MSVC 调用约定修复

5. 含模板构造函数的类（#GH86384） 如果一个类包含模板构造函数，则该类应通过间接方式返回（indirect return），即使它满足在寄存器中返回类的所有其他要求。此变更影响某些 std::pair 的使用场景。
6. 含删除拷贝赋值运算符的类 如果一个类包含已删除的拷贝赋值运算符（deleted copy assignment operator），则该类应通过间接方式返回（indirect return）。
对数通设备的影响 这些 MSVC ABI 修复主要影响 Windows 平台上的 MSVC 互操作场景。对于 Linux AArch64 上的数通产品线，影响范围有限。但如果存在交叉编译到 Windows/x86 的测试环境，或使用了 MSVC 兼容模式的代码与 MSVC 编译的库链接，需要注意这些 ABI 变更。使用 -fms-compatibility-version=19.14 可保持与旧版 Clang 的向前兼容。
链接器变更 LLD ELF 关键变更汇总
LLD 19 引入多项重要改进 LLD ELF 链接器在 LLVM 19 中引入了多项变更，涉及默认行为、压缩、调试信息、链接脚本等。

--build-id 默认变更

从 8 字节 fast 改为 20 字节 sha1 --build-id 现在默认生成 20 字节摘要（sha1），而非之前的 8 字节摘要（fast）。此变更改善了与 RPM 打包工具的兼容性。若需旧行为，可显式指定 --build-id=fast。（#93943）

CREL 实验性重定位

实验性功能，无版本兼容性保证 现在支持带有显式 addend 的 CREL（压缩重定位）格式，使用临时节类型代码 0x40000020（clang -c -Wa,--crel,--allow-experimental-crel）。LLVM 将更改此代码并破坏兼容性——Clang 和不同版本的 lld 之间不保证协作。不支持隐式 addend 的 CREL。（#98115）

--compress-sections

新增选项 --compress-sections <section-glob>={none,zlib,zstd}[:level] 用于压缩匹配的非 SHF_ALLOC 输出节。（#84855、#90567）

--debug-names

新增选项 --debug-names 从输入的 .debug_names 节创建合并的 .debug_names 索引。Type units 尚未处理。（#86508）

EI_OSABI 推断

行为变更 输出的 EI_OSABI 字段现在从输入的目标文件中推断，而非总是使用默认值。（#97144）

--enable-non-contiguous-regions

新增选项 --enable-non-contiguous-regions 允许在 MEMORY 区域溢出时自动将输入段装到匹配的后续区域。这减少了手动打包区域的繁琐工作（典型场景：嵌入式开发）。这也使得全 LTO 在这种情况下可行，因为 IR 合并之前会阻止链接脚本引用输入文件。（#90007）

zlib 默认压缩级别

行为变更 zlib 的默认压缩级别现在独立于链接器优化级别，固定为 Z_BEST_SPEED，以获得更快的链接速度。

zstd 多线程

构建依赖变更 zstd 压缩的并行处理不再要求构建时启用 ZSTD_MULTITHREAD。

GNU_PROPERTY_AARCH64_FEATURE_PAUTH

新增支持 LLD 现在支持 GNU_PROPERTY_AARCH64_FEATURE_PAUTH notes、R_AARCH64_AUTH_ABS64 和 R_AARCH64_AUTH_RELATIVE 重定位类型。（#72714）

其他 LLD 改进

  • -z pack-relative-relocs：当 AArch64 PAuth 启用时，现在在 .rela.auth.dyn 中编码 R_AARCH64_AUTH_RELATIVE 重定位。（#96496）
  • -z gcs / -z gcs-report：AArch64 Guarded Control Stack 扩展支持。
  • --default-script / -dT：指定默认链接脚本（当 --script/-T 未指定时处理）。
  • --force-group-allocation：丢弃 SHT_GROUP 节并合并重定位节。
  • -z lrodata-after-bss：将 .lrodata 放在 .bss 之后。
  • --export-dynamic 在 -no-pie 静态链接时不再创建动态节。
  • Thumb2 PLT：现在支持 Cortex-M 处理器的 Thumb PLT。（#93644）
对数通设备的价值 --enable-non-contiguous-regions 对嵌入式场景尤其有用，可自动处理内存区域溢出；--compress-sections 和 zstd 改进可减小固件体积；GNU_PROPERTY_AARCH64_FEATURE_PAUTH 和 GCS 支持完善了 AArch64 安全特性的链接器端处理。
基础设施变更 LLVM IR 关键变更
多项 IR 层面的重要变更 LLVM 19 在 IR 层面引入了多项变更，包括 constexpr 移除、debug records 切换、新 GEP 标志、MMRAs 和 MC/DC 语义变更。

icmp/fcmp/shl constexpr 移除

破坏性变更 以下指令的常量表达式变体已被移除：icmp、fcmp、shl。任何使用这些 constexpr 的 IR 可能需要在升级时更新。这些移除是 LLVM 逐步淘汰 constexpr 的持续工作的一部分。
需要更新的 IR 模式
; 旧 IR（LLVM 18 及之前）：允许 icmp constexpr
@g = global i1 icmp eq (i32 ptrtoint (ptr @foo to i32), i32 0)

; LLVM 19：不再支持 icmp constexpr，
; 需改为在函数体内计算或使用其他方式表达

Debug intrinsics 切换到 Debug records

IR 表示层重大重构 LLVM 19 将 LLVM IR 中的调试信息基础设施从"debug intrinsics"（llvm.dbg.value、llvm.dbg.declare 等）切换为"debug records"——一种不嵌入指令流的独立调试数据表示。这是 LLVM 调试信息子系统自 2010 年以来最大的一次架构变更。

传统的 debug intrinsics 作为 IR 指令嵌入在基本块中，与普通指令混合。这种设计要求优化 pass 专门处理 debug intrinsics，增加了每个 pass 的复杂度，且 debug intrinsics 可能干扰优化决策。Debug records 将这些调试信息从指令流中分离，存储为指令的附加标记，使优化 pass 可以在不感知调试信息的情况下正常工作。

IR 表示对比（概念层面）
旧：Debug Intrinsics（LLVM 18 及之前）
; Debug info 作为 IR 指令嵌入指令流
  %x = add i32 %a, %b
  call void @llvm.dbg.value(metadata i32 %x, ...)
  %y = mul i32 %x, %c
  call void @llvm.dbg.value(metadata i32 %y, ...)
  store i32 %y, ptr %p

; 所有优化 pass 必须处理这些 dbg 调用
新：Debug Records（LLVM 19+）
; Debug info 作为指令的附属数据
  %x = add i32 %a, %b    #+dbg(value: %x)
  %y = mul i32 %x, %c    #+dbg(value: %y)
  store i32 %y, ptr %p

; 优化 pass 无需感知 debug records
; 指令移动/删除时 debug info 自动跟随

nusw / nuw GEP 标志

getelementptr 指令新增了 nusw（No Unsigned Signed Wrap）和 nuw（No Unsigned Wrap）标志。这些标志为指针算术提供了无符号/有符号溢出保证，使优化器能够基于这些不变式进行更激进的优化。

MMRAs（Memory Model Relaxation Annotations）

新增了 Memory Model Relaxation Annotations（MMRAs），用于标注内存访问操作的内存模型宽松语义信息。这些注解帮助优化器在符合内存模型约束的前提下进行更精确的代码变换。

MC/DC 语义变更

MC/DC intrinsics 语义调整 MC/DC（Modified Condition/Decision Coverage）相关 intrinsics 的语义发生变化：llvm.instprof.mcdc.parameters 的第 3 个参数从字节改为位；llvm.instprof.mcdc.condbitmap.update 已移除；llvm.instprof.mcdc.tvbitmap.update 的第 3 个参数已移除，下一个参数从字节索引改为位索引。
对数通产品线的影响 icmp/fcmp/shl constexpr 移除主要影响手写 LLVM IR 的工具和下游 pass。Debug records 切换对大多数用户透明，LLVM 19 仍能读取旧式 IR 并自动转换。nusw/nuw GEP 和 MMRAs 是优化器改进，对前端用户透明。MC/DC 语义变更影响代码覆盖率工具的用户。数通设备开发者若维护了自定义 LLVM pass，需要适配 debug records API。
ISA 移除 3DNow! 完全移除 / Intel KNL/KNM 移除
不可逆的移除 LLVM 19 从代码库中完全删除了以下 ISA 支持：AMD 3DNow! 指令集的所有 intrinsics 和 code generation 支持，以及 Intel Xeon Phi Knights Landing（KNL）和 Knights Mill（KNM）微架构支持。

3DNow! 移除详情

3DNow! 是 AMD 于 1998 年在 K6-2 处理器上引入的 SIMD 指令集扩展，用于加速 3D 图形和浮点运算。该指令集已被 AMD 废弃多年：

  • 2010 年：AMD 在 Bulldozer 架构中停止支持 3DNow!（除 PREFETCH/PREFETCHW 指令外）
  • 2011 年：GCC 4.7 移除 3DNow! intrinsics 支持
  • 2019 年：GCC 9 完全移除后端支持
  • 2024 年：LLVM 19 完全移除所有 3DNow! 支持
受影响的 intrinsics（部分列表）
// 以下 intrinsics 已从 <mm3dnow.h> 和 <x86intrin.h> 中移除：

// 浮点 SIMD 操作
__m64 _m_pfadd(__m64, __m64);     // 已移除
__m64 _m_pfsub(__m64, __m64);     // 已移除
__m64 _m_pfmul(__m64, __m64);     // 已移除
void _m_prefetch(void*);       // 已移除（改用 _mm_prefetch）

// 整数 SIMD 操作（3DNow! 扩展）
__m64 _m_pavgusb(__m64, __m64);    // 已移除
void _m_femms(void);            // 已移除（改用 _mm_empty）

// 三角函数近似
__m64 _m_pf2iw(__m64);            // 已移除
__m64 _m_pi2fw(__m64);            // 已移除

Intel KNL/KNM 移除详情

Intel Xeon Phi Knights Landing（KNL，knl）和 Knights Mill（KNM，knm）是 Intel 的众核架构产品线，已于 2018-2020 年间停产。LLVM 19 移除了对这两个目标的专门支持和调优。

受影响的编译选项
# 以下 -march/-mtune 目标不再可用：
clang -march=knl example.c    # ERROR: unknown target CPU 'knl'
clang -march=knm example.c    # ERROR: unknown target CPU 'knm'
clang -mtune=knl example.c    # ERROR: unknown target CPU 'knl'
clang -mtune=knm example.c    # ERROR: unknown target CPU 'knm'
对数通设备的影响 数通产品线主要面向 AArch64 平台，3DNow! 和 KNL/KNM 移除基本无影响。但如果构建系统中有 x86 回退路径、仿真测试环境或交叉编译脚本引用了 -march=knl/-march=knm 或 3DNow! intrinsics，需要清理或更新这些引用。使用 3DNow! 指令的遗留 x86 代码需要迁移到 SSE/AVX 指令集。
弃用与移除 -Ofast 弃用 / LLVM_ENABLE_TERMINFO 移除 / Python 3.8

-Ofast 已弃用

编译器标志变更 -Ofast 命令行选项已被弃用。该选项同时启用 -O3 优化级别和非标准的 -ffast-math 行为，因此作为"优化级别"具有误导性。建议用户改用 -O3 -ffast-math（如需非标准数学行为）或 -O3（标准行为）。详见 RFC。

LLVM_ENABLE_TERMINFO 移除

构建系统变更 LLVM_ENABLE_TERMINFO CMake 标志已被移除。LLVM 不再依赖 terminfo，现在始终使用 TERM 环境变量进行颜色支持自动检测。

Python 最低版本 3.6 → 3.8

依赖变更 整个 LLVM 项目的最低 Python 版本已从 3.6 提升到 3.8。这使得可以使用更多现代 Python 特性，使代码更接近现代 Python 最佳实践，并改善 CI 可维护性。详见 #78828。
对数通设备的影响 -Ofast 弃用意味着现有构建脚本中的 -Ofast 应替换为 -O3 -ffast-math（或仅 -O3）。Python 3.8 要求影响构建服务器——确保构建环境中的 Python 版本不低于 3.8（对于使用较旧 LTS 发行版的构建服务器，可能需要注意此变更）。
安全特性 Guarded Control Stack (GCS) 链接器支持
AArch64 硬件安全栈 LLVM 19 为 LLD 链接器添加了 AArch64 Guarded Control Stack（GCS）支持，通过 -z gcs 和 -z gcs-report 选项控制。GCS 是 ARMv9.4-A 引入的硬件特性（FEAT_GCS），提供硬件级别的返回地址完整性保护。

GCS 工作原理

Guarded Control Stack 在硬件层面维护一个独立的、仅可被特定指令写入的"影子栈"。函数调用时，返回地址被同时压入常规栈和 GCS 影子栈。函数返回时，硬件自动比对两个栈上的返回地址——如果不匹配，说明返回地址被篡改，触发异常。

GCS 与 PAC-RET 互补：

  • PAC-RET：签名/验证返回地址，防止伪造（但无法防止重放攻击）
  • GCS：维护完整的返回地址链，防止任何形式的篡改（包括重放）

链接器选项

-z gcs — 启用 GCS 支持
# 编译目标文件（编译器端标记 GCS 特性）
clang -target aarch64-linux-gnu \
      -march=armv9.4-a \
      -mbranch-protection=gcs \
      -c example.c

# 链接时启用 GCS（lld / ld.lld）
ld.lld -z gcs -o output example.o

# 完整示例：GCS + BTI + PAC-RET 组合保护
clang -target aarch64-linux-gnu \
      -march=armv9.4-a \
      -mbranch-protection=bti+pac-ret+gcs \
      -O2 -c example.c

ld.lld -z gcs -o example example.o
-z gcs-report — 报告 GCS 兼容性
# 仅报告哪些目标文件支持/不支持 GCS，不实际启用
ld.lld -z gcs-report -o output *.o

# 典型输出：
#   module_a.o: GCS compatible
#   module_b.o: GCS compatible
#   legacy.o:   NOT GCS compatible (missing .note.gnu.property)
# （静态链接场景需所有目标文件都标记 GCS 兼容）

对嵌入式网络设备的意义

  • 纵深防御：GCS + PAC-RET + BTI 构成完整的控制流完整性三层防护（间接跳转保护 + 返回地址签名 + 硬件影子栈）
  • 硬件强制：GCS 由硬件直接执行检查，旁路难度远高于软件 shadow stack
  • 零运行时开销：GCS 的检查由硬件在返回指令执行时自动完成，基本无性能开销
  • 固件级保护：嵌入式设备固件往往缺乏地址空间随机化，GCS 硬件保护尤为关键
迁移注意事项 GCS 需要 ARMv9.4-A（FEAT_GCS）硬件支持。对于运行在较旧 ARM 平台上的设备，此功能不可用但也不会造成问题。-z gcs 和 -z gcs-report 是 LLD 特有的选项；如果使用 GNU ld 或 gold，需参考各自对应的选项。GCS 与 PAuth-LR 可以同时使用，提供互补的保护。
