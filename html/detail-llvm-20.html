🛡 1. TBAA 默认启用 最高风险

Clang 20 起对不兼容指针生成不同的 Type-Based Alias Analysis (TBAA) 标签。 编译器据此假定不同类型的指针永不别名（即永不指向同一内存），从而启用更强力的别名分析优化。 这一变更可能导致过去靠"侥幸"运行的 strict aliasing 违规代码在 LLVM 20 下产生错误结果。
⚠ 最高风险 🔧 需代码修复 💡 可临时禁用

🐞 示例 1：Strict Aliasing 违规（错误代码）

旧行为 (LLVM < 20)

int foo(float *f, int *i) {
  *i = 1;      // 向 int 写入
  *f = 2.0f;   // 向 float 写入（通过不同指针类型）
  return *i;   // 老编译器返回 1
}
// 编译器未积极利用 TBAA，两个 store、一个 load 顺序执行

新行为 (LLVM 20+)

int foo(float *f, int *i) {
  *i = 1;      // TBAA 标签: int
  *f = 2.0f;   // TBAA 标签: float — 与 int 不别名
  return *i;   // 编译器可能直接返回 1（常量折叠）
               // 或更糟：重排顺序后返回 2
}
// TBAA 认为 float* 写不改变 *i，因此可以重排甚至消除 load

⚠ 注意：此代码违反 C 标准 strict aliasing 规则，旧版本碰巧"能跑"，LLVM 20 将积极利用该规则进行优化。

✅ 示例 2：正确的 Union-based Aliasing

修复方案

union Buffer {
  int   as_int;
  float as_float;
};

int foo_correct(float *f, int *i) {
  union Buffer u;
  u.as_int = 1;      // 通过 union 写入 int
  u.as_float = 2.0f; // 通过 union 写入 float — 合法
  return u.as_int;   // 行为明确
}

✔ 通过 union 访问不同类型是标准允许的 aliasing 方式。

💡 应对措施

1. 临时迁回：添加编译选项 -fno-pointer-tbaa 禁用基于指针类型的 TBAA，使行为与老版本一致。

2. 根本修复：排查代码中的 strict aliasing 违规，改用 union 或 memcpy 进行跨类型访问。

3. 检测工具：启用 -Wstrict-aliasing 和 -fstrict-aliasing 配合静态分析工具扫描潜在违规。

建议：先用 -fno-pointer-tbaa 稳定迁移，确认功能正确后，再逐步修复代码中的 strict aliasing 违规并移除该标志。

🛡 2. 指针溢出 UB 积极优化 最高风险

在 C/C++ 标准中，构造超出对象边界一个元素以上的指针是未定义行为 (UB)。 LLVM 20 开始更积极地利用这一事实进行优化：ptr + unsigned_offset < ptr 这类传统上用于边界检查的模式，现在会被优化为 false（因为如果指针加法溢出了，程序就已经是 UB）。
⚠ 最高风险 🔧 需代码修复 ⚠ -fwrapv 不再覆盖指针

🐞 示例：典型的边界检查代码

旧行为 (LLVM < 20)

// 一种常见的溢出检查模式
void process_buffer(char *buf, size_t len) {
  char *end = buf + len;
  if (end < buf) {  // 检查指针加法是否回绕
    handle_overflow();
    return;
  }
  // ... 正常处理 ...
}
// 旧编译器不会优化掉这个比较

新行为 (LLVM 20+)

// 同样的代码，LLVM 20 的优化：
void process_buffer(char *buf, size_t len) {
  char *end = buf + len;
  if (end < buf) {  // 优化为 false！
    handle_overflow();   // 此分支被消除，不会生成代码
    return;
  }
  // 编译器推理：如果 buf+len 真的溢出了，程序就是 UB
  // 因此编译器假定这永远不会发生，直接删除溢出检查
}

⚠ 这是一个非常危险的变更：运行了数十年的边界检查代码可能在静默中被优化消除，导致缓冲区溢出漏洞。

✅ 修复方案 1：使用整数运算

推荐修复

#include <stdint.h>

void process_buffer(char *buf, size_t len) {
  // 将指针转为整数后再做溢出检查 — 整数溢出行为是明确的
  uintptr_t buf_addr = (uintptr_t)buf;
  if (buf_addr + len < buf_addr) {  // 整数运算，行为确定
    handle_overflow();
    return;
  }
  // ... 安全处理 ...
}

✅ 修复方案 2：只用偏移量比较

替代方案

// 将 "ptr+offset < end_ptr && ptr+offset >= ptr"
// 改写为纯偏移量比较
if (offset < (uintptr_t)(end_ptr - ptr)) {
  // offset 在有效范围内
}
💡 关键提醒

1. -fwrapv 不再有效：LLVM 20 中该标志只控制有符号整数溢出，不控制指针溢出。必须单独使用 -fwrapv-pointer。

2. 排查范围：搜索代码库中 ptr + N < ptr、ptr + N >= ptr 等涉及指针溢出的比较模式。

3. 检测工具：可使用 -fsanitize=pointer-overflow 在运行时检测指针溢出 UB。

4. 推荐方案：将指针比较改为 uintptr_t 整数比较，这是最可移植且不依赖编译器标志的修复方式。

⚠ 3. -fwrapv / -fwrapv-pointer 语义变更 行为变更

LLVM 20 对几个关键的溢出控制标志进行了重新定义，使其与 GCC 行为对齐：
  • -fwrapv：仅控制有符号整数溢出（不再影响指针溢出）
  • -fwrapv-pointer：新增标志，独立控制指针溢出行为
  • -fno-strict-overflow：现在隐含 -fwrapv 和 -fwrapv-pointer 两者
⚠ 行为变更 💡 需评估构建系统

🐞 示例：-fwrapv 不再覆盖指针

旧行为 (LLVM < 20)

# 旧命令：-fwrapv 被认为同时覆盖整数和指针溢出
clang -fwrapv -O2 foo.c
# 结果：有符号整数溢出为 wrapping，指针加法溢出也类似

新行为 (LLVM 20+)

# -fwrapv 只控制有符号整数溢出
clang -fwrapv -O2 foo.c
# 结果：
#   有符号整数溢出 → wrapping（正常）
#   指针加法溢出   → UB（不会被 -fwrapv 覆盖！）

# 正确做法：同时添加两个标志
clang -fwrapv -fwrapv-pointer -O2 foo.c

# 或使用 -fno-strict-overflow（等价于两者）
clang -fno-strict-overflow -O2 foo.c
💡 clang-cl 注意事项

LLVM 20 中 clang-cl 也支持 -fno-strict-overflow、-fwrapv 和 -fwrapv-pointer，行为与 clang 一致。

💡 建议

1. 检查构建系统：查找所有使用 -fwrapv 的构建配置，评估是否需要添加 -fwrapv-pointer。

2. 生产环境推荐：如果项目历史上有指针溢出相关 bug 或依赖指针回绕行为，建议启用 -fwrapv-pointer 作为安全过渡措施。

3. 长期方向：逐步将指针溢出检查改为 uintptr_t 方案，消除对编译器标志的依赖。

📚 4. enum constexpr 转换不可压制 硬错误

C++ 标准要求 constexpr 上下文中枚举值必须在声明的枚举器范围内。 LLVM 20 开始严格执行这一规则：将超出范围的整数值显式转换为枚举类型不再被允许为常量表达式， 且此错误无法通过 -Wno-* 等警告标志压制。 LLVM 16~19 期间可用 -Wno-enum-constexpr-conversion 压制，现在该选项不再有效。
❌ 硬错误 🔧 需代码修复

🐞 示例：超出范围的 enum constexpr

旧行为 (LLVM 16–19)

enum E { Zero, One, Two, Three, Four };

constexpr E Val1 = (E)3;   // Ok
constexpr E Val2 = (E)7;   // Ok, 在范围 [0,7] 内
constexpr E Val3 = (E)8;   // 警告（可用 -Wno-enum-constexpr-conversion 压制）
constexpr E Val4 = (E)-1;  // 警告（可压制）

新行为 (LLVM 20+)

enum E { Zero, One, Two, Three, Four };

constexpr E Val3 = (E)8;   // error: 常量表达式中枚举值超出范围 [0,7]
constexpr E Val4 = (E)-1;  // error: 超出范围
// -Wno-enum-constexpr-conversion 不再有效，必须修复源代码

✅ 修复方案

做法 1：去掉 constexpr

E v = (E)8;  // 去掉 constexpr，不再是常量表达式上下文

做法 2：使用固定底层类型的 scoped enum

enum class E : int { Zero, One, Two, Three, Four };
constexpr E v = static_cast<E>(8);  // scoped enum + 固定底层类型允许任意值

做法 3：扩展枚举定义

enum E { Zero, One, Two, Three, Four, Five, Six, Seven, Eight = 8 };
constexpr E v = Eight;
💡 建议

• 用 grep -rn "constexpr.*(E)\|constexpr.*static_cast.*enum" 搜索涉及的 constexpr 枚举转换。

• 优先采用方案 1（去掉 constexpr）或方案 3（扩展枚举定义），避免未定义行为。

📚 5. __is_nullptr 移除 / __is_referenceable 弃用

LLVM 20 对两个使用率极低的 Clang 内置类型特征进行了清理。
❌ __is_nullptr 已移除 ⚠ __is_referenceable 已弃用 🔧 需代码修复

5.1 __is_nullptr 已移除

__is_nullptr(T) 内置类型特征已被直接移除。该特征使用量极少，且可用 GCC 兼容写法替代。

✅ 替代写法

// 取代 __is_nullptr(T)
// 等价于 GCC 也支持的写法
__is_same(__remove_cv(T), decltype(nullptr))

5.2 __is_referenceable 已弃用

__is_referenceable(T) 已被标记为弃用，将在 Clang 21 中移除。该特征使用量极少， 且标准库中所有可能依赖它的类型特征均已拥有专用的内置实现。
💡 建议

• 搜索代码中 __is_nullptr 和 __is_referenceable 的使用，替换为标准类型特征。

• 这些特征极少在业务代码中直接使用，大多数项目不受影响。

📚 6. _Complex _BitInt 被拒绝

Clang 20 现在拒绝 _Complex _BitInt(N) 类型组合。这个组合在标准中没有明确定义， 之前 Clang 可能接受但生成不正确的代码。现在编译器直接报错拒绝。
❌ 编译报错 🔧 需代码修复

🐞 示例

旧行为 (LLVM < 20)

_Complex _BitInt(128) x;  // 可能通过编译，行为不明

新行为 (LLVM 20+)

_Complex _BitInt(128) x;  // error: _Complex _BitInt is not supported
💡 建议

• 此组合极少被使用，绝大多数项目不受影响。

• 如需表示高精度复数，使用两个独立的 _BitInt 变量分别表示实部和虚部，或使用结构体封装。

📚 7. -Wdeprecated-literal-operator 默认启用

-Wdeprecated-literal-operator 警告现在默认启用。 WG21 已表示有兴趣从语言中移除此语法，Clang 20 开始默认警告。 使用 -Werror 的项目将会因此编译失败。 此变更与 CWG2521 决议一致。
⚠ 警告变更 🔧 修复简单

🐞 示例：字面量运算符声明

旧写法（已弃用）

// operator"" 与后缀名之间有空格 — 已弃用
unsigned operator"" _udl_name(unsigned long long);

正确写法

// 去掉空格即可，修复极其简单
unsigned operator""_udl_name(unsigned long long);
💡 建议

• 搜索代码中 operator"" （带空格）的模式，将空格删除即可。

• 此修复简单直接，风险极低。

📚 8. 多余 template header 默认报错 硬错误

C++ 标准要求显式特化声明前不应有多余的 template<> 头。 例如嵌套的 template<> template <typename T> 在规范上非法， LLVM 20 将此从警告升级为默认报错。 可使用 -Wno-error=extraneous-template-head 临时降级为警告。
❌ 硬错误 🔧 需代码修复

🐞 示例：错误的多余 template head

旧行为 (LLVM < 20)

template <>              // 多余的 template<> 头
template <typename T>    // C++ 标准要求此处不应有 template<>
void f();                // 旧编译器：警告（可能被忽略）

新行为 (LLVM 20+)

template <>              // error: extraneous template head
template <typename T>
void f();
// LLVM 20 默认报错，编译失败

✅ 修复方案

删除多余的 template<>

// 正确的写法：去掉多余的 template<>
template <typename T>
void f();
💡 建议

• 搜索代码中 template <> 后紧跟 template < 的模式，删除多余的 template head。

• 此修复简单直接，通常只需删除一行。

📚 9. 字符串字面量比较 CWG2765 行为变更

Clang 20 按照核心议题 CWG2765 的预期方向， 修改了常量求值中对字符串字面量比较的处理。 同一字符串字面量的不同求值结果之间的比较现在被视为非常量（因为它们可能指向不同内存）， 而绝不可能重叠的字符串字面量之间的比较现在被视为常量。 注意：此行为仍可能在 CWG2765 决议后变化。
⚠ 行为变更 💡 影响 constexpr 代码

🐞 示例：constexpr 中字符串比较

旧行为 (LLVM < 20)

constexpr const char *f() { return "hello"; }
constexpr const char *g() { return "world"; }
// 旧行为：求值为 false
constexpr bool a = f() == f();
// 旧行为：因无法确定是否重叠而报错
constexpr bool b = f() == g();

新行为 (LLVM 20+)

constexpr const char *f() { return "hello"; }
constexpr const char *g() { return "world"; }
// 新行为：error: 非常量比较（不同求值可能返回不同地址）
constexpr bool a = f() == f();
// 运行时仍然有效
bool at_runtime() { return f() == f(); }
// 新行为：求值为 false（"hello" 与 "world" 不可能重叠）
constexpr bool b = f() == g();
💡 建议

• 在 constexpr 上下文中，避免依赖字符串字面量地址的比较。使用 __builtin_strcmp 或比较内容。

• 如果使用编译期字符串散列或类似技术，需要考虑此变更的影响。

📚 10. [[clang::lifetimebound]] 错误诊断 硬错误

[[clang::lifetimebound]] 属性现在有更严格的语法检查。 以前被静默忽略的错误用法现在会直接编译报错。
❌ 硬错误 🔧 需代码修复

10.1 void 返回函数上使用 lifetimebound — 现在报错

LLVM 20+ 报错

// error: 'lifetimebound' attribute cannot be applied to a parameter of
//        a function that returns void
void f(int& i [[clang::lifetimebound]]);

10.2 在类型（非参数）上使用 lifetimebound — 现在报错

LLVM 20+ 报错

// error: 'lifetimebound' attribute only applies to function parameters
int* [[clang::lifetimebound]] x;

// error: 在类型上（非参数声明）
void f(int* [[clang::lifetimebound]] i);

// error: 未命名参数
void g(int* [[clang::lifetimebound]]);
💡 补充

LLVM 20 还新增了 [[clang::lifetime_capture_by(X)]] 属性，可指定函数参数引用的生命周期被实体 X 捕获。

💡 建议

• 将 lifetimebound 属性仅应用在有返回值的函数参数上（且参数为引用或指针类型）。

• 在 void 返回函数上使用 lifetimebound 本就是无意义的用法，直接删除即可。

💳 11. ABI 名称修饰变更 ABI 变更

LLVM 20 包含三项 ABI 层面的名称修饰 (name mangling) 修正。 这些修正可能导致与旧版本 Clang 编译的代码链接不兼容。 影响 C++ ABI 的符号名称，需要使用统一编译器版本全量重编，或使用兼容选项。
⚠ ABI 变更 💡 可用 -fclang-abi-compat=19

11.1 Itanium 构造 vtable 名称修正

修正了 Itanium C++ ABI 下构造 vtable (construction vtable) 的符号名称生成错误。 构造 vtable 用于虚基类子对象的构造/析构期间，受影响的场景包括包含虚基类的继承层次结构。 可使用 -fclang-abi-compat=19 恢复旧行为。 
// 涉及虚基类的继承层次结构
struct Base { virtual ~Base(); };
struct Derived : virtual Base { virtual ~Derived(); };
// LLVM 20: 构造 vtable 符号名称可能改变

11.2 成员式友元函数模板名称修饰

成员式的友元函数模板 (member-like friend function templates) 现在被修饰为 封闭类的成员。这更符合 Itanium ABI 规范。 可使用 -fclang-abi-compat=19 恢复旧行为。

11.3 MSVC 名称修饰修正

修正了 MSVC 1920+ 下 placeholder、auto 和 decltype(auto) 返回类型的名称修饰，与 MSVC 行为对齐。与早期 Clang 版本不兼容， 除非使用 -fms-compatibility-version=19.14 模拟 MSVC 1914 修饰行为。
💡 建议

• 全量重编：升级编译器后对所有 C++ 代码进行全量重编译，避免新旧 ABI 混用。

• 过渡期：如有无法立即重编的预编译库，使用 -fclang-abi-compat=19 或 -fms-compatibility-version=19.14 保持兼容。

• 影响面：Item 11.1 仅涉及带虚基类的复杂继承体系；Item 11.2 涉及类内友元模板；Item 11.3 仅影响 Windows MSVC ABI。

🔄 12. 目标平台与工具移除

LLVM 20 移除了几个不再活跃维护的目标平台和工具。
⚠ 移除 💡 需检查构建配置

12.1 le32 / le64 目标移除

le32 和 le64 目标已移除。这些目标主要用于 PNaCl (Portable Native Client)，该技术已不再活跃维护。 
# 以下目标三元组不再有效
-target le32-unknown-nacl
-target le64-unknown-nacl
# error: unknown target triple

12.2 RenderScript 目标移除

RenderScript 目标支持已被移除。Android 已正式弃用 RenderScript， 用户应迁移至 Vulkan 或其他方案。

12.3 clang-rename 工具移除

clang-rename 工具已被移除。该工具使用率低，建议使用 clangd 的 rename 功能或其他替代方案。
💡 建议

• le32/le64 / RenderScript：一般 Linux/x86-64/ARM 项目不受影响。

• clang-rename：检查 CI 或构建脚本中是否使用了 clang-rename，迁移至 clangd。

📚 13. SPARC: clang -m32 默认 -mcpu=v9

在 SPARC Linux 上，clang -m32 现在默认使用 -mcpu=v9。 仍需要支持 SPARC V8 CPU 的发行版需要通过 配置文件 显式指定 -mcpu=v8。
⚠ 行为变更 💡 仅影响 SPARC 
# SPARC Linux 上
clang -m32 foo.c    # 默认 -mcpu=v9（新增行为）
clang -m32 -mcpu=v8 foo.c  # 如需兼容 V8 需显式指定
💡 建议

• 非 SPARC 平台完全不受影响。

🔍 14. LLD 20 重要改进 新功能

LLD 20 引入了多项重要新功能和行为变更，涵盖 ELF、COFF、MinGW 和 MachO 后端。
💡 ELF 新功能 ⚠ 行为变更

14.1 ELF 重要新功能

  • -z nosectionheader：省略 section header table，类似 llvm-objcopy --strip-sections，可用于减小二进制体积。
  • --randomize-section-padding=<seed>：在输入 section 之间和每个 segment 起始处插入随机填充，可用于 A/B 实验测量偏差控制。
  • --symbol-ordering-file 与 call graph profile 现在可以同时使用，两者共同优化函数布局。
  • --call-graph-ordering-file：指定此选项后，可重定位文件中的 .llvm.call-graph-profile 段不再被使用。
  • --lto-basic-block-sections=labels 已弃用，使用 --lto-basic-block-address-map 替代。

14.2 ELF 行为变更

  • .note.GNU-stack exec 检查：非可重定位链接中，带有 SHF_EXECINSTR 标志的 .note.GNU-stack 段现在被拒绝，除非指定 -z execstack。
  • Section CLASS 语法：链接器脚本新增 CLASS 语法，可将输入 section 绑定到命名类别，提供对 --enable-non-contiguous-regions 自动溢出的精细控制。
  • INCLUDE 循环检测：链接器脚本的 INCLUDE 循环检测已修复，同一个脚本可以被包含两次。
  • archivename: 语法：匹配输入 section 时现在支持 archivename: 前缀语法。

14.3 AArch64 / x86-64 / LoongArch 改进

  • AArch64：支持 BTI-aware 长分支 thunk 到无 BTI 指令的目标函数；支持 GOT/TLSDESC 的指针认证 ABI 重定位。
  • x86-64：新增多种 GOT/TPOFF/TLSDESC 的 CODE_4/CODE_6 重定位类型支持。
  • LoongArch：支持 TLS LD/GD/DESC 的 PCREL20_S2 重定位类型。

14.4 COFF / MinGW / MachO

  • COFF：/includeglob（匹配 ELF 的 --undefined-glob）；/lldsavetemps 保存 LTO 中间结果；/machine:arm64ec 支持 ARM64EC 镜像链接；COFF weak anti-dependency alias 符号支持。
  • MinGW：--undefined-glob 现在通过转换为 /includeglob 标志支持。
  • Break change：已移除对 RISC-V 已弃用的 R_RISCV_RVC_LUI 重定位支持。
💡 建议

• -z nosectionheader 可用于减小生产二进制体积，但会丢失 section header 信息（影响某些调试工具）。

• .note.GNU-stack exec 检查 可能影响使用手写汇编且未正确标注栈可执行属性的项目。

• --randomize-section-padding 对安全和 A/B 测试有用，但会小幅增加二进制体积。

🔍 15. AArch64 后端改进 新功能

AArch64 后端在 LLVM 20 中有多项重要更新，包括对齐填充行为变更和新 CPU 支持。
⚠ 行为变更 💡 新架构支持

15.1 .balign N,0 对齐填充行为变更

在代码段中，.balign N, 0、.p2align N, 0、.align N, 0 现在使用 0x0 字节序列填充，而非 NOP 指令。 此变更同时影响 AArch64、ARM、RISC-V、LoongArch 等多个后端。 如果仍需要 NOP 填充，省略填充值参数即可（.balign N 等）。 
# 代码段中
.balign 16, 0     # LLVM 20: 填充 0x00 字节（而非 NOP 指令）
.balign 16        # 仍然填充优化的 NOP 指令（未指定填充值）

15.2 Armv9.6-A 架构支持

汇编器/反汇编器已添加对 Armv9.6-A (2024) 架构扩展的支持，包括 FEAT_FAMINMAX、FEAT_LUT、FEAT_FP8 等特性。

15.3 FUJITSU-MONAKA CPU 支持

新增对 FUJITSU-MONAKA CPU 的支持，可通过 -mcpu=fujitsu-monaka 启用。

15.4 其他改进

  • SVE2.1 和 SME2.1 的 ACLE 实现现已可用。
  • SME 关键字属性现在体现在函数类型的名称修饰中。
  • 新增 __arm_agnostic 关键字属性。
  • Function Multi Versioning 的运行时特性检测已按 ACLE 规范实现。
💡 建议

• .balign N,0 变更：如果项目中的手写汇编或内联汇编依赖 NOP 填充（例如某些安全加固技术），需要检查并适配。

• 一般 C/C++ 项目代码不受 AArch64 对齐变更影响，编译器自动生成的填充行为不变。

🔍 16. Realtime Sanitizer (RTSan) + Sanitizer 改进 新功能

LLVM 20 引入了全新的 Realtime Sanitizer 以及多项 Sanitizer 基础设施改进。
💡 新 Sanitizer 🔧 诊断增强

16.1 Realtime Sanitizer (RTSan)

RTSan 是一个全新的 Sanitizer，通过 -fsanitize=realtime 启用。 它可以检测实时上下文中的不安全系统库调用，如内存分配和互斥锁操作。 如果任何此类函数在标记为 [[clang::nonblocking]] 的函数中被调用， RTSan 会输出错误信息并异常退出。

🐞 示例

[[clang::nonblocking]]
void process_audio() {
  // RTSan 会在运行时检测并报错：
  void *buf = malloc(1024);  // 错误：在 nonblocking 上下文中调用 malloc
  mutex.lock();              // 错误：在 nonblocking 上下文中获取互斥锁
}

// 编译时启用 RTSan
// clang -fsanitize=realtime audio.c

16.2 Sanitizer Special Case List (SSCL) 改进

SSCL 现在对更多 sanitizer 类型正确支持 type: 前缀， 包括 signed-integer-overflow、unsigned-integer-overflow、 implicit-signed-integer-truncation、implicit-unsigned-integer-truncation、 enum 等类型。 这允许在 supression 文件中按类型精确控制 sanitizer 行为。

16.3 其他 Sanitizer 改进

  • -fsanitize-undefined-ignore-overflow-pattern：新标志，可忽略特定整数溢出模式（如 add-mul、negated-unsigned-const、unsigned-post-decr-while），减少已有项目启用整数 sanitizer 时的噪音。
  • Type Sanitizer (实验性)：通过 -fsanitize=type 启用，检测 C/C++ 基于类型的别名违规。
  • -f[no-]sanitize-trap=local-bounds 和 -f[no-]sanitize-recover=local-bounds 已实现。
  • -fsanitize-merge / -fno-sanitize-merge 新增，用于控制 sanitizer 检查合并。
  • -fsanitize=pointer-overflow 可用于检测指针溢出 UB（建议在测试环境中启用）。
💡 建议

• RTSan：适合音频处理、嵌入式实时系统、游戏引擎等需要保证实时性的场景。

• SSCL type 前缀：如果项目使用了 suppression 文件，可以利用此功能更精细地控制 sanitizer 行为。

• Type Sanitizer：作为 TBAA 变更的配套工具，可用于检测 strict aliasing 违规。但当前为实验性，建议在非生产环境使用。

🔍 17. Size-aware Machine Block Placement

LLVM 20 引入了代码大小感知的基本块布局优化（Size-aware Machine Block Placement）。 该优化在 -Oz（最小体积）和 -Os（优化体积）场景下尤为有效， 通过更智能的代码布局减少跳转指令开销和指令缓存未命中。
💡 性能优化 📈 体积改善

🐞 典型影响

// 编译选项
clang -Oz -o output input.c    // 目标：最小体积
clang -Os -o output input.c    // 目标：平衡体积与性能

// 新优化在 LLVM IR → Machine IR 阶段改进基本块布局
// 效果：
//   1. 减少无条件跳转指令数量
//   2. 改善热路径指令缓存局部性
//   3. 更紧凑的代码生成
💡 建议

• 正面影响：对 -Oz / -Os 构建场景，代码体积有望改善。

• 验证方法：对比 LLVM 19 和 LLVM 20 的 -Oz 构建产物，使用 size 或 bloaty 工具测量体积变化。

• 性能验证：虽然目标是小体积，也建议在目标设备上运行性能回归测试，确保布局变更未引入性能退化。

• 风险低：此优化在 LLVM 后端层面运作，不影响前端语义，兼容性风险极低。
