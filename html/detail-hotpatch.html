热补丁影响

毕昇编译器升级 — LLVM 15 到 21 的热补丁兼容性分析
← 返回主页

概述

对于电信 / 数据通信产品，现场热补丁（Field Hot Patching）是关键的运维能力——在不重启系统的情况下修复漏洞或更新功能。编译器升级（LLVM 15 到 21）涉及多项与热补丁机制相关的底层变更，包括函数入口 NOP 序列、outlining 行为、代码对齐填充、BTI 着陆垫等。如果未评估这些变更，可能导致线上热补丁注入失败或产生未定义行为。

以下章节逐项分析各关键变更点、对热补丁机制的影响，以及推荐的验证与迁移策略。

跨版本 -fpatchable-function-entry 行为变化

-fpatchable-function-entry=N 选项指示编译器在函数入口处插入 N 条 NOP 指令，为运行时热补丁工具（如 Linux ftrace）预留跳转空间。LLVM 15 到 21 之间，NOP 条数的计算、与内联/outline 标志的交互、以及补丁记录段的生成方式都发生了变化。

各版本关键变更

  • LLVM 16： 修复了 __builtin_assume_aligned 与 patchable function 交互时的崩溃问题。
  • LLVM 17/18： 修复多个架构（LoongArch、PowerPC）的支持，并在 X86 上修复了 patchable-function pass 的崩溃。
  • LLVM 19： 新增 hybrid_patchable 属性，支持 ARM64EC 混合二进制场景。
  • LLVM 20： PatchableFunction pass 移植到 New Pass Manager（NPM），执行时机可能变化。
  • LLVM 21： 新增 -fpatchable-function-entry=N,M,S 的第三个参数：允许指定补丁记录段名称（如将 __patchable_function_entries 放入自定义段）。
-fpatchable-function-entry 用法 
// 两个 NOP 在函数入口，补丁记录偏移 0
// clang -fpatchable-function-entry=2,0

// 带自定义段名（LLVM 21 新增）
// clang -fpatchable-function-entry=2,0,.my_patch_entries

// __attribute__ 精确控制
__attribute__((patchable_function_entry(5, 3)))
void critical_handler(void) {
    // 入口：5 条 NOP，实际可 patch 的代码起始于偏移 3
    handle_event();
}
升级影响： NOP 序列的长度和位置可能随编译器版本变化。如果热补丁工具依赖固定的 NOP 长度（如 hard-coded 5 字节），升级后 NOP 序列可能变短或变长，导致补丁代码覆盖超出预期范围。升级后务必重新验证目标函数入口处的 NOP 序列。

NOP 计数交互

-fpatchable-function-entry 与以下编译器特性存在交互：

  • 内联： 被内联的函数不再有独立入口，其 NOP 序列消失。若热补丁期望在某函数上 hook，需确保该函数不被内联（使用 __attribute__((noinline))）。
  • Outlining： Machine Outliner 可能将函数体的一部分提取为独立函数，被提取部分的 NOP 序列行为不确定。
  • KCFI / 控制流完整性： LLVM 21 允许将补丁记录放入自定义段，以解决 -fsanitize=kcfi 与 -fpatchable-function-entry 的兼容性问题——KCFI 在函数入口插入类型哈希前缀，需与 NOP 序列共存。

LLVM 21 nooutline 属性语法变更

nooutline 属性最初在 LLVM 15 后期（D140438）作为字符串属性引入，用于阻止 Machine Outliner 和 IR Outliner 从该函数中提取代码。在 LLVM 21 中（commit 0d08cb0e7037），nooutline 从字符串属性转换为枚举属性（Enum Attribute），带来了 IR 序列化格式的变化。

行为对比

版本IR 表示说明
LLVM 15 ~ 20 "nooutline" (字符串属性) 通过 Attribute::get(Context, "nooutline") 查询
LLVM 21 nooutline (枚举属性) 通过 Attribute::NoOutline 查询，bitcode 自动升级
C 源码中使用 nooutline 
// 关键函数：不允许被 outliner 提取
__attribute__((nooutline))
void critical_timer_callback(void) {
    // 此函数体不会被 Machine Outliner 拆分
    update_watchdog();
    process_timed_events();
}

// 组合用法：禁止内联 + 禁止 outlining
__attribute__((noinline, nooutline))
void hot_patchable_handler(int event) {
    // 保留独立入口用于热补丁，同时防止被拆分
    dispatch_event(event);
}
LLVM IR 变化（16 -> 21） 
; LLVM 15-20 IR（字符串属性）
define void @critical_func() #0 {
  ret void
}
attributes #0 = { "nooutline" ... }

; LLVM 21 IR（枚举属性）
define void @critical_func() #0 {
  ret void
}
attributes #0 = { nooutline ... }

; bitcode reader 自动将旧格式升级为新格式
兼容性说明： LLVM 21 的 bitcode reader 包含自动升级逻辑，旧格式的 "nooutline" 字符串属性会被自动转换为 nooutline 枚举属性。但如果代码中有 hard-coded 字符串匹配（如自定义 pass 检查属性名），需要更新为使用 Attribute::NoOutline。
升级影响： 如果升级后不显式使用 nooutline，Machine Outliner 可能在 -Oz 或特定目标上默认将关键函数的部分代码提取出去。被 outlining 的函数体被拆分后，热补丁替换的函数入口代码可能无法覆盖被提取到外部的部分逻辑，导致补丁不完整。

LLVM 20 .balign / NOP 填充变化

在 LLVM 15 ~ 19 中，.balign N, 0 在非 x86 目标的 .text 段中实际上未按填充值 0 来填充——汇编器将其视为"使用 NOP 指令对齐"（因为大多数非 x86 目标的 TextAlignFillValue 默认值为 0，汇编器在 code section 中不会使用字节 0x00 填充）。LLVM 20（commit ea222be0d926）修复了此行为，使得 .balign N, 0 真正使用 0x00 字节填充。

影响范围

  • AArch64： NOP 指令为 0xd503201f（4 字节）。若对齐填充使用 0x00，CPU 可能将其解码为 0x00000000（UDEF 或非法指令），导致热补丁跳转后 crash。
  • ARM： NOP 为 0xe320f000 或 0x46c0（Thumb）。0x00 填充同样可能是非法指令。
  • RISC-V： NOP 为 0x00000013（addi x0, x0, 0），而非全零字节。
  • LoongArch： NOP 为 0x03400000，全零字节为非法指令。
汇编指令对齐差异 
/* 内联汇编中常见的对齐写法（危险！） */
__asm__ volatile(
    ".balign 16, 0\n"     // LLVM 15-19: 使用 NOP 填充（正确）
                          // LLVM 20+:   使用 0x00 填充（可能非法指令！）
    "my_label: \n"
    "str x0, [x1]\n"
);

/* 正确写法 */
__asm__ volatile(
    ".balign 16\n"        // 不指定 fill value，汇编器使用目标 NOP
    "my_label: \n"
    "str x0, [x1]\n"
);
高风险： 如果产品代码的内联汇编或链接脚本中使用了 .balign N, 0 来对齐代码段，升级到 LLVM 20 后，生成的对齐填充将从 NOP 指令变为 0x00 字节。在 AArch64 上，CPU 遇到全零指令时将触发非法指令异常。请务必在升级前扫描所有汇编文件。
排查方法： 使用 objdump -d 反汇编二进制，搜索连续的 0x00000000 出现在 .text 段中。也可用 grep -rn "\.balign.*, *0" 扫描汇编源码。

跨版本 Machine Outliner 对热补丁的影响

Machine Outliner 在 -Oz 优化级别默认启用（部分目标在 -Os 也启用），它将多个函数中重复的指令序列提取为独立的"outlined function"。LLVM 15 到 21 之间，Machine Outliner 持续演进，可能提取更多的指令序列。

版本演进

  • LLVM 16： 加入了 nooutline 属性的完整支持（D140438），允许函数级别禁用 outlining。
  • LLVM 17~19： 持续改进指令序列匹配算法，保留了 instruction bundles、修复了 outlined candidates 中 LOH（Linker Optimization Hints）的处理。
  • LLVM 20： 引入 Global Outlining（commit 0f5254528967），利用跨模块的 codegen data 识别跨 TU 的可 outlining 序列，outlining 范围从单个模块扩展到全程序。
  • LLVM 21： 修复 outlined candidates 中 LOH 的遗留问题，同时 nooutline 转为枚举属性。

对热补丁的影响

当 Machine Outliner 从函数 A 中提取指令序列并创建 outlined function OUTLINED_FUNCTION_x 后：

  1. 函数 A 的函数体中对原指令序列的引用被替换为对 OUTLINED_FUNCTION_x 的调用
  2. 热补丁替换函数 A 的入口代码时，只能覆盖留在函数 A 中的逻辑，无法覆盖被提取到 OUTLINED_FUNCTION_x 中的部分
  3. 如果补丁需要同时修改被提取的代码路径，需要额外对 outlined function 进行补丁——但 outlined function 可能被多个函数共享
Machine Outliner 影响示意 
// 原始代码（hot_patchable 函数）
void hot_patchable_func(void) {
    init_device();        // 公共序列 A
    configure_io();       // 公共序列 A
    // ... 函数特定逻辑 ...
    cleanup_device();     // 公共序列 B
    disable_irq();        // 公共序列 B
}

// Machine Outliner 后:
// OUTLINED_FUNCTION_0:
//   init_device(); configure_io(); ret
//
// OUTLINED_FUNCTION_1:
//   cleanup_device(); disable_irq(); ret
//
// hot_patchable_func:
//   bl OUTLINED_FUNCTION_0
//   ... 函数特定逻辑 ...
//   bl OUTLINED_FUNCTION_1
//
// 如果热补丁替换 init_device 的行为，
// 需要同时 patch hot_patchable_func 和 OUTLINED_FUNCTION_0

缓解策略

禁用 Outlining 
// 方案1: 函数级别禁用（推荐用于关键热补丁函数）
__attribute__((nooutline))
void hot_patchable_func(void) {
    // ...
}

// 方案2: 编译单元级别禁用
// clang -mno-outline ...

// 方案3: 链接时禁用（如果使用 LTO）
// clang -mllvm -enable-machine-outliner=never ...

// 方案4: Makefile / CMake 配置
// CFLAGS += -mno-outline  # 仅用于需要热补丁的编译单元
Global Outlining 特别注意： LLVM 20 引入的 Global Outlining 可能跨模块提取代码。即使在单个编译单元禁用了 outlining，链接时的全局 outlining pass 仍可能提取代码。确保在启用 -mno-outline 的同时，不在链接阶段使用 -codegen-data-generate 或 -codegen-data-use（这些选项触发跨模块 outlining）。

LLVM 21 noipa 属性（新增）

LLVM 21 引入了 noipa 函数属性（commit c07bc2962c5f），禁用所有检查函数定义的过程间分析（Interprocedural Analysis, IPA）。设置此属性等价于将该函数定义移动到一个独立的、优化器不透明的模块中。

noipa 与 noinline / nooutline 的关系

属性阻止内联阻止 Outlining阻止 IPA
noinline是否否
nooutline否是否
noipa否否是
noipa + noinline + nooutline是是是

noipa 的关键特点：它不阻止内联和 outlining。如果希望函数入口保持完整且不受 IPA 干扰，需要同时组合使用三个属性。

noipa 使用示例 
// LLVM 21 新增: 阻止 IPA 优化破坏函数边界
__attribute__((noipa))
int compute_checksum(const uint8_t *buf, size_t len) {
    // 优化器不会跨此函数边界进行过程间分析
    // IP-CP, IP-SCCP, 死参数消除等不会影响此函数
    int sum = 0;
    for (size_t i = 0; i < len; i++)
        sum += buf[i];
    return sum;
}

// 完整的热补丁安全组合（LLVM 21 推荐）
__attribute__((noipa, noinline, nooutline))
__attribute__((patchable_function_entry(5, 3)))
void hot_patchable_handler(int event_id, void *data) {
    switch (event_id) {
    case EVENT_INIT:
        init_subsystem(data);
        break;
    case EVENT_SHUTDOWN:
        shutdown_subsystem();
        break;
    }
    // 这三个属性共同保证:
    // - noinline:   保留独立入口，不被内联到调用者
    // - nooutline:  函数体不会被 Machine Outliner 拆分
    // - noipa:      过程间分析不会修改函数签名或边界行为
    // + patchable_function_entry: 入口处有足够的 NOP 空间
}
使用建议： noipa 主要用于防止过程间分析破坏热补丁函数的外部可观测行为——例如 IP-CP（Interprocedural Constant Propagation）将常量传播跨函数边界，死参数消除移除补丁代码依赖的参数等。对于需要保持 ABI 稳定、可被外部热补丁替换的函数，推荐使用 __attribute__((noipa, noinline, nooutline)) 组合。

LLVM 19+ BTI（Branch Target Identification）对热补丁跳转的影响

BTI（Branch Target Identification）是 ARMv8.5-A 引入的安全特性，要求间接跳转的目标地址必须是一条合法的 BTI 着陆指令（bti c、bti j 等）。如果热补丁跳转到未标记 BTI 的地址，CPU 将在启用了 BTI 的系统上触发 Branch Target Exception。

版本变更

  • LLVM 19： 大幅改进 BTI 生成策略——无地址被取（non-addr-taken）的静态函数不再生成 BTI 着陆垫（ELF 目标），减少了不需要间接调用的函数的代码膨胀。但如果热补丁工具通过 地址（而非符号名）跳转到这些函数，将缺少 BTI 指令。
  • LLVM 20： 进一步优化，增加更多场景下的 BTI 省略。
  • LLVM 21： 为异常处理入口添加 BTI 指令；同时修改了 asm goto 的行为——不再在 asm goto 的 label 目标处自动生成 BTI 指令（commit 56acb06bc6a1）。如果热补丁通过 asm goto 机制将控制流转移到 label，且 label 处需要 BTI，需要手动插入。
BTI 对热补丁的影响示意 
// AArch64, -mbranch-protection=bti

// LLVM 15-18: 所有外部可见函数自动生成 BTI
__attribute__((patchable_function_entry(4, 2)))
void critical_func(void) {
    // 反汇编 (LLVM 18):
    // critical_func:
    //   nop              ; patchable NOP
    //   nop              ; patchable NOP
    //   bti c            ; BTI landing pad
    //   stp x29, x30, [sp, #-16]!
    //   ...
}

// LLVM 19-21: 若函数地址未被显式取用，可能不生成 BTI
// 热补丁跳转到此函数入口时：
// - 如果 BTI 被省略 & 系统启用了 BTI → Branch Target Exception
// - 如果 BTI 存在 → 正常执行

// LLVM 21: asm goto 不再自动生成 BTI
__asm__ goto(
    "cmp %0, #0\n"
    "b.eq %l[done]\n"
    : : "r"(val) : : done);
done:
    // LLVM 15-20: 此 label 处自动生成 bti j
    // LLVM 21:    不再自动生成，需手动添加
    return;
风险场景： 对于在 AArch64 上使用 -mbranch-protection=bti 编译的产品，如果热补丁机制需要在运行时跳转到函数入口，需要确认目标函数仍然生成了 BTI 着陆指令。LLVM 19 后省略 BTI 的函数是补丁安全的前提是：运行时跳转不经过间接调用路径（而是通过符号解析+绝对跳转），并且 CPU 处于允许非 BTI 目标的上下文。
验证方法： 使用 readelf -n <binary> 检查 GNU Property 中的 GNU_PROPERTY_AARCH64_FEATURE_1_BTI；使用 objdump -d 检查目标函数的入口指令是否为 bti c 或 bti j。如需确保生成 BTI，可使用 __attribute__((used)) 使函数地址被保留，从而触发 BTI 生成。

LLVM 21 Windows Secure Hot-Patching

虽然 Windows 热补丁场景与电信 / 数据通信产品的 Linux 环境通常不同，但 LLVM 21 新增的 Windows Secure Hot-Patching 支持（commit 0a3c5c42a178）引入了一些通用的热补丁机制概念，值得了解：

  • Patchable globals indirection： 被标记为 hot-patchable 的函数通过 _ref_* 全局变量间接访问全局变量，确保热补丁代码访问的是原始镜像中的变量，而非补丁镜像中的版本。
  • CodeView S_HOTPATCHFUNC 符号： 在调试信息中标记已热补丁的函数，供调试器和分析工具使用。
  • 标记方式： -fms-hotpatch-functions-list=func1,func2 或 -fms-hotpatch-functions-file=<path>（Clang 层面）；-mllvm --ms-hotpatch-functions-list=func1（LLVM 层面）。
注意： Windows Secure Hot-Patching 是 LLVM 21 的新增功能，目前主要针对 Windows/COFF 目标，与 Linux/ELF 上的 -fpatchable-function-entry 机制是独立的两种热补丁方案。Linux 产品不需要迁移到此方案，但了解其存在有助于评估未来可能出现的跨平台热补丁标准化。

验证建议

1. 检查函数入口 NOP 序列

升级编译器后，对于所有标记为 patchable_function_entry 的函数，使用 objdump -d 反汇编并验证：

  • 入口处 NOP 数量是否与预期一致（与 -fpatchable-function-entry=N,M 参数匹配）
  • NOP 指令是否正确（AArch64: nop / 0xd503201f；x86-64: nop / 0x90）
  • NOP 之后的第一条实际指令偏移量是否符合 M 参数
NOP 序列验证脚本 
#!/bin/bash
# 验证所有 patchable 函数的 NOP 序列
OBJDUMP=llvm-objdump-21
FUNC=$1

$OBJDUMP -d binary.o | awk -v func="$FUNC" '
  /^[0-9a-f]+ <.*>:/ { current = $2; gsub(/[<>:]/, "", current) }
  current == func && /nop/ { count++; print }
  current == func && !/nop/ && count > 0 {
    print "Total NOPs at entry: " count
    if (count != expected) print "WARNING: NOP count mismatch!"
    count = 0; exit
  }'

2. 验证 nooutline 属性被遵守

对标记了 nooutline 的关键函数，确认 Machine Outliner 不会提取其代码。可以通过以下方式验证：

  • 使用 -Rpass=MachineOutliner 检查优化记录，确认 critical 函数未出现在 outlining 决策中
  • 使用 llvm-objdump -d 反汇编，确认函数体不含对 OUTLINED_FUNCTION_* 的调用
Outlining 检测命令 
# 编译时检查 outlining 备注
clang -Oz -Rpass=MachineOutliner \
      -Rpass-analysis=MachineOutliner \
      critical.c -c -o critical.o 2>&1 | grep -i outline

# 反汇编检查 outlined calls
llvm-objdump-21 -d binary | grep 'OUTLINED_FUNCTION_'

3. 测试热补丁注入

在编译器升级后的二进制上实际执行一次完整的热补丁注入流程：

  1. 使用升级后的编译器重新构建目标二进制
  2. 在测试环境中使用热补丁工具注入一个测试补丁（例如替换一个函数的前几条指令）
  3. 验证补丁生效且不引发非法指令异常、Branch Target Exception 或段错误
  4. 特别关注 AArch64 目标，测试 BTI 启用和未启用两种场景

4. 统一使用 -fpatchable-function-entry

推荐在构建系统中统一使用 -fpatchable-function-entry 标志，避免依赖内联汇编中的 .balign N, 0 NOP sled 或其他手工编写的入口 padding。标准的 -fpatchable-function-entry 会正确处理 NOP 生成、补丁记录段和 BTI 交互。

推荐的 CMake 配置 
# 全局热补丁标志（所有需要热补丁的编译单元）
set(HOTPATCH_FLAGS "-fpatchable-function-entry=4,2")

# 对于关键的热补丁目标函数，额外属性
# __attribute__((noipa, noinline, nooutline, patchable_function_entry(4, 2)))

# AArch64 + BTI + 热补丁
if(CMAKE_SYSTEM_PROCESSOR MATCHES "aarch64")
  set(HOTPATCH_FLAGS "${HOTPATCH_FLAGS} -mbranch-protection=bti")
endif()

# 禁用 Machine Outlining 以避免拆分热补丁函数
set(HOTPATCH_FLAGS "${HOTPATCH_FLAGS} -mno-outline")

target_compile_options(my_hotpatch_lib PRIVATE ${HOTPATCH_FLAGS})

5. 检查 .balign 用法

在升级到 LLVM 20+ 之前，扫描所有汇编源文件（*.s、*.S）、内联汇编（在 C/C++ 中）以及链接脚本（*.ld、*.lds）中的 .balign / .p2align 指令：

  • 将代码段中的 .balign N, 0 改为 .balign N（去掉显式的 0 填充值）
  • 数据段中的 .balign N, 0 保持不变（数据段本就应该用 0x00 填充）
.balign 扫描脚本 
#!/bin/bash
# 扫描所有源文件中的 .balign 用法
echo "=== 汇编文件 ==="
grep -rn '\.balign.*,[[:space:]]*0' --include='*.s' --include='*.S' .

echo "=== C/C++ 内联汇编 ==="
grep -rn '\.balign.*,[[:space:]]*0' --include='*.c' --include='*.cpp' --include='*.h' .

echo "=== 链接脚本 ==="
grep -rn '\.balign.*,[[:space:]]*0' --include='*.ld' --include='*.lds' --include='*.x' .
