函数模板名称重整（Name Mangling）

最关键的 ABI Break
🔴 这是 LLVM 18 中最关键、影响最广的 ABI 变更 所有满足特定条件的 C++ 函数模板的 mangled name 都会发生变化，导致符号不匹配、动态加载失败等严重问题。

变更说明

LLVM 18 修复了 Clang 在 Itanium C++ ABI 下对函数模板的名称重整（Name Mangling）实现。此前，某些函数模板的 mangled name 未能正确反映模板参数之间的依赖关系、C++20 约束（concepts/requires）、以及 auto 推导类型等信息。LLVM 18 将这些因素纳入 mangling 计算，使得生成的符号名与 GCC 的行为保持一致，但因此改变了这些函数模板的 ABI。

通俗地说：两个同名模板函数，在旧编译器中可能产生相同的 mangled name（误判为同一符号），在新编译器中则会正确地区分出不同的 mangled name。反过来，原来匹配的符号也可能不再匹配。

“模板参数的依赖关系和约束条件现在会影响符号名”

Itanium ABI 规范要求：当模板参数的依赖关系、约束条件、或推导类型不同时，函数模板的 mangled name 必须不同。 旧版本的 Clang 在某些情况下未严格遵守此规范，LLVM 18 修复了这一问题。

四种受影响场景

  1. 模板参数依赖于前一个参数，如 template<typename T, T V> void f()
  2. 函数带有任何约束（constraints），包括 constrained template parameters 或 requires-clauses
  3. 模板参数列表包含推导类型，包括 auto、decltype(auto) 或推导的类模板特化类型
  4. 模板模板参数被赋予不同模板参数列表的模板模板实参

场景一：模板参数依赖前一个参数

示例 1 — 参数依赖
// template 的第二个参数 V 的类型 依赖于 第一个参数 T
// 旧编译器可能对所有实例化生成相同的 mangled name
// 新编译器会根据 T 的实际类型生成不同的符号

template<typename T, T V>
void f() {}

void example1() {
    f<int, 42>();      // mangled name 变化：T=int, V=42(int)
    f<char, 'x'>();    // mangled name 变化：T=char, V='x'(char)
    f<long, 99L>();     // 每个实例化现在有唯一确定的符号名
}

场景二：带 C++20 约束（constraints/requires）的模板

示例 2 — C++20 约束
// C++20 requires 子句 —— 约束条件现在参与 name mangling
// 旧：约束被忽略，所有未约束版本和约束版本可能产生相同符号
// 新：约束条件不同 = 不同的 mangled name

#include <concepts>

template<typename T>
requires std::integral<T>
void f(T x) {}

template<typename T>
requires std::floating_point<T>
void f(T x) {} // 与上面的 mangled name 不同

void example2() {
    f(42);       // 调用 integral 重载
    f(3.14);     // 调用 floating_point 重载
                 // 两个重载现在有正确区分的 mangled name
}

场景三：auto 推导类型参数

示例 3 — auto 推导类型
// auto 非类型模板参数 —— C++17 特性
// 旧：auto 推导的实际类型不影响 mangling
// 新：推导出的具体类型参与 mangling 计算

template<auto V>
void f() {}

void example3() {
    f<42>();        // V 推导为 int，mangled name 含 int 信息
    f<'x'>();       // V 推导为 char，mangled name 含 char 信息
    f<3.14>();      // V 推导为 double（C++20），mangled name 变化
}

影响评估

影响维度具体表现受影响场景
动态库 ABI 使用新/旧编译器分别编译的 .so 之间，上述模板函数的符号名不匹配，链接时找不到符号 动态库升级场景；插件加载系统（dlopen/dlsym）；跨编译器版本的库分发
静态库链接 新旧目标文件中的符号不一致，链接器可能报告未定义引用或重复定义 增量构建；预编译静态库分发
二进制兼容 已部署的二进制文件调用新编译的库时，因符号名变化导致运行时符号解析失败 热更新/热补丁系统；插件架构
编译隔离 全量从源码重新编译（不涉及预编译库）时通常不受影响，因为编译+链接使用同一编译器 纯源码构建的项目

诊断方法

使用 nm 检查符号变化
# 用旧编译器 (LLVM 17) 编译
clang++-17 -c example.cpp -o example_old.o
nm -C example_old.o | grep "f<"

# 用新编译器 (LLVM 18) 编译
clang++-18 -c example.cpp -o example_new.o
nm -C example_new.o | grep "f<"

# 对比两个输出，检查符号名是否有差异
diff <(nm -C example_old.o | sort) <(nm -C example_new.o | sort)

# 也可以直接查看未 demangle 的原始符号名
nm example_old.o | c++filt
nm example_new.o | c++filt

恢复兼容性

🟡 过渡期兼容方案 如果暂时无法全量重新编译所有依赖库，可以通过 -fclang-abi-compat=17 编译选项让 LLVM 18 使用与 LLVM 17 兼容的 ABI（包括旧的 name mangling 行为）。
注意：这是一个过渡期方案。长期应升级所有依赖库到新的 ABI，并在全量重新编译后移除此标志。

建议的应对策略

  • 全量重新编译：如果项目所有代码和依赖都是源码构建，统一用 LLVM 18 重新编译即可，不需要额外处理
  • 检查动态库接口：对导出 API 使用 nm -C 检查是否有上述模板模式，评估对外部调用者的影响
  • 插件系统：如果通过 dlopen/dlsym 按 mangled name 加载符号，需要更新符号名（或改用 extern "C" 包装）
  • 过渡期：使用 -fclang-abi-compat=17 保持兼容，逐步迁移

__int128 x86-64 SystemV ABI 变更

ABI 变更 x86-64 Linux
🟡 x86-64 Linux 平台的调用约定变更 涉及 __int128 类型参数的函数，在 LLVM 18 中其参数传递方式发生了变化，与旧版本编译的代码二进制不兼容。

变更说明

在 x86-64 SystemV ABI 下，__int128（128 位整数）类型的函数参数，旧版本的 Clang 采用"拆分传递"方案：将 128 位数据拆分为两部分，一部分通过寄存器传递，剩余部分通过栈传递。LLVM 18 修正了这一行为，现在 __int128 参数完全通过寄存器对（register pair）传递，不再涉及栈操作。

这个修正使 Clang 的行为与 GCC 保持一致，但改变了函数调用约定。使用不同版本编译器编译的调用方和被调用方之间会出现 ABI 不兼容。

代码示例

示例 — __int128 参数传递
// 一个接受 __int128 参数的函数
// 旧 ABI：val 被拆分为寄存器 + 栈
// 新 ABI：val 完全通过寄存器对 (rdx:rax 或类似) 传递

__int128 add128(__int128 a, __int128 b) {
    return a + b;
}

void caller() {
    __int128 x = (__int128)1 << 100;
    __int128 y = (__int128)1 << 64;
    __int128 result = add128(x, y);
    // 调用方和被调用方必须使用同一 ABI 约定
}

影响评估

维度详情
影响平台 仅限 x86-64 Linux（SystemV AMD64 ABI）。ARM64 (AArch64)、Windows、macOS 等其他平台不受影响
触发条件 函数参数或返回值类型包含 __int128（包括 signed/unsigned 变体）
风险 新旧编译器混编的 .o/.so 之间调用此类函数时，参数传递不匹配，可能导致数据损坏或崩溃
发生概率 相对较低 — __int128 在大多数业务代码中使用并不频繁，主要出现在加密算法、大数运算、哈希函数等场景

应对建议

  • 排查 __int128 使用：在代码库中搜索 __int128、unsigned __int128，确认使用范围
  • 全量重编译：涉及 __int128 的模块，调用方和被调用方必须使用同一版本编译器编译
  • 优先关注：加解密库、哈希库、大整数运算库（如自定义的 BigInt 实现）
  • 过渡方案：使用 -fclang-abi-compat=17 保持旧 ABI 行为

模板化 operator== 反转修复 & operator!= 查找修复

C++20 语言行为变更
🟡 C++20 operator== 重写规则的边界情况修正 LLVM 18 修复了模板化 operator== 在 C++20 反转重写规则下的处理，以及 operator!= 配合反转 operator== 时的查找缺陷。

变更一：模板化 operator== 反转歧义修复

C++20 引入了 operator== 的反转重写规则（reversed rewriting）：如果 a == b 找不到匹配的 operator==(a, b)，编译器会尝试反转参数顺序，查找 operator==(b, a)。

LLVM 18 修复了此规则应用于模板化 operator== 时的一个问题。对于某些同时定义了正向和反向匹配的模板 operator== 场景，之前 Clang 会接受（选出一个候选），现在正确报告为歧义（ambiguous）。这可能导致之前可编译通过的代码在 LLVM 18 下编译失败。

代码示例

示例 — 变为歧义的 operator== 调用
// C++20 模式
// LLVM 17：接受此代码（选择非模板或其中一个模板）
// LLVM 18：报告歧义错误（两个候选 operator== 同等匹配）

struct P {};

// 候选1：正向 operator==
template<class S>
bool operator==(const P&, const S&);

// 候选2：另一个模板 operator==，反转后也能匹配
template<class T>
bool operator==(const T&, const P&);

void test() {
    P p1, p2;
    if (p1 == p2) {  // 歧义：候选1 正向匹配 (P, P)
                        //       候选2 反转匹配  P==P -> P==P 反转
                        // LLVM 18 报告：call to 'operator==' is ambiguous
    }
}

变更二：operator!= 配合反转 operator== 的查找修复（P2468）

C++20 引入了基于 operator== 自动合成 != 表达式的规则。根据 P2468R2 "The Equality Operator You Are Looking For"，编译器在查找 operator!= 时也需要考虑反转的 operator==。LLVM 18 修复了此前 Clang 在查找匹配的 operator!= 时的缺陷，使得带有反转 operator== 的 != 调用能正确匹配。

示例 — operator!= 通过反转 operator== 匹配
// P2468R2 场景：operator!= 的查找考虑反转 operator==

struct P {};
template<class S> bool operator==(const P&, const S&);

struct A : public P {};
struct B : public P {};

// 这个相等比较现在在 C++20 中是歧义的
bool ambiguous(A a, B b) { return a == b; }

template<class S> bool operator!=(const P&, const S&);
// OK：找到了匹配的 operator!=
bool fine(A a, B b) { return a == b; }

诊断与处理

🔵 使用 -Wambiguous-reversed-operator 提前检测 该告警选项可以帮助在旧编译器（LLVM 17）上提前发现可能存在歧义的 operator== 使用。
升级到 LLVM 18 之前，建议先启用此告警进行一轮代码筛查和修复。

应对建议

  • 启用 -Wambiguous-reversed-operator 在升级前检测潜在歧义
  • 对于确实歧义的 operator== 调用，显式指定候选（例如添加更特化的重载）
  • 检查代码中自定义的模板化 operator==，特别是涉及对称比较运算符的场景
  • 对于依赖 operator!= 反转匹配的代码，确认升级后行为符合预期（P2468 语义）

PCH 扩展名从 .gch 改为 .pch

构建系统适配
🟡 预编译头部（PCH）文件扩展名变更 LLVM 18 将预编译头部的默认扩展名从 .gch 改为 .pch，且 -include 不再自动识别 .gch 文件。

变更说明

预编译头部（Precompiled Header）是加速 C/C++ 编译的重要机制。LLVM 18 对 PCH 文件的处理做了两项关键变更：

  1. 默认扩展名改为 .pch：使用 clang -x c++-header 编译头部生成的预编译文件，旧版本使用 .h.gch（GCC 兼容）作为扩展名，LLVM 18 改为 .h.pch
  2. -include 不再查找 .gch：-include a.h 在旧版本中会自动查找 a.h.gch 作为 PCH 文件。LLVM 18 起只查找 a.h.pch（如果存在），不再回退到 .gch
  3. 已有 .gch 文件的处理：如果 a.h.gch 不是有效的 Clang PCH 文件（或是目录但其中没有 PCH），-include a.h 会忽略它

影响示例

示例 — PCH 生成和使用
# 旧行为 (LLVM 17 及之前)：
clang++-17 -x c++-header common.h -o common.h.gch        # 生成 .gch
clang++-17 -include common.h main.cpp                    # 自动查找 common.h.gch ✓

# 新行为 (LLVM 18)：
clang++-18 -x c++-header common.h -o common.h.pch        # 生成 .pch
clang++-18 -include common.h main.cpp                    # 自动查找 common.h.pch ✓
                                                         # 不再查找 common.h.gch ✗

影响评估

场景影响
Makefile/CMake 构建脚本中硬编码 .gch 扩展名的地方需要更新为 .pch，否则 PCH 不会被自动发现
外部工具 任何依赖 -include + PCH 自动查找机制的工具链（如 distcc、ccache 的 PCH 模式）可能需要更新
显式指定 如果构建脚本显式指定 PCH 文件路径（通过 -include-pch 或直接作为输入文件），则不受此变更影响
存量 .gch 文件 已有的 .gch 文件不会被自动识别。可以通过 -include-pch common.h.gch 显式指定来继续使用

完整示例：更新构建脚本

示例 — Makefile 适配
# 旧 Makefile (LLVM <18)
PCH_FILE = common.h.gch
$(PCH_FILE): common.h
	clang++ -x c++-header $< -o $@

main.o: main.cpp $(PCH_FILE)
	clang++ -include common.h -c main.cpp

# --- 改为 ---

# 新 Makefile (LLVM 18+)
PCH_FILE = common.h.pch                               # 改扩展名
$(PCH_FILE): common.h
	clang++ -x c++-header $< -o $@

main.o: main.cpp $(PCH_FILE)
	clang++ -include common.h -c main.cpp             # -include 不变，自动找 .pch

应对建议

  • 在 Makefile / CMakeLists.txt 中搜索 .gch 引用，替换为 .pch
  • 清理构建目录中的旧 .gch 文件，防止混淆
  • 检查 CI/CD 构建脚本中的 PCH 路径
  • 如果使用 ccache，确认其 PCH 模式与新扩展名兼容

-Wenum-constexpr-conversion 默认启用

LLVM 19 升级为硬 Error
🔴 LLVM 18 在系统头文件和宏中默认启用；LLVM 19/20 起升级为不可压制的硬 Error 这是一个分期收紧的变更：LLVM 18 只是默认启用告警（包括系统头文件和宏），LLVM 19/20 将升级为强制错误。在 LLVM 18 阶段必须完成相关代码的修复。

变更说明

-Wenum-constexpr-conversion 检测编译期将超出枚举范围的整数值转换为枚举类型的操作。C++ 标准规定，枚举类型的值必须在其底层类型能表示的范围内且与某个枚举器对应（或有足够的位宽表示所有枚举器的组合）。

LLVM 18 之前，此告警在系统头文件和宏中被默认静默。LLVM 18 起，该告警在系统头文件和宏中默认启用。LLVM 19/20 将升级为硬 Error，不可通过编译选项降级。

代码示例

示例 — enum 超范围值
// 定义一个只有两个有效值的枚举
enum E { A, B };  // A=0, B=1, 底层类型为 int

// LLVM 18：触发 -Wenum-constexpr-conversion 告警（包括系统头文件中）
// LLVM 19/20：编译错误
constexpr E v1 = (E)10;     // 10 超出 [0,1] 范围，错误！

// 标准库中也可能触发，例如：
// 某些实现中 std::byte 相关的转换可能涉及枚举类型
// LLVM 18 起在系统头文件中也会报告

// 正确做法：确保值在有效范围内
constexpr E v2 = (E)1;      // OK，1 = B
示例 — 带底层类型指定（fixed underlying type）
// 指定底层类型的枚举
enum class Flags : unsigned int {
    None  = 0,
    Read  = 1 << 0,
    Write = 1 << 1,
    Exec  = 1 << 2
};

// 组合标志 —— 看似合理，但 7 不是任何枚举器
constexpr Flags all = (Flags)7;  // LLVM 19+ 报错！

// 规避方案1：使用底层类型而非枚举类型
constexpr unsigned int all_flags = 7;

// 规避方案2（C++23）：使用 std::to_underlying + 显式转换
// 或考虑使用位域 / 整数类型组合标志

影响评估

版本阶段行为应对
LLVM 17 及之前 系统头文件和宏内不告警 无影响
LLVM 18 系统头文件和宏中默认启用告警（warning） 可暂时用 -Wno-enum-constexpr-conversion 降级
LLVM 19+ 升级为硬 Error，不可降级 必须在升级到 LLVM 19 之前修复所有违规代码

应对建议

  • 在 LLVM 18 阶段完成修复：利用 -Wenum-constexpr-conversion 告警定位所有违规点
  • 枚举标志组合：对于位掩码用途的枚举，改用底层整数类型存储组合值，而非强制转换为枚举类型
  • 枚举值校验：检查所有 constexpr 上下文中对枚举的显式转换，确保值在合法范围内
  • 标准库头文件：注意系统头文件（如 <filesystem>、<chrono> 等）也可能触发，这些需要等待标准库修复
🔴 特别提示 如果项目计划跳过 LLVM 18 直接从 17 升级到 19/20，请务必先用 LLVM 18 的 -Wenum-constexpr-conversion 完成一轮代码筛查，因为 LLVM 19 起此错误不可压制。

LLVM IR 变更：常量表达式变体移除 & 栈内建函数重载

LLVM IR 变更
🟡 LLVM IR 中的多种 ConstantExpr 子类被移除；栈内建函数指针重载 直接影响手写 LLVM IR 或使用 LLVM C++ API 构建 IR 的工具。纯 C/C++ 源码编译的用户不受直接影响。

变更一：常量表达式变体移除

LLVM IR 中的 ConstantExpr 表示编译期可计算的常量表达式。历史上，LLVM 为每种二元运算都定义了对应的常量表达式子类。随着 LLVM 向 opaque pointers 和其他 IR 现代化方向的演进，许多常量表达式变体变得冗余。LLVM 18 移除了一批不再需要的变体。移除后，这些操作在编译期仍可正常计算，只是不再以独立的 ConstantExpr 子类表示，而是统一使用 ConstantFold 机制处理。

移除的常量表达式变体（共 12 种）

类别移除的 ConstantExpr 变体说明
位运算 And、Or、LShr、AShr 按位与、或、逻辑右移、算术右移
整数扩展 ZExt、SExt 零扩展、符号扩展
浮点转换 FPTrunc、FPExt、FPToUI、FPToSI、UIToFP、SIToFP 浮点精度截断/扩展、浮点转整数、整数转浮点

变更二：llvm.stacksave / llvm.stackrestore 指针类型重载

llvm.stacksave 和 llvm.stackrestore 内建函数现在使用重载的指针类型（overloaded pointer type），以支持非零地址空间（non-0 address spaces）。此前这些内建函数仅支持默认地址空间（address space 0），LLVM 18 扩展为支持任意地址空间，使得 GPU 等使用非零地址空间的后端也能正确使用栈操作。

代码示例

示例 — LLVM C++ API 中已不可用的类型
// 旧代码（LLVM 17 及之前可用）：
// 使用 ConstantExpr::getZExt() 创建常量零扩展表达式
Constant *C = ConstantExpr::getZExt(Value, Int64Ty);

// 新代码（LLVM 18+）：
// 直接使用 ConstantFold 或 IR Builder
Constant *C = ConstantFoldCastOperand(Instruction::ZExt, Value, Int64Ty, DL);
// 或者通过 IRBuilder:
// IRBuilder<> Builder(...);
// Value *C = Builder.CreateZExt(Value, Int64Ty);
示例 — 手写 LLVM IR 中的变化
; 旧 IR（LLVM 17 及之前，常量表达式语法可用）：
@g = global i64 zext (i32 ptrtoint (ptr @foo to i32) to i64)

; 新 IR（LLVM 18+，不能嵌套这些常量表达式）：
; 需要改为使用指令序列或在编译期预先计算：
@ptr_val = global i32 ptrtoint (ptr @foo to i32)
@g = global i64 0  ; 改为运行时初始化或使用 ConstantFold
示例 — llvm.stacksave/llvm.stackrestore 地址空间
; 旧（LLVM 17）：指针类型固定为 ptr（addrspace 0）
%sp = call ptr @llvm.stacksave()
call void @llvm.stackrestore(ptr %sp)

; 新（LLVM 18+）：支持非零地址空间的 ptr
%sp = call ptr addrspace(5) @llvm.stacksave.p5()
call void @llvm.stackrestore.p5(ptr addrspace(5) %sp)
; 主要影响 GPU 后端（AMDGPU、NVPTX 等）

影响评估

用户类别影响
普通 C/C++ 源码编译 不受影响 — Clang 前端已适配，自动生成新的 IR 格式
使用 LLVM C++ API 的工具 需要更新代码 — 不能再调用已移除的 ConstantExpr::get*() 静态方法，改用 ConstantFoldCastOperand 或 IRBuilder
手写/生成 LLVM IR 的工具 需要更新 IR 生成逻辑 — 不能再在常量表达式中使用已移除的操作类型；llvm.stacksave 地址空间参数需适配
LLVM Pass 插件 需要更新 — 如果 Pass 中模式匹配了这些 ConstantExpr 子类，需要修改匹配逻辑

应对建议

  • 纯 C/C++ 项目：通常无需关注
  • 有自定义 LLVM Pass：检查 Pass 代码中是否使用了已移除的 ConstantExpr API，替换为新的常量折叠接口
  • 生成 IR 的工具：检查生成的 IR 中是否包含已移除的常量表达式语法，改用指令序列
  • 汇编级别的 IR 测试：更新 .ll 测试文件，移除已废弃的常量表达式用法
  • GPU 后端用户：确认 llvm.stacksave/llvm.stackrestore 的地址空间参数正确

FatLTO 支持 (LLD)

新特性
🟢 LLVM 18 新增 FatLTO 链接器支持 LLD 新增 --fat-lto-objects 选项，目标文件中同时包含机器码和 LLVM IR，避免 ThinLTO/Full LTO 与无 LTO 构建之间的不兼容。

变更说明

FatLTO（Fat Link-Time Optimization）是 LLVM 18 引入的一种新的 LTO 目标文件格式。传统 LTO 模式下，目标文件要么包含机器码（无 LTO），要么包含 LLVM IR bitcode（LTO 模式），二者不能混用。FatLTO 的目标文件同时包含机器码和 LLVM IR，使同一份目标文件既可以用于 LTO 链接，也可以用于非 LTO 链接。

LLD 在 LLVM 18 中新增 --fat-lto-objects 链接器选项，用于支持这种格式的目标文件。

工作流程

示例 — FatLTO 编译和链接流程
# 生成 FatLTO 目标文件：同时包含机器码和 LLVM IR
clang++-18 -c -ffat-lto-objects foo.cpp -o foo.o
clang++-18 -c -ffat-lto-objects bar.cpp -o bar.o

# 非 LTO 链接（使用机器码部分，忽略 IR）：
clang++-18 foo.o bar.o -o app_no_lto

# LTO 链接（使用 IR 部分进行跨模块优化）：
clang++-18 -flto foo.o bar.o -o app_lto

# 或直接用 LLD + --fat-lto-objects：
ld.lld --fat-lto-objects foo.o bar.o -o app
# LLD 自动识别 FatLTO 格式，根据需要选择机器码或 IR

为什么需要 FatLTO

问题传统方案FatLTO 方案
构建变体管理 LTO 和非 LTO 构建需要分别生成目标文件，两套编译产物 同一份目标文件，链接时灵活选择
增量构建 切换 LTO 模式需要全量重新编译 无需重新编译，仅重新链接即可
库分发 分发 LTO 版本的库需要单独构建或同时分发两套 单一构建产物同时满足 LTO 和非 LTO 用户
文件大小 单套文件较小 文件稍大（包含两份数据），但省去双份构建的存储开销

影响评估

🔵 这是一个新增功能，而非默认行为变更 FatLTO 是可选功能。不使用 -ffat-lto-objects 编译选项或 --fat-lto-objects 链接选项时，行为与旧版本完全一致。对现有构建流程零影响。

适用场景与建议

  • 大型项目：希望同一份编译产物同时支持 LTO 和快速非 LTO 调试构建
  • SDK/库分发：分发的预编译库同时支持 LTO 和非 LTO 用户
  • CI/CD 优化：减少构建变体的编译次数，一份编译 + 多种链接配置
  • 暂不需要：如果项目统一使用或无 LTO 或统一使用 LTO，且没有库分发需求，FatLTO 带来的收益有限

C++ 语言与 AST 变更

语言行为 / AST 破坏性变更

8.1 ClassScopeFunctionSpecializationDecl AST 节点移除

ClassScopeFunctionSpecializationDecl AST 节点已被移除。依赖类作用域的显式函数模板特化现在改用 DependentFunctionTemplateSpecializationInfo 来存储候选主模板和显式模板实参。

这对 Clang 作为编译器的使用者无影响，但可能破坏 Clang 工具链（如 clang-tidy、自定义 AST Matcher、Refactoring 工具）中遍历 AST 时的假设。如果工具的 AST 遍历逻辑依赖于此节点类型的存在性，需要进行适配。

🟡 影响范围 仅影响基于 Clang 的AST 工具（clang-tidy 检查、AST Visitor/Matcher 插件等）。如果工具代码中有 isa<ClassScopeFunctionSpecializationDecl> 或 dyn_cast<ClassScopeFunctionSpecializationDecl> 的调用，需要更新为新的 AST 遍历方式。

8.2 -fdelayed-template-parsing 不再默认为 C++20 MSVC 启用

以前，当以 MSVC 兼容模式（--target=x86_64-pc-windows-msvc）编译 C++20 代码时，Clang 默认开启 -fdelayed-template-parsing。LLVM 18 起，C++20 模式下不再默认启用此标志，以匹配 MSVC 的行为（MSVC 在 C++20 模式下也默认关闭延迟模板解析）。

延迟模板解析允许模板体在被实例化之前包含语法错误，这是一种非标准的行为扩展。关闭后，模板体中的语法错误会在解析时立即报告。

条件LLVM 17 行为LLVM 18 行为
MSVC 目标 + C++20 延迟模板解析默认启用 延迟模板解析默认关闭（匹配 MSVC）
MSVC 目标 + C++17 及以下 延迟模板解析默认启用 延迟模板解析默认启用（不变）
非 MSVC 目标 延迟模板解析默认关闭 延迟模板解析默认关闭（不变）
🔵 跨平台项目的注意点 对于在 MSVC 目标下编译的 C++20 代码，如果之前依赖延迟模板解析（即有些模板在未实例化时才暴露出语法错误），升级 LLVM 18 后这些错误会立即暴露。如果确实需要，可以显式添加 -fdelayed-template-parsing 标志恢复旧行为。

8.3 C++20 命名模块：移除硬编码导入路径

LLVM 18 移除了 C++20 命名模块（named modules）的硬编码导入路径。现在要求所有依赖模块必须通过命令行指定（例如 -fmodule-file=），不再有隐式搜索路径。这符合 C++20 模块设计的明确性原则：每个导入的模块都必须显式告知编译器如何找到它。

此变更主要影响使用 C++20 模块的项目（import M; 语法）。如果之前依赖编译器自动查找模块文件，升级后需要在命令行中显式传递所有依赖模块的路径。（相关 Issue: #62707）

示例 — 命令行变更
# 旧行为 (LLVM 17)：依赖硬编码或隐式搜索路径
clang++-17 -std=c++20 -c foo.cpp   # 隐式寻找模块

# 新行为 (LLVM 18)：必须显式指定所有依赖模块文件
clang++-18 -std=c++20 -fmodule-file=MyModule=MyModule.pcm -c foo.cpp
# 每个 import 的模块都需要对应的 -fmodule-file= 参数

8.4 import XXX 不再允许查找显式 Clang 模块

在 C++ 代码中，import XXX; 不再允许从显式 Clang 模块（explicit clang modules，即传统的 .modulemap 定义的模块）中查找模块 XXX。这严格区分了 C++20 命名模块（named modules）和传统的 Clang 模块机制。（相关 Issue: #64755）

🟡 影响范围 影响同时使用 C++20 import 语法和传统 Clang 模块（.modulemap / @import）的混合项目。如果有代码依赖 import XXX; 来导入传统模块，需要改用 @import XXX; 或 #include，或将模块迁移到 C++20 命名模块标准。

Sugared 类型转储简化

AST 转储破坏性变更

变更说明

在 -ast-dump 输出（文本和 JSON 格式）中，当含糖类型（sugared type）的文本表示与去糖类型（desugared type）相同时，Clang 不再重复打印去糖类型。这意味着转储输出更加简洁，但依赖转储输出格式的工具可能需要适配。

文本转储变更

示例 — 文本 AST 转储
// 旧（LLVM 17）：重复打印相同表示
'foo':'foo'

// 新（LLVM 18+）：仅打印一次
'foo'

JSON 转储变更

示例 — JSON AST 转储
// 旧（LLVM 17）：同时包含 qualType 和 desugaredQualType
"type": {
  "qualType": "foo",
  "desugaredQualType": "foo"
}

// 新（LLVM 18+）：仅当表示不同时才包含 desugaredQualType
"type": {
  "qualType": "foo"
}

// 当两者不同时，仍保留 desugaredQualType 字段
"type": {
  "qualType": "ElaboratedType",
  "desugaredQualType": "int *"
}

影响评估

此变更主要影响依赖 AST 转储输出的工具和脚本（如解析 -ast-dump 文本输出或 JSON 输出的自动化工具）。如果工具假设 desugaredQualType 字段始终存在，需要适配为处理该字段可能缺失的情况。

TARGET_OS_* 宏默认定义（Darwin 平台）

Darwin / Apple 平台
🟡 Darwin (Apple) 平台上 Clang 现在默认定义 TARGET_OS_* 系列宏 这是一项 Clang 扩展，可能破坏那些未正确包含 TargetConditionals.h 而对 TARGET_OS_* 宏做存在性检查的现有代码。

变更说明

在 Darwin 平台上，Apple SDK 的 TargetConditionals.h 头文件传统上负责定义 TARGET_OS_* 系列宏（如 TARGET_OS_IOS、TARGET_OS_MAC、TARGET_OS_WATCH 等）。LLVM 18 起，Clang 默认自行定义这些宏，不再依赖 SDK 头文件。

对于那些未正确包含 TargetConditionals.h 但又依赖 TARGET_OS_* 宏来控制条件编译的代码，此变更可能导致编译行为变化：以前宏可能未被定义（条件分支走入 #else），现在宏被 Clang 自动定义，条件分支选择可能改变。

示例 — 受影响的代码模式
// 旧代码：未包含 TargetConditionals.h，依赖 SDK 隐式定义
// LLVM 17：TARGET_OS_IOS 可能未定义 → 走入 #else
// LLVM 18：TARGET_OS_IOS 被 Clang 自动定义 → 走入 #if 分支

#if TARGET_OS_IOS
// 原来可能不执行，现在可能执行
#else
// 原来可能执行，现在可能不执行
#endif

// 正确做法：先包含 SDK 头文件
#include <TargetConditionals.h>
// 现在 TARGET_OS_* 宏由 Clang 或头文件定义，行为一致

关于 TargetConditionals.h

Apple SDK 的 TargetConditionals.h 现在会检查 Clang 是否已定义这些宏，如果已定义则使用 Clang 的值，保持向后兼容。但如果代码未包含此头文件（例如仅在条件编译中检查宏是否存在），行为可能改变。

关闭此扩展

可通过 -fno-define-target-os-macros 编译选项关闭此扩展，恢复旧行为。

__has_cpp_attribute / __has_c_attribute 返回值修正

诊断行为变更

变更说明

LLVM 18 修复了 __has_cpp_attribute 和 __has_c_attribute 对某些 C++11 风格属性返回错误值的问题。此前，某些属性的无命名空间前缀版本会错误地返回非零值（表示支持），而实际上只有带命名空间前缀的版本才是正确的。

具体变更详情

测试项LLVM 17 值LLVM 18 值说明
__has_cpp_attribute(unused) 201603 0 无前缀版本不再错误地报告支持
__has_cpp_attribute(gnu::unused) 201603 1 带 gnu:: 前缀的返回值修正
__has_c_attribute(unused) 202106 0 C 属性无前缀版本不再错误报告支持
__has_cpp_attribute(clang::fallthrough) 201603 1 带 clang:: 前缀的返回值修正
__has_cpp_attribute(gnu::fallthrough) 201603 1 带 gnu:: 前缀的返回值修正
__has_c_attribute(gnu::fallthrough) 201910 1 C 属性 gnu:: 版本修正
__has_cpp_attribute(warn_unused_result) 201907 0 无前缀版本不再错误地报告支持
__has_cpp_attribute(clang::warn_unused_result) 201907 1 带 clang:: 前缀的返回值修正
__has_cpp_attribute(gnu::warn_unused_result) 201907 1 带 gnu:: 前缀的返回值修正
__has_c_attribute(warn_unused_result) 202003 0 C 属性无前缀版本不再错误报告支持

影响评估

核心模式：无命名空间前缀的属性（如 unused、warn_unused_result）在 LLVM 17 中 __has_cpp_attribute / __has_c_attribute 会错误地返回非零值。LLVM 18 修正后返回 0（表示不支持）。正确的做法是使用带命名空间前缀的版本（gnu::unused、clang::fallthrough 等），这些版本在 LLVM 18 中返回 1 或正确的标准版本号。

🟡 代码适配 如果代码使用 __has_cpp_attribute(unused)（无前缀）来检测编译器是否支持 [[unused]] 属性，在 LLVM 18 中此检测会返回 0。应改为使用 __has_cpp_attribute(gnu::unused) 或直接使用标准 C++17 的 [[maybe_unused]]。

LLD 链接器新增功能

新特性 / 行为变更

LLD 在 LLVM 18 中除了 FatLTO（见第 7 节）外，还有多项重要新增功能和改进：

12.1 -Bsymbolic-non-weak

新增 -Bsymbolic-non-weak 选项。与 -Bsymbolic 类似地将符号绑定到本地定义，但仅适用于非弱符号（non-weak definitions）。弱符号（weak symbols）仍允许被覆盖。这对于希望减少非弱符号的 GOT 重定位、同时保留弱符号覆盖能力的场景很有用。

12.2 --no-allow-shlib-undefined

增强的 --no-allow-shlib-undefined 选项。当共享库引用非导出定义时，LLD 现在报告错误。增强了在构建 DSO 时对未定义符号的检测能力，有助于避免运行时符号解析失败。

12.3 --save-temps 改进

--save-temps 和 --lto-emit-asm 现在从 bitcode 文件名派生 ELF/汇编输出文件名。旧行为生成 out1.lto.o、out2.lto.o 等序号命名，新行为使用更直观的命名：ld.lld --save-temps a.o d/b.o -o out 会生成 out.lto.a.o 和 d/out.lto.b.o。

示例 — save-temps 命名变更
# LLVM 17：顺序编号
ld.lld --save-temps a.o d/b.o -o out
# → out1.lto.o, out2.lto.o （难以追踪来源）

# LLVM 18：基于输入文件命名
ld.lld --save-temps a.o d/b.o -o out
# → out.lto.a.o, d/out.lto.b.o （保留目录结构和源文件名）

12.4 common-page-size 可大于 system-page-size

-z common-page-size= 现在可以设置为大于 -z max-page-size= 或系统页大小的值。此前这会被限制。这对于需要大对齐要求的场景（如 huge page 映射）很有用。相关 Issue: #57618

12.5 OVERLAY 支持起始地址和 LMA

链接脚本中的 OVERLAY 命令现在支持可选的起始地址和LMA（Load Memory Address）指定。这增强了对嵌入式系统中常见的内存覆盖（overlay）功能的支持。相关 PR: #77272

12.6 cdsort：调用图剖面驱动的段排序

当存在调用图剖面信息（通过 instrumentation 或 sample PGO 获得）时，输入段的排序现在使用新的 cdsort 算法，替代了之前的 hfsort 算法。cdsort 提供更好的排序结果，进一步优化指令缓存局部性和 TLB 命中率。

12.7 --lto-validate-all-vtables-have-type-infos

新增 --lto-validate-all-vtables-have-type-infos 选项，作为 --lto-whole-program-visibility 的补充，用于禁用不安全的全程序去虚化。可选的 --lto-known-safe-vtables=<glob> 可用于标记已知安全的虚函数表符号。这为 LTO 下的虚函数去虚拟化提供了更细粒度的安全控制。

影响评估

功能类型适用场景
-Bsymbolic-non-weak 新选项 希望减少 GOT 开销但保留弱符号可覆盖能力的共享库
--no-allow-shlib-undefined 行为增强 构建 DSO 时的严格未定义符号检测
--save-temps 命名改进 行为变更 调试 LTO 编译过程的构建系统；影响 parse 输出文件名的脚本
common-page-size 放宽 行为变更 需要大页对齐的嵌入式或高性能场景
OVERLAY 起始地址/LMA 新功能 嵌入式系统的内存覆盖链接脚本
cdsort 新算法 使用 PGO 优化的项目（自动生效，无需额外配置）
--lto-validate-all-vtables 新选项 LTO 下需要安全保证的虚函数去虚拟化

AArch64 后端变更

新支持 架构级别修正

13.1 新增 CPU 支持

LLVM 18 的 AArch64 后端新增了对以下 CPU 的支持：

  • Cortex-A520：ARM 的高效核心（LITTLE core）
  • Cortex-A720：ARM 的中等性能核心（MID core）
  • Cortex-X4：ARM 的高性能核心（BIG core）

使用 -mcpu=cortex-a520、-mcpu=cortex-a720、-mcpu=cortex-x4 即可启用对应的调度模型和微架构优化。

13.2 Neoverse-N2 架构级别修正

Neoverse-N2 之前被错误地标记为 Armv8.5a 核心。LLVM 18 修正为 Armv9.0a 核心。作为 Armv9 核心，crypto 选项不再默认启用，因此需要 -mcpu=neoverse-n2+crypto 来显式启用加密扩展。

🟡 兼容性注意事项 编译方面，Armv9.0a 启用的特性与 Armv8.5a 相同，唯一的例外是 crypto（不再默认启用）。如果项目使用 -mcpu=neoverse-n2 且依赖 crypto 扩展（AES、SHA 等），必须在编译选项中添加 +crypto 后缀。
示例 — Neoverse-N2 编译选项变更
# LLVM 17：crypto 默认启用（错误地按 Armv8.5a 处理）
clang-17 --target=aarch64-linux-gnu -mcpu=neoverse-n2 -c foo.c

# LLVM 18：crypto 不再默认启用（正确按 Armv9.0a 处理）
clang-18 --target=aarch64-linux-gnu -mcpu=neoverse-n2 -c foo.c
#          ^-- crypto 未启用

# 需要 crypto 时，显式添加：
clang-18 --target=aarch64-linux-gnu -mcpu=neoverse-n2+crypto -c foo.c
#          ^-- crypto 显式启用

13.3 2023 架构扩展支持

汇编器和反汇编器新增了对 2023 年 ARM 架构扩展的支持。这些扩展涵盖了 ARMv8.x 和 ARMv9.x 在 2023 年发布的新指令集和系统寄存器特性。具体可参考 ARM 架构参考手册（Arm ARM）的 2023 版本。

13.4 栈冲突保护（Stack Clash Protection）

AArch64 后端新增了对栈冲突保护（Stack Clash Protection）的支持。在函数帧创建和动态栈分配期间，编译器会按固定间隔发出内存访问，确保栈顶的保护区域不会被跳过。这有助于防御栈冲突攻击（stack clash attack）。

以下是针对数通产品线从 LLVM 17 升级到 LLVM 18 的优先级建议：

优先级变更项类型核心行动

🔵 关键结论 对于数通产品线，函数模板名称重整是 LLVM 18 影响最大、最需要优先关注的变更。如果产品使用了动态加载插件或预编译动态库，必须在升级前完成符号兼容性评估。

-Wenum-constexpr-conversion 虽然在 LLVM 18 中只是告警，但因为 LLVM 19 起将升级为不可压制的错误，必须在 LLVM 18 阶段完成所有修复，为后续升级铺平道路。

Darwin 平台的 TARGET_OS_* 宏变更、AArch64 平台的 Neoverse-N2 修正、C++20 模块的导入路径变化是需要关注的平台/特性特定变更。

LLD 的 cdsort、OVERLAY、--save-temps 命名改进等虽为默认行为变更，但影响相对可控，主要是改进和增强。
