EJIT · EmbeddedJIT · 时间窗常量 × 运行时特化

把运行时，
变成编译期。

一个长在裸核固件里的 JIT 编译器 —— 以及，我们如何在一颗没有 std::thread 的核上，手搓了一整个并发运行时。

开场（30 秒）：先别管 JIT。看屏幕下方这条信号线：在大部分时间里它上蹿下跳，编译器对它一无所知，只能老老实实每次从内存读；但在某几段时间里，它是平的——值不变。EJIT 做的事只有一件：在那段平的时间里，把运行时的值当成编译期常量，重新编一份代码。

这条线今天会反复出现：窗口打开（activate）→ 特化代码接管；窗口关上（deactivate）→ 立刻回到 AOT，什么都不会坏。

自我介绍后直接翻页。不要在这里解释任何术语；下一页先给约束，让观众先觉得"这不可能"。

四步讲完 EJIT 的全部协议，它们构成一个环：标注 → 激活 → 特化 → 失效 → 再激活。按 → 逐个出现四张卡片和箭头。

强调两点：（1）用户只写标注，调用还是调原函数名，没有 API 入侵；（2）"先 deactivate 再改、改完再 activate"是唯一的契约——它取代了传统 JIT 里那一整套去优化（deopt）机制。

如果有架构背景的听众，可以补一句：async-only 是 11 月才定的，之前的同步模式已经整个删掉，代码更少、竞态也更少。

第一幕 · 问题

配置不是常量。但在它自己那段时间里，它是。

对编译器来说

这 4 个全局变量在 AOT 那一刻"可能随时会变"。于是每次循环都要从内存读、每次都要判——哪怕它们整整 40% 的时间里一动不动。

对业务来说

改配置是一件大事：要停业务、要重新建链。它发生在清楚的边界上，业务自己知道。

这是基带开发者最熟悉的一张图。单板类型上电就定了；小区类型、小区 ID 在建链之后不变；调度模式在重配之前不变。它们不是 C 意义上的 const——会变——但变化只发生在清晰的边界上。

按 → 出现蓝色窗口。窗口里所有通道都是平的。问题在于：编译器在 AOT 的时候看不见这个窗口，它只能假设最坏情况。

第一幕 · 第三条路

数据不是常量。
但在一段时间里，它是。

所以别问"它是不是常量"，问"它在哪段时间里是常量"。把这个窗口告诉编译器——这就是 EJIT 的全部赌注。

AOT

编译发生在 t = 0 之前。配置值还不存在，只能假设"随时会变"。

传统 JIT

编译发生在第一次调用。值已知，但每个函数、每个取值都要来一遍，还要防它变。

EJIT

编译发生在窗口打开之后。值已知，而且业务承诺它在窗口内不变。

停在这页久一点，这是整场演讲的核心一句话。

三个小时间轴：AOT 编译得太早，值还不存在；传统 JIT 编译得刚好，但它不知道值会不会变，所以需要 deopt、需要 profile、需要一堆基础设施；EJIT 多知道一件事——业务承诺"这个窗口里它不变"——于是整栋大楼都可以省掉。

标注变成了什么
  • load 级：!ejit.period_const 直接挂在 load 指令上 —— 仿照 volatile 的传递链，但用 metadata 而不是指令位
  • GV 级：!ejit.metadata 记录数组属于哪个窗口、哪些字节偏移是常量字段
  • 软标注：任何 pass 丢掉它，只会少一次优化，不会错
为了保住它，我们动了两处核心 LLVM

instruction metadata 很脆，任何重写 load 的优化都可能把它丢掉。于是：

  • PASS1在一切优化之前抽 bitcode，再按 GV 偏移表把丢掉的标注挂回去
  • IRFixedMetadataKinds.def：给它一个固定编号（42）
  • Local.cpp复制 load 时保留它（copyMetadataForLoad）

左边是从 ejit_dump_test.c 真实 dump 出来的 IR，只去掉了 tbaa/align 噪声。两条 period_const load、一条普通 load，一目了然。

关键设计是"软标注"：metadata 不是语义，丢了不会错。这也是我们敢把 LLVM 的整套优化流水线直接搬过来跑的原因——它不认识这个标注，顶多忽略它。

右边卡片是给编译器同学的彩蛋：为了不让标注在优化里丢失，核心 LLVM 加了一个固定 metadata kind，并在复制 load 的地方多保留一行。整个项目对核心 LLVM 的"语义性"改动就这么点，其余都是 #ifdef 裁剪。

第二幕 · AOT 编译期

两阶段 AOT：先备份 bitcode，再插探针，然后才轮到 O2

PASS1 抽出的是还没被任何优化碰过的 bitcode；wrapper 留在函数入口。所有特化决策，都推迟到窗口打开之后。

AOT 侧一共就做两件事：备份一份干净的 bitcode（PASS1），以及在函数入口插一段探针（PASS2–4）。其它全是 LLVM 原有流水线。

两个"为什么"值得讲：PASS1 排在最前，是因为 load 级 metadata 经不起优化；PASS2–4 排在 O2 前面（非 LTO），是故意的——这样 O2 会把探针的 fallback 路径一起优化掉，而且 noinline 属性能在 inliner 之前生效，防止 wrapper 被内联进调用者。

下面两条是精确的 pass 顺序，给编译器同学看。挤在中间的 LowerFreeDim 是 EJIT_FREE_DIM 的下推（PassBuilderPipelines.cpp:1679，无开关、永远跑）；LTO 路径下 post-link 还会各再跑一次。

一个基本块，没有分支

≤ 2 维时 cell 表在定义时就预填 &f_miss，读出来永远可调用。域外下标不判跳，走 select。

3–4 维：判空 + expect

表太大（16³ / 16⁴ 个重定位），改成零初始化 + 判空，分派到 dispatch / miss。

热路径不拿读令牌

探针里塞不进别的东西。安全性来自另一条规则：特化代码永不释放（drain ≠ reclaim）。

这一页是"一次调用到底发生了什么"的真实答案。按 → 先看慢路径，再看热路径。

慢路径 f_miss 是 noinline 的：funcIndex 守卫、拼维度、问运行时要函数指针、命中就调并归还读令牌、否则跑原函数体。它在第一次调用、以及没激活的时候才会被走到。

热路径只有一个基本块：算 cell 地址、（域外的用 select 换成 miss 哨兵）、原子读、musttail 尾调用。没有判空、没有分支、没有栈帧。能用这种"无脑跳"的前提，是 cell 表定义时就填好了 &f_miss —— 读到谁就跳谁。

右下那张小图是整件事的形状：上面一条是热路径，往左下落到慢路径，往右下直接跳进特化代码；慢路径编译完把结果发布进 cell，下一次调用就从右边走了。

第三步三张卡是设计取舍：为什么不拿读令牌？因为热路径已经塞不进别的东西。代价是特化代码永远不能释放 —— 如果哪天要释放，就得把 inline cache 关掉。这是有意为之的"用空间换确定性"。

第三幕 · W^X

写完就封：一个 6 字节的函数，独占 4096 字节

① 开池

SRE_MemDbgAlloc 一块 2 MiB、对齐；一次 split_2m_to_4k → 512 个 4 KiB 页。

② 写（RW）

bump 分配，每个特化至少独占一页。池子保持可写 —— allocate 绝不 enable_ex。

③ 封（RX）

finalize 逐页 enable_ex；任一页失败，整个 finalize 失败。sealAndSyncCache 清 D-cache、失效 I-cache。

④ 代价

compute_cell 特化后 6 字节，独占 4096 字节。封过的池子永不复用；代码永不释放。

空闲RW · 正在写RX · 已封固6 B 的函数

一个 2 MiB 池 = 512 × 4 KiB（全部画出）。生产预设另有 .text.ejit 固定池 16 MiB（≈ 7 池）；Tier-1 插桩代码放远端动态池。

"enable_rw 必须同时清执行位 —— 只翻 AP 位，会留下一个 RWX 的写窗口。" · EJIT_SRE_CODE_POOL §14.2

裸核上没有 mmap，没有 mprotect。可执行内存要靠平台接口一页一页地要。按 → 分四步。

① 开一块 2 MiB，切成 512 个 4 KiB 页。② 写代码的时候整块是 RW —— 写入期间绝不同时可执行。③ finalize 时逐页封成 RX，同时清 D-cache、失效 I-cache。④ 代价：每个特化至少占一页。那个 6 字节的函数，独占 4096 字节。

最下面那句引言是血泪教训：把页改回可写时必须同时清掉执行位，否则就是一个 RWX 窗口。

EJitAtomic

MPSC 环

Vyukov 有界环 1024 槽。producer CAS(enqueuePos) 抢槽，写完 storeRelease 发布。

去重

inFlight[funcIndex] 存 generation，CAS(0→gen) 占位，O(1)。同一个函数在队列里最多一份。

32 桶 × 16 槽的 POD，没有哈希表分配。读 tryRead 不等待；写者举旗后自旋，等读者归零。

version

U32 单调递增。worker 过两个检查点，发布前在桶写锁里再校验一次（commit gate）。

"单 consumer 是 Vyukov 无锁正确性的硬约束"：多一个消费者，就会出现"幽灵空"伪信号。

没有 std::thread，没有 <atomic>，没有 std::mutex。但我们需要：多个业务核同时提交编译请求、一个 worker 核消费、所有核共享一份结果缓存，还不能有锁。

右边是仿真：三个 producer（业务核）往一个 1024 槽的环里抢位；同一个函数被两个核同时提交时，第二个会被去重弹回（红色的那个）；唯一的 consumer（worker）从另一头取。

第三幕 · 跨核

八个核，一个 worker：用 CAS 选出来的独裁者

待真机：真实 core id 与跨核选举、共享 section 同 VA、跨核 I/D-cache 一致性 —— host 上只能 mock，文档自己写着"未在本机验证"。

多核怎么办？八个核都会调 ejit_init，但只能有一个 worker。做法是一段 CAS：谁把 initState 从 Uninitialized 改成 Initializing，谁就是 owner，由它把共享 blob 铺好，最后 storeRelease(Ready)。其他核看到 Initializing 只会让出几次，绝不会"等不及自己再建一个"。

按 → 第二步：共享 blob 必须是纯 POD，连构造函数都不能有 —— 否则后启动的核一跑构造函数，就把正在运行的队列清零了。

第三步是最反直觉的一条：同 VA ≠ 同执行权限。enable_ex 改的是调用核自己的页表，所以每个核都得自己封一遍。这些都还没上真机验证。

第四幕 · 校准

PGO 的内联阶段是个 no-op —— 而且我们是量出来的

PGO 的阶段预期在真实 EJIT 闭包上
内联（ModuleInliner）按热度补内联no-op AOT 预内联已经把 callee 全部消化掉
块布局（MachineBlockPlacement）热路径顺排有效 构造用例：taken 99% → fall-through；"收益真实但非数量级"
间接调用提升（ICP）按目标特化有限 真实闭包里间接调用很少
代价—运行时 +640 KB · 插桩 · 多一次重编译

所以 go / no-go 至今没有拍板："MBP 的收益，是否配得上 +640 KB"。设计文档里自己写着：等真机数据。中途还有过一次方向反转（v0.10）——推翻了前两个版本"非内联版常优于内联版"的假设。

PGO 做出来之后，我们拿 12 个真实的 EJIT 程序校准了一遍，结论很尴尬：AOT 预内联已经把所有 callee 消化了，JIT 的 PGO 内联阶段无事可做，是个 no-op。

真正还有事做的只剩后端的块布局：分支方向翻转、冷块外提。一个构造出来的用例里，taken 99% 的分支从跳转变成了 fall-through。但文档自己的措辞是"收益真实，但不是数量级"。

所以 go/no-go 到今天没有拍板：这点收益配不配得上 640 KB 和一次额外的重编译。中途还推翻过一次自己的假设。这些我们都写进了文档。

别问一个值是不是常量，问它在哪段时间里是常量。把这个窗口写进程序，编译器就能替你把"这段时间"变成编译期。
