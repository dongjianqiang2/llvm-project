1. EJIT 是什么

EmbeddedJIT 是面向嵌入式场景的运行时特化编译系统。它允许开发者把“某个业务时间窗内保持不变的数据”标注出来，运行时在时间窗激活后将这些数据当作编译期常量，生成针对当前配置的特化机器码。

核心思想

在 ejit_activate 与 ejit_deactivate 之间，标注为 EJIT_PERIOD_CONST 的字段可被 JIT 读成常量。

主要收益

常量传播、分支折叠、死代码消除、局部内联和 CFG 简化，减少配置分支和重复判断。

安全语义

JIT 失败、缓存未命中、时间窗未激活、内存不足等情况均回退到原 AOT 代码执行。

用户源码标注 → Clang 生成 EJIT metadata → AOT Pass 嵌入 bitcode 并插入 wrapper → 运行时 activate 时间窗 → 调用 EJIT_ENTRY → cache hit 则执行特化代码，否则 fallback AOT

典型使用场景：

  • 板级配置、制式配置、cell/trp/channel 等在一段时间内稳定的业务配置；
  • 配置字段决定大量分支路径，且同一实例会被重复调用；
  • 可接受首次调用 JIT 编译成本，或使用异步模式先 fallback、后台编译。

2. 快速开始

2.1 引入头文件

用户侧推荐直接包含运行时 C API 头文件。该头文件已提供 6 个属性宏；定义 EJIT_DISABLE 可临时关闭所有 EJIT 标注，用于 A/B 对比或非 Clang 编译。

#include "llvm/ExecutionEngine/EJIT/EJitRuntime.h"

2.2 标注配置结构体和时间窗数组

#include <stdint.h>
#include "llvm/ExecutionEngine/EJIT/EJitRuntime.h"

#define MODE_FDD 1
#define MODE_TDD 2

struct CellConfig {
    EJIT_PERIOD_CONST uint32_t mode;      // 时间窗内可特化为常量
    EJIT_PERIOD_CONST uint32_t threshold; // 时间窗内可特化为常量
    uint32_t runtimeCounter;           // 普通字段，不参与常量替换
};

// 每个 cell 下标是一个独立时间窗实例
EJIT_IN_PERIOD_ARRAY(cell) struct CellConfig g_cellCfg[16];

static void fdd_path(int value);
static void tdd_path(int value);
static void default_path(int value);

// 用户仍然调用原函数名；编译器会在函数入口插入 wrapper
EJIT_ENTRY
void process_cell(EJIT_DIM(cell) uint8_t cellIdx, int value) {
    if (g_cellCfg[cellIdx].mode == MODE_FDD) {
        fdd_path(value + g_cellCfg[cellIdx].threshold);
    } else if (g_cellCfg[cellIdx].mode == MODE_TDD) {
        tdd_path(value);
    } else {
        default_path(value);
    }
}

// 修改 cell 配置的函数要标注生命周期，编译器自动插入 deactivate/activate
EJIT_PERIOD_GUARD(cell)
void update_cell_cfg(EJIT_DIM(cell) uint8_t cellIdx,
                     uint32_t mode,
                     uint32_t threshold) {
    g_cellCfg[cellIdx].mode = mode;
    g_cellCfg[cellIdx].threshold = threshold;
}

2.3 初始化、激活并调用

int main(void) {
    ejit_config_t cfg = {0};
    cfg.compileMode = EJIT_COMPILE_SYNC; // 或 EJIT_COMPILE_ASYNC
    cfg.optLevel = EJIT_OPT_L2;
    cfg.maxCodeMemory = 2 * 1024 * 1024;
    cfg.maxCacheEntries = 4096;
    cfg.enableLogger = true;

    if (ejit_init(&cfg) != EJIT_OK) {
        return 1;
    }

    g_cellCfg[3].mode = MODE_FDD;
    g_cellCfg[3].threshold = 10;

    // 激活 cell[3] 时间窗；之后 process_cell(3, ...) 可触发特化
    ejit_activate("cell", 3);

    process_cell(3, 100); // 首次：同步模式编译；异步模式 fallback 并提交后台编译
    process_cell(3, 101); // 后续：命中 cache 时执行特化版本

    // 修改配置时应通过生命周期函数，或手动 deactivate / activate
    update_cell_cfg(3, MODE_TDD, 20);
    process_cell(3, 102); // 重新特化或 fallback

    ejit_shutdown();
    return 0;
}
最小使用闭环： 标注 EJIT_PERIOD_CONST 字段 → 标注 EJIT_IN_PERIOD_ARRAY 全局数组 → 标注 EJIT_ENTRY 和 EJIT_DIM → ejit_init → ejit_activate → 调用原函数。

3. 源码标注接口

3.1 属性总览

宏标记对象作用常见约束
EJIT_PERIOD_CONST结构体字段字段在激活时间窗内可被 JIT 当作常量支持整型、布尔、浮点、嵌套结构体及数组；volatile 不特化
EJIT_IN_PERIOD(static)非数组全局变量运行期不变的全局配置，默认永远激活当前推荐只使用内置 static 标量时间窗
EJIT_IN_PERIOD_ARRAY(name)全局数组或指向结构体的全局指针定义按下标独立激活的时间窗数组固定数组建议 < 100；全程序最多 1024 个数组
EJIT_ENTRY函数标记可 JIT 特化的入口函数不支持递归；异步模式下副作用应幂等
EJIT_DIM(name)函数参数声明该参数是某个时间窗数组的下标维度必须为整数；每函数最多 4 个维度
EJIT_PERIOD_GUARD(name)函数标记会修改时间窗数据的生命周期函数必须存在同名 EJIT_DIM 参数；可标多个 period

3.2 静态配置：EJIT_IN_PERIOD(static)

struct BoardConfig {
    EJIT_PERIOD_CONST uint32_t boardType;
    uint32_t flags;
};

EJIT_IN_PERIOD(static) struct BoardConfig g_boardCfg;

EJIT_ENTRY
void process_board(void) {
    if (g_boardCfg.boardType == 1) {
        // JIT 时 boardType 可被折叠为常量
    }
}

static 时间窗代表 JIT 运行期不变的全局配置，不需要调用 ejit_activate。

3.3 数组时间窗：EJIT_IN_PERIOD_ARRAY(name)

多个全局数组可以使用同一个时间窗名称。调用 ejit_activate("cell", idx) 会激活该名称下所有数组的同一下标。激活状态仅以时间窗名称 + 实例 index 为键，没有数组指针维度；若多个数组共享同一时间窗名称，激活对该 period 实例整体生效。

struct CellConfig { EJIT_PERIOD_CONST uint32_t mode; };
struct CellState  { EJIT_PERIOD_CONST uint32_t state; };

EJIT_IN_PERIOD_ARRAY(cell) struct CellConfig g_cellCfg[16];
EJIT_IN_PERIOD_ARRAY(cell) struct CellState  g_cellState[16];

// 激活 g_cellCfg[3] 和 g_cellState[3]
ejit_activate("cell", 3);

3.4 多维特化

一个 EJIT_ENTRY 函数最多可声明 4 个时间窗数组下标。运行时 cache key 使用高 32 位函数索引 + 低 4 字节维度值编码。

EJIT_IN_PERIOD_ARRAY(cell) struct CellConfig g_cellCfg[16];
EJIT_IN_PERIOD_ARRAY(trp)  struct TrpConfig  g_trpCfg[8];

EJIT_ENTRY
void process_pair(EJIT_DIM(cell) uint8_t cellIdx,
                  EJIT_DIM(trp)  uint8_t trpIdx,
                  int payload) {
    if (g_cellCfg[cellIdx].mode == 1 && g_trpCfg[trpIdx].type == 2) {
        // cellIdx/trpIdx 均可成为特化维度
    }
}

3.5 生命周期函数

凡是会修改 EJIT_PERIOD_CONST 字段或其所在结构体的函数，建议用 EJIT_PERIOD_GUARD 标注。编译器会在函数入口插入失效操作，在所有返回点前重新激活。

EJIT_PERIOD_GUARD(cell) EJIT_PERIOD_GUARD(trp)
void update_both(EJIT_DIM(cell) uint8_t cellIdx,
                 EJIT_DIM(trp)  uint8_t trpIdx) {
    g_cellCfg[cellIdx].mode = 2;
    g_trpCfg[trpIdx].type = 4;
}
注意： 如果绕过生命周期函数直接修改已激活时间窗内的 EJIT_PERIOD_CONST 字段，旧的特化代码可能基于旧值。请使用 EJIT_PERIOD_GUARD 或手动 ejit_deactivate / 修改 / ejit_activate。

4. 运行时 API

4.1 初始化配置

当前 C API 的配置结构体位于 llvm/include/llvm/ExecutionEngine/EJIT/EJitRuntime.h：

typedef struct {
  ejit_compile_mode_t compileMode; // EJIT_COMPILE_SYNC / EJIT_COMPILE_ASYNC
  ejit_opt_level_t optLevel;       // EJIT_OPT_L1 / L2 / L3
  size_t maxCodeMemory;            // JIT 代码内存上限
  size_t maxDataMemory;            // 数据内存上限
  size_t maxCacheEntries;          // cache 条目数上限
  size_t maxCacheSize;             // cache 总大小上限
  bool enableLogger;               // 是否启用日志
  bool forceStaticRegistry;        // 裸核：强制使用静态注册表
  const char *dumpJITDir;          // 非空时输出优化后的 JIT IR
} ejit_config_t;
接口说明
ejit_init(const ejit_config_t *config)初始化 EJIT。传 NULL 使用默认配置。会消费构造期或静态表注册的 bitcode/period 信息。
ejit_shutdown(void)释放 EJIT 运行时资源。
ejit_set_compile_mode(mode)运行期切换同步/异步编译模式。
ejit_get_compile_mode()查询当前编译模式。

4.2 同步与异步模式

模式首次未命中行为适用场景注意事项
EJIT_COMPILE_SYNC阻塞等待 JIT 编译完成，成功后直接执行特化版本可接受首次延迟，希望尽快获得性能收益首次调用延迟更明显
EJIT_COMPILE_ASYNC提交后台编译，当前调用 fallback 到 AOT对首次延迟敏感EJIT_ENTRY 副作用应幂等，避免首次 AOT 与后续 JIT 行为不一致

4.3 时间窗生命周期 API

ejit_status_t ejit_activate(const char *periodName, uint8_t cellIdx);
ejit_status_t ejit_deactivate(const char *periodName, uint8_t cellIdx);

ejit_status_t ejit_activate_all(const char *periodName);
ejit_status_t ejit_deactivate_all(const char *periodName);
bool ejit_is_active(const char *periodName, uint8_t cellIdx);
  • activate(name, idx)：激活该名称下所有数组的 idx 实例。
  • deactivate：标记时间窗失效，并使依赖该实例的缓存条目失效。
  • 激活仅以时间窗名称 + 实例 index 为键；数组级接口 ejit_activate_array / ejit_deactivate_array 已移除（产品不需要数组级生命周期激活）。
  • 如果同名数组长度不同，越界数组会被跳过；用户仍应保证业务下标合法。

4.4 Cache、统计和错误

void ejit_clear_cache(void);
void ejit_invalidate(const char *periodName, uint8_t cellIdx);

ejit_status_t ejit_get_stats(ejit_stats_t *stats);
const ejit_error_t *ejit_get_last_error(void);

ejit_stats_t 包含条目数、代码大小、cache hit/miss、eviction 等信息。遇到 JIT 不生效时，建议先看 stats 和 last error，再打开 dumpJITDir 输出优化后 IR。

4.5 外部符号注册

void ejit_register_symbol(const char *name, void *addr);

host 环境下外部符号通常由 PASS1 自动扫描注册。裸核或无 dlsym 环境下，如果 JIT bitcode 引用了平台函数、全局变量或库函数，需要确保它们通过自动注册表或手动调用注册到 EJIT。

5. 构建与链接

5.1 构建 EJIT 编译器与运行时

本仓库推荐使用顶层 build.sh：

# x86 开发构建：clang/opt/lld 等
./build.sh debug x86

# x86 release：用于 EJIT 运行时测试
./build.sh release x86

# AArch64 release：用于嵌入式目标或交叉验证
./build.sh release aarch64

资源受限机器上推荐目标化增量构建：

# 开发构建核心工具
ninja -C build_debug_x86 clang opt lld

# EJIT runtime + linker
ninja -C build_release_x86 LLVMEJIT lld

# AArch64 runtime
ninja -C build_release_aarch64 LLVMEJIT lld

5.2 编译用户程序

用户程序需要使用带 EJIT 属性和 AOT pass 的 Clang 编译，并链接 libLLVMEJIT.a。实际项目建议复用 ejit_test/build.sh 中的链接规则。概念上流程如下：

# 示例：以 build_release_x86 为例，具体 include/lib 路径按构建目录调整
build_release_x86/bin/clang -O2 -g \
  -Illvm/include -Ibuild_release_x86/include \
  my_ejit_app.c \
  build_release_x86/lib/libLLVMEJIT.a \
  -fuse-ld=lld -o my_ejit_app
说明： EJIT 的 AOT pass 已集成到当前分支的 Clang/LLVM pipeline 中；正常使用带 EJIT 的 Clang 编译即可生成 metadata、嵌入 bitcode、插入 wrapper 和生命周期调用。

5.3 关闭 EJIT 做 A/B 对比

build_release_x86/bin/clang -DEJIT_DISABLE -O2 my_ejit_app.c -o my_aot_app

EJIT_DISABLE 会把属性宏展开为空，便于确认逻辑正确性、比较 AOT 和 EJIT 行为。

5.4 裁剪与单对象打包

面向裸核或小型化交付时，可以启用 LLVM 后端裁剪并用 lipo pipeline 将多个 LLVM archive 合并为单个 ejit.o。

# 推荐通过项目脚本生成 AArch64 单对象
./ejit_test/lipo/run_aarch64_pipeline.sh build_release_aarch64 ejit_test/lipo/ejit.o

# 使用 lipo 产物运行集成测试
./ejit_test/build.sh --run --lipo=ejit_test/lipo/ejit.o

稳定裁剪选项为 -DEJIT_TRIM_LLVM_BACKEND=ON。SRE code pool 相关选项见第 8 节。

6. AOT/JIT 流程

6.1 AOT 编译期做了什么

  1. Clang 解析 EJIT 属性，生成函数/全局变量级 !ejit.metadata，并在 may_const 字段 load 上生成 !ejit.may_const。
  2. PASS1 EJitRegisterBitcode 在标准优化前提取 EJIT_ENTRY 闭包 bitcode，嵌入二进制并生成注册信息。
  3. PASS2 EJitRegisterPeriod 生成 period 数组和 static 变量注册。
  4. PASS3 EJitWrapperGen 在原函数入口插入 wrapper：构造 cache key，调用运行时，成功则跳转特化函数，失败则继续原 AOT 函数体。
  5. PASS4 EJitPeriodHandler 在生命周期函数入口插入 deactivate，在所有 return 前插入 activate。
  6. PASS5 EJitAotModulePass 协调 PASS2-4。

6.2 运行时 JIT 做了什么

  1. 按 cache key 查缓存，命中则返回函数指针。
  2. 未命中时加载嵌入 bitcode。
  3. 把 EJIT_DIM 参数替换为本次调用的常量下标。
  4. 运行 InstCombine 折叠 zext/GEP 等常量链。
  5. 内联被调函数，使跨函数字段访问暴露为全局变量 GEP。
  6. PASS6 EJitStructFieldPass 将 EJIT_PERIOD_CONST 字段 load 替换为当前内存值常量。
  7. 按 L1/L2/L3 运行标准 LLVM 优化，生成机器码，放入 cache。

6.3 优化等级

等级定位典型优化
EJIT_OPT_L1保守常量传播、死代码消除、分支折叠
EJIT_OPT_L2默认/均衡L1 + CFG 简化、适度内联
EJIT_OPT_L3激进L2 + 更激进循环优化；注意代码体积

8. 裸核与 SRE 部署

8.1 Host 与 bare-metal 注册路径

环境注册机制建议
Host/Linuxllvm.global_ctors 触发 ejit_auto_register正常调用 ejit_init 即可消费注册信息
Bare-metal构造函数可能不可用；使用 __ejit_registry_*[] 静态注册表配置 forceStaticRegistry = true，链接脚本保留 registry section
无动态符号解析无法依赖 dlsym使用自动或手动 ejit_register_symbol 注册外部符号

8.2 SRE Code Pool

SRE code pool 用于替代常规 mmap/mprotect JIT 代码内存路径，适合对可执行内存权限有严格要求的平台。

# CMake 选项示意
-DEJIT_SRE_CODE_POOL=ON
-DEJIT_CODE_POOL_4K_SEAL=ON
  • 从 2MiB 对齐代码池分配 JIT 机器码；
  • 4K seal 模式下只将写入的 4K 页标记为可执行；
  • 避免写 RX 页，finalize 后不再修改；
  • 需要平台提供 enable_ex、split_2m_to_4k、SRE_MemDbgAlloc 等符号。

8.3 SRE Taskpool

SRE taskpool 是面向无 C++ thread 库环境的异步编译调度模式，默认关闭。它使用单 worker task、MPSC 队列、去重表和分桶 cache。跨核共享 taskpool 依赖共享内存映射、可执行权限、I/D cache 一致性和 owner 选举。

# 构建选项示意
./build.sh release aarch64_be --freestanding --sre-taskpool
状态提示： SRE taskpool / shared taskpool 属于平台相关能力，host 单测可验证核心逻辑，但最终仍需在目标 SRE 多核环境验证共享 section、跨核执行、任务删除和 cache 一致性。

9. 排障指南

9.1 编译期常见诊断

现象原因处理
EJIT_IN_PERIOD 用在数组上数组应使用 EJIT_IN_PERIOD_ARRAY改为 EJIT_IN_PERIOD_ARRAY(name)
EJIT_IN_PERIOD_ARRAY 用在非数组上标量变量不应使用数组时间窗静态标量使用 EJIT_IN_PERIOD(static)
EJIT_DIM 参数不是整数下标必须可编码为整数维度使用 uint8_t / int 等整数类型
超过 4 个维度cache key 只编码 4 个 8-bit 维度减少维度或拆分函数
EJIT_PERIOD_GUARD 没有同名 index 参数生命周期函数无法知道修改哪个实例添加 EJIT_DIM(name) 参数
递归 EJIT_ENTRY当前不支持递归入口特化移除 EJIT_ENTRY 或改造调用结构

9.2 JIT 没有触发

  1. 确认函数是否标注 EJIT_ENTRY。
  2. 确认使用的是带 EJIT 的 Clang，而不是系统 Clang。
  3. 确认 ejit_init 已在调用 EJIT_ENTRY 前执行。
  4. 确认相关时间窗已经 ejit_activate。
  5. 确认编译产物中存在 @__ejit_bitcode 和 ejit_compile_or_get。
  6. 裸核场景确认 registry section 没被链接器垃圾回收。
  7. 查看 ejit_get_last_error() 和 ejit_get_stats()。

9.3 JIT 触发但分支没有被折叠

  1. 字段是否标注了 EJIT_PERIOD_CONST。
  2. 字段是否为 volatile；volatile 字段不会被常量替换。
  3. 全局变量是否标注 EJIT_IN_PERIOD(static) 或 EJIT_IN_PERIOD_ARRAY(name)。
  4. 入口函数参数是否标注匹配的 EJIT_DIM(name)。
  5. 时间窗是否激活，且下标是否正确。
  6. 访问模式是否能被 InstCombine/Inline 化为常量 GEP；复杂 PHI/select 指针路径可能被跳过。
  7. 设置 dumpJITDir，检查优化后 IR 是否已将 load 替换为常量。

9.4 运行时 fallback 常见原因

  • 时间窗未激活或已失效；
  • 异步模式首次调用尚未编译完成；
  • bitcode 未找到或注册失败；
  • 外部符号未注册；
  • JIT 编译失败、目标后端缺失；
  • 内存不足、cache 已满、单函数代码量超过上限；
  • 指针型 EJIT_IN_PERIOD_ARRAY 未初始化或越界；
  • 字段访问模式太复杂，PASS6 安全跳过。

10. 限制与建议

10.1 当前限制

  • 仅支持 Clang 属性路径；GCC 兼容为未来工作。
  • EJIT_ENTRY 不支持递归。
  • 函数指针调用目标暂不特化。
  • 自定义标量 EJIT_IN_PERIOD(name) 依赖声明为未来扩展；当前标量建议使用 static。
  • 单个函数最多 4 个 EJIT_DIM 维度。
  • 时间窗数组建议较小；固定数组设计目标为 <100，全局最多 1024 个 period array。
  • !ejit.may_const 是软标注：丢失时只会少优化，不应影响正确性。
  • 复杂指针、PHI/select、非线性下标路径可能无法替换为常量。
  • JIT bitcode 与运行时 LLVM 版本需要匹配。

10.2 使用建议

优先选择稳定配置字段

只把真正时间窗内不变的字段标为 EJIT_PERIOD_CONST，不要标记频繁变化字段。

让维度简单

使用 uint8_t 下标和直接数组访问，避免复杂指针别名。

集中修改配置

通过 EJIT_PERIOD_GUARD 函数修改配置，避免分散写 may_const 字段。

先验证再优化

使用 EJIT_DISABLE 做 A/B 对比，再开启 dump IR 和 stats 验证优化收益。

10.3 上线前检查清单

  • 所有 EJIT_ENTRY 均有 fallback 正确性测试。
  • 所有配置修改路径都有 EJIT_PERIOD_GUARD 或手动 deactivate/activate。
  • 同步/异步模式下行为一致，异步首次 fallback 不影响业务副作用。
  • cache size、单函数 size、code memory 上限符合目标设备内存约束。
  • 裸核场景确认外部符号、registry section、代码内存权限、I/D cache 刷新路径。
  • 性能数据包含 cold compile、hot cache hit、fallback、失效重编译四类场景。
