1. 总体架构一览

EJIT 的核心目标是：用户仍然调用原函数名；AOT 阶段把可 JIT 的函数闭包、时间窗 metadata 和 wrapper 放进二进制；运行时根据当前时间窗实例查 cache、编译或 fallback。

编译期

Clang 识别 ejit_* 属性并生成 metadata；AOT pass 嵌入 bitcode、注册 period/static、插入 wrapper 和生命周期逻辑。

运行期

wrapper 在函数入口计算 cache key；cache 命中时直接调用特化代码；未命中时按同步/异步模式进入编译路径。

同步编译

首次 miss 时当前线程阻塞编译；编译成功后立刻执行 JIT 代码，失败则 fallback 到 AOT 原函数体。

异步编译

首次 miss 时提交后台任务并立即 fallback；worker 编译完成后发布到 cache，后续调用命中特化代码。

编译期 产物 / 热路径 同步编译 异步编译

2. AOT 编译期流水线

AOT 流水线的职责是把“可运行的原始 AOT 程序”和“可供运行时重新优化的 JIT 输入”同时放进最终二进制。PASS1 必须尽早运行，防止标准优化丢失原始 metadata；PASS2-4 在 late 阶段补齐 runtime 需要的入口。

阶段输入输出为什么需要
PASS1带 metadata 的原始 IR__ejit_bitcode / 函数闭包 bitcode运行时 JIT 需要未被破坏的可优化 IR。
PASS2period/static 全局 metadata动态注册调用或静态 registry 表运行时需要知道哪些内存对象属于哪个时间窗。
PASS3EJIT_ENTRY 函数 metadata原函数入口 wrapper用户不改调用点，仍调用原函数名即可触发 JIT。
PASS4EJIT_PERIOD_GUARD metadatadeactivate / activate 插桩配置修改时自动失效旧 cache，维持 may_const 语义。

3. Runtime 热路径与模式选择

wrapper 热路径先做低成本判断：runtime 是否初始化、时间窗是否 active、cache 是否命中。只有 miss 且允许 JIT 时，才根据 ejit_config_t::compileMode 进入同步或异步路径。

用户调用 EJIT_ENTRY 原函数 ↓ wrapper 读取 period index / 计算 cacheKey ↓ 未初始化 / inactive / disabled? ── 是 → fallback AOT ↓ 否 cache hit? ── 是 → 调用特化函数 ↓ 否 compileMode == SYNC ? ── 是 → 当前线程编译 → 成功则执行 JIT，失败 fallback ↓ 否 compileMode == ASYNC → 提交后台编译任务 → 当前调用 fallback → 后续调用命中

Cache Key

典型布局为 funcIdx + 最多 4 个维度下标。相同函数和相同时间窗实例组合命中同一份特化代码。

版本 / 失效

deactivate 或 lifecycle 插桩会标记实例 invalid，并使旧 cache entry 不再作为有效特化代码使用。

Fallback 原则

无论 miss、pending、OOM、符号失败还是编译失败，wrapper 都必须能回到 AOT 原函数体，保持正确性。

4. 同步编译模式

EJIT_COMPILE_SYNC 适合验证、调试和可接受首次调用延迟的场景。cache miss 后，当前业务线程直接完成 JIT 编译；编译成功则本次调用就执行特化代码。

步骤动作失败时
1wrapper miss 后调用 ejit_compile_or_get 的同步分支runtime 未初始化或实例 inactive 时直接 fallback
2加载嵌入 bitcode，按 cacheKey 克隆待优化模块bitcode 找不到则返回 NULL
3替换 period index 参数，执行 PASS6 读取当前 may_const 字段值不可分析 load 保守跳过，不影响正确性
4运行 LLVM 优化和 ORC/JITLink，生成机器码目标后端、符号、内存失败时 fallback
5发布 cache entry，并把函数指针返回 wrappercache 满或发布失败时 fallback

5. 异步编译模式

EJIT_COMPILE_ASYNC 适合实时敏感路径：业务线程不能被首次 JIT 编译阻塞。cache miss 时，wrapper 只提交后台任务并立即 fallback；worker 编译完成后发布代码，后续调用再命中。

任务去重

同一 cacheKey 的 miss 只需要一个后台编译任务；其他调用继续 fallback，避免队列被重复编译填满。

发布时机

worker 完成 JITLink、内存 finalize 和必要的 I/D cache 同步后，才把函数指针发布给 cache。

实时性

业务线程只承担排队和 fallback 成本，不承担 LLVM 优化和目标代码生成成本。

一致性

如果时间窗在任务编译期间被 deactivate，发布前必须检查版本/状态，避免发布过期特化代码。

6. JIT 优化 Pipeline

同步和异步模式共享同一套 JIT 优化管线，只是触发线程不同。PASS6 的核心任务是把当前时间窗内稳定的内存字段替换成常量，随后交给 LLVM 标准优化折叠分支和删除死代码。

ModuleLoader ↓ 参数替换：period index / static dim → LLVM 常量 ↓ InstCombine：GEP / cast / 简单算术折叠 ↓ Inline：把跨函数配置访问展开到 JIT 闭包内 ↓ PASS6 EJitStructFieldPass：may_const load → 当前内存值常量 ↓ 标准 LLVM opts：SCCP / SimplifyCFG / DCE / GVN / InstCombine ↓ ORC LLJIT / JITLink：目标代码生成 + 符号解析 + code memory finalize
阶段作用用户可观察结果
参数替换把 EJIT_DIM 参数替换为当前实例常量数组下标、GEP 路径变得可折叠
Inline把小函数中的配置读取展开到入口闭包跨函数读配置也可被 PASS6 识别
PASS6读取 active 时间窗内 EJIT_PERIOD_CONST 字段值，替换 loadIR 中 load 变成常量，分支条件固定
标准优化常量传播、分支折叠、死代码删除、CFG 简化dump IR 可看到只保留当前配置路径
JITLink生成机器码，解析外部符号，放入可执行内存cache entry 增加，后续 hits 增加

7. 时间窗生命周期与 Cache 失效

时间窗控制 JIT 是否允许把内存值当作常量。只要配置可能被修改，旧的特化代码就必须失效；修改完成并再次 activate 后，后续 miss 会使用新值重新编译。

异步编译特别需要版本检查：任务开始时看到的 period 版本，发布时必须仍然有效；否则应丢弃编译结果，避免过期常量进入 cache。

9. Fallback 与失败处理

EJIT 的正确性边界是：JIT 失败不能改变业务语义。wrapper 只在拿到可执行、版本有效、签名匹配的函数指针后才 dispatch，否则必须执行原 AOT 函数体。

直接 fallback

runtime 未初始化、实例 inactive、EJIT 被禁用、cacheKey 无效、bitcode 不存在。

编译失败 fallback

LLVM 优化失败、JITLink 失败、外部符号缺失、目标后端缺失、内存不足。

异步 pending fallback

任务已排队或正在编译时，当前调用不等待，继续走 AOT；完成发布后后续调用命中。

保守跳过

PASS6 遇到不可证明安全的 load、volatile、复杂指针来源时跳过替换，不影响正确性。

10. Bare-metal / SRE 部署架构

在无操作系统或 SRE 环境下，EJIT 需要替代 host 依赖：构造函数注册、动态符号查找、线程库、mmap/mprotect 和 JIT 可执行内存管理。
