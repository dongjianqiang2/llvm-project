1. What EJIT is

EmbeddedJIT is a runtime specialization compilation system for embedded scenarios. It lets developers annotate "data that stays constant within a certain business time window"; at runtime, once the time window is activated, it treats this data as a compile-time constant and generates specialized machine code for the current configuration.

Core idea

Between ejit_activate and ejit_deactivate, fields annotated EJIT_PERIOD_CONST can be read as constants by the JIT.

Main benefits

Constant propagation, branch folding, dead code elimination, local inlining, and CFG simplification — reducing config branches and repeated checks.

Safety semantics

JIT failure, cache miss, time window not active, out of memory, and similar cases all fall back to the original AOT code.

User source annotations → Clang emits EJIT metadata → AOT pass embeds bitcode and inserts the wrapper → runtime activates the time window → calls EJIT_ENTRY → on a cache hit runs specialized code, otherwise falls back to AOT

Typical scenarios:

  • Board-level config, mode config, and business config such as cell/trp/channel that stays stable for a period of time;
  • Config fields that drive many branch paths, where the same instance is called repeatedly;
  • You can accept the JIT compile cost on the first call, or use async mode to fall back first and compile in the background.

2. Quick start

2.1 Include the header

On the user side, simply include the runtime C API header. It already provides the 6 attribute macros; defining EJIT_DISABLE temporarily turns off all EJIT annotations, useful for A/B comparison or non-Clang compilation.

#include "llvm/ExecutionEngine/EJIT/EJitRuntime.h"

2.2 Annotate the config struct and time-window array

#include <stdint.h>
#include "llvm/ExecutionEngine/EJIT/EJitRuntime.h"

#define MODE_FDD 1
#define MODE_TDD 2

struct CellConfig {
    EJIT_PERIOD_CONST uint32_t mode;      // can be specialized as a constant within the time window
    EJIT_PERIOD_CONST uint32_t threshold; // can be specialized as a constant within the time window
    uint32_t runtimeCounter;           // ordinary field, does not participate in constant substitution
};

// each cell index is an independent time-window instance
EJIT_IN_PERIOD_ARRAY(cell) struct CellConfig g_cellCfg[16];

static void fdd_path(int value);
static void tdd_path(int value);
static void default_path(int value);

// the user still calls the original function name; the compiler inserts a wrapper at the function entry
EJIT_ENTRY
void process_cell(EJIT_DIM(cell) uint8_t cellIdx, int value) {
    if (g_cellCfg[cellIdx].mode == MODE_FDD) {
        fdd_path(value + g_cellCfg[cellIdx].threshold);
    } else if (g_cellCfg[cellIdx].mode == MODE_TDD) {
        tdd_path(value);
    } else {
        default_path(value);
    }
}

// functions that modify cell config must be annotated with lifecycle; the compiler auto-inserts deactivate/activate
EJIT_PERIOD_GUARD(cell)
void update_cell_cfg(EJIT_DIM(cell) uint8_t cellIdx,
                     uint32_t mode,
                     uint32_t threshold) {
    g_cellCfg[cellIdx].mode = mode;
    g_cellCfg[cellIdx].threshold = threshold;
}

2.3 Initialize, activate, and call

int main(void) {
    ejit_config_t cfg = {0};
    cfg.compileMode = EJIT_COMPILE_SYNC; // or EJIT_COMPILE_ASYNC
    cfg.optLevel = EJIT_OPT_L2;
    cfg.maxCodeMemory = 2 * 1024 * 1024;
    cfg.maxCacheEntries = 4096;
    cfg.enableLogger = true;

    if (ejit_init(&cfg) != EJIT_OK) {
        return 1;
    }

    g_cellCfg[3].mode = MODE_FDD;
    g_cellCfg[3].threshold = 10;

    // activate the cell[3] time window; afterwards process_cell(3, ...) can trigger specialization
    ejit_activate("cell", 3);

    process_cell(3, 100); // first call: compiles in sync mode; falls back and submits a background compile in async mode
    process_cell(3, 101); // subsequent: runs the specialized version on a cache hit

    // when modifying config, use a lifecycle function, or manually deactivate / activate
    update_cell_cfg(3, MODE_TDD, 20);
    process_cell(3, 102); // recompile or fallback

    ejit_shutdown();
    return 0;
}
Minimal usage loop: Annotate EJIT_PERIOD_CONST fields → annotate the EJIT_IN_PERIOD_ARRAY global array → annotate EJIT_ENTRY and EJIT_DIM → ejit_init → ejit_activate → call the original function.

3. Source annotation API

3.1 Attribute overview

MacroApplies toPurposeCommon constraints
EJIT_PERIOD_CONSTStruct fieldThe field can be treated as a constant by the JIT within an active time windowSupports integer, bool, float, nested struct, and array; volatile is not specialized
EJIT_IN_PERIOD(static)Non-array global variableGlobal config that does not change at runtime, always active by defaultCurrently recommended to use only the built-in static scalar time window
EJIT_IN_PERIOD_ARRAY(name)Global array or global pointer to a structDefines a time-window array activated independently per indexFixed arrays should stay < 100; at most 1024 arrays per program
EJIT_ENTRYFunctionMarks a JIT-specializable entry functionNo recursion; side effects should be idempotent in async mode
EJIT_DIM(name)Function parameterDeclares that this parameter is the index dimension of a time-window arrayMust be an integer; at most 4 dimensions per function
EJIT_PERIOD_GUARD(name)FunctionMarks a lifecycle function that modifies time-window dataMust have a matching EJIT_DIM parameter; multiple periods allowed

3.2 Static config: EJIT_IN_PERIOD(static)

struct BoardConfig {
    EJIT_PERIOD_CONST uint32_t boardType;
    uint32_t flags;
};

EJIT_IN_PERIOD(static) struct BoardConfig g_boardCfg;

EJIT_ENTRY
void process_board(void) {
    if (g_boardCfg.boardType == 1) {
        // at JIT time boardType can be folded to a constant
    }
}

The static time window represents global config that does not change during JIT runtime; it does not require calling ejit_activate.

3.3 Array time window: EJIT_IN_PERIOD_ARRAY(name)

Multiple global arrays can share the same time-window name. Calling ejit_activate("cell", idx) activates the same index across all arrays of that name. Active state is keyed by time-window name + instance index only; there is no array-pointer dimension, so if multiple arrays share a name, activation applies to that period instance as a whole.

struct CellConfig { EJIT_PERIOD_CONST uint32_t mode; };
struct CellState  { EJIT_PERIOD_CONST uint32_t state; };

EJIT_IN_PERIOD_ARRAY(cell) struct CellConfig g_cellCfg[16];
EJIT_IN_PERIOD_ARRAY(cell) struct CellState  g_cellState[16];

// activate g_cellCfg[3] and g_cellState[3]
ejit_activate("cell", 3);

3.4 Multi-dimension specialization

A single EJIT_ENTRY function can declare up to 4 time-window array indices. The runtime cache key encodes the high 32 bits as the function index and the low 4 bytes as the dimension values.

EJIT_IN_PERIOD_ARRAY(cell) struct CellConfig g_cellCfg[16];
EJIT_IN_PERIOD_ARRAY(trp)  struct TrpConfig  g_trpCfg[8];

EJIT_ENTRY
void process_pair(EJIT_DIM(cell) uint8_t cellIdx,
                  EJIT_DIM(trp)  uint8_t trpIdx,
                  int payload) {
    if (g_cellCfg[cellIdx].mode == 1 && g_trpCfg[trpIdx].type == 2) {
        // both cellIdx/trpIdx can become specialization dimensions
    }
}

3.5 Lifecycle functions

Any function that modifies an EJIT_PERIOD_CONST field or its containing struct should be annotated with EJIT_PERIOD_GUARD. The compiler inserts an invalidation operation at the function entry and re-activates before every return point.

EJIT_PERIOD_GUARD(cell) EJIT_PERIOD_GUARD(trp)
void update_both(EJIT_DIM(cell) uint8_t cellIdx,
                 EJIT_DIM(trp)  uint8_t trpIdx) {
    g_cellCfg[cellIdx].mode = 2;
    g_trpCfg[trpIdx].type = 4;
}
Note: If you bypass the lifecycle function and directly modify an EJIT_PERIOD_CONST field inside an already-active time window, the old specialized code may be based on the old value. Use EJIT_PERIOD_GUARD or manually ejit_deactivate / modify / ejit_activate.

4. Runtime API

4.1 Initialization config

The current C API config struct lives in llvm/include/llvm/ExecutionEngine/EJIT/EJitRuntime.h:

typedef struct {
  ejit_compile_mode_t compileMode; // EJIT_COMPILE_SYNC / EJIT_COMPILE_ASYNC
  ejit_opt_level_t optLevel;       // EJIT_OPT_L1 / L2 / L3
  size_t maxCodeMemory;            // JIT code memory cap
  size_t maxDataMemory;            // data memory cap
  size_t maxCacheEntries;          // cache entry count cap
  size_t maxCacheSize;             // cache total size cap
  bool enableLogger;               // whether to enable logging
  bool forceStaticRegistry;        // bare-metal: force the static registry
  const char *dumpJITDir;          // when non-null, dump the optimized JIT IR
} ejit_config_t;
APIDescription
ejit_init(const ejit_config_t *config)Initialize EJIT. Pass NULL for default config. Consumes bitcode/period info registered at construction time or via the static table.
ejit_shutdown(void)Release EJIT runtime resources.
ejit_set_compile_mode(mode)Switch sync/async compile mode at runtime.
ejit_get_compile_mode()Query the current compile mode.

4.2 Sync and async modes

ModeFirst-miss behaviorSuitable scenariosCaveats
EJIT_COMPILE_SYNCBlocks until JIT compilation finishes, then directly runs the specialized version on successYou can accept first-call latency and want performance gains as early as possibleFirst-call latency is more noticeable
EJIT_COMPILE_ASYNCSubmits a background compile; the current call falls back to AOTSensitive to first-call latencyEJIT_ENTRY side effects should be idempotent, to avoid inconsistency between the first AOT and later JIT behavior

4.3 Time-window lifecycle API

ejit_status_t ejit_activate(const char *periodName, uint8_t cellIdx);
ejit_status_t ejit_deactivate(const char *periodName, uint8_t cellIdx);

ejit_status_t ejit_activate_all(const char *periodName);
ejit_status_t ejit_deactivate_all(const char *periodName);
bool ejit_is_active(const char *periodName, uint8_t cellIdx);
  • activate(name, idx): activates the idx instance across all arrays of that name.
  • deactivate: marks the time window invalid and invalidates cache entries that depend on that instance.
  • Active state is keyed by name + instance index only; the array-level APIs ejit_activate_array / ejit_deactivate_array were removed (the product does not need array-level lifecycle activation).
  • If same-named arrays have different lengths, out-of-bounds arrays are skipped; the user should still keep business indices valid.

4.4 Cache, stats, and errors

void ejit_clear_cache(void);
void ejit_invalidate(const char *periodName, uint8_t cellIdx);

ejit_status_t ejit_get_stats(ejit_stats_t *stats);
const ejit_error_t *ejit_get_last_error(void);

ejit_stats_t includes entry count, code size, cache hit/miss, and eviction info. When JIT does not take effect, first check stats and last error, then enable dumpJITDir to dump the optimized IR.

4.5 External symbol registration

void ejit_register_symbol(const char *name, void *addr);

In a host environment, external symbols are usually auto-scanned and registered by PASS1. On bare-metal or in environments without dlsym, if the JIT bitcode references platform functions, global variables, or library functions, you must ensure they are registered with EJIT via the auto-registry or a manual call.

5. Build and linking

5.1 Build the EJIT compiler and runtime

This repository recommends the top-level build.sh:

# x86 dev build: clang/opt/lld etc.
./build.sh debug x86

# x86 release: for EJIT runtime testing
./build.sh release x86

# AArch64 release: for embedded targets or cross-validation
./build.sh release aarch64

On resource-constrained machines, targeted incremental builds are recommended:

# dev build of core tools
ninja -C build_debug_x86 clang opt lld

# EJIT runtime + linker
ninja -C build_release_x86 LLVMEJIT lld

# AArch64 runtime
ninja -C build_release_aarch64 LLVMEJIT lld

5.2 Compile the user program

The user program must be compiled with a Clang that has the EJIT attributes and AOT passes, and linked with libLLVMEJIT.a. For real projects, reuse the link rules in ejit_test/build.sh. Conceptually:

# example: using build_release_x86; adjust include/lib paths per your build dir
build_release_x86/bin/clang -O2 -g \
  -Illvm/include -Ibuild_release_x86/include \
  my_ejit_app.c \
  build_release_x86/lib/libLLVMEJIT.a \
  -fuse-ld=lld -o my_ejit_app
Note: The EJIT AOT passes are already integrated into the Clang/LLVM pipeline on this branch; compiling normally with an EJIT-enabled Clang produces the metadata, embedded bitcode, wrapper, and lifecycle calls.

5.3 Disable EJIT for A/B comparison

build_release_x86/bin/clang -DEJIT_DISABLE -O2 my_ejit_app.c -o my_aot_app

EJIT_DISABLE expands the attribute macros to nothing, making it easy to confirm logic correctness and compare AOT vs EJIT behavior.

5.4 Trimming and single-object packaging

For bare-metal or minimal-footprint delivery, you can enable LLVM backend trimming and use the lipo pipeline to merge multiple LLVM archives into a single ejit.o.

# recommended: generate the AArch64 single object via the project script
./ejit_test/lipo/run_aarch64_pipeline.sh build_release_aarch64 ejit_test/lipo/ejit.o

# run integration tests with the lipo artifact
./ejit_test/build.sh --run --lipo=ejit_test/lipo/ejit.o

The stable trimming option is -DEJIT_TRIM_LLVM_BACKEND=ON. SRE code pool options are covered in section 8.

6. AOT/JIT pipeline

6.1 What the AOT compile phase does

  1. Clang parses the EJIT attributes, emits function/global-level !ejit.metadata, and emits !ejit.may_const on loads of may_const fields.
  2. PASS1 EJitRegisterBitcode extracts the EJIT_ENTRY closure bitcode before standard optimization, embeds it in the binary, and generates registration info.
  3. PASS2 EJitRegisterPeriod generates period-array and static-variable registration.
  4. PASS3 EJitWrapperGen inserts the wrapper at the original function entry: builds the cache key, calls the runtime, jumps to the specialized function on success, or continues the original AOT body on failure.
  5. PASS4 EJitPeriodHandler inserts deactivate at lifecycle-function entries and activate before every return.
  6. PASS5 EJitAotModulePass coordinates PASS2-4.

6.2 What the runtime JIT does

  1. Look up the cache by cache key; on a hit, return the function pointer.
  2. On a miss, load the embedded bitcode.
  3. Substitute the EJIT_DIM parameters with the constant indices for this call.
  4. Run InstCombine to fold zext/GEP and other constant chains.
  5. Inline callees so cross-function field accesses are exposed as global-variable GEPs.
  6. PASS6 EJitStructFieldPass replaces EJIT_PERIOD_CONST field loads with the current memory-value constant.
  7. Run standard LLVM optimization at L1/L2/L3, generate machine code, and place it in the cache.

6.3 Optimization levels

LevelPositioningTypical optimizations
EJIT_OPT_L1ConservativeConstant propagation, dead code elimination, branch folding
EJIT_OPT_L2Default / balancedL1 + CFG simplification, moderate inlining
EJIT_OPT_L3AggressiveL2 + more aggressive loop optimization; mind code size

8.2 SRE Code Pool

The SRE code pool replaces the usual mmap/mprotect JIT code-memory path and suits platforms with strict requirements on executable-memory permissions.

# CMake option example
-DEJIT_SRE_CODE_POOL=ON
-DEJIT_CODE_POOL_4K_SEAL=ON
  • Allocates JIT machine code from a 2MiB-aligned code pool;
  • In 4K seal mode, only the written 4K pages are marked executable;
  • Avoids writing to RX pages; not modified after finalize;
  • Requires the platform to provide symbols such as enable_ex, split_2m_to_4k, and SRE_MemDbgAlloc.

8.3 SRE Taskpool

The SRE taskpool is an async compile-scheduling mode for environments without a C++ thread library; it is off by default. It uses a single worker task, an MPSC queue, a dedup table, and a bucketed cache. Cross-core sharing of a taskpool depends on shared-memory mapping, execute permission, I/D cache coherence, and owner election.

# build option example
./build.sh release aarch64_be --freestanding --sre-taskpool
Status note: SRE taskpool / shared taskpool is a platform-dependent capability; host unit tests can validate the core logic, but shared sections, cross-core execution, task deletion, and cache coherence must ultimately be verified on the target SRE multi-core environment.

9. Troubleshooting

9.1 Common compile-time diagnostics

SymptomCauseFix
EJIT_IN_PERIOD used on an arrayArrays should use EJIT_IN_PERIOD_ARRAYChange to EJIT_IN_PERIOD_ARRAY(name)
EJIT_IN_PERIOD_ARRAY used on a non-arrayA scalar variable should not use an array time windowFor a static scalar use EJIT_IN_PERIOD(static)
EJIT_DIM parameter is not an integerThe index must be encodable as an integer dimensionUse an integer type such as uint8_t / int
More than 4 dimensionsThe cache key only encodes four 8-bit dimensionsReduce dimensions or split the function
EJIT_PERIOD_GUARD has no matching index parameterThe lifecycle function cannot tell which instance to modifyAdd an EJIT_DIM(name) parameter
Recursive EJIT_ENTRYRecursive entry specialization is not supportedDrop EJIT_ENTRY or restructure the calls

9.2 JIT did not trigger

  1. Confirm the function is annotated EJIT_ENTRY.
  2. Confirm you are using an EJIT-enabled Clang, not a system Clang.
  3. Confirm ejit_init ran before calling EJIT_ENTRY.
  4. Confirm the relevant time window has been ejit_activate-d.
  5. Confirm the build output contains @__ejit_bitcode and ejit_compile_or_get.
  6. On bare-metal, confirm the registry section was not garbage-collected by the linker.
  7. Check ejit_get_last_error() and ejit_get_stats().

9.3 JIT triggered but branches were not folded

  1. Is the field annotated EJIT_PERIOD_CONST.
  2. Is the field volatile; volatile fields are not substituted by constants.
  3. Is the global annotated EJIT_IN_PERIOD(static) or EJIT_IN_PERIOD_ARRAY(name).
  4. Is the entry-function parameter annotated with the matching EJIT_DIM(name).
  5. Is the time window active, and is the index correct.
  6. Can the access pattern be reduced to a constant GEP by InstCombine/Inline; complex PHI/select pointer paths may be skipped.
  7. Set dumpJITDir and check whether the optimized IR has replaced the load with a constant.

9.4 Common causes of runtime fallback

  • Time window not active or already invalidated;
  • First call in async mode has not finished compiling;
  • Bitcode not found or registration failed;
  • External symbols not registered;
  • JIT compilation failed or the target backend is missing;
  • Out of memory, cache full, or a single function's code size exceeds the cap;
  • A pointer-type EJIT_IN_PERIOD_ARRAY was not initialized or is out of bounds;
  • The field access pattern is too complex and PASS6 safely skips it.

10. Limitations and advice

10.1 Current limitations

  • Only the Clang attribute path is supported; GCC compatibility is future work.
  • EJIT_ENTRY does not support recursion.
  • Function-pointer call targets are not specialized yet.
  • Custom scalar EJIT_IN_PERIOD(name) depends on declarations planned as a future extension; for now scalars should use static.
  • At most 4 EJIT_DIM dimensions per function.
  • Time-window arrays should be small; fixed arrays target <100, with at most 1024 period arrays globally.
  • !ejit.may_const is a soft annotation: losing it only means less optimization, never incorrectness.
  • Complex pointers, PHI/select, and non-linear index paths may not be replaceable by constants.
  • The JIT bitcode and the runtime LLVM version must match.

10.2 Usage advice

Prefer stable config fields

Only mark fields that are truly constant within the time window as EJIT_PERIOD_CONST; do not annotate frequently changing fields.

Keep dimensions simple

Use uint8_t indices and direct array access; avoid complex pointer aliasing.

Centralize config modification

Modify config through EJIT_PERIOD_GUARD functions; avoid scattered writes to may_const fields.

Verify before optimizing

Use EJIT_DISABLE for an A/B comparison, then enable dump IR and stats to verify the optimization gain.

10.3 Pre-launch checklist

  • All EJIT_ENTRY functions have fallback-correctness tests.
  • All config-modification paths use EJIT_PERIOD_GUARD or manual deactivate/activate.
  • Behavior is consistent across sync/async; the async first-call fallback does not affect business side effects.
  • Cache size, single-function size, and code-memory caps fit the target device's memory constraints.
  • On bare-metal, confirm external symbols, the registry section, code-memory permissions, and the I/D cache flush path.
  • Performance data covers four scenarios: cold compile, hot cache hit, fallback, and invalidation recompile.
