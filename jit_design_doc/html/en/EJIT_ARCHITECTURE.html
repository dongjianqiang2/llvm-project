1. Overall architecture

EJIT's core goal: the user still calls the original function name; the AOT phase places the JIT-able function closure, time-window metadata, and wrapper into the binary; at runtime the wrapper looks up the cache, compiles, or falls back based on the current time-window instance.

Compile time

Clang recognizes the ejit_* attributes and emits metadata; the AOT pass embeds bitcode, registers period/static, and inserts the wrapper and lifecycle logic.

Runtime

The wrapper computes the cache key at the function entry; on a cache hit it calls the specialized code directly; on a miss it enters the compile path in sync or async mode.

Synchronous compile

On the first miss the current thread blocks to compile; once compilation succeeds it runs the JIT code immediately, and on failure falls back to the original AOT body.

Asynchronous compile

On the first miss it submits a background task and falls back immediately; the worker publishes to the cache after compiling, and later calls hit the specialized code.

2. AOT compile pipeline

The AOT pipeline's job is to place both "the runnable original AOT program" and "the JIT input for runtime re-optimization" into the final binary. PASS1 must run as early as possible to prevent standard optimization from losing the raw metadata; PASS2-4 fill in the runtime-needed entry points in the late stage.

3. Runtime hot path and mode selection

The wrapper hot path first does cheap checks: is the runtime initialized, is the time window active, is the cache hit. Only on a miss when JIT is allowed does it enter the sync or async path based on ejit_config_t::compileMode.

User calls the EJIT_ENTRY original function ↓ wrapper reads period index / computes cacheKey ↓ uninitialized / inactive / disabled? ── yes → fallback AOT ↓ no cache hit? ── yes → call specialized function ↓ no compileMode == SYNC ? ── yes → current thread compiles → run JIT on success, fallback on failure ↓ no compileMode == ASYNC → submit background compile task → current call falls back → later calls hit

Cache Key

The typical layout is funcIdx + up to 4 dimension indices. The same function and the same time-window instance combination hit the same specialized code.

Version / invalidation

deactivate or lifecycle instrumentation marks the instance invalid and makes old cache entries no longer usable as valid specialized code.

Fallback principle

Whether miss, pending, OOM, symbol failure, or compile failure, the wrapper must always be able to return to the original AOT body, preserving correctness.

4. Synchronous compile mode

EJIT_COMPILE_SYNC suits validation, debugging, and scenarios that can accept first-call latency. After a cache miss, the current business thread directly completes the JIT compile; on success this call runs the specialized code.

StepActionOn failure
1After a wrapper miss, calls the sync branch of ejit_compile_or_getIf the runtime is uninitialized or the instance is inactive, falls back directly
2Loads the embedded bitcode and clones the module to optimize by cacheKeyIf the bitcode is not found, returns NULL
3Substitutes the period index parameter, runs PASS6 to read the current may_const field valueUnanalyzable loads are conservatively skipped, with no correctness impact
4Runs LLVM optimization and ORC/JITLink to produce machine codeFalls back on target backend, symbol, or memory failure
5Publishes the cache entry and returns the function pointer to the wrapperFalls back if the cache is full or publish fails

5. Asynchronous compile mode

EJIT_COMPILE_ASYNC suits latency-sensitive paths where the business thread cannot be blocked by the first JIT compile. On a cache miss, the wrapper only submits a background task and falls back immediately; the worker publishes the code after compiling, and later calls hit.

Task dedup

A miss for the same cacheKey needs only one background compile task; other calls keep falling back, preventing the queue from being filled by duplicate compiles.

Publish timing

The worker publishes the function pointer to the cache only after JITLink, memory finalize, and any necessary I/D cache sync are complete.

Latency

The business thread bears only the enqueue and fallback cost, not the LLVM optimization and target codegen cost.

Consistency

If the time window is deactivated while the task is compiling, the version/state must be re-checked before publishing, to avoid publishing stale specialized code.

6. JIT optimization pipeline

Sync and async modes share the same JIT optimization pipeline; only the triggering thread differs. PASS6's core task is to replace memory fields that are stable within the current time window with constants, then hand off to standard LLVM optimization to fold branches and delete dead code.

7. Time-window lifecycle and cache invalidation

The time window controls whether the JIT may treat a memory value as a constant. Whenever config may be modified, the old specialized code must be invalidated; after modification and re-activation, later misses recompile using the new value.

Async compilation especially needs version checks: the period version seen when the task started must still be valid at publish time; otherwise the compile result should be discarded to avoid stale constants entering the cache.

9. Fallback and failure handling

EJIT's correctness boundary: a JIT failure must not change business semantics. The wrapper dispatches only after obtaining an executable, version-valid, signature-matching function pointer; otherwise it must execute the original AOT body.

Direct fallback

Runtime uninitialized, instance inactive, EJIT disabled, cacheKey invalid, or bitcode missing.

Compile-failure fallback

LLVM optimization failure, JITLink failure, external symbol missing, target backend missing, or out of memory.

Async pending fallback

When a task is already queued or compiling, the current call does not wait and continues with AOT; once published, later calls hit.

Conservative skip

PASS6 skips substitution for loads it cannot prove safe, volatile, or complex pointer origins — no correctness impact.

10. Bare-metal / SRE deployment architecture

In an OS-less or SRE environment, EJIT must replace host dependencies: constructor registration, dynamic symbol lookup, the thread library, mmap/mprotect, and JIT executable-memory management.
