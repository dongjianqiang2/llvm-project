# EJIT 全局小表路线：规格与可行性评估

日期：2026-09-10。状态：独立 RFC / Draft PR 讨论稿，尚未批准实现。
目标基线：`dongjianqiang2:ejit_dev_spec5@3f0e190dd54752f9c1dcb4bcd1fcb5d6349ae59c`。
规格分支：`ChenRuan:codex/ejit-small-table-spec`；仅文档，不依赖 PR230 实现。
最新产品确认：实例边跑边初始化，首次业务前不能给出全部就绪的 cell/TRP 域。

这不是 PR230 的追加需求，不改变6号当前的版本合并任务。
本文借鉴已验证的 preserved-dim/load-only 替换基础，但不以 IR hash 合并作为主机制。
“全局应用”是 EJIT 级别选择这一优化策略，不是强行改写所有 load 或一次编译所有函数。

## 1. 结论与边界

方案可行，但适合程度取决于配置管理契约，而不是仅取决于 may_const 有多相似。

- 如果能枚举一轮配置的完整实例集合，并证明相关字段已经初始化且可稳定读取，推荐不可变小表方案。
- 如果实例边运行边出现、字段没有明确就绪点，则不能从“暂时见到的值相同”推出“所有实例相同”。全自动实现将明显复杂化。
- 不需要等待每个实例执行过，也不需要先给每个 cell 编译一份 IR 再比较。
- 相同字段直接常量化；不同字段改成小表 load；无法证明安全的字段保持原始读取。
- 单份共同代码会牺牲部分逐实例分支折叠，可能换来更少的代码和重复编译；不能预先保证产品加速。
- 本路线目标是每 entry、每配置域代际一份最终 T2 代码，不是整个程序只有一个函数，也不是所有历史代际只有一份代码。

最重要的取舍：不能同时无条件要求“任意时刻增加或修改实例”“不做任何就绪声明”“跨全部实例常量化”“永不重编”“热路径零额外检查”。必须明确选择。

### 1.1 针对最新产品约束的修订结论

用户已确认实例会边跑边初始化。因此第6.2节的封闭域/不可变表不是当前推荐首版，只保留为有配置事务的可选模式。
推荐先评估第6.5节的“共同代码 + 增量就绪行”：不等待全部实例，未来行可以有不同值，原先的全等常量化目标暂不作为保证。
这意味着先前“小表可得到与合并相同的load/branch结果”的结论有严格前提；该前提在开放成员集合上尚不成立。
本路线此时主要换取更少的物理版本、较集中数据，以及可能减少的重复编译，而不是保证消掉相同配置load。
若仍必须保留全等字段的常量/分支折叠，应选第6.6节的验证接入或封闭子域增强，它会重新引入拒绝接入、重编和生命周期复杂度。

## 2. 与版本合并的区别

| 维度 | PR230 版本合并 | 本文小表路线 |
| --- | --- | --- |
| 构造方式 | 对逻辑实例分别替换并生成 IR，最终精确比较 | 对完整配置域生成一份参数化 IR |
| 共同值 | 各版本都折成相同常量后复用 | 扫描合法域后直接判定全等，折成一个常量 |
| 差异值 | 保留不同物理版本的机会 | 用表数据表达，通常不增加物理版本 |
| 逐实例分支优化 | 可保留较多 | 差异字段的分支通常保留 |
| 编译成本 | 仍可能重复进行逐实例 IR 优化 | 有机会只优化一次，但需要扫描配置与建立表 |
| 主要复杂度 | 组身份、精确比较、代表采样、共享发布 | 就绪域、字段读取、表布局、整体失效 |
| 更新影响 | 可将不同实例拆出共享组 | 首版保守重建受影响的共同代码/表代际 |

当所有获准字段全等、其他绑定及优化策略一致时，最终代码可能相同，不承诺机器码必然逐字节相同。
小表路线本身不要求 DeepSeek/PR230 的组表或最终 IR hash 目录；只复用经审查的安全读取与参数保留能力。

## 3. 概念与身份

- `DomainSchema`：entry 涉及的 cell/TRP、可用组合、可选 phase 表达式、来源字段布局和类型。
- `DomainEpoch`：封闭模式的一组已确认就绪成员、配置代际及其读借用契约；不是采样 session，也不是编译队列水位。
- `TableCodeEpoch / RowGeneration`：在线模式分别表示固定schema/表地址/代码代际和每行配置代际。晚接入行不改变TableCodeEpoch，不冒充封闭DomainEpoch扩容。
- `RowKey`：实际 cell/TRP/phase 组成的合法数据行身份；phase 不产生额外 JIT 版本。
- `LogicalKey`：沿用 entry、生命周期维度及版本，用于缓存、关闭、失效和诊断。
- `CodeIdentity`：entry、源位码、编译策略、schema、所选模式的DomainEpoch或TableCodeEpoch和有效绑定。
- `TableImage`：类型正确的获准字段值集合，不是原始结构体的可替代地址。封闭模式整表不可变；在线模式固定地址、按行发布，已接入行在其有效执行代际内不可修改。
- `AttemptToken`：一次排队/编译尝试，旧回调不能完成取消后重建的新请求。

保留 cell/TRP 的真实调用参数和原有逻辑身份，不把它们改成 free_dim，也不丢弃生命周期依赖。
多个 LogicalKey 可以指向同一 CodeIdentity；跨核准备、icache 失效、实际代码范围仍分别负责。
不因机器码指针相同就认为两个逻辑实例相同。

## 4. 基本变换

原始行为示意，may_const 的真实语法沿用所选基线：

```c
unsigned process(unsigned cell, unsigned trp, unsigned slotNo, unsigned x) {
    unsigned phase = slotNo % 10;
    unsigned gain = cfg[cell][trp][phase].gain; /* may_const */
    unsigned mode = cfg[cell][trp][phase].mode; /* may_const */
    unsigned live = cfg[cell][trp][phase].pending; /* ordinary load */
    out[cell][trp] = slotNo;                     /* ordinary store */
    return mode == 1 ? x * gain + live : slow(cell, trp, slotNo, x);
}
```

若整个有效域内 mode=1、gain=7，则目标等价于：

```c
unsigned process_common(unsigned cell, unsigned trp, unsigned slotNo, unsigned x) {
    unsigned phase = slotNo % 10;
    unsigned live = cfg[cell][trp][phase].pending;
    out[cell][trp] = slotNo;
    return x * 7 + live;
}
```

若 mode 全等、gain 随 phase 不同，则目标等价于：

```c
/* Illustrative generated immutable data, not a per-call stack array. */
static const unsigned gain_by_phase[10] = {7, 8, 7, 8, 7, 8, 7, 8, 7, 9};
unsigned gain = gain_by_phase[slotNo % 10];
```

如果 gain 还随 cell/TRP 变化，表必须保留对应轴。只有精确证明某轴无关，才可消掉该轴。
封闭域对照原型先实现“全等 -> 常量；否则合法完整表”；按轴降维作为后续收益增强，不做前置依赖。在线首版按第6.5节执行，不从当前可见行推出全等。
原始 slotNo 仍为 0..1023 的参数，回绕后继续计算真实 `%5/%10`，不能用连续循环计数替代。
不把 slotNo 本身 RAUW 成 phase，不假定有函数内部循环，不依赖分支预测正确性保证语义。

## 5. 替换的安全条件

每个候选 load 必须同时证明：

1. 来源有实际生效的 may_const 授权；类型、字段偏移、宽度、地址空间及 provenance 可验证。
2. 地址可以表达为有效域内的行和字段；读取范围完全属于登记对象及相应生命周期子对象。
3. 全部将读取的行都已初始化、可访问且在读借用期间稳定。数据在未执行分支中也不能因此随意解引用。
4. cell/TRP/phase 依赖完整，不能仅跟踪 cell 却读取未登记的 TRP 或相邻 cell。
5. 非 volatile、非 atomic、非设备/MMIO；不是函数指针、对象地址、带有身份语义的指针值。
6. 调用实参、普通 load、store 目标和可能逃逸的原始对象指针仍保持动态语义。

标量类型按实际 IR 支持能力逐项覆盖，而非只支持 int/bool；整数保留位宽，浮点按位比较和构造，包括负零与 NaN payload。
大端读取与表发射均按目标 DataLayout。第一版不通过把整个结构体 reinterpret_cast 成新表来处理 padding 或指针。
来源不明、布局不匹配、borrowed 地址不能枚举、未知索引、负向/溢出 GEP、未证明的 helper 入边，保持原 load 并报告原因。
保守不替换不等于整个函数必须 AOT；如果入口域/生命周期/绑定本身不合法，则该逻辑实例只能 AOT。

表项缺失不能填0、undef 或沿用某个代表 cell。未知行也不能简单用 `%row_count` 绕回已有行。
不能在已经发生副作用的函数中间跳到整函数 AOT 重跑。索引安全无法证明时，候选 load 保持原样。
嵌套 entry 或间接调用仍遵守基线边界，不能假定被调用函数的参数落在父 entry 的就绪域。

## 6. 编译时机：就绪不是执行过

### 6.1 三个独立时刻

```text
配置域 Ready：可以安全读取哪些实例/字段，代际是否稳定
T1 采样结束：这份共同代码的优化反馈是否足够
代码发布：机器码、表数据、权限与逻辑身份是否全部就绪
```

编译队列为空、等了某个 tick、某 cell 曾经被调用、代表采了64次，都不能证明其他行已经初始化。
同样，配置 Ready 不表示必须立即把全部 entry 编译完。可以由该 entry 首次正常 miss 懒启动一轮。

### 6.2 可选模式：封闭配置域 + 不可变表

产品在已有配置事务完成点提供“本轮有效成员及版本已就绪”的事实；可通过扩展集成现有生命周期接口实现，不强制业务每次手动触发编译。
这个事实必须来自配置系统，不能由 EJIT 猜测。具体 C API 尚未定，不把下述动作名当成现有接口：

```text
产品完成配置初始化 -> 确认 DomainEpoch E 及合法成员集合
entry 首次业务 miss -> owner 读取并冻结 E 的获准字段
得到 TableImage E -> 编译共同 T1 -> 采样 -> 编译共同 T2
代码与数据就绪 -> 发布属于 E 的逻辑缓存记录
```

可以读取 cell5 的已就绪配置，即使 cell5 从没执行业务。不等待所有 entry 调用，也不等待所有 phase 采样。
“所有配置”只指该 entry 本轮声明的合法域，不是所有可能的16/256个预留槽或整个进程的全部结构体。
cell 与 TRP 各自 active 并不自动证明任意笛卡尔组合可访问；组合有效性和初始化仍需有来源。

已核对参考源码 `1d7ad493` 的 `ejit_activate/ejit_deactivate` 包装层：它们处理生命周期与失效；本文不把它们视为已经实现配置事务完成、冻结成员集合或编译读者排空。
若希望不新增产品调用，需要明确强化并实现原 activate 集成契约，不能只改注释宣称支持。

### 6.3 晚加入与配置更新

- 尚未属于 E 的实例保持 AOT，不自动获得 E 的共享指针；未来加入走新域代际。
- 启动时分批 activate 若导致成员集合反复扩大，不应每个成员到达就重编所有 entry。由明确的配置事务合并，而非无界等待或固定时间猜测。
- 可选后续策略是只编译已就绪子域、晚加入重建；正确但会产生编译抖动和多份历史代码，不能宣传成只编一次。
- 不更新已发射的 LLVM constant TableImage；新配置生成新表/代码绑定或新的重建代际。
- 编译前、最后一次源读取后、发布前校验身份与代际；校验本身不替代读取期间所需的同步/有效借用。

### 6.4 在线表不能同时获得的保证

这种方式能更早编译通用代码，但要处理有效位、发布顺序、行更新、读者并发和未知行回退。
热函数内可能增加表指针读取或有效性检查，缺值也不能被当成常量；若后来要全等常量化，仍需第二次编译及域失效协议。
不能把可变表标成 LLVM constant 或对其无条件使用 invariant.load；这会给优化器不真实的不可变保证。
因此它是另一个“可变配置缓存”设计，不是不可变小表的一项无成本增强。[LLVM 语义](https://llvm.org/docs/LangRef.html#global-variables)

### 6.5 当前推荐实验：共同代码 + 增量就绪行

目的：实例陆续初始化时也能运行，不等全域、不为每个新cell生成代码。代价：无法证明永久全等的字段保留表load。

```text
entry 的字段/行schema就绪 -> 预留有界、固定地址的表，尚无行可执行
cell0 自身配置就绪 -> 验证并填写cell0所需行 -> 发布行就绪
-> 正常排队编译共同T1/T2；code与cell0行都ready后绑定cell0逻辑槽
cell1 自身配置就绪 -> 验证并填写cell1所需行 -> 发布行就绪
-> 已有共同代码则仅完成逻辑接入，不重编、不重封代码页
cell2... -> 同样接入；与cell0值不同也可以使用同一通用代码
```

实现约束：

- “每行已就绪”仍需要可靠依据。建议复用产品每实例配置完成/activate的集成点，但必须证明相关候选字段已全部初始化；一次调用本身不能证明其它分支才使用的字段也就绪。
- `tableReady(row)` 与 `codeReady(code_id)` 分开；两者都成立且身份/生命周期/权限已校验，才发布该行所属的逻辑icache槽。
- 表放独立共享数据资源，不放stack，也不能放到会随代码封成RX的可修改混合页。表的填充不再次调用enable_rw去解封旧代码。
- 第一版由owner串行负责表行写入/接入；使用可证明的发布和跨核可见性协议。未来行写入与当前已发布行读取不得产生数据竞争或覆盖。
- 已发布行在本实例有效运行代际内不修改。未就绪的行不能由任何优化后的读取触达；依赖其他cell/TRP行而尚未就绪的load保留原始读取或暂不接入该实例。
- 优先固定容量和可证明的直接索引，不在稳定wrapper加入哈希查表。稀疏/复杂映射若需要额外索引load，其代价必须明确测量。
- 表整体在LLVM里是可变global/外部数据，不能以“每行以后不会变”为由虚假声明整表constant。不引入未经证明的invariant元数据。
- 表与物理代码地址稳定，不扩容搬迁；容量/row schema不支持的新成员维持AOT并计数。是否未来重建更大表另行设计，不偷做可变基址快路径。
- 只创建实际字段计划需要的表；普通结构体指针和live数据仍原样使用。复制的是紧凑标量列，不恢复整结构体snapshot。
- 选择该策略的entry不同时启用PR230全量版本合并。不自动把当前已见行相等优化成常量；合法的静态不变量证明可以单独使用。

PGO可对同一通用T1已经接入的行累计真实64次进入，不要求全部成员到齐。后加入成员使用已生成的通用T2，可能得到不适合自己的布局，但正确性不能依赖旧样本覆盖它。
若PGO进行value specialization，必须保留真实守卫/fallback；不得把采到同值当作未来行也同值的语义契约。

### 6.6 可选增强：首批全等折叠 + 新成员验证接入

不读尚未初始化的实例，也可以先对已就绪成员折叠，但这不再是“任意值都能立即接入”的简单小表：

1. 记录共同代码实际折叠的字段与位精确常量，形成明确的接入合同。
2. 新成员初始化后、填逻辑指针之前，验证它所有会被折叠的字段满足合同；相同则接入，校验只发生冷路径。
3. 某项不同或无法读取，保持AOT；不能仅把不同值写进表就继续调用已经硬编码常量的代码。
4. 若希望不同成员也获得JIT，需要生成更通用的表版本并切换整个受影响域，或生成不同代码组。后者已接近版本合并路线。

该方式可以减少预先读全域的要求，但把难点换成了接入证明、依赖与重编。首版不叠加，以免两条路线再次混合。

## 7. 生命周期与更新代价

封闭常量化模式建议按 entry 的配置域依赖进行保守失效，不做任意行热更新：

```text
阻止受影响域的新执行与新编译借用
-> 清理旧逻辑入口，并通过已有产品安全点排空可能访问旧配置的执行者
-> 等待编译读取结束/取消确认
-> 修改真实配置并提交新的 Ready 代际
-> 懒生成新表/共同 T1/T2，未就绪期间 AOT
```

必须阻止可能在 in-flight JIT 中通过真实参数访问被修改行的调用；仅清掉一个 cell 的 wrapper 槽不证明旧共同代码不会访问它。
若产品允许新旧配置同时执行，需要额外的双代原对象/表绑定和读者生命周期协议，首版不默认支持。
共享代码的普通动态 load 仍访问真实业务对象；保留旧小表不等于保留了旧业务对象的一致视图。
新成员加入或任一依赖修改，可保守使本 entry 整个域重建；独立 entry/无关生命周期不必全局重启。

代码中硬编码了某个表地址时，换表通常需要重新链接/编译；若想只换表指针，就增加一层运行时间接读取。
即使所有值从未变化，只是生命周期代际前进，也不能未经新一轮有效性证明直接复用旧代码。
NO_RECLAIM 下旧 T1/T2/表存储不能自动回收，必须统计保留字节并设置上限；元数据释放不等于可重用仍被执行的物理页。

第6.5节的在线纯表模式可以采用更窄的行更新：阻止对应逻辑实例新进入，等待所有可能读取该行的执行者及编译借用结束，修改原配置和表行，再用新逻辑代际重新接入同一物理代码。
这只适用于表值没有被优化器折成常量、没有跨行优化依赖的情况。不能只依赖invalidate就认定已排空，也不能在并发读时直接memcpy覆盖整行。
源代码或字段schema改变、共享代码替换、PGO重新编译属于代码代际变化，不是普通数据行更新。

## 8. 表存储、大小与访问成本

- 不放调用栈，不每次初始化，不复制整个1KiB结构体；仅在 owner 冷路径构建所需标量数据。
- 封闭模式的表可作为JIT对象私有只读数据；当前推荐的在线模式必须使用独立稳定地址的共享数据资源，允许写未发布行及在安全点更新，不能随代码整体封为不可写。
- 表数据的同 VA 可访问性、数据映射/可读权限/缓存可见性需与代码一起验收；不能把 data 当作 executable range 上报。
- 不改变当前 codepool 对 rodata/GOT/对齐的处理策略，也不承诺混合代码/表对象仍能16B/64B紧凑封页。
- 禁止为了更新表去重开已经发布代码页的写权限。本方案不负责修改 enable_ex/enable_rw 策略。
- 布局先按字段建连续列；若多个字段总一起读，再独立比较按行或分组布局，不承诺 SoA 在所有业务最好。

估算：20个 entry，每个域6 cell x 2 TRP x 10 phase，保留8个4B字段，未去重/降维 payload 为
`20 x 6 x 2 x 10 x 8 x 4 = 76,800 B`。还要计算对齐、映射页、metadata、T1/T2及历史代际，不是全部成本。
字段全等时该字段没有表 payload。多个字段/entry 跨表去重不是首版必须项。
表可能引入地址物化、索引、GOT或额外load；原结构体已命中L1D、相关行其他字段仍必读时，实际节省可能很少。

## 9. Replace 与优化流水线

建议统一沿用已有 pipeline，增加一种策略而非复制一套优化器：

```text
源位码与合法 domain/schema
-> 参数保留；建立分析专用的域/字段求值环境
-> 多轮 may_const replace：全等立即数 / 差异小表 / 无法证明则原load
-> 既有 inline、常量传播、cleanup；每轮重新推导当前 IR 映射
-> Gen/Use 共同前缀与稳定 schema 边界
-> T1 light pipeline + instrumentation，或 T2 profile use + 后续优化
-> 原有最后一轮 replace/cleanup；验证表/依赖与代际一致
-> CodeGen/JITLink -> 代码和数据准备 -> 逻辑发布
```

上图的全等/冻结动作针对封闭模式。第6.5节在线模式用schema和稳定table绑定建立共同前缀，只进行表load替换，不依据当前已就绪行数做全等推断。
共同前缀的具体 pass 顺序须按实际基线提炼并测试，不直接把上图当作可随意重排的命令序列。
实例值只用于分析；不得把 cell/TRP 或 slotNo 整个参数替换成代表值，也不得冻结普通指针基址以帮助求值。
不得借用free_dim的0见证值假装证明开放域全等；只有独立明确的永久不变量契约才可使用对应常量化规则。
inline 后暴露的新字段仍应处理，不能删掉末轮。不得长期保存已经删除的 Instruction/Value 指针。
合成表读取需要可验证的来源标签，以免下一轮把它当原始配置再次提取；普通优化后标签若丢失则重新证明或放弃，不能凭标签制造合法性。
封闭模式同一轮T1/T2使用同一冻结配置映像/字段计划；在线模式使用同一schema与表地址，编译器不读取当前行值来常量化。若新增字段导致schema变化，需新建代码/表代际；不能让已接入行缺少新字段。
封闭模式若后续发现字段需要补读，必须持有相同代际的读借用且不得改写旧表；不能混合新旧配置。
Gen/Use 前缀和 profile schema 要一致。profile 不匹配时拒绝使用，而不是忽略告警继续“优化”。

“9格使条件成立、1格不成立”不允许无条件删掉分支；可保留分支或在真实语义证明下化简。
PGO 只能指导布局/代价决策，不能把有可能出现的第10格当成不可达。未知/未采到也不等于零概率。

## 10. PGO 建议

这里不要求逐cell采样再选代表，而建议每entry/代码代际一份通用T1，汇总已就绪成员的真实调用；封闭模式按DomainEpoch，在线模式按TableCodeEpoch。
这是独立于 PR230“仅代表 cell 采样”的规格建议，必须确认后实现，不能直接沿用旧的每逻辑版本64次计数。

- 建议预算是每份通用 T1 总计64次真实进入，而不是每 cell 64次；所有成员共享一次 session/额度。
- 非就绪或本核权限准备失败的 AOT 调用不计入额度；计数并发与阈值转换需要真实 worker/producer 回归。
- 64次进入允许近似有界快照，原始 edge/IC/memop/scalar 数据按 entry/epoch/session 隔离。
- 采样有明确可配置的上限/超时；只调用一次的冷 entry 不能永久占 admission 或阻塞其他 entry 编译/发布。
- 不要求所有 cell/phase 都出现。样本可能被首个热 cell 主导，应报告覆盖和质量，而非假装均匀采样。
- 冻结完整 ProfileBundle，再生成共同 T2；只有来自同一配置/站点 schema 的 profile 可使用。
- 在线模式晚加入行不因取值不同就让通用代码失效，但profile只能作为热度反馈，不能证明未见值不可能出现。采样时行配置更新须按明确策略取消/重启该session或标注混合质量，不得冒充同一冻结配置观测。
- “配置读齐才能判全等”与“采样不要求覆盖全域”并不矛盾，二者分别证明语义与估计热度。
- 保留单 owner worker、现有 throttle、发布触发与权限协议；不叠加新的排序、分池或封页阈值。

实验首版建议只支持 Async + 正常在线 PGO，开关默认OFF。全局策略不代表支持所有运行模式；Sync/audit-only/PGO-off需明确拒绝或另行实现，不静默等待不存在的T2。
不直接用当前基线 function-level dedup/finish 同时承担域编译、采样完成和所有逻辑成员发布。

## 11. 快路径、间接调用与共享发布

稳定 wrapper 的目标不变：原有按真实维度找指针并调用，不新增 hash、表就绪轮询、refcount 或共享组查找。
只有已证明属于域、生命周期有效且完成执行准备的逻辑槽才允许指向共同代码；域外/晚加入槽维持 miss/AOT。
表索引与差异load发生在函数体内，属于真实的运行成本，不能因为 wrapper 不变就说全程零开销。
对直接/间接进入 JIT helper 的路径也要证明域边界；不能只依赖顶层 wrapper 对输入的限制然后给所有 helper 加 inbounds/assume。
同一完整身份跨核迁移时继续使用既有首次准备/失效重填路径，不以另一核已调用或相同指针替代本核权限证明。
链接完成不等于发布完成；函数指针不得先暴露后再让表可读或代码可执行。

## 12. 性能收益与缺陷

| 场景 | 预期机会 | 主要代价/风险 |
| --- | --- | --- |
| 全等且有封闭域或新成员接入证明 | 接近充分load/branch折叠，且少一批重复机器码/IR编译 | 必须维护完整依赖；cell立即数相关的其他优化仍减少 |
| 当前已见成员全等，但允许未知成员加入 | 通用代码少、数据集中，不等全域 | 不能直接把当前表值全等当作未来保证，load/branch可能保留 |
| 少量差异散在大结构体 | 差异值集中，小表可能改善数据局部性 | 表load/索引仍在；结构体仍被普通业务读取时收益小 |
| 差异决定昂贵分支/循环 | 代码版本少 | 失去逐实例常量分支消除，可能明显慢于多版本 |
| 大部分字段不能证明安全 | 保留原行为 | 只失去参数常量化却没换来足够load收益，需允许该entry不采用此策略 |
| 多维度/很多字段 | 避免机器码组合膨胀 | 表和扫描成本也会按真实行数乘积增长 |
| 初始化一次、很少更新 | 编译摊销有利 | 启动前读域/建表可能有延迟 |
| 经常新增/更新cell | 减少稳态代码份数 | 共同域反复重编、AOT窗口和NO_RECLAIM残留可能抵消收益 |

后端停滞占比50%不是“小表可拿回50%性能”的依据；应区分内存延迟/带宽、算术依赖、执行端口和调用开销。
常量load少2%也不等于收益上限2%，因为分支和地址依赖可能一起改变；同样不能由静态load数量承诺加速。
首次原型保持原有池/对齐/优化等级作为控制变量，不将64B/4K、MFS、SVE变化混进A/B。

## 13. 调测与预算

必须区分：`original_mayconst_sites`、`uniform_folded_sites`、`table_replaced_sites`、`kept_original_sites`。
原load换成表load不算消除load。动态hits要区分命中的原site及其最终策略，不能按逻辑槽重复累计同一物理profile。
展示 entry、domain/epoch、合法/就绪行数、缺失原因、表payload/分配/保留字节、物理T1/T2与逻辑槽数量。
编译耗时拆成域枚举、受保护读取、建表、IR优化、CodeGen、JITLink与发布等待；记录配置变化重试次数。
codepool/executable range统计不包含只读表字节；另报数据段、GOT、对齐/页尾浪费。
ranking 的近似hits与cycles若不在同一窗口，标记approximate，不用于伪精确的跨策略收益排序。
设置有检查的行数、字段数、乘法/地址溢出、表字节、扫描工作量、活跃域、历史code/data和重试预算。
耗尽时受控AOT/停止该entry实验策略，不无限独立编译；旧完成记录必须回收，不能把历史计数当活跃容量。
新增公共C API必须包含lipo roots；共享状态布局变化需升级ABI和全核镜像，不能提前承诺“完全无ABI改动”。

## 14. 实验与验收

先做真实IR/JIT小原型，不先改全产品默认配置；不依赖产品提供内部源码。

1. 6 cell x 20 entry，1KiB结构体，动态load/少量store/普通helper调用；封闭模式全等字段要求load和相关分支真实消失，在线模式则必须诚实记录表load仍存在。
2. 同样场景改一个cell字段：仍一份当前共同T2，差异走表，所有cell结果与AOT一致，更新后不读旧值；需要重建代码的封闭模式不隐瞒历史代码残留。
3. TTI `%5/%10`，raw slotNo两个0..1023回绕；保留其它原始slotNo用途，不新增phase版本。
4. cell/TRP稀疏合法组合、域外输入、邻居cell、未初始化行、借用地址缺失、错误生命周期：均不得误读/错误常量化。
5. 初始化顺序不同但最终相同域：配置Ready后输出等价。冷实例从不被调用也不得卡住域编译。
6. 配置事务中断、并发更新、编译/发布前代际切换、取消旧回调、长期反复更新、容量失败、shutdown。
7. 真正T1->采样->T2的worker/producer路径，热成员抢先/冷entry只调用一次、session隔离、超时与queue-full重试。
8. 强调当前目标freestanding AArch64 BE：最终对象/ELF、字节序、scalar位模式、未解析libcall、rodata权限与跨核首次执行。
9. 控制组：现有多版本、保留参数但不建表、小表、独立hash合并路线；比较运行cycles、L1I/L2I、L1D/L2D、DTLB/ITLB、编译和内存。
10. 板端单.c，worker6/producer16，持续轮询所有6cell x20entry；init-array由启动负责，打印不重init，第二次调用可验已发布代码。
11. 在线模式专测cell0先开始并完成T2、cell1以后初始化且值不同：cell1填行后复用同一代码，结果正确，CodeGen和代码enable_ex次数不因接入而增加；未就绪行不提前填逻辑槽。
12. 在线行更新期间暂停实际读者，确认安全点前不覆盖行；容量耗尽/非本行依赖/字段schema改变保持受控行为，不虚假标constant。

不靠手写宏展开出来的共同函数冒充编译器实现；若先做行为模型必须明确标注。
首批重点验证“语义正确、就绪不死等、真实load/branch结果、总体收益”，而非只有静态表尺寸好看。

## 15. 分阶段交付与待确认规格

阶段A（按最新约束）：真实JIT验证固定地址共享表、增量行接入和晚加入不同值；同时保留一个封闭域的全等/差异对照，不把常量化作为在线模式保证。
阶段B：真实生命周期、就绪信号、共同T1/T2和逻辑发布，补取消/借用/超时/更新回归。
阶段C：调测、目标产物及标准板端用例；默认开关是否开启由A/B收益决定。
全局策略可覆盖全部entry入口，但先逐类证明候选安全性；不支持项必须有解释和回退，不暗中沿用会冻结真实参数的旧路径。

动工前需要确认以下规格，不自动当成用户批准：

- 全域就绪：已确认不能，实例边跑边初始化；首版建议第6.5节在线表而非第6.2节预读全域。
- 每实例就绪：是否能保证每个成员接入时，其本轮候选may_const字段均已初始化并稳定？借助哪个既有配置完成点？
- 收益取舍：是否接受在线表首版主要降低代码份数/改善数据局部性，而不保证相同值的load和分支消失？若不接受，需要第6.6节接入合同或回到版本合并。
- 更新范围：是否接受首版某个依赖变化时重建受影响entry的共同域，以及期间AOT？
- PGO：是否采用共同T1汇总跨实例64次进入，接受不均匀覆盖，而不是PR230的固定代表cell？
- 性能合同：wrapper不增步骤，但函数体允许差异表索引/load，必要的安全检查不能伪装成零成本。
- 覆盖面：注册数组可枚举；任意borrowed结构体目前不能从一个调用参数推导全域地址，需要可靠resolver/注册信息，否则该load保留。

总评：针对已确认的边初始化边运行，纯在线表可把编译时机与全体配置收集解耦，值得先做可控原型；但它不是“更简单且保留全部常量优化”的合并替代品。若同时追求全等折叠和任意成员无感加入，复杂度会再次接近合并方案。
