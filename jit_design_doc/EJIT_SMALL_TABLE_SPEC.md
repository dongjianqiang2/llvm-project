“全局应用”是 EJIT 级别选择这一优化策略，不是强行改写所有 load 或一次编译所有函数。

## 1. 结论与边界

方案可行，但适合程度取决于配置管理契约，而不是仅取决于 may_const 有多相似。

- 如果能枚举一轮配置的完整实例集合，并证明相关字段已经初始化且可稳定读取，推荐不可变小表方案。
- 如果实例边运行边出现、字段没有明确就绪点，则不能从“暂时见到的值相同”推出“所有实例相同”。全自动实现将明显复杂化。
- 不需要等待每个实例执行过，也不需要先给每个 cell 编译一份 IR 再比较。
- 在已证明的特化域与接入合同内，相同字段必须直接常量化且不建该字段的表；部分相同则按字段消轴，只有差异维度保留小表 load；无法证明安全的字段保持原始读取并说明原因。
- 单份共同代码会牺牲部分逐实例分支折叠，可能换来更少的代码和重复编译；不能预先保证产品加速。
- 本路线目标是每 entry、每配置域代际一份最终 T2 代码，不是整个程序只有一个函数，也不是所有历史代际只有一份代码。
- 当前规划轴是已声明的cell/TRP。独立slot工作不阻塞这些字段的优化；同一entry仍可包含普通动态slot逻辑，但不能因此将未建模的slot相关配置读误当成cell/TRP-only字段。

最重要的取舍：不能同时无条件要求“任意时刻增加或修改实例”“不做任何就绪声明”“跨全部实例常量化”“永不重编”“热路径零额外检查”。必须明确选择。

### 1.1 针对最新产品约束的修订结论

用户已确认实例会边跑边初始化。因此第6.2节的封闭域/不可变表不是当前推荐首版，只保留为有配置事务的可选模式。
第6.5节“共同代码 + 增量就绪行”仅保留为纯表化对照，不是当前默认交付目标。
用户已接受接入校验和暂时AOT，并再次确认特化为核心，因此当前默认是第6.6节：当前契约内全等字段常量化，部分相同按字段消轴，差异字段表化，新成员先校验再接入。
这仍不意味着从当前值相同推断未来实例相同。新成员若违反已折叠字段的契约，必须先AOT，不能直接调用旧JIT。
第6.6节的接入、重编和代际管理是实现核心特化所需的工作，不能以第6.5节仅换表load代替完成验收。

### 1.2 新确认的产品目标与当前建议

- 主瓶颈是数据访问。编译时间与内存不是首要优化目标，但资源仍需有安全上限。
- 只收每个entry的候选字段，包括属于该entry优化视图的内联字段；不做跨entry表合并。重复字段可在本entry内部去重。
- 允许接入校验。默认逐字段选择：统一值经接入证明后直接常量化；不统一值消掉获证无关的维度后用紧凑表。不同字段可以混用，而非整个entry非黑即白；不要求业务逐字段再声明一次“开启全等折叠”。
- 每TTI函数被调用不证明每个cell/TRP组合被调用，更不要求等待16个cell到齐。只由真实合法请求发现成员，再确认其本轮字段就绪。
- 接入不匹配或更新时，新调用继续走原AOT，不丢请求、不等待JIT编完才执行业务。异步准备成功后后续调用才切JIT。
- 不能要求暂停/排空业务。用户确认允许几轮旧配置效果，关键是不释放旧JIT而引起crash；采用保留旧代码和旧表、异步准备新代的方向，不强求逐调用线性一致。
- 表替换本身不要求新增业务条件分支。所谓分支代价，是相对“常量化后被删掉的分支”而言，不是相对原业务凭空加判断。
- 用户报告ld instructions/cycles约0.3。这是负载指令吞吐观测，不是DCache miss率，也不能推出必然加速比例。

不能保证“换小表至少一定快一点”：源字段共用已热缓存行、live字段仍需读源对象、表的地址物化/冲突/布局、以及依赖链都可能抵消收益。
手写对照必须包含源字段本来紧凑和分散两种布局，不能只选最有利于小表的用例。

## 2. 与版本合并的区别

| 维度 | PR230 版本合并 | 本文小表路线 |
| --- | --- | --- |
| 构造方式 | 对逻辑实例分别替换并生成 IR，最终精确比较 | 对已证明的配置域/接入合同生成一份参数化 IR |
| 共同值 | 各版本都折成相同常量后复用 | 安全读取获准域后按字段判等，生成常量或消轴表及接入合同 |
| 差异值 | 保留不同物理版本的机会 | 用表数据表达，通常不增加物理版本 |
| 逐实例分支优化 | 可保留较多 | 差异字段的分支通常保留 |
| 编译成本 | 仍可能重复进行逐实例 IR 优化 | 有机会只优化一次，但需要扫描配置与建立表 |
| 主要复杂度 | 组身份、精确比较、代表采样、共享发布 | 就绪域、字段读取、表布局、整体失效 |
| 更新影响 | 可将不同实例拆出共享组 | 首版保守重建受影响的共同代码/表代际 |

当所有获准字段全等、其他绑定及优化策略一致时，最终代码可能相同，不承诺机器码必然逐字节相同。
小表路线本身不要求 DeepSeek/PR230 的组表或最终 IR hash 目录；只复用经审查的安全读取与参数保留能力。

## 3. 概念与身份

- `DomainSchema`：entry 涉及的cell/TRP、可用组合、来源字段布局和类型；当前不包含slot派生轴。
- `DomainEpoch`：封闭模式的一组已确认就绪成员、配置代际及其读借用契约；不是采样 session，也不是编译队列水位。
- `TableCodeEpoch / RowGeneration`：在线模式分别表示固定schema/表地址/代码代际和每行配置代际。晚接入行不改变TableCodeEpoch，不冒充封闭DomainEpoch扩容。
- `RowKey`：实际cell/TRP组成的合法数据行身份；本规格不定义slot/phase版本或数据行身份。
- `FieldPlan / AdmissionContract`：每字段的类型、来源、保留轴/消去轴、位精确常量或投影表值、就绪证明与依赖代际。字段消轴不删除 RowKey 或生命周期依赖。
- `LogicalKey`：沿用 entry、生命周期维度及版本，用于缓存、关闭、失效和诊断。
- `CodeIdentity`：entry、源位码、编译策略、schema、所选模式的DomainEpoch或TableCodeEpoch和有效绑定。
- `TableImage`：类型正确的获准字段值集合，不是原始结构体的可替代地址。封闭模式整表不可变；在线模式固定地址、按行发布，已接入行在其有效执行代际内不可修改。
- `AttemptToken`：一次排队/编译尝试，旧回调不能完成取消后重建的新请求。

保留 cell/TRP 的真实调用参数和原有逻辑身份，不把它们改成 free_dim，也不丢弃生命周期依赖。
多个 LogicalKey 可以指向同一 CodeIdentity；跨核准备、icache 失效、实际代码范围仍分别负责。
不因机器码指针相同就认为两个逻辑实例相同。

## 4. 基本变换

原始行为示意，may_const 的真实语法沿用所选基线：

```c
unsigned process(unsigned cell, unsigned trp, unsigned x) {
    unsigned gain = cfg[cell][trp].gain; /* may_const */
    unsigned mode = cfg[cell][trp].mode; /* may_const */
    unsigned live = cfg[cell][trp].pending; /* ordinary load */
    out[cell][trp] = x;                    /* ordinary store */
    return mode == 1 ? x * gain + live : slow(cell, trp, x);
}
```

若整个有效域内 mode=1、gain=7，则目标等价于：

```c
unsigned process_common(unsigned cell, unsigned trp, unsigned x) {
    unsigned live = cfg[cell][trp].pending;
    out[cell][trp] = x;
    return x * 7 + live;
}
```

若mode全等、gain随cell不同但在各cell内部跨TRP相同，则gain读取目标等价于：

```c
/* Illustrative generated immutable data, not a per-call stack array. */
static const unsigned gain_by_cell[6] = {7, 8, 7, 9, 8, 10};
unsigned gain = gain_by_cell[cell];
```

如果gain还随TRP变化，表必须保留cell/TRP联合索引。只有精确证明某轴无关，才可消掉该轴。
封闭模式与第6.6节在线默认模式都必须落实下述逐字段规则。全等折叠和可证明的按轴降维不是后续可选收益；尚未实现时必须标为未完成，不能用完整小表冒充特化完成。
cell/TRP及其他原始参数仍按真实值传入，不把整个参数替换成代表实例值，不依赖分支预测正确性保证语义。

### 4.1 核心规则：逐字段判等、消轴与常量特化

判等只覆盖该entry当前合同内、已就绪且能稳定安全读取的合法依赖行，不扫描未初始化的预留槽，也不靠PGO样本判定。cell、TRP使用同一规则；不同字段独立规划。

| 字段在有效域内的取值 | 必须生成的字段策略 |
| --- | --- |
| 跨全部相关维度全等 | 位精确常量；无该字段的表列、payload 或表load；消除仅由该常量决定的可折叠分支 |
| 固定TRP时跨cell相同，但不同TRP取值不同 | 仅 `field_by_trp[trp]`，消掉cell轴；cell仍是原始参数和生命周期依赖 |
| 每个cell内部跨TRP相同，但不同cell取值不同 | 仅 `field_by_cell[cell]`，消掉TRP轴；不能误折成所有cell共享的常量 |
| 多轴确有差异 | 保留必要的联合索引和表值，不将代表行冒充其余行 |
| 类型、读取、合法域或判等无法证明 | 保持原load并诊断；入口安全本身无法证明则AOT |

正式判据：为字段选择保留轴集合 R 后，任意两条合法依赖行若投影到 R 的坐标相同，其字段值必须按类型位精确相同。R 为空时必须证明整个有效域全等。每次消轴后都重新验证最终联合投影；稀疏域不能因为某单轴没有可比较邻居，就把多个轴分别“证明无关”后一起删空。
此规则要求支持已声明、可枚举轴上的判等/消轴，不要求首版求任意索引表达式的全局最优压缩。超出支持范围或预算必须显式报告，不影响安全回退。

首版cell/TRP的确定求解过程如下，表中示例不是可独立叠加的删轴规则：

1. 对每字段取得非空的合法依赖域D及位精确值；D必须覆盖本合同允许的调用可达的全部相关依赖，且每次源读取满足§5/§6.1.1。空域、不可证明的可达范围不能以真空成立生成常量。
2. 枚举已声明轴的子集；两轴至多为`{}`、`{cell}`、`{TRP}`、`{cell,TRP}`四种。对每个候选R，按投影坐标分组并检查同组字段值全部相同。每次均检查完整原始D，不能复用独立删轴结论或丢掉旧行后再验证。
3. R为空且验证通过时必须常量化；否则在通过证明的候选中先取保留轴数最少者，再按固定容量下实际分配字节数、最后按schema声明轴序确定性择一。候选同时合法不代表其交集合法。连续晚接入时不重新改选布局，按§6.6.1单调扩轴；显式新优化轮次才重新择优。
4. 对最终R再验证一次并导出合同、完整依赖和表容量。分组可用有界排序实现，两轴每字段最多四次完整域扫描/分组；行数、字段数、排序内存及工作量纳入§13预算。失败候选被丢弃，不能带着未验证的R继续生成代码；无受支持的安全计划时保持原load或按入口安全条件AOT。

例：D仅有`(cell0,TRP0)=7`与`(cell1,TRP1)=9`时，按cell或按TRP均可表示，空R则失败。D只有一个TRP且跨cell同值时，可以在受控接入合同内常量化；跨cell不同则不能常量化。不能用缺少比较邻居代替完整D的分组验证。
不设“就绪行占笛卡尔积达到某比例才允许消轴”的正确性门槛；这不是统计推断，未来成员另行验证。成本选择不得以“每成员独占一格”为由否决已证明的全等常量化或强制保留可消轴。
表轴是函数体内的数据索引，不等于wrapper的`ejit_dim`轴。上述操作不回写、缩减或重新解释LogicalKey、RowKey和生命周期维度，也不扩充现有wrapper维度容量。

在线域允许以已就绪成员形成合同，但未来成员必须通过§6.6的投影一致性检查；“目前相同”本身不是未来保证。当前合同覆盖的全部可达cell/TRP依赖都要先有就绪和读取证明，不能只读本次请求命中的一格就消掉仍有差异的轴。
常量和消轴均保留实际cell/TRP及其他实参、原对象地址、普通load/store及原生命周期。只改获准字段的读取及由此合法派生的优化，不要求业务再加一个“全等”attribute。

### 4.2 排除项：slot/phase独立设计

slot/phase、`%5/%10`余数查表、按余数生成特化版本、对应attribute/wrapper/生命周期接入及策略选择，整体归独立TTI-C规格。PR231不单独承诺其中的“余数查表”，也不把这些工作列为cell/TRP交付的依赖。具体设计与既有实现状态由独立规格维护，本文不重复定义。

拆分不撤销cell/TRP全等常量化、按字段消轴、差异小表及新成员接入校验。函数中普通动态slot运算照常保留；可独立证明只依赖cell/TRP的字段继续优化。若候选地址还依赖未建模的slot/phase，就保持该读取原样并说明原因，不能忽略该依赖而错误常量化，也不因此让整个entry丧失其他安全优化。

## 5. 替换的安全条件

每个候选 load 必须同时证明：

1. 来源有实际生效的 may_const 授权；类型、字段偏移、宽度、地址空间及 provenance 可验证。
2. 地址可以表达为有效域内的行和字段；读取范围完全属于登记对象及相应生命周期子对象。
3. 全部将读取的行都已初始化、可访问且在读借用期间稳定。数据在未执行分支中也不能因此随意解引用。
4. cell/TRP依赖完整，不能仅跟踪cell却读取未登记的TRP或相邻cell；额外未建模的动态索引不得被忽略。
5. 非 volatile、非 atomic、非设备/MMIO；不是函数指针、对象地址、带有身份语义的指针值。
6. 调用实参、普通 load、store 目标和可能逃逸的原始对象指针仍保持动态语义。

标量类型按实际 IR 支持能力逐项覆盖，而非只支持 int/bool；整数保留位宽，浮点按位比较和构造，包括负零与 NaN payload。
大端读取与表发射均按目标 DataLayout。第一版不通过把整个结构体 reinterpret_cast 成新表来处理 padding 或指针。
比较单位是已授权的类型字段值，不是整个结构体字节；字段间padding不参与判等。冷路径提取/接入校验同样受上述读取合法性、范围和同步要求约束，“冷路径”不是提前解引用未就绪对象的许可。
来源不明、布局不匹配、borrowed 地址不能枚举、未知索引、负向/溢出 GEP、未证明的 helper 入边，保持原 load 并报告原因。
保守不替换不等于整个函数必须 AOT；如果入口域/生命周期/绑定本身不合法，则该逻辑实例只能 AOT。

表项缺失不能填0、undef 或沿用某个代表 cell。未知行也不能简单用 `%row_count` 绕回已有行。
不能在已经发生副作用的函数中间跳到整函数 AOT 重跑。索引安全无法证明时，候选 load 保持原样。
嵌套 entry 或间接调用仍遵守基线边界，不能假定被调用函数的参数落在父 entry 的就绪域。

## 6. 编译时机：就绪不是执行过

### 6.1 三个独立时刻

```text
配置域 Ready：可以安全读取哪些实例/字段，代际是否稳定
T1 采样结束：这份共同代码的优化反馈是否足够
代码发布：机器码、表数据、权限与逻辑身份是否全部就绪
```

编译队列为空、等了某个 tick、某 cell 曾经被调用、代表采了64次，都不能证明其他行已经初始化。
同样，配置 Ready 不表示必须立即把全部 entry 编译完。可以由该 entry 首次正常 miss 懒启动一轮。

### 6.1.1 在线启用前置：就绪事实与受保护读取

接口的语义必须先明确，具体C API名称与产品接入点仍待落实，不能把下述记录当成已有能力：

- 配置侧提供成员/合法cell/TRP组合、所覆盖字段或对象范围、完整依赖及配置代际；来源必须是可核实的初始化完成/配置提交事实。若现有每成员完成点能证明所有相关字段及依赖就绪，可复用，不强制业务维护逐字段ready位或等待全部成员完成。
- 提取前取得范围有效、对象存活且读取期间稳定的借用或等价同步保证；取得后确认代际，最后一次读取后与发布前再次校验。前后版本相等本身不是同步保证，不能把并发非法读取变合法。取消和失败必须释放精确的读取借用。
- 全部可达依赖都要有证明，不仅是成员本行。只有地址/类型/值相同、调用过、activate过、PGO采过或等待足够久，均不构成就绪事实。
- 无证明时不读取该候选，不发布依赖它的特化入口；按§5保持原load或AOT。产品原对象的live读取寿命仍须成立，旧表保留不能替代这一条件。

阶段A先定义并测试上述输入合同，可使用明确标注的测试provider验证编译器；真实配置完成点、同步与失效集成是阶段B上线门槛。接口尚未接上时必须报告“在线模式未实现/不可启用”，不能宣称可用，也不将产品默认目标改为§6.2全域封闭模式。

### 6.2 可选模式：封闭配置域 + 不可变表

产品在已有配置事务完成点提供“本轮有效成员及版本已就绪”的事实；可通过扩展集成现有生命周期接口实现，不强制业务每次手动触发编译。
这个事实必须来自配置系统，不能由 EJIT 猜测。具体 C API 尚未定，不把下述动作名当成现有接口：

```text
产品完成配置初始化 -> 确认 DomainEpoch E 及合法成员集合
entry 首次业务 miss -> owner 读取并冻结 E 的获准字段
得到 TableImage E -> 编译共同 T1 -> 采样 -> 编译共同 T2
代码与数据就绪 -> 发布属于 E 的逻辑缓存记录
```

可以读取cell5的已就绪配置，即使cell5从没执行业务。不等待所有entry或所有cell/TRP组合被采样。
“所有配置”只指该 entry 本轮声明的合法域，不是所有可能的16/256个预留槽或整个进程的全部结构体。
cell 与 TRP 各自 active 并不自动证明任意笛卡尔组合可访问；组合有效性和初始化仍需有来源。

已核对参考源码 `1d7ad493` 的 `ejit_activate/ejit_deactivate` 包装层：它们处理生命周期与失效；本文不把它们视为已经实现配置事务完成、冻结成员集合或编译读者排空。
若希望不新增产品调用，需要明确强化并实现原 activate 集成契约，不能只改注释宣称支持。

### 6.3 晚加入与配置更新

- 尚未属于 E 的实例保持 AOT，不自动获得 E 的共享指针；未来加入走新域代际。
- 启动时分批 activate 若导致成员集合反复扩大，不应每个成员到达就重编所有 entry。由明确的配置事务合并，而非无界等待或固定时间猜测。
- 可选后续策略是只编译已就绪子域、晚加入重建；正确但会产生编译抖动和多份历史代码，不能宣传成只编一次。
- 不更新已发射的 LLVM constant TableImage；新配置生成新表/代码绑定或新的重建代际。
- 编译前、最后一次源读取后、发布前校验身份与代际；校验本身不替代读取期间所需的同步/有效借用。

### 6.4 在线表不能同时获得的保证

这种方式能更早编译通用代码，但要处理有效位、发布顺序、行更新、读者并发和未知行回退。
热函数内可能增加表指针读取或有效性检查，缺值也不能被当成常量；若后来要全等常量化，仍需第二次编译及域失效协议。
不能把可变表标成 LLVM constant 或对其无条件使用 invariant.load；这会给优化器不真实的不可变保证。
因此它是另一个“可变配置缓存”设计，不是不可变小表的一项无成本增强。[LLVM 语义](https://llvm.org/docs/LangRef.html#global-variables)

### 6.5 纯表化对照：共同代码 + 增量就绪行

目的：实例陆续初始化时也能运行，不等全域、不为每个新cell生成代码。代价：无法证明永久全等的字段保留表load。

```text
entry 的字段/行schema就绪 -> 预留有界、固定地址的表，尚无行可执行
cell0 自身配置就绪 -> 验证并填写cell0所需行 -> 发布行就绪
-> 正常排队编译共同T1/T2；code与cell0行都ready后绑定cell0逻辑槽
cell1 自身配置就绪 -> 验证并填写cell1所需行 -> 发布行就绪
-> 已有共同代码则仅完成逻辑接入，不重编、不重封代码页
cell2... -> 同样接入；与cell0值不同也可以使用同一通用代码
```

实现约束：

- “每行已就绪”仍需要可靠依据。建议复用产品每实例配置完成/activate的集成点，但必须证明相关候选字段已全部初始化；一次调用本身不能证明其它分支才使用的字段也就绪。
- `tableReady(row)` 与 `codeReady(code_id)` 分开；两者都成立且身份/生命周期/权限已校验，才发布该行所属的逻辑icache槽。
- 表放独立共享数据资源，不放stack，也不能放到会随代码封成RX的可修改混合页。表的填充不再次调用enable_rw去解封旧代码。
- 第一版由owner串行负责表行写入/接入；使用可证明的发布和跨核可见性协议。未来行写入与当前已发布行读取不得产生数据竞争或覆盖。
- 已发布行在本实例有效运行代际内不修改。未就绪的行不能由任何优化后的读取触达；依赖其他cell/TRP行而尚未就绪的load保留原始读取或暂不接入该实例。
- 优先固定容量和可证明的直接索引，不在稳定wrapper加入哈希查表。稀疏/复杂映射若需要额外索引load，其代价必须明确测量。
- 表整体在LLVM里是可变global/外部数据，不能以“每行以后不会变”为由虚假声明整表constant。不引入未经证明的invariant元数据。
- 表与物理代码地址稳定，不扩容搬迁；容量/row schema不支持的新成员维持AOT并计数。是否未来重建更大表另行设计，不偷做可变基址快路径。
- 只创建实际字段计划需要的表；普通结构体指针和live数据仍原样使用。复制的是紧凑标量列，不恢复整结构体snapshot。
- 选择该策略的entry不同时启用PR230全量版本合并。不自动把当前已见行相等优化成常量；合法的静态不变量证明可以单独使用。

PGO可对同一通用T1已经接入的行累计真实64次进入，不要求全部成员到齐。后加入成员使用已生成的通用T2，可能得到不适合自己的布局，但正确性不能依赖旧样本覆盖它。
若PGO进行value specialization，必须保留真实守卫/fallback；不得把采到同值当作未来行也同值的语义契约。

### 6.6 默认必需：逐字段特化、消轴 + 新成员验证接入

不读尚未初始化的实例，也可以先对已就绪成员折叠，但这不再是“任意值都能立即接入”的简单小表：

1. 由planner按§4.1自动生成每字段的常量/保留轴/投影表计划，记录位精确值、来源、类型与完整依赖，形成可由runtime验证的接入合同。只有调用方手填uniform常量的底层接口不算默认策略已完成。
2. 新成员初始化后、填逻辑指针之前，验证所有常量字段及消轴表的投影一致性。对于已存在的投影坐标，字段必须与合同值相同；校验只发生冷路径。
3. 新成员投影到尚未发布的保留轴坐标时，只有固定schema/容量支持、安全提取和发布协议成立，才可补充新表项；不能修改已有投影值。其他可达行依赖也必须就绪，不能只验证成员本行。
4. 常量不同、已有投影值冲突、缺行或无法安全读取时，该成员保持AOT；不能只填原始全维表，就继续调用已经硬编码常量或删去索引轴的旧代码。
5. 若要让不兼容成员获得JIT，异步生成新代共同代码：仅为变化字段恢复必要的表轴/表读取，仍然全等的其他字段继续常量化。旧代码/表按寿命协议保留；不自动扩展成不同代码组。

用户已确认接入校验和核心特化，本节为默认实现合同，不代表当前原型已完整实现。
全维表的独立新行值可以不同；消轴表若与已有投影坐标重合则必须相同，不能把“表字段允许不同”错误套用到已共享的压缩表项。任一被用到的合同、合法域或代际无法验证，不发布该成员的JIT入口。

建议状态对应业务动作如下：

| 状态/事件 | 本次业务调用 | owner后续动作 |
| --- | --- | --- |
| 首次见到合法成员，字段未确认就绪 | 原AOT，不阻塞业务 | 等可靠的本成员就绪事实；不猜测inactive行 |
| 已就绪，字段提取/校验中 | 原AOT | 冻结获准字段及依赖，执行有界校验 |
| 常量/投影合同均相容，表数据也准备完成 | 首次仍经基线权限/身份准备；之后JIT | 绑定已有物理代码，不因新成员重新封代码页 |
| 某个常量字段不同或已消轴投影冲突 | 原AOT | 异步生成只为必要字段恢复表读取/索引轴的新代共同代码 |
| 新共同代码未就绪或发布失败 | 原AOT，已有合法成员可继续旧JIT | 有界重试，未就绪地址绝不进入icache |
| 当前成员配置更新 | 后续新调用AOT | 使旧逻辑绑定失效，准备新代数据/校验；旧调用按确认后的契约完成 |
| 新代身份、数据及代码就绪 | 后续调用JIT | 通过原发布路径接入，不重放已经完成的AOT业务 |

每次新的优化轮次必须先执行判等/消轴；同一轮连续接入时只扩展必要差异轴，不因成员退出重新编译收缩。常量转表或恢复轴均通过新代码代际，绝不修改已发布代码合同；再次晋升需显式新优化轮次，不能把临时全表策略永久当成核心规则已完成。
本表不批准隐藏热路径守卫、自动转多代码组或无界重编。配置变动合并/重试有界，但不以debounce猜测数据已初始化。

### 6.6.1 冲突、合并重建与迁移的确定规则

1. 新成员不相容时先AOT，再由owner请求新共同代际；两者是前后步骤，不是互斥模式。新成员违反旧合同不自动否定旧成员的合法性，但旧成员的依赖或代际若变化，仍须立即走已有失效路径。
2. 每entry至多一个在途重建和一个有界待处理集合，owner串行合并已确认的变更。启动一次重建时冻结本次输入；编译期间到达的变化记入待处理集合，不修改在途合同。发布前重验证，失效的结果不得发布；按预算处理下一批，不能每次到达都无界取消重启或逐成员重复编译。
3. 只因新成员加入而放宽字段计划时，保留轴只能增加，且每次增加后重新验证联合投影。仍全等的其他字段保持常量。schema/字段固定、已有值不变且只增成员的情况下，F个字段的cell/TRP轴最多累计恢复2F次；这是计划扩轴上界，不是T1/T2总份数、重试或任意配置更新次数的上界。
4. 新代数据/代码就绪后，owner对当前目标成员逐一验证新合同，通过原逻辑发布、跨核失效/首次准备协议迁移；不为每个旧成员各编一份代码。未就绪/不相容/准备失败的成员AOT并有界重试；新接入优先采用新代，不继续把旧代当成新的默认绑定。无需所有核心在同一瞬间切换，已进入旧代码的调用按寿命协议完成。
5. 新代未就绪前，旧合同仍合法的成员可以继续旧JIT；迁移与首次本核准备可以懒完成，但必须可诊断，不能把长期新旧分裂隐藏成“全部已迁移”。没有新调用的冷成员不阻塞其他成员或本次编译完成。
6. 重建尝试、待处理成员/依赖数、迁移失败重试和历史保留字节必须有明确配置上限与耗尽原因。达到重试/等待上限即释放本次调度占用，未接入成员保持AOT；不创建私有代码组、不阻塞业务，也不因每个新请求而清零预算。历史字节超限按§13停止该entry策略，不能复用尚未安全回收的旧页。

配置提交事件用于证明数据状态；队列批处理用于合并工作，两者不可互相替代。若已有字段持续改值，仍可能频繁生成历史代际，不能用单调扩轴证明掩盖这种成本。

## 7. 生命周期与更新代价

以下为需要安全点/读者排空的传统更新序列，仅保留用于说明难点，**不是用户已接受的首版方案**。用户不接受为此停流量或排空业务：

```text
阻止受影响域的新执行与新编译借用
-> 清理旧逻辑入口，并通过已有产品安全点排空可能访问旧配置的执行者
-> 等待编译读取结束/取消确认
-> 修改真实配置并提交新的 Ready 代际
-> 懒生成新表/共同 T1/T2，未就绪期间 AOT
```

必须阻止可能在 in-flight JIT 中通过真实参数访问被修改行的调用；仅清掉一个 cell 的 wrapper 槽不证明旧共同代码不会访问它。
若产品允许新旧配置同时执行，需要原对象可读性、代码/表绑定和读者寿命协议；最新默认方向见下文的保留旧代与异步准备，不以这段传统序列要求产品停流量。
共享代码的普通动态 load 仍访问真实业务对象；保留旧小表不等于保留了旧业务对象的一致视图。
新成员加入或任一依赖修改，可保守使本 entry 整个域重建；独立 entry/无关生命周期不必全局重启。

代码中硬编码了某个表地址时，换表通常需要重新链接/编译；若想只换表指针，就增加一层运行时间接读取。
即使所有值从未变化，只是生命周期代际前进，也不能未经新一轮有效性证明直接复用旧代码。
NO_RECLAIM 下旧 T1/T2/表存储不能自动回收，必须统计保留字节并设置上限；元数据释放不等于可重用仍被执行的物理页。

第6.5节的在线纯表模式可以采用更窄的行更新：阻止对应逻辑实例新进入，等待所有可能读取该行的执行者及编译借用结束，修改原配置和表行，再用新逻辑代际重新接入同一物理代码。
这只适用于表值没有被优化器折成常量、没有跨行优化依赖的情况。不能只依赖invalidate就认定已排空，也不能在并发读时直接memcpy覆盖整行。
源代码或字段schema改变、共享代码替换、PGO重新编译属于代码代际变化，不是普通数据行更新。

在“不停业务”的最新约束下，以上原地改行方案不得直接实施。候选是：新调用立即AOT；在后台构建新代不可变小表，保留旧代供在途调用使用，再在合适时刻切换逻辑绑定。
这只复制所需标量，不是复制大结构体；也不能借此宣称原结构体的并发读写已安全，因为旧JIT仍可能保留原对象live读取。
如果要维持同一份机器码并只切表代，需要增加稳定间接表基址/行指针读取，或利用已有业务版本指针；这是函数体的一次额外读取候选，不是免费更新。
用户进一步确认允许几轮旧配置效果，已有并发读写容错。因此不把等待全部旧调用退出作为新调用走AOT或新代编译的前置条件，旧代码/旧表在现有NO_RECLAIM或已证明安全的回收协议下保留。
这一业务容错不允许runtime元数据数据竞争、部分初始化的表发布、悬空指针、undef或越界，也不能证明任意混合长度/地址字段都安全。字段提取仍需满足现有may_const可读性与范围契约，不将产品的“几轮容错”放大为任意C/LLVM未定义行为许可。
对必须防止旧长度访问已释放对象的候选读取，应保守保持原读取/使用AOT或沿用已有对象版本机制；不能只因为旧机器码保留就宣称所有数据访问安全。

### 7.1 待确认：直接绑定地址还是运行时表指针

用户要求展开讨论这项，以下是候选建议，不是已批准实现。

- A：每份共同代码直接绑定本代稳定表地址。数据更新时准备新表和新代码绑定；旧代码/旧表保留，在新代就绪后切逻辑入口。默认允许完整重编一次，不预先承诺可无条件只重链接。重建的是该entry的共同代码，不是每cell各生成一份。
- B：共同代码在每次进入时读取一个当前表指针，在调用内复用该基址。纯表字段更新可发布新表指针而不重新生成代码；新增一次依赖的基址读取，不是每个字段都多一次。它仍需身份、表代际、发布可见性和寿命协议；指针原子替换本身不完成这些工作。
- 两者都保留差异字段的表load。A的优势是没有为了可换表额外设计的运行时间接层，不保证实际目标没有GOT或地址物化成本。
- A不修改已发布机器码或对旧代码页重新enable_rw。只在新位置编译/链接并通过既有代码发布路径切换。
- 新cell不等于已有配置更新：若采用有界预留行，且旧已接入执行无法访问未就绪行，A可以准备所需新表项、校验常量及消轴投影合同后接入而不重编。整表存在运行期写入时不得宣称LLVM constant/invariant；已接入行及共享投影值不原地覆盖。
- B不能通过换表更新已写进机器码的常量或已删除的分支。折叠合同/schema变化时，A/B都需重新优化或让不兼容实例AOT。
- 当前倾向A，因为产品优先稳定执行成本，接受更新期间AOT及较高编译/内存成本。具体失效范围和重建合并有界，不把更新变成全产品暂停。

选择A/B前必须附产品更新频率与保留成本算式。令K为实际产生的代码代数，L为实际表代数，则NO_RECLAIM下保留量按实际分配计为`sum(code_T1[g] + code_T2[g] + code_aux[g]) + sum(table_alloc[t]) + retained_metadata`，未产生的T1/T2项记0；代码页、表页、GOT、对齐浪费不能仅以payload代替。
A若N次更新都需要新代码/表且无回收，简单等尺寸估算为`(N + 1) * (code_per_generation + table_alloc_per_generation + metadata_per_generation)`。B仅在合同/schema与代码相容的纯数据更新中可能保持K不变，L仍增加；常量或已消轴合同变化时B也可能增加K。须同时给出预期运行周期、预算能容纳的更新次数及超限行为，不宣称A总最差或B可无限更新。
表指针读取在函数体内计入成本，与§11不改变稳定wrapper并不矛盾。当前倾向A不等于最终启用决定；无法满足产品保留预算时不得默认开启，应重新评估策略或保持AOT。

## 8. 表存储、大小与访问成本

- 不放调用栈，不每次初始化，不复制整个1KiB结构体；仅在 owner 冷路径构建所需标量数据。
- 封闭模式的差异表可作为JIT对象私有只读数据；在线增量接入所需的差异表使用独立稳定地址的共享数据资源，仅允许安全填写未发布表项，已发布值不原地修改。常量字段不分配表列；更新按§7准备新代。
- 表数据的同 VA 可访问性、数据映射/可读权限/缓存可见性需与代码一起验收；不能把 data 当作 executable range 上报。
- 不改变当前 codepool 对 rodata/GOT/对齐的处理策略，也不承诺混合代码/表对象仍能16B/64B紧凑封页。
- 禁止为了更新表去重开已经发布代码页的写权限。本方案不负责修改 enable_ex/enable_rw 策略。
- 布局先按字段建连续列；若多个字段总一起读，再独立比较按行或分组布局，不承诺 SoA 在所有业务最好。

估算：20个entry，每个域6 cell x 2 TRP，保留8个4B字段，未去重/降维payload为
`20 x 6 x 2 x 8 x 4 = 7,680 B`。还要计算对齐、映射页、metadata、T1/T2及历史代际，不是全部成本。
字段全等时该字段没有表 payload或表load；部分相同按字段消轴后计算实际payload。不同字段可有不同保留轴与stride，不能强制共用一张全维布局以规避消轴。多个字段/entry 跨表去重不是首版必须项。
表可能引入地址物化、索引、GOT或额外load；原结构体已命中L1D、相关行其他字段仍必读时，实际节省可能很少。

固定容量来自经证明的源数组extent，或产品声明且入口可强制遵守的坐标上界/合法域；不是当前ready行数，也不默认等于全局`kEJitMaxInstances=256`。直接索引要求容量覆盖可达坐标的最大值和stride，不能拿稀疏域的成员个数当最大下标。较小域没有可执行的入口/依赖证明时，不得假装可以少分配。
若必须覆盖256 cell x 2 TRP，前述全维对照的payload应改报`20 x 256 x 2 x 8 x 4 = 327,680 B`；7,680B仅是6 cell假设，不是部署承诺。逐字段按实际保留轴容量计算，并分开报告reserved、ready、published、payload和allocated字节；不因源数组预留较大而读取未就绪成员。
本代容量耗尽或出现域外坐标时，新成员AOT并记录具体原因，不重映射到旧行、不搬迁旧表、不自动新增热路径间接层。扩大容量属于另行批准的新schema/重建策略；其缺失必须在启用前暴露，而不是等业务首次越界才发现。

## 9. Replace 与优化流水线

建议统一沿用已有 pipeline，增加一种策略而非复制一套优化器：

```text
源位码与合法 domain/schema
-> 参数保留；建立分析专用的域/字段求值环境
-> 逐字段判等并建立常量/联合投影接入合同
-> 多轮 may_const replace：全等立即数 / 按字段消轴的差异小表 / 无法证明则原load
-> 既有 inline、常量传播、cleanup；每轮重新推导当前 IR 映射
-> Gen/Use 共同前缀与稳定 schema 边界
-> T1 light pipeline + instrumentation，或 T2 profile use + 后续优化
-> 原有最后一轮 replace/cleanup；验证表/依赖与代际一致
-> CodeGen/JITLink -> 代码和数据准备 -> 逻辑发布
```

上图适用于封闭模式和第6.6节在线默认模式；后者必须把判等/消轴结果交给运行时作为接入合同，不能仅凭当前行相同生成无约束代码。只有第6.5节纯表化对照不执行基于当前成员的判等折叠。
共同前缀的具体 pass 顺序须按实际基线提炼并测试，不直接把上图当作可随意重排的命令序列。
实例值只用于分析；不得把cell/TRP或其他动态参数整体替换成代表值，也不得冻结普通指针基址以帮助求值。
不得借用free_dim的0见证值假装证明开放域全等；只有独立明确的永久不变量契约才可使用对应常量化规则。
inline 后暴露的新字段仍应处理，不能删掉末轮。不得长期保存已经删除的 Instruction/Value 指针。
合成表读取需要可验证的来源标签，以免下一轮把它当原始配置再次提取；普通优化后标签若丢失则重新证明或放弃，不能凭标签制造合法性。
同一轮T1/T2使用兼容的字段计划、类型、保留轴与合同身份；封闭模式使用同一冻结配置映像，在线默认模式使用同一已验证常量/投影合同和有效表绑定。符号同名不证明两次编译得到同一表地址，必须校验实际资源身份。新增字段或改变合同/保留轴需新建代码/表代际；不能让已接入行缺少新字段或绕过新合同。
封闭模式若后续发现字段需要补读，必须持有相同代际的读借用且不得改写旧表；不能混合新旧配置。
Gen/Use 前缀和 profile schema 要一致。profile 不匹配时拒绝使用，而不是忽略告警继续“优化”。

分析/规划与执行替换必须有明确边界：planner基于受保护的完整依赖生成不可变FieldPlan/AdmissionContract，各轮replace只消费可验证计划；不得绕过计划沿用代表配置的旧may_const常量折叠。inline新字段、未覆盖helper及标签变化按上述规则重新证明或保留原读取。这要求职责分离和多轮回归，但不强制拆成两个新LLVM pass或复制既有pipeline；实现可沿用已有planner与pass接口。

“9格使条件成立、1格不成立”不允许无条件删掉分支；可保留分支或在真实语义证明下化简。
PGO 只能指导布局/代价决策，不能把有可能出现的第10格当成不可达。未知/未采到也不等于零概率。

## 10. PGO 建议

这里不要求逐cell采样再选代表，而建议每entry/代码代际一份通用T1，汇总已就绪成员的真实调用；封闭模式按DomainEpoch，在线模式按TableCodeEpoch。
这是独立于 PR230“仅代表 cell 采样”的规格建议，必须确认后实现，不能直接沿用旧的每逻辑版本64次计数。

- 建议预算是每份通用 T1 总计64次真实进入，而不是每 cell 64次；所有成员共享一次 session/额度。
- 非就绪或本核权限准备失败的 AOT 调用不计入额度；计数并发与阈值转换需要真实 worker/producer 回归。
- 64次进入允许近似有界快照，原始 edge/IC/memop/scalar 数据按 entry/epoch/session 隔离。
- 采样有明确可配置的上限/超时；只调用一次的冷 entry 不能永久占 admission 或阻塞其他 entry 编译/发布。
- 不要求所有cell/TRP组合都出现。样本可能被首个热cell主导，应报告覆盖和质量，而非假装均匀采样。
- 冻结完整 ProfileBundle，再生成共同 T2；封闭模式绑定冻结DomainEpoch，在线模式绑定已验证的CodeIdentity、合同、Gen/Use CFG/站点schema与session。不能把所有在线成员误称为同一个冻结配置快照。
- 在线模式晚加入行在常量/投影合同相容时可复用代码，独立差异表项可有新值；合同冲突按§6.6先AOT并准备新代。profile只能作为热度反馈，不能证明未见值不可能出现。晚加入与已有行配置更新分别按下述规则处理。
- “配置读齐才能判全等”与“采样不要求覆盖全域”并不矛盾，二者分别证明语义与估计热度。
- 保留单 owner worker、现有 throttle、发布触发与权限协议；不叠加新的排序、分池或封页阈值。

实验首版建议只支持 Async + 正常在线 PGO，开关默认OFF。全局策略不代表支持所有运行模式；Sync/audit-only/PGO-off需明确拒绝或另行实现，不静默等待不存在的T2。
不直接用当前基线 function-level dedup/finish 同时承担域编译、采样完成和所有逻辑成员发布。

第10节PGO策略仍待用户确认：候选为每entry/代码代际一套通用T1，汇总已就绪且已接入成员的实际调用，而非每cell64次，也不默认固定第一个cell代表全部。
总64次仅为初始可配置预算，诊断记录参与cell/TRP与覆盖偏差，不要求未开启cell到齐。T1仅用于热度与有守卫优化，不能证明配置全等或未采路径不可达。
后续纯表内容更新若要复用profile，必须验证Gen/Use CFG、站点schema与映射等兼容条件；折叠合同或IR结构变化需新session或明确回退，不无条件沿用旧profile。

共同T1候选策略下，首版的更新处理规定如下；总64次及跨成员采样选择仍需产品确认，不通过本段暗自变成已批准默认值：

| 事件 | session与T2处理 |
| --- | --- |
| 同TableCodeEpoch的相容晚加入，既有行未更新，代码/合同/站点schema不变 | 保留当前session，累计实际获准T1进入；记录参与成员和覆盖偏差，不因加入而重启，也不称为全域冻结采样 |
| 旧成员配置/依赖代际更新，或常量/保留轴/schema/代码身份变化 | 首版保守终止受影响session，隔离其迟到写入/回调并释放额度；新代取得自己的session。旧bundle不得无条件用于新T2，未接入调用AOT |
| 未来采用B且仅差异表内容更新，希望跨代复用profile | 非首版默认能力；须单独证明CFG/站点映射、合同及守卫相容，显式记录各代来源和混合质量，否则拒绝复用 |
| 采样超时、反复更新或重启次数达到配置上限 | 结束本次session并释放调度占用，尚无可用JIT的成员AOT；保留仍合法的已有T2，不无限占T1额度或等待未开启成员 |

这允许“不停业务但本轮暂时没有T2”；必须报告这种优化进展失败，不能把AOT正常执行当作PGO成功。§14的真实T1->T2与隔离/超时验收保留；具体采样人数/次数作为已记录的实验参数，不把待确认64次阈值冒充产品批准。

## 11. 快路径、间接调用与共享发布

稳定 wrapper 的目标不变：原有按真实维度找指针并调用，不新增 hash、表就绪轮询、refcount 或共享组查找。
只有已证明属于域、生命周期有效且完成执行准备的逻辑槽才允许指向共同代码；域外/晚加入槽维持 miss/AOT。
表索引与差异load发生在函数体内，属于真实的运行成本，不能因为 wrapper 不变就说全程零开销。
对直接/间接进入 JIT helper 的路径也要证明域边界；不能只依赖顶层 wrapper 对输入的限制然后给所有 helper 加 inbounds/assume。
同一完整身份跨核迁移时继续使用既有首次准备/失效重填路径，不以另一核已调用或相同指针替代本核权限证明。
链接完成不等于发布完成；函数指针不得先暴露后再让表可读或代码可执行。

## 12. 性能收益与缺陷

| 场景 | 预期机会 | 主要代价/风险 |
| --- | --- | --- |
| 全等且有封闭域或新成员接入证明 | 接近充分load/branch折叠，且少一批重复机器码/IR编译 | 必须维护完整依赖；cell立即数相关的其他优化仍减少 |
| 当前已就绪成员全等，未知成员未来加入 | 默认先在受控接入合同内常量特化，不等全产品到齐 | 新成员必须先校验；冲突先AOT/新代重建，不允许无约束接入 |
| 少量差异散在大结构体 | 差异值集中，小表可能改善数据局部性 | 表load/索引仍在；结构体仍被普通业务读取时收益小 |
| 差异决定昂贵分支/循环 | 代码版本少 | 失去逐实例常量分支消除，可能明显慢于多版本 |
| 大部分字段不能证明安全 | 保留原行为 | 只失去参数常量化却没换来足够load收益，需允许该entry不采用此策略 |
| 多维度/很多字段 | 避免机器码组合膨胀 | 表和扫描成本也会按真实行数乘积增长 |
| 初始化一次、很少更新 | 编译摊销有利 | 启动前读域/建表可能有延迟 |
| 经常新增/更新cell | 减少稳态代码份数 | 共同域反复重编、AOT窗口和NO_RECLAIM残留可能抵消收益 |

后端停滞占比50%不是“小表可拿回50%性能”的依据；应区分内存延迟/带宽、算术依赖、执行端口和调用开销。
常量load少2%也不等于收益上限2%，因为分支和地址依赖可能一起改变；同样不能由静态load数量承诺加速。
首次原型保持原有池/对齐/优化等级作为控制变量，不将64B/4K、MFS、SVE变化混进A/B。
启用评估须事先登记工作负载、测量窗口、允许的cycles回退/内存/编译预算和重复测量方法；源字段紧凑、分散、差异控制昂贵分支及频繁更新均须覆盖。关键场景稳定超出已约定预算的entry不启用此策略，按显式配置保留原路线/AOT，不自动切到PR230多代码组。表load不能算作被消除的load，但其局部性收益可以由实测cycles/cache指标证明，不能规定“只有常量折叠才算所有收益”。

## 13. 调测与预算

必须区分：`original_mayconst_sites`、`uniform_folded_sites`、`table_replaced_sites`、`kept_original_sites`。
原load换成表load不算消除load。动态hits要区分命中的原site及其最终策略，不能按逻辑槽重复累计同一物理profile。
逐字段报告原始轴、保留轴、消去轴、常量/表策略、优化前后payload，以及安全拒绝/不支持/预算拒绝原因；另计常量合同与投影冲突拒绝。仅统计table_replaced_sites不能作为特化收益验收。
展示 entry、domain/epoch、合法/就绪行数、缺失原因、表payload/分配/保留字节、物理T1/T2与逻辑槽数量。
编译耗时拆成域枚举、受保护读取、建表、IR优化、CodeGen、JITLink与发布等待；记录配置变化重试次数。
codepool/executable range统计不包含只读表字节；另报数据段、GOT、对齐/页尾浪费。
ranking 的近似hits与cycles若不在同一窗口，标记approximate，不用于伪精确的跨策略收益排序。
设置有检查的行数、字段数、乘法/地址溢出、表字节、扫描工作量、活跃域、历史code/data和重试预算。
耗尽时受控AOT/停止该entry实验策略，不无限独立编译；旧完成记录必须回收，不能把历史计数当活跃容量。
新增公共C API必须包含lipo roots；共享状态布局变化需升级ABI和全核镜像，不能提前承诺“完全无ABI改动”。

## 14. 实验与验收

先做真实IR/JIT小原型，不先改全产品默认配置；不依赖产品提供内部源码。

1. 6 cell x 20 entry，1KiB结构体，动态load/少量store/普通helper调用；封闭模式及在线默认模式的获证全等字段都必须无对应表列/payload/load，且可由这些常量决定的分支真实消失。纯表化对照单列，不能算此项通过。
2. 同样场景改一个cell字段：仅该字段恢复必要的cell轴，其他全等字段保持常量。新调用AOT，准备好新代后验证所有成员与本代AOT一致；在途旧调用允许约定的旧配置效果。每个当前代码代际一份共同T2，不隐瞒历史代码/表残留。
3. 排除项隔离回归：同一entry包含普通动态slot逻辑或未支持的slot相关配置读时，保留其原始语义；独立的cell/TRP字段仍能常量化/表化，不错误扩大候选域。slot优化收益和余数策略矩阵属于独立规格。
4. cell/TRP稀疏合法组合、域外输入、邻居cell、未初始化行、借用地址缺失、错误生命周期：均不得误读/错误常量化。
5. 初始化顺序不同但最终相同域：配置Ready后输出等价。冷实例从不被调用也不得卡住域编译。
6. 配置事务中断、并发更新、编译/发布前代际切换、取消旧回调、长期反复更新、容量失败、shutdown。
7. 真正T1->采样->T2的worker/producer路径，热成员抢先/冷entry只调用一次、session隔离、超时与queue-full重试。
8. 强调当前目标freestanding AArch64 BE：最终对象/ELF、字节序、scalar位模式、未解析libcall、rodata权限与跨核首次执行。
9. 控制组：现有多版本、保留参数但不建表、小表、独立hash合并路线；比较运行cycles、L1I/L2I、L1D/L2D、DTLB/ITLB、编译和内存。
10. 板端单.c，worker6/producer16，持续轮询所有6cell x20entry；init-array由启动负责，打印不重init，第二次调用可验已发布代码。
11. 在线默认模式专测晚接入三类：常量及已有投影值相同则复用代码；只在独立保留轴新坐标上不同且容量/发布证明成立则补表接入；常量或已有投影值冲突则保持AOT，直到新代就绪。前两类不额外CodeGen/封代码页，第三类不得调用旧特化代码；未就绪行不提前填逻辑槽。
12. 不停业务更新：新调用可AOT、在途调用可持旧代码/表，已发布行与共享投影值不覆盖；容量耗尽/非本行依赖/字段schema改变保持受控行为，不虚假标constant。停读者原地改行仅作为非默认协议的独立对照。
13. 逐字段消轴矩阵：固定TRP时跨cell同值但TRP间不同、同cell内跨TRP相同但cell间不同、全维全等、cell/TRP联合差异及字段混用；检查真实IR索引、表尺寸、load/branch形态及动态参数/live load/store保持。
14. 稀疏合法cell/TRP组合、只有首个cell就绪、尚未调用但已就绪的依赖行、未就绪依赖行、字段不同位宽和浮点位模式：不得凭采样/缺少邻居误消轴或越域读取。新成员破坏单个投影时只扩展必要字段计划，其他常量优化仍保留。
15. 对角稀疏不同值、单TRP同值/不同值、空合法域、候选投影同时成立及扫描预算耗尽：验证§4.1的确定选择和最终完整域证明，不以覆盖比例拒绝本来合法的特化；IR检查不能只验证模型。
16. 就绪provider缺失、错误字段范围、借用期间代际变化、跨成员依赖未就绪及取消：不得先读后检查；真实配置接入与测试provider证据分列，不以activate冒充就绪。
17. 连续晚加入/退出、重建期间再次变化、旧成员懒迁移、本核准备失败及预算耗尽：检查一份共同重建、有界待处理集合、单调恢复必要轴、旧合同不改写、冷成员不阻塞和所有历史保留量。
18. 相容晚加入不重启共同T1；已有行更新终止受影响session，迟到写入/回调不得污染新代；达到超时/重启预算释放额度。沿真实producer/worker链路验证，采样阈值按已声明实验配置。
19. 6与256的容量对照、稀疏大下标、NO_RECLAIM反复更新：分列payload/分配/历史code/data及预算退出。原load换表load不计作load消除；全等特化形态和整体性能收益分开验收。

不靠手写宏展开出来的共同函数冒充编译器实现；若先做行为模型必须明确标注。
首批重点验证“语义正确、就绪不死等、真实load/branch结果、总体收益”，而非只有静态表尺寸好看。

## 15. 分阶段交付与待确认规格

阶段A（编译器能力）：在明确cell/TRP就绪域/合同输入上，用真实planner、IR/ORC验证自动逐字段判等、全等无表、部分消轴、差异表与保守拒绝，导出可验证的常量/投影合同。先修复当前原型并独立审查；仅手动uniform合同或全维表通过不算A完整完成。slot/phase的识别扩展、attribute和策略选择不在本阶段。
阶段B（在线闭环）：真实生命周期、就绪信号、常量/消轴合同接入、固定容量增量表、共同T1/T2和逻辑发布，补晚成员冲突、取消/借用/超时/不停业务新代更新回归。A的测试合同不冒充runtime已自动接入。
阶段C：调测、目标产物及标准板端用例；默认开关是否开启由A/B收益决定。
全局策略可覆盖全部entry入口，但先逐类证明候选安全性；不支持项必须有解释和回退，不暗中沿用会冻结真实参数的旧路径。

验收里程碑不得混用；“作者报告通过”只有在代码、构建配置、日志及独立审查对应后才能升级状态：

| 门槛 | 必需交付 | 不算通过的替代物 |
| --- | --- | --- |
| A0 原型修复审查 | 当前提交的位宽/类型、旧折叠约束、表资源身份回归及独立复核 | 旧提交日志、仅诊断开关当assertions-on、主机结果当板端结果 |
| A1 编译器核心 | 自动判等、无表常量、逐字段联合投影、确定消轴与可导出接入合同；真实IR/ORC矩阵 | 手填UniformContracts、只有完整维度表、行为模型替代compiler |
| B0 接入契约 | 真实每成员就绪/借用来源、容量声明、数据所有权与同步；配置点说明及拒绝回归 | 假provider冒充产品、等待全产品初始化 |
| B1 在线数据/发布 | 晚成员校验、共用表资源身份、T1/T2绑定、重建/迁移/预算及不停业务寿命 | 每次编译同名但不同表、手填逻辑指针 |

A1推进不必等待全产品就绪，但B0未落实前不能开启在线模式。B0的接口定义可与A1并行准备；B1/B2建立在通过审查的编译器合同之上。slot/phase不占这些门槛，也不因本计划被恢复开发。

已确认项与仍需明确的集成规格如下，不把待定项当成已实现：

- 全域就绪：已确认不能，实例边跑边初始化；默认第6.6节受控接入，不要求第6.2节预读全产品域。
- 每实例就绪：是否能保证每个成员接入时，其本轮候选may_const字段均已初始化并稳定？借助哪个既有配置完成点？
- 容量与更新：实际cell/TRP坐标上界、合法组合、配置更新频率、预期连续运行周期及可接受的历史code/data预算；未给出时不能把6cell示例当成部署容量，也不能默认批准无限更新。
- 核心特化：已确认必须保留全等字段的load/branch折叠及可证明消轴，不接受仅纯表化替代。安全前提未满足可回退，但须明确未优化原因，不能把实现遗漏写成产品已接受的收益取舍。
- 更新容忍度：用户已接受更新期间AOT、几轮旧配置效果，不接受跳过业务或强制排空。保留旧代码/表、异步重建；具体数据所有权与安全读取按上述边界实现。
- PGO：是否采用共同T1汇总跨实例64次进入，接受不均匀覆盖，而不是PR230的固定代表cell？
- 性能合同：wrapper不增步骤，但函数体允许差异表索引/load，必要的安全检查不能伪装成零成本。
- 覆盖面：注册数组可枚举；任意borrowed结构体目前不能从一个调用参数推导全域地址，需要可靠resolver/注册信息，否则该load保留。

总评：本路线是“cell/TRP共同代码中的逐字段特化 + 仅差异数据的小表”，不是单纯把大结构体load搬到另一张表。在线就绪、合同接入和异步新代负责让核心特化在分批初始化时仍然安全成立；纯表化只是对照。slot余数查表与余数多版本一起在独立TTI-C规格中设计，不阻塞本路线。
