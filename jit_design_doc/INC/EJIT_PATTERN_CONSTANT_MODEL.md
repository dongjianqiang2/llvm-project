# 嵌值安全模型：哪些 period 数组访问可以被常量化

> 草稿 v0.1（2026-08-19，待讨论）。本文自包含，从一维场景讲起，术语集中在文末定义。
> 前置：已了解 EJIT 的基本标记（`ejit_dim` / `ejit_period_arr`）与 JIT 特化概念。

## 0. 要解决的问题（一句话）

JIT 编译某个特化版本时，编译器把 period 数组的访问**嵌成常量**（编译期读内存、写死进代码）。问题：**哪些访问可以嵌，哪些不能？** 判断必须在**编译前的源码形态**上做——因为编译后形态信息就丢了。

## 1. 基本模型（三个概念）

**特化版本**：按 dim 取值编译出来的代码。`f(cell)` 在 cell=0 时编译出 f_0，cell=1 时编译出 f_1。

**实例与生命周期**：period 数组的每个格子是一个"实例"。每个实例有自己的生命周期：激活 → 失效 → 可以**再次激活**。数据在激活时写入，**再次激活时可能重写**（写的是新数据）。谁管实例的生命周期？`ejit_activate/deactivate` 之类的接口，按实例切换。

**版本复核**：每次调用特化版本（如 f_0）时，运行时检查"和这次调用相关的实例"的版本号。实例再次激活 → 版本号提升 → 版本复核发现变化 → **f_0 作废，重新编译**。这样 f_0 里嵌的值一定是"当前有效的数据"。

到这里有一个关键事实，它是全文的地基：

> **版本复核只覆盖"本次调用的 dim 取值对应的实例"。** f_0 的复核只查 cell=0 那个实例（以及函数里其他 dim 对应的实例）。复核不查别的实例。

## 2. 一维的例子：问题是怎么产生的

```c
f(dim cell) {
  use(g[cell]);     // 访问实例 (0)
  use(g[cell + 1]); // 访问实例 (1) —— 注意这个
}
```

cell=0 编译出 f_0。编译器把两处访问都嵌成常量：

- `g[cell]` → 嵌的是实例 **(0)** 的数据。实例 (0) 再次激活、数据重写 → 版本号提升 → f_0 复核时发现 → 重新编译 ✓ 安全。
- `g[cell+1]` → 嵌的是实例 **(1)** 的数据。但是——f_0 的复核只查实例 (0)，**不查实例 (1)**。实例 (1) 再次激活、数据重写 → 版本号提升发生在 (1) 上 → f_0 完全不知道 → 继续用旧值 ✗ **错误**。

一句话：**f_0 事实上依赖实例 (1) 的生命周期，但这层依赖没有被记录、没有被复核。** 数据重写后，f_0 里 `g[cell+1]` 嵌的还是旧值。

### 为什么编译期拦不住

参数替换之后，`g[cell]` 变成 `g[0]`，`g[cell+1]` 变成 `g[1]`——**两个访问在编译产物里一模一样**。负责嵌值的编译步骤只能看到 `g[0]` 和 `g[1]`，看不到"这个 0 是 cell 本身、那个 1 是 cell+1 算出来的"。所以：

> **判断"能不能嵌"必须发生在参数替换之前，在源码形态上做。**

## 3. 规则：唯一的判据

> **允许嵌值的访问，其下标（替换为常量后）必须精确等于"本次调用的 dim 取值元组"**——即每个下标要么是某个 dim 参数**本身**，要么是该 dim 参数的**折叠表达式**（见 §5）。

换成人话：**只有"这个格子的下标恰好就是本函数这次调用时 dim 的值"的访问，才允许嵌值。** 因为版本复核恰好覆盖的就是这些格子——嵌值和复核是同一组格子，数据一变就重编译，永远一致。

| 访问形式（cell=0 编译时） | 下标对应实例 | 复核覆盖？ | 允许嵌值？ |
|---|---|---|---|
| `g[cell]` | (0) | 是（复核查 (0)） | ✓ |
| `g[cell + 1]` | (1) | **否**（复核只查 (0)） | ✗ |
| `g[5]`（写死的字面量） | (5) | 否 | ✗ |
| `g[loop_var]`（循环变量） | 运行期变量 | 否（且替换不了） | ✗ |

不嵌值的访问怎么办？**保持运行期读取**——代码里留着 `g[cell+1]` 的地址计算和读取，每次运行读最新数据。行为永远正确，只是少一次优化。

> 注意"cell 恰好等于 5"的特殊情况：`g[5]` 和 `g[cell]` 在 cell=5 时指向同一个格子。但编译 f_5 时，`g[5]` 的 (5) 在复核范围内、`g[cell]` 的 (5) 也在——两种情况都安全。判定标准始终是"下标是否**由 dim 参数精确推导**"，`g[5]` 是字面量，即使值碰巧相同也不通过判定（保守，避免分析复杂度）。

## 4. 取地址的情况

```c
f(dim cell) {
  p = &g[cell];     // 地址来自合法下标 → 允许
  use(p->field);    // 经指针访问 → 只要 p 的地址可追溯到上面的合法下标，就允许
}
```

同一函数内，指针从合法下标地址出发，经赋值/分支流传，**继续允许**（编译期能追踪）。指针传给别的函数 → **不再允许**（跨函数追踪不做，保守处理）。

## 5. 多维与折叠的扩展

同一规则，只是下标变成元组：

**多维数组**（period = (dim1, dim2)）：
- `g[cell][slot]`：下标元组 (cell, slot) == 本次调用元组 ✓ 允许
- `g[cell][slot+1]`：元组 (cell, slot+1) ≠ ✓ 不允许

**折叠**（period = (cell, slot%10)，即 slot 维折叠）：
- 实例是折叠后的元组 **(cell, slot%10)**；版本复核也按折叠后的元组查
- `g[cell][slot%10]`：下标元组 (cell, slot%10) == 复核元组 ✓ 允许（嵌的值 = 折叠后格子 (cell, k) 的数据）
- `g[cell][slot]`（没有写 %10）：**不能嵌**——slot 原值对应的格子不在复核范围（复核查的是 slot%10 的格子）→ 保持运行期读取 ✓（这正是不要求"自动改写访问"的原因：写 `slot` 就是运行时读，写 `slot%10` 才允许嵌）
- `g[cell][slot%10 + 1]`：偏置了 → 不允许

**展平数组**（一维，下标自己算）：`g[cell*10 + slot%10]`——下标的成分 = cell（dim 本身）和 slot%10（折叠表达式），构成的格子 == 复核元组 ✓ 允许。判定的方法是把下标表达式拆成"成分"，每个成分必须是 dim 本身或它的折叠表达式。

**嵌套结构体**（外层数组 + 成员数组）：`g[cell].member[slot%10]`——两段下标各自判定，都合法就允许。

**一个容易混淆的点**：编译后 `g[cell][slot%10]` 的下标也会变成常量（如 (5, 8)），和 `g[5][8]` 字面量长得一样——但判定在编译前做，`g[cell][slot%10]` 通过、`g[5][8]` 不通过，两者天然区分，不会误判。

## 6. 这个规则是新加的还是现状已有的？

**现状没有这条规则**：现状编译管线对"参数替换后全常量"的访问一律嵌值——`g[cell+1]` 这类访问现状也会被嵌，且无复核跟踪。**只要业务里存在"非精确 dim 下标"的 period 数组访问，现状就有同样的洞。**（可能现状业务没这么写，洞没被触发；也可能触发了没人发现。）

所以这条规则同时是：
1. **新设计**：多维/折叠场景下嵌值资格判定
2. **现状的修复**：补上"下标必须精确等于复核元组"的限制

实现落点：编译期（源码形态）判定 → 给"允许嵌值"的访问打上标记（复用 `ejit_may_const` 机制，兜底恢复路径同步升级为按本规则判定）。

## 7. 待确认

1. 折叠表达式的"精确"范围：`slot%10` 必须与 fold 声明**完全一致**（operand 相同）？还是允许等价形式（如 `slot - slot/10*10`）？——倾向完全一致，等价形式不做识别。
2. 字面量下标 `g[5]`：倾向一律不嵌（保守），即使值碰巧在复核范围内。
3. 跨函数指针传递：本轮不做（§4），列为后续。
4. 现状的洞：是否需要在文档中正式记录为"已知问题"，并加 Sema 警告（非精确 dim 下标的 period 访问提示）？

## 8. 术语对照（本文用到的词，一次性定义）

| 词 | 含义 |
|---|---|
| 特化版本 | 按 dim 取值编译的代码（cell=0 → f_0） |
| 实例 | period 数组的一个格子；生命周期（激活/失效）的粒度 |
| 版本复核 | 调用特化版本时检查相关实例的版本号；实例重新激活 → 版本提升 → 特化作废重编译 |
| dim 取值元组 | 本次调用时各 dim 参数的值（如 (cell, slot)）；复核覆盖的就是这个元组对应的实例 |
| 折叠 | dim 值到实例下标的变换（如 slot → slot%10） |
| 折叠表达式 | 源码里写出来的折叠形式（`slot%10`）；只有这种形式允许嵌值 |
| 嵌值 | 编译期读内存、把 period 数据写死进特化代码 |
| 精确推导 | 下标由 dim 参数本身或它的折叠表达式构成，无任何额外加减 |

## 9. 编译器实现路径（初稿，供讨论）

### 9.0 现状链路与洞的定位

现状嵌值的完整判定链（消费端只看两件事：**may_const 资格** 和 **替换后 GEP 全常量**）：

| 环节 | 代码 | 行为 |
|---|---|---|
| clang 打标 | `CGExpr.cpp:2076-2079`（字段属性驱动） | 宽松：may_const 字段的访问一律打 `!ejit.may_const`，**不看下标** |
| PASS1 兜底 | `EJitRegisterBitcode.cpp:135-201` reAnnotateMayConst | 恢复被优化丢弃的标记（GV 偏移表 + `ejitMayConstFieldOffset` 匹配，**只允许一个动态索引**） |
| JIT 替换 | `EJitOptimizer.cpp:129-166` preReplacePeriodIndices | dim 形参 → `ConstantInt(cellIdx)`（全 use 替换） |
| 消费 | `EJitStructFieldPass.cpp:137-167` isMayConstLoad + `:247-269` | may_const 资格（标记或偏移兜底）→ 根在 registry → GEP 全常量 → 版本复核 → 嵌值 |

**洞的机制**：`g[cell+1]` 被 clang 宽松打标 → 替换后 GEP `(0,1)` 全常量 → 嵌值，且复核不覆盖实例 (1)。**没有任何环节检查下标是否由 dim 精确推导**——因为消费端运行时已无法区分（替换后都是常量）。修复必须发生在替换前。

### 9.1 原则

1. **判定在替换前（AOT）**：IR 层面可判——早期 IR 保留源码形态（`g[cell+1]` 的 index 是 `add(形参, 1)`，`slot%10` 是 `urem(形参, 10)`，展平是 add/mul 树）。
2. **标记 = 判定的结论**：判定只在替换前做一次，结果编码进标记（有 = 精确，无 = 非精确）。**关卡（替换后）不识别 pattern**——替换后 `g[0]`/`g[1]`/`g[5]` 不可区分，关卡只查标记，无条件信任。
3. **兜底只活在替换前**：偏移兜底在 PASS1（替换前）可用；JIT 期（替换后）**禁用**——替换后兜底无法判定精确性（全常量下标按偏移匹配会把非精确访问放行，洞复辟）。标记丢失 = 错过嵌值（保守正确，软注解语义）。

### 9.2 改动清单（4 项，均为升级现有代码）

**① `ejitMayConstFieldOffset` 升级（`EJitCommon.h:206-289`）—— 核心判定**

现状"至多一个动态索引（元素选择器）"改为**逐个动态索引的 pattern 精确判定**，需要函数上下文（形参集合 + fold 声明表）：

| 动态索引形态 | 判定 |
|---|---|
| 形参直用（`cell`） | 精确 ✓ |
| `urem(形参, 常量N)` 且 N == 该 dim 的 fold operand | 精确 ✓（fold 表达式） |
| 展平线性组合（`add/mul` 树，成分均为上述两者） | 精确 ✓（逐成分判定，**无独立常量偏置**） |
| 其余（`add(形参,1)`、常量、非 dim 来源） | 不精确 ✗ |

（signature 增加参数：函数的形参集合、dim→fold operand 映射；两者均来自现有元数据。）

**② PASS1 收紧（`EJitRegisterBitcode.cpp` reAnnotateMayConst）**

恢复逻辑改为"**先删后打**"：对根在 period 数组的访问——精确 → 打/保留标记；非精确 → **清除标记**（覆盖 clang 的宽松打标）。判定 = 升级后的 ①。

**③ JIT 替换（`EJitOptimizer.cpp` preReplacePeriodIndices）**

- spec_fold dim：**跳过形参替换**（slot 取值保持运行期）
- 新增折叠表达式替换：对**带 `!ejit.may_const` 的 GEP**（已被 ② 认证精确），index 中 `urem(spec_fold 形参, operand)` 形态 → `ConstantInt(cellIdx)`（cellIdx 即折叠后实例值，wrapper 已传入）。替换后 GEP 全常量 → InstCombine 折叠 → 现状嵌值路径（零改动）
- 普通 dim：现状照旧

**④ 消费端（`EJitStructFieldPass.cpp` isMayConstLoad）**

标记路径不变（不识别 pattern，只查标记 + GEP 全常量）。**JIT 期禁用偏移兜底**：替换后兜底无法判定精确性，会把非精确访问按字段偏移放行（洞复辟）——它是"全量标记时代洞"的组成部分，不是可保留的保护；PASS1 的 raw bitcode 标记已全量覆盖（每个 period 访问都有判定结论），JIT 期只信标记。

**关于"丢失一次兜底"**：拆掉的是 JIT 期偏移恢复（替换后不可安全化），保留的是升级后的 PASS1（恢复 + 判定，覆盖范围 ≥ 现状 PASS1 + 现状 JIT 兜底中安全的部分）。JIT 期真丢标记的代价 = 错过嵌值（保持运行期读，正确性无损，软注解语义）；管线可控（preReplace → InstCombine → StructFieldPass，InstCombine 折叠 GEP 时 load 的 metadata 保留），丢标记属保险丝场景。补救预案（实现期验证项）：preReplace 入口（标记必然完整）把"精确访问集合"快照传给 StructFieldPass，不依赖优化中标记存活。

### 9.3 你提醒的双重性如何落实（spec_fold dim）

| slot 的位置 | 处理 | 落点 |
|---|---|---|
| 取值本身（`printf(slot)`、一般运算） | **不作常量**：形参不替换 | ③ 跳过替换 |
| pattern 访问下标（`g[cell][slot%10]`） | **作常量**：`urem(slot,10)` → `ConstantInt(cellIdx)` | ③ 折叠表达式替换 |

两处独立、互不冲突：跳过替换保住了"slot 不是常量"；折叠替换让精确访问的地址常量化 → mayconst 优化生效。非精确访问（`g[cell][slot%10+1]`）无标记 → 折叠替换不碰它 → 保持运行期计算 → 不嵌值。

### 9.4 各形态的 IR 判定样例

| 源码 | 早期 IR index（PASS1 判定时） | 替换后（JIT） | 结果 |
|---|---|---|---|
| `g[cell]` | `i64 %cell`（形参） | `0` | 嵌值 ✓ |
| `g[cell+1]` | `add(i64 %cell, 1)` | `1`（无标记） | **不嵌值**，运行期读 ✓ |
| `g[cell][slot%10]` | GEP 两级：`%cell` / `urem(%slot, 10)` | `5` / `8` | 嵌值 ✓ |
| `g[cell*10+slot%10]` | `add(mul(%cell,10), urem(%slot,10))` | `58` | 嵌值 ✓ |
| `g[cell*10+5]` | `add(mul(%cell,10), 5)` 常量偏置 | `5`（无标记） | **不嵌值** ✓ |
| `g[5]` | 常量 | `5`（无标记） | **不嵌值** ✓ |

### 9.5 取舍与风险

1. **判定落点选 PASS1（IR）而非 clang（AST）**：PASS1 信息足够（形参集合、fold 声明、period 绑定都在元数据），一处实现同时覆盖主路径与兜底，clang 零改动；代价是早期 IR 形态必须保留（preOptimize 提取时点满足，已验证）。
2. **标记删除方案 vs 负标记方案**：删除方案复用现有"软注解"语义——标记丢失 = 错过特化 = 保守正确。**JIT 期禁用偏移兜底**（§9.1 原则 3）：替换后兜底无法判定精确性，是全量标记时代洞的组成部分；PASS1 的 raw bitcode 标记全量覆盖后，JIT 期只信标记。
3. **`ejitMayConstFieldOffset` 语义变化**："元素选择器"校验（stride 匹配）用于防 `((int*)&g[ci])[j]` 类指针算术误判——升级后该防护保留（形参直用仍要求匹配根数组元素 stride），同时新增 fold 形态支持。
4. **待确认**：② "先删后打"的删除范围——仅非精确访问，还是对 period 数组访问全量重打（更干净，但需要识别"访问的是 period 数组"，靠 `TAG_EJIT_PERIOD_ARR` 元数据）。
5. **现状洞修复**：同一条路径天然修复——现状 `g[cell+1]`（无 spec_fold）在标记收紧后不再嵌值；无需单独设计。
