# 嵌值安全模型：哪些 period 数组访问可以被常量化

> 草稿 v0.2（2026-08-19，待讨论）。本文自包含，从一维场景讲起，术语集中在文末定义。
> 前置：已了解 EJIT 的基本标记（`ejit_dim` / `ejit_period_arr`）与 JIT 特化概念。
> v0.2 核心修正：嵌值判定**不需要**在替换前做——安全性不依赖下标"来源"，只依赖"值"（格子 == 复核实例），替换后两者都是常量，可直接比较（§9.1）。实现大幅简化：clang/PASS1 零改动，关卡加一条 `L == cellIdx` 检查（§9）。

## 0. 要解决的问题（一句话）

JIT 编译某个特化版本时，编译器把 period 数组的访问**嵌成常量**（编译期读内存、写死进代码）。问题：**哪些访问可以嵌，哪些不能？** 答案：**访问指向的格子 == 本次调用的实例**才允许嵌（§3）。这个判断在替换后做（§9.1）：替换后访问的格子是常量坐标、本次调用实例也是常量，两个常量直接比较。

## 1. 基本模型（三个概念）

**特化版本**：按 dim 取值编译出来的代码。`f(cell)` 在 cell=0 时编译出 f_0，cell=1 时编译出 f_1。

**实例与生命周期**：period 数组的每个格子是一个"实例"。每个实例有自己的生命周期：激活 → 失效 → 可以**再次激活**。数据在激活时写入，**再次激活时可能重写**（写的是新数据）。谁管实例的生命周期？`ejit_activate/deactivate` 之类的接口，按实例切换。

**版本复核**：每次调用特化版本（如 f_0）时，运行时检查"和这次调用相关的实例"的版本号。实例再次激活 → 版本号提升 → 版本复核发现变化 → **f_0 作废，重新编译**。这样 f_0 里嵌的值一定是"当前有效的数据"。

到这里有一个关键事实，它是全文的地基：

> **版本复核只覆盖"本次调用的 dim 取值对应的实例"。** f_0 的复核只查 cell=0 那个实例（以及函数里其他 dim 对应的实例）。复核不查别的实例。

## 2. 一维的例子：问题是怎么产生的

```c
f(dim cell) {
  use(g[cell]);     // 访问实例 (0)
  use(g[cell + 1]); // 访问实例 (1) —— 注意这个
}
```

cell=0 编译出 f_0。编译器把两处访问都嵌成常量：

- `g[cell]` → 嵌的是实例 **(0)** 的数据。实例 (0) 再次激活、数据重写 → 版本号提升 → f_0 复核时发现 → 重新编译 ✓ 安全。
- `g[cell+1]` → 嵌的是实例 **(1)** 的数据。但是——f_0 的复核只查实例 (0)，**不查实例 (1)**。实例 (1) 再次激活、数据重写 → 版本号提升发生在 (1) 上 → f_0 完全不知道 → 继续用旧值 ✗ **错误**。

一句话：**f_0 事实上依赖实例 (1) 的生命周期，但这层依赖没有被记录、没有被复核。** 数据重写后，f_0 里 `g[cell+1]` 嵌的还是旧值。

### 为什么"来源"不重要、"值"才重要（v0.2 修正）

参数替换之后，`g[cell]` 变成 `g[0]`，`g[cell+1]` 变成 `g[1]`——编译产物看不出 0 是 cell 本身、1 是 cell+1 算出来的。**但安全性不需要知道来源**：嵌值安全 ⟺ "这个格子 == 本次调用的实例"。替换后格子的坐标是常量（`g[1]` 就是格子 (1)），本次调用的实例也是常量（cell=0 → 实例 (0)）——**两个常量直接比较：1 == 0？不等 → 不嵌**。

> **判断"能不能嵌"在替换后做即可，不需要源码形态。**（v0.1 曾写"必须替换前判定"，v0.2 推翻：把"无法区分来源"误推成了"无法判定安全性"。）

## 3. 规则：唯一的判据

> **允许嵌值的访问，其指向的格子（下标替换为常量后）必须等于本次调用的实例**（版本复核覆盖的实例，含折叠后坐标）。

换成人话：**只有"这个格子的下标恰好就是本函数这次调用时 dim 的值"的访问，才允许嵌值。** 因为版本复核恰好覆盖的就是这些格子——嵌值和复核是同一组格子，数据一变就重编译，永远一致。（v0.2：判据是**值**——格子坐标 == 本次调用实例坐标，替换后两个都是常量，直接比较，不需要知道下标来源。）

| 访问形式（cell=0 编译时） | 下标对应实例 | 复核覆盖？ | 允许嵌值？ |
|---|---|---|---|
| `g[cell]` | (0) | 是（复核查 (0)） | ✓ |
| `g[cell + 1]` | (1) | **否**（复核只查 (0)） | ✗ |
| `g[5]`（写死的字面量） | (5) | 取决于调用值 | 取决于调用值：cell=0 时 ✗；**cell=5 时 ✓**（复核恰好覆盖实例 (5)，v0.2） |
| `g[loop_var]`（循环变量） | 运行期变量 | 否（且替换不了） | ✗ |

不嵌值的访问怎么办？**保持运行期读取**——代码里留着 `g[cell+1]` 的地址计算和读取，每次运行读最新数据。行为永远正确，只是少一次优化。

> 字面量 `g[5]`（v0.2 修正）：编译 f_5（cell=5）时格子 (5) 在复核范围内 → 嵌值**安全**（不再保守拒绝）；编译 f_0（cell=0）时格子 (5) 不在复核范围 → 不嵌。判定只看值：`5 == 本次调用实例`。这正是值级判定的好处——不需要分析下标来源。

## 4. 取地址的情况

```c
f(dim cell) {
  p = &g[cell];     // 地址来自合法下标 → 允许
  use(p->field);    // 经指针访问 → 只要 p 的地址可追溯到上面的合法下标，就允许
}
```

同一函数内，指针从合法下标地址出发，经赋值/分支流传，**继续允许**（编译期能追踪）。指针传给别的函数 → **不再允许**（跨函数追踪不做，保守处理）。

## 5. 多维与折叠的扩展

同一规则，只是下标变成元组：

**多维数组**（period = (dim1, dim2)）：
- `g[cell][slot]`：下标元组 (cell, slot) == 本次调用元组 ✓ 允许
- `g[cell][slot+1]`：元组 (cell, slot+1) ≠ ✓ 不允许

**折叠**（period = (cell, slot%10)，即 slot 维折叠）：
- 实例是折叠后的元组 **(cell, slot%10)**；版本复核也按折叠后的元组查
- `g[cell][slot%10]`：下标元组 (cell, slot%10) == 复核元组 ✓ 允许（嵌的值 = 折叠后格子 (cell, k) 的数据）
- `g[cell][slot]`（没有写 %10）：**不能嵌**——slot 原值对应的格子不在复核范围（复核查的是 slot%10 的格子）→ 保持运行期读取 ✓（这正是不要求"自动改写访问"的原因：写 `slot` 就是运行时读，写 `slot%10` 才允许嵌）
- `g[cell][slot%10 + 1]`：偏置了 → 不允许

**展平数组**（一维，下标自己算）：`g[cell*10 + slot%10]`——下标的成分 = cell（dim 本身）和 slot%10（折叠表达式），构成的格子 == 复核元组 ✓ 允许。判定的方法是把下标表达式拆成"成分"，每个成分必须是 dim 本身或它的折叠表达式。

**嵌套结构体**（外层数组 + 成员数组）：`g[cell].member[slot%10]`——两段下标各自判定，都合法就允许。

**一个容易混淆的点**：编译后 `g[cell][slot%10]` 的下标变成常量 (5, 8)，和字面量 `g[5][8]` 长得一样——**但不需要区分**（v0.2）：两者指向同一格子，与复核实例 (5,8) 比较结果相同。cell=5、slot=18 时都嵌（都安全）；调用其他值时都不嵌。值级判定下"来源"完全不参与决策。

## 6. 这个规则是新加的还是现状已有的？

**现状没有这条规则**：现状编译管线对"参数替换后全常量"的访问一律嵌值——`g[cell+1]` 这类访问现状也会被嵌，且无复核跟踪。**只要业务里存在"非精确 dim 下标"的 period 数组访问，现状就有同样的洞。**（可能现状业务没这么写，洞没被触发；也可能触发了没人发现。）

所以这条规则同时是：
1. **新设计**：多维/折叠场景下嵌值资格判定
2. **现状的修复**：补上"下标必须精确等于复核元组"的限制

实现落点：JIT 期关卡（`EJitStructFieldPass`）——替换后 GEP 全常量时，算数组线性下标 L，与本次调用的 period 实例索引 `cellIdx` 比较：`L == cellIdx` 才嵌值（§9.2/§9.5）。clang、PASS1、偏移兜底全部零改动。

## 7. 待确认

1. 折叠表达式的"命中"范围：`slot%10` 必须与 fold 声明**完全一致**（operand 相同）？——倾向完全一致；等价形式（如 `slot - slot/10*10`）不被折叠替换 → 保持运行期计算（错过嵌值，保守正确）。注意（v0.2）：语义从"判定"变为"替换命中"，失败后果是保守的。
2. 字面量下标 `g[5]`：**已由值级判定自然处理**（v0.2 关闭）——调用实例恰为该格子时嵌（安全），否则不嵌；无需特殊规则。
3. 跨函数指针传递：本轮不做（§4），列为后续。
4. 现状的洞：正式记录为"已知问题"（§6），关卡检查为修复；Sema 警告（advisory）保留与否待定。

## 8. 术语对照（本文用到的词，一次性定义）

| 词 | 含义 |
|---|---|
| 特化版本 | 按 dim 取值编译的代码（cell=0 → f_0） |
| 实例 | period 数组的一个格子；生命周期（激活/失效）的粒度 |
| 版本复核 | 调用特化版本时检查相关实例的版本号；实例重新激活 → 版本提升 → 特化作废重编译 |
| dim 取值元组 | 本次调用时各 dim 参数的值（如 (cell, slot)）；复核覆盖的就是这个元组对应的实例 |
| 折叠 | dim 值到实例下标的变换（如 slot → slot%10） |
| 折叠表达式 | 源码里写出来的折叠形式（`slot%10`）；只有这种形式允许嵌值 |
| 嵌值 | 编译期读内存、把 period 数据写死进特化代码 |
| 精确推导 | 下标由 dim 参数本身或它的折叠表达式构成，无任何额外加减 |

## 9. 编译器实现路径（初稿，供讨论）

### 9.0 现状链路与洞的定位

现状嵌值的完整判定链（消费端只看两件事：**may_const 资格** 和 **替换后 GEP 全常量**）：

| 环节 | 代码 | 行为 |
|---|---|---|
| clang 打标 | `CGExpr.cpp:2076-2079`（字段属性驱动） | 宽松：may_const 字段的访问一律打 `!ejit.may_const`，**不看下标** |
| PASS1 兜底 | `EJitRegisterBitcode.cpp:135-201` reAnnotateMayConst | 恢复被优化丢弃的标记（GV 偏移表 + `ejitMayConstFieldOffset` 匹配，**只允许一个动态索引**） |
| JIT 替换 | `EJitOptimizer.cpp:129-166` preReplacePeriodIndices | dim 形参 → `ConstantInt(cellIdx)`（全 use 替换） |
| 消费 | `EJitStructFieldPass.cpp:137-167` isMayConstLoad + `:247-269` | may_const 资格（标记或偏移兜底）→ 根在 registry → GEP 全常量 → 版本复核 → 嵌值 |

**洞的机制**：`g[cell+1]` 被 clang 宽松打标 → 替换后 GEP `(0,1)` 全常量 → 嵌值，且复核不覆盖实例 (1)。**没有任何环节检查"访问的格子 == 本次调用的实例"**——而替换后这两者都是已知常量，只是没人比较。修复 = 关卡加这条比较（§9.1）。

### 9.1 核心修正：值级判定（v0.2）

v0.1 曾论证"判定必须发生在替换前，因为替换后无法区分 g[0]/g[1] 的来源"。**这个结论是错的**：嵌值安全不依赖来源，只依赖值——

> 嵌值安全 ⟺ 访问的格子 == 本次调用的实例（复核覆盖的实例）

替换后：
- 访问的格子：GEP 全常量 ⟹ 数组线性下标 L 可算（常量）
- 本次调用的实例：编译请求自带的 per-period 实例索引 `cellIdx`（常量）

**两个常量直接比较：`L == cellIdx` ⟹ 嵌值；否则不嵌**（保持运行期读取）。

v0.1 的错误推演：把"无法区分来源"（真）推成"无法判定安全性"（假）。事实上 g[1] 无论来自 cell+1 还是字面量，安全 ⟺ 1 == 本次调用实例：cell=0 时 1≠0 不嵌；cell=1 时字面量 g[1] 嵌值且安全（复核恰好覆盖实例 (1)）。

### 9.2 改动清单（比 v0.1 方案简单得多）

| 环节 | 改动 |
|---|---|
| clang 全量打标 | **零改动** |
| PASS1 兜底恢复 | **零改动** |
| JIT 折叠表达式替换（`EJitOptimizer::preReplacePeriodIndices`） | 全量化：所有 `urem(spec_fold 形参, fold operand)` 形态 → `ConstantInt(折叠值)`（**不需要标记区分**，非精确访问的 urem 也替换，由关卡兜底）；spec_fold dim 形参跳过替换 |
| 关卡（`EJitStructFieldPass`） | **新增检查**：GEP 全常量 ⟹ 算数组线性下标 L ⟹ `L == cellIdx(该 period)` 才嵌值；偏移兜底**保留**（兜底放行的非精确访问也被 L 检查拦截） |

**唯一新数据流**：StructFieldPass 构造传入 per-period 实例表（periodName → cellIdx，来自 `SpecializationContext.dimensions`）。

### 9.3 instanceId 的获取与传递

| 环节 | 代码 | 内容 |
|---|---|---|
| 生成 | wrapper（`EJitWrapperGen.cpp:695-741`） | 每 period 一个 `EJitDimPair{dimType, instanceId}`；instanceId = dim 实参（L3：spec_fold dim 插入 `urem %LCM` 传折叠值；复合 period 需计算多 dim 折叠元组的线性实例索引——L3 既有改动） |
| 校验/打包 | `EJitCompileDriver.cpp:494-550` | instanceId ≤ 255 校验、按 dim 槽打包 cacheKey |
| 携带 | `SpecializationContext.dimensions`（`EJitOrcEngine.h:52-56`） | `{periodName, cellIdx}` per-period 结构（现状就有） |
| 传关卡 | `EJitStructFieldPass` 构造 | **唯一新增**：runPipeline 时把 periodName → cellIdx 表传入 |

**坐标系要求**：cellIdx = period 实例线性索引（折叠元组行优先线性化）；L = 数组线性下标（行优先）——同一坐标系由 D10 保证（数组维度 = 折叠值域、线性下标 == 实例索引）。

### 9.4 依赖关系：不同全局依赖不同 dim 组合

每个 period 数组全局只属于一个 period；比较时按**该全局自己的 period** 取 cellIdx——不是全局一个 instanceId：

| 访问 g | gvMap 查 GV（`GVPeriodInfo.periodName`，现状已有） | ctx.dimensions 按名匹配 | 比较 |
|---|---|---|---|
| `gA[cell]`（gA ∈ periodA=(cell)） | `"periodA"` | `cellIdx(periodA)` | L(在 gA 坐标系) == cellIdx(periodA) |
| `gB[cell][slot%10]`（gB ∈ periodB=(cell, slot%10)） | `"periodB"` | `cellIdx(periodB)` | L(在 gB 坐标系) == cellIdx(periodB) |

多 period 函数天然支持：每个全局用自己 period 的实例，互不干扰。这正是现状 1:1 per-period 机制（`DimInfo{periodName, cellIdx}`）的沿用。

### 9.5 三种数组形态的可行性

统一框架：GEP 链按"数组段"切分（跳过 struct 段），每段关联一个 period，逐段做 `L == cellIdx` 比较，**全部通过才嵌**（任一不过 → 整条不嵌，与 §3.7 规则 2 一致）。

| 形态 | GEP 链 | 段数 | L 来源 | cellIdx 来源 | 检查 |
|---|---|---|---|---|---|
| a 逐维 `g[cell][slot%10]` | 根数组多级 GEP | 1 | 行优先组合（`byteOff / elemSize` 即可，现状 `accumulateFullOffset` 已算字节偏移） | period 线性索引（多 dim 行优先） | L == cellIdx |
| b 展平 `g[cell*10+slot%10]` | 根数组单 GEP | 1 | 替换后常量 index（add/mul 树被 InstCombine 折叠成单常量） | 同上 | L == cellIdx |
| c 嵌套 `g[cell].dim2_var[slot%10]` | 外层段 + struct 段 + 成员段 | 2 | **逐段**各自索引（不能 byteOff/elemSize，跨段） | 每段各自 period 的 cellIdx（成员 period 名查 D11 绑定表） | **每段各自**比较，全过才嵌 |

要点：
- a：`L = byteOff / sizeof(元素)`（GEP 全常量时直接可得）
- b：index 是 add/mul 树——替换后 InstCombine 自动折叠成常量，L = index 值；折叠表达式替换递归遍历 index 操作数命中 `urem(slot,10)` 即可，不需要"偏置"分析——`g[cell*10+5]` 替换后 55 ≠ 58 由值比较拦截
- c：byteOff 跨段（含 memberOffset），需要段级索引提取（现状 `ejitMayConstFieldOffset` 已遍历 GEP 链，扩展为段收集即可）；嵌入值读取仍走现状 `base + byteOff`（数据读取不用改，只加检查）
- 非精确段（索引非常量）→ byteOff 不可算 → 现状路径天然不嵌；任一段 L ≠ cellIdx → 整条不嵌（新检查）
- 维度不一致（D10 warning）时检查偏保守：坐标系错位 → 多数拒绝（错过嵌值，不破坏正确性）

### 9.6 你提醒的双重性如何落实（spec_fold dim）

| slot 的位置 | 处理 | 落点 |
|---|---|---|
| 取值本身（`printf(slot)`、一般运算） | **不作常量**：形参不替换 | §9.2 JIT 替换 |
| pattern 访问下标（`g[cell][slot%10]`） | **作常量**：`urem(slot,10)` → `ConstantInt(折叠值)` | §9.2 JIT 替换（全量化，无需判定） |

两处独立、互不冲突。非精确访问（`g[cell][slot%10+1]`）的 urem 也被替换 → GEP 全常量 → 但 L ≠ cellIdx → 关卡拦截 → 保持运行期计算。**关卡检查是最后防线，折叠替换全量化也安全。**

### 9.7 取舍与风险

1. **值级判定 vs 替换前判定**：值级判定简单得多（一处检查、无标记依赖、clang/PASS1/兜底全零改动），代价是"来源不可知"——但值比较本身精确，无过度保守（字面量 g[5] 在值相等时嵌值且安全）。
2. **折叠替换全量化**：非精确访问的 urem 也被替换，靠关卡拦截——正确性由关卡保证；若未来想少替换（性能），可加"带标记才替换"，本轮不需要。
